# 开发规则

> 状态：有效  
> 文档类型：项目强制规则  
> 适用范围：Java 源码、测试、配置与数据库资产  
> 最后更新：2026-09-01  
> 事实来源：Java 架构基线、Maven 配置与 ArchUnit 测试

## 1. 包与模型

模块按职责使用 `api`、`facade`、`controller`、`domain`、`repository`、`config` 包。`api` 是唯一可跨模块访问的包；外部请求和响应使用 `XxxRequest`、`XxxResponse` 或 `XxxDTO`，持久化对象使用 `XxxPO`。禁止将 PO、Mapper、ORM 分页对象或查询条件对象暴露到 API。

## 2. HTTP 与错误处理

1. Controller 仅处理参数绑定、协议校验、领域调用和统一响应，禁止直接访问 Repository。
2. 公共 HTTP 路径使用 `/api/<模块>/<资源>`；`/internal/**` 不得公开到外部反向代理。
3. 统一返回 `ApiResponse`，请求与错误响应均使用 `X-Trace-Id` 追踪；不得吞异常或伪造成功响应。
4. 使用构造器注入；禁止字段注入和静态方式持有 Spring Bean。

## 3. 数据库与 SQL

1. SQL 资产只能进入根 `sql/`，规则见 `rule/文档规则.md`；禁止在多个位置维护内容相同的迁移 SQL。
2. 禁止 `select *`、注解 SQL、循环查询数据库、未校验动态 SQL 和无依据的全表扫描。
3. 状态更新必须带原状态条件；影响行数为零时按并发或状态冲突处理。
4. 数据库事务内禁止调用远程服务、模型服务和不可控长耗时操作。

## 4. AI 接合面

1. 只有 `com.aiep.platformai.agent` 可以包含 Agent 地址、端点常量、HTTP 客户端和内部传输实现。
2. Agent 端点固定为文本生成、对话流、Skill 执行、知识库问答、文档入库、任务查询和向量删除；新增端点必须先形成 ADR。
3. Java 负责模型配置选择、权限过滤范围计算、调用审计、引用落库、会话摘要和业务降级；Agent 只执行 Java 传入的任务。
4. Agent 不可用时，非 AI 核心业务不得整体不可用。

## 5. 测试与质量门禁

1. 新增生产行为先写失败测试；单元测试不得依赖真实数据库、模型服务或公网。
2. 真实依赖联调测试使用 `*IntegrationTest` 命名，并只在受控 Profile 执行。
3. `aiep-boot` 的 ArchUnit 测试是强制门禁：模块依赖、Controller→Repository、API 泄露 Repository、Agent 传输越界和包循环均不得突破。
4. 代码交付至少执行受影响模块测试；涉及模块或架构边界时执行 `mvn -q -pl :aiep-boot -am test`。

## 6. 代码设计与可维护性

### 6.1 面向对象原则

1. 业务对象必须保护自身不变量：状态修改通过具名业务方法完成，禁止将可变内部集合、状态字段或持久化对象直接暴露给调用方。
2. 优先使用组合、接口和依赖倒置；只有存在稳定的“是一个”关系、可替换行为和共享实现时才允许继承。禁止为了复用几行代码创建继承层级。
3. 调用方必须依赖抽象契约而不是具体实现。模块间只依赖 `api` 中的 Facade 和 DTO；模块内对可替换的策略依赖接口。
4. 多态必须服务于真实的行为差异。存在多个稳定实现且调用方不应感知具体类型时，使用接口加实现类、策略模式或责任链；只有一个实现且不存在近期扩展点时，禁止为形式新增空接口、空实现或无意义抽象层。
5. 领域规则、状态流转和权限判断不得散落在 Controller、Mapper、工具类或多个调用方；必须收敛到拥有该规则的领域服务、领域对象或明确的规则类。

### 6.2 复用、抽象与设计模式

1. 遵循 DRY 和 YAGNI：不得复制粘贴后仅修改变量名、错误文案、SQL 片段或分支条件。出现两处以上语义相同且需同步维护的逻辑，必须收敛为私有方法、领域协作类、公共组件或稳定接口。
2. 抽象必须有至少两个语义一致的真实使用点，或者有已经确认的近期扩展需求；禁止“可能以后会用”的过度设计。
3. 对具有多种稳定算法、渠道、模型提供方或规则实现的场景，必须选择与变化点匹配的设计模式：
   - 算法、路由或处理规则可替换时，使用策略模式。
   - 对象创建依赖类型、配置或渠道时，使用工厂方法或工厂类。
   - 固定主流程、局部步骤可变时，使用模板方法或编排器。
   - 多个处理器按顺序决定是否继续时，使用责任链。
   - 外部协议、SDK 或 Agent 模型差异需要隔离时，使用适配器。
4. 设计模式用于消除真实耦合和变化风险，不得为了“使用模式”额外创建无行为的接口、枚举、工厂或层级。
5. 禁止创建职责不清的 `Util`、`Helper`、`Common`、`Manager` 大杂烩类。纯无状态且跨领域复用的技术函数可以放入 `util`；业务规则必须放在业务所属领域。

### 6.3 类、方法与依赖控制

1. 一个类只承担一个清晰职责。Service 同时包含协议解析、权限、状态机、SQL 拼接、第三方调用和格式化输出时，必须按职责拆分。
2. 方法必须通过名称表达业务意图；一个方法应完成一个可独立测试的业务动作。存在多个独立阶段、深层嵌套条件或重复分支时，必须抽取具名私有方法、规则对象或策略实现。
3. 禁止超过三层的业务条件嵌套；优先使用提前返回、卫语句、状态机、策略或责任链表达分支。
4. 禁止使用 `Map<String, Object>`、裸字符串、魔法数字承载稳定业务语义；应使用强类型 DTO、枚举、值对象、常量或配置属性。
5. 禁止静态全局可变状态、跨请求共享可变对象和隐藏副作用。缓存、连接、线程池与客户端必须由 Spring 或明确的基础设施组件管理。
6. 任何新增外部调用必须明确超时、失败语义、幂等键、重试边界和降级行为；不得在业务代码中散落重复的 HTTP 或 SDK 调用模板。

### 6.4 注释、命名与可读性

1. 注释使用中文，技术协议、类名、字段名、命令和标准术语可保留原文。注释解释“为什么、约束是什么、违反后会怎样”，不得逐行复述代码表面含义。
2. 所有公共 Facade、对外 Controller、公共 DTO 字段、枚举值和非显而易见的领域对象必须具备 Javadoc 或等价中文说明，明确用途、约束、单位、时间语义、可空性与兼容性（按适用项填写）。
3. 涉及权限、金额、状态机、并发、缓存一致性、SQL 性能、补偿、重试、兼容或安全边界的代码，必须说明关键决策、前置条件和不可违反的约束。
4. 禁止保留无主的 `TODO`、`FIXME`、注释掉的大段代码、无意义日志和复制来的过期注释。确需追踪的待办必须写明负责人、跟踪编号或删除条件。
5. 类、方法、变量和布尔值必须使用可读且反映业务含义的英文技术命名；禁止 `data`、`info`、`temp`、`obj`、`flag`、`doHandle` 等无上下文名称。中文解释写在文档、注释和接口说明中。

### 6.5 评审与自动化要求

1. 代码评审必须检查：职责是否单一、是否存在重复逻辑、抽象是否有真实使用点、设计模式是否匹配变化点、注释是否解释约束、异常与日志是否泄露敏感信息。
2. 新增复杂规则、策略、状态机、适配器或补偿分支时，测试必须覆盖每个实现、选择逻辑、异常分支和默认/拒绝路径。
3. 可由 ArchUnit、静态检查或测试自动验证的规则，应优先补充自动化门禁；不能自动化的规则必须在设计、评审和交付说明中逐项核对。
