## 真实调用期间发现并修复的问题

1. 模型漏产或产出不闭合 Claim：复用同一证据校验器筛选模型 Claim，对缺失事件再调用一次真实模型；仍不合格即剔除，不使用程序生成 Claim 冒充模型成功。
2. 模型相关性摘录不是来源原文：直接丢弃对应决策，不再用标题替换后保留 `relevant` 结论。
3. 热点次序原本只是事件哈希顺序：改为读取 HN score/comments 等真实来源指标做平台内归一化热度排序，缺失指标时才按时间兜底。
4. 公众号模型多次低于 3000 字、固定补写又可能越过 4000 字：按缺口动态要求每字段 1～5 段，截取约定段数后重新执行全文长度、逐热点结构、Markdown、引用与安全校验。
5. Java 持久化正文语义不一致：制品正文优先保存 Agent 的 `content.body_markdown`，`copy_text` 仅作为缺少结构化正文时的兼容后备。
6. 取消响应与 SSE 投影发生竞争：Java 对 run 行执行 `FOR UPDATE`，终态后拒绝晚到事件覆盖或生成制品，真实取消接口稳定落为 `cancelled`。
7. ClaimExtractor 与最终物化器门禁不一致：前移正文范围和全文数字证据校验，避免晚阶段失败。
8. 日志门禁把 `stream_error`、`errors=` 等 INFO/告警文本误判为 ERROR：只匹配大写错误级别和真实异常关键字。
9. Windows 上隔离 RSS 解析进程偶发超过 3 秒，导致来源退化为单一 Hacker News：把隔离解析上限调整为 10 秒，随后真实研究恢复为 2 个来源域。

最终两轮有效验收的 Java 与 Agent 日志增量均通过错误门禁。此前一次验收启动前，Agent 重启脚本返回早于服务 ready，Java 留下一条 `Connection refused`；等待 `/health/ready` 后从头重跑，未把该失败记录为通过。

所有上述修复均在真实接口重放后才记录为通过；历史失败证据保留在相邻时间戳目录中，没有删除或改写。
