# AI 智能客服项目面试问题详解

> 状态：当前有效
>
> 适用范围：AI 效能平台内部智能客服项目面试准备
>
> 最后更新：2026-10-28
>
> 回答口径：以项目全权负责人和核心开发者的身份回答，说明目标、判断、取舍、风险和验证边界，不背接口，不按代码调用顺序机械复述。

## 回答原则

我会始终区分三类事实：已经实现并经过真实链路验证的能力、已有设计但验证范围有限的能力、下一阶段才会建设的能力。面试中最忌讳把设计稿说成生产事实，也不能把单元测试通过等同于真实模型、真实数据库和真实接口已经可用。

## 一、项目整体架构

### 1. 请介绍这个智能客服项目解决的核心问题和目标用户。

**回答：** 我负责的这套智能客服首先服务公司内部员工，核心问题不是“让模型能聊天”，而是让员工能够基于公司制度、业务流程、产品资料和技术文档获得可追溯的答案。公司知识存在版本、生效范围和冲突，普通大模型即使语言能力很强，也不能天然知道哪一份是当前有效资料。因此，我把项目目标定义为知识版本可控、回答有依据、执行可回放、质量可评测。

项目首期没有覆盖外部客户、订单查询、退款操作和人工坐席。这个边界是主动选择：先把知识问答闭环做扎实，再扩展实时业务工具和客服工作流，避免第一版同时承担过多高风险能力。

### 2. 请说明一次员工提问从浏览器到最终答案的完整调用链。

**回答：** 员工在前端提交问题后，请求先进入 Java。Java 校验身份和会话，创建用户消息、待处理的助手消息和一次 Run，并选定当前激活的智能客服发布版本。随后 Java 把问题、有限的会话历史和冻结的发布身份交给 Python Agent。

Agent 先判断问题意图和是否需要检索；公司知识问题会经过查询规划、冻结索引范围内的向量和全文召回、排名融合、重排、父证据恢复、冲突检查和证据充分性判断，再选择回答模式并生成结构化答案。执行过程通过有序事件返回 Java，Java将事件投影成前端可消费的 SSE、消息、引用和回放记录。最终用户看到的是经过契约校验和引用校验的回答，不是模型原始输出。

### 3. 为什么项目采用“Java 控制面＋Python Agent 执行端”的架构？

**回答：** Java 适合承载身份、权限、业务状态、事务、发布管理和长期数据治理，Python 更适合承载模型调用、文档解析、Embedding、检索、Rerank 和 Agent 编排。我没有强行让一种语言承担所有职责，而是按照稳定业务控制与快速演进的智能执行来划分边界。

这种拆分也让模型能力可以快速迭代，同时不破坏业务真相。代价是跨进程契约、状态投影和故障处理更复杂，所以我们用版本化协议、发布快照、事件序号和运行回放来约束两端协作。

### 4. Java 和 Python Agent 分别是谁的真相源？

**回答：** Java 是用户可见业务和管理配置的真相源，包括知识库业务状态、文档版本、索引发布、Agent 配置、会话、消息、反馈和权限。Python Agent 是一次智能执行的事实来源，包括用了哪些检索查询、召回了什么、怎样重排、采用了哪些证据、调用了什么模型以及在哪一步失败。

两者不是双主写同一份数据。Java保存需要面向业务长期查询的投影，Agent保存执行事实。出现差异时，以各自职责范围内的原始事实为准，通过共同的 Run ID、Release ID 和 Trace ID 对齐，而不是让任意一端覆盖另一端。

### 5. 为什么前端只能访问 Java，不能直接调用 Agent？

**回答：** 如果前端直连 Agent，浏览器就可能绕过身份、租户、资源归属、发布版本和审计控制，还会让业务会话状态分散在多个系统。模型调用通常还涉及服务端凭证，更不能暴露给浏览器。

因此前端只负责交互和严格解析公开契约；Java统一注入身份、选择发布版本、保存会话并治理错误；Agent只接受受控的内部请求。这样即使未来更换模型或调整 Agent 实现，前端和业务权限边界也不会被打散。

### 6. Java MySQL、Agent MySQL、PostgreSQL＋pgvector、Redis、COS 分别保存什么？

**回答：** Java MySQL保存业务主数据，如知识库、文档版本、索引发布、Agent配置、会话、消息、引用、反馈和评测批次。Agent MySQL保存执行侧事实，如发布快照、运行、事件、检查点、检索快照和模型调用摘要。PostgreSQL＋pgvector保存父子片段、向量以及索引成员关系，承担检索。

Redis用于短期协调，例如取消标志、幂等缓存和限流；COS保存原始文件和可预览文件。我的原则是对象存储不决定业务状态，向量库不决定哪个版本已发布，缓存也不成为长期真相源。

### 7. 为什么智能客服需要独立于运营助手，拥有独立的 Graph、Prompt、策略和 Release？

**回答：** 两个 Agent 的业务目标、输入输出、风险和评测标准不同。运营助手可能强调研究、规划和任务执行，智能客服强调公司知识证据、拒答、引用和版本稳定。如果共享业务状态和 Prompt，一个 Agent 的优化很容易无意中改变另一个 Agent 的行为。

所以我只让它们共享无业务语义的底座，例如 Provider、运行框架、预算、取消和日志。客服的 Graph、状态、Prompt、模型策略、RAG策略和发布版本全部独立，从而可以单独发布、回滚和评测。

### 8. 为什么没有把 Java 各模块拆成多个独立微服务？

**回答：** 当前规模下，模块化单体更符合成本和复杂度。知识管理、AI中心、文件和身份虽然有清晰模块边界，但它们共享事务、一致的发布流程和同一团队运维。过早拆成微服务会引入分布式事务、部署、链路追踪和跨服务版本治理成本，却没有足够的独立扩缩容收益。

我保留了模块依赖边界和对外接口边界，将来只有当团队、负载、发布节奏或故障隔离诉求真正分化时，才会考虑物理拆分。

### 9. 如果 Java 记录的 Run 状态和 Agent 执行状态不一致，应该如何处理？

**回答：** 我不会简单选择“最后写入者获胜”。先根据 Java Run、Agent Run、事件序号和终态时间线判断是事件丢失、重复、乱序、网络中断还是投影失败。Agent侧保留原始执行事实，Java侧保存用户可见投影，两者通过补拉或重放已有事件进行修复。

终态具有单调性，已经完成、失败或取消的 Run 不能被迟到的中间事件改回运行中。无法自动修复时要保留差异和告警，不能伪造成功状态。

### 10. 当前架构最大的优点和代价分别是什么？

**回答：** 最大优点是职责清楚：业务状态、权限和发布治理稳定地留在 Java，智能能力在 Python 快速演进；每次回答又能通过冻结版本和证据快照被追溯。最大代价是系统跨越多个数据源和两个运行时，协议兼容、状态一致性、真实环境部署和排障都更复杂。

作为负责人，我接受这项代价的前提是建立严格契约、运行回放、真实验收和明确的真相源，否则这种分层只会变成难以定位问题的分布式复杂度。

## 二、CustomerServiceGraph 与 Agent 编排

### 1. CustomerServiceGraph 包含哪些主要执行阶段？

**回答：** 我把主链路划分为意图识别与查询规划、知识检索、候选融合与重排、父证据组装、冲突和充分性判断、回答模式选择、回答生成与引用校验。每个阶段有独立输入输出和运行事实，因此出现错误时可以明确归因。

这不是为了把流程做复杂，而是避免“一个 Prompt 从头做到底”。拆开后，检索错误、证据错误和生成错误可以分别验证，也可以对不同阶段使用不同模型策略。

### 2. 哪些问题会进入知识检索，哪些问题会跳过检索？

**回答：** 与公司制度、业务流程、内部产品或技术资料有关的问题进入知识检索；同时包含公司事实和通用建议的问题也会检索。纯通用知识问题不需要消耗公司知识检索，信息明显不足的问题优先澄清。

判断依据不是关键词硬匹配，而是结构化意图结果加确定性路由。这样既避免所有问题都检索造成延迟，也防止公司问题直接由模型常识回答。

### 3. 意图识别、查询计划、检索、充分性判断和回答生成为什么需要分开？

**回答：** 这些阶段解决的是不同问题：意图决定走哪条业务路径，查询计划决定如何找资料，检索负责找候选，充分性判断决定证据够不够，生成只负责在允许边界内组织语言。如果合并在一个 Prompt 里，模型可能一边找不到证据一边自行补全，难以审计。

分开之后，我们能判断失败发生在哪一层，也能用评测分别优化召回、重排、拒答和答案质量。

### 4. 哪些判断交给模型，哪些判断必须由确定性代码完成？

**回答：** 语义理解类判断可以交给模型，例如意图、改写、证据是否回答了问题、两段内容是否语义冲突。权限、租户、索引成员、版本唯一性、Token预算、引用ID范围、原文偏移、状态流转和幂等必须由代码强制执行。

我的原则是模型负责“理解”，代码负责“授权和约束”。凡是越权、数据一致性或不可逆结果，都不能只依赖模型自觉遵守 Prompt。

### 5. 为什么不允许模型完全自主循环调用各种能力？

**回答：** 完全自主循环容易产生无限思考、重复调用、成本失控和业务顺序错误。客服场景要求稳定、可解释和低风险，核心步骤本来就可以明确建模，没有必要把所有流程都交给模型临场规划。

我们允许模型在受控节点做语义判断，但执行图、最大次数、可用能力和失败路径由系统限定。这种有限自主更符合企业知识问答的可靠性要求。

### 6. 模型推荐的回答模式和代码允许的模式冲突时，最终听谁的？

**回答：** 最终由确定性策略裁决。模型可以根据语义推荐模式，但只有证据充分、意图允许且引用条件满足时，系统才允许输出公司知识模式。例如模型想给公司结论，但证据被冲突检查阻断，最终必须降为证据不足。

这样设计是为了把模型建议和业务授权分开，避免模型通过改变一个字段绕过证据规则。

### 7. 模型结构化输出不符合契约时如何处理？

**回答：** 先把它判定为模型输出失败，而不是猜测字段或填默认值。对于可修复的格式问题，可以在严格次数内使用修复提示重试；仍不符合契约就记录失败阶段、错误码和模型调用事实，终止当前路径。

我不接受“看起来能用就继续”，因为缺失的模式、引用或充分性字段可能直接改变业务语义。

### 8. 为什么当前流程更接近受控工作流，而不是完全自主 Agent？

**回答：** 当前任务的阶段和安全边界是可预先定义的：识别问题、查知识、核验证据、生成回答。真正需要模型的是每个阶段内部的语义判断，而不是让模型决定能否越过验证、任意添加步骤。

因此我们仍然称它为 Agent，是因为它具备状态、语义决策和条件分支；但它是受业务规则约束的 Agent，而不是无限自主的通用执行体。

### 9. 如何限制一次请求的查询改写数量和模型调用次数？

**回答：** 查询数量、各阶段候选数、重排数和最终证据数都由已发布的 RAG 策略限制，不能由模型任意扩张。模型调用还受到阶段设计、超时、有限重试和运行预算约束。

这些限制必须随 Release 冻结，保证同一版本的成本和行为边界稳定，也方便通过评测比较策略调整的真实收益。

### 10. Agent 执行到一半失败时，如何保留已经发生的运行事实？

**回答：** 每个阶段开始、完成或失败都会形成有序事件和阶段摘要，检索候选、证据选择和模型错误也按可审计事实保存。失败不会把整次运行抹掉，而是将 Run 置为明确终态，并保留已经完成的阶段。

这样我们能够回放到失败点，区分是模型、检索、数据还是网络问题。重试会形成新的运行事实，不覆盖旧失败记录。

## 三、五种回答模式

### 1. 项目的五种回答模式分别是什么？

**回答：** 五种模式是公司知识回答、通用建议、混合回答、澄清问题和证据不足。公司知识回答必须有有效证据和引用；通用建议明确不是公司制度；混合回答将两部分分区表达；澄清用于问题缺少关键对象；证据不足用于确实需要公司依据但当前资料不能支持结论。

这五种模式的价值是把“能不能答、以什么身份答”显式化，避免所有请求最后都变成一段看似确定的自然语言。

### 2. COMPANY_KNOWLEDGE 在什么条件下使用？

**回答：** 问题必须属于公司知识范围，当前 Release 绑定的索引要召回相关资料，父证据经过版本、冲突、预算和充分性检查后能够完整支持结论，并且最终每条公司事实能够闭合到合法引用。

只要关键条件缺失、证据冲突或引用不支持结论，就不能因为模型“知道答案”而使用这个模式。

### 3. GENERAL_ADVICE 为什么必须明确标注“非公司制度”？

**回答：** 员工很容易把系统给出的建议理解成公司正式要求。通用建议来自模型的一般知识，不代表当前企业规则，如果不标注来源边界，会造成制度误用。

因此这个模式不附带公司引用，并在展示上明确说明性质。它可以提供思路，但不能替代需要公司授权或正式制度依据的结论。

### 4. MIXED 如何区分公司事实与通用建议？

**回答：** 混合回答把公司知识和通用建议作为两个独立部分生成和展示。公司部分只能使用冻结证据并附引用；通用部分可以给补充方法，但必须明确不是公司规定，也不能反向改变公司部分的结论。

这种分区比在同一段落里混写更容易让用户判断哪些内容具有组织约束力。

### 5. CLARIFY 和 INSUFFICIENT_EVIDENCE 有什么区别？

**回答：** 澄清表示系统还不知道用户具体在问什么，补充一个关键条件后可能继续处理；证据不足表示问题已经明确，但当前已发布知识无法支撑答案。前者缺的是问题信息，后者缺的是可用证据。

如果把两者混淆，系统可能对明确但无资料的问题反复追问，或者对含糊问题错误宣称知识库没有答案。

### 6. 用户问题缺少关键对象时，为什么应该先澄清？

**回答：** 在对象、时间、制度或方案不明确时直接检索，容易召回多个无关版本并产生看似合理的错误结论。先提出一个最关键、最小的澄清问题，能降低检索噪声和误答风险。

澄清不是把责任推给用户，而是避免系统替用户猜测业务条件。

### 7. 检索不到公司知识时，是否可以直接返回通用建议？

**回答：** 不能一概而论。如果用户明确询问公司规定、审批结果或内部流程，没有证据就必须返回证据不足；如果问题本身允许一般性建议，可以在明确标注后给通用内容。混合问题还可以保留可回答的通用部分，同时说明公司部分缺乏依据。

关键是不能用通用常识填补公司事实空缺。

### 8. 证据之间存在冲突时，为什么不能让模型自行选择？

**回答：** 模型的选择通常受措辞、位置和相关度影响，并不等同于制度效力判断。没有明确的生效关系、适用对象或权威来源时，选择任意一份都会把不确定性伪装成事实。

因此关键冲突会阻断公司结论，返回证据不足并保留冲突事实，等待知识治理人员处理。

### 9. 公司证据部分充分时，系统应该返回哪种模式？

**回答：** 要看问题是否允许一般性补充。若用户只要公司制度且关键结论不完整，应返回证据不足，不能用半份证据作完整结论；若问题同时包含可独立回答的通用部分，可以使用混合或通用降级，但必须明确公司部分只覆盖到哪里。

部分证据不是“降低一下置信度就继续答”，而是要判断缺失部分是否影响核心结论。

### 10. 为什么回答模式不能完全由最终回答模型自行决定？

**回答：** 最终模型最接近自然语言生成，也最容易为了完成回答而扩大解释。回答模式涉及是否允许使用公司身份、是否需要引用和是否必须拒答，本质上是业务授权，不只是语言风格。

所以模型可以在证据范围内组织内容，但模式由前置意图、充分性和确定性规则共同约束。

## 四、知识治理与版本管理

### 1. 文档、文档版本、索引发布版本和 Agent Release 分别解决什么问题？

**回答：** 文档代表一个长期逻辑对象，例如《研发规范》；文档版本代表某次不可变内容；索引发布版本固定本次可检索的文档版本集合；Agent Release 再把索引、Prompt、模型和 RAG 策略绑定为一次完整运行配置。

这四层分别解决业务身份、内容历史、检索快照和运行复现。缺少任何一层，都可能出现“知道用了哪个 Agent，却不知道它查了哪版资料”的问题。

### 2. 为什么知识库要区分公司制度、业务流程、产品文档和技术文档？

**回答：** 不同知识类型的完整性要求和回答风险不同。公司制度和业务流程通常包含强约束、条件和例外，默认必须保留完整条款；产品和技术文档中可能存在较长叙述，可以在严格可追溯条件下做原文节选。

分类也为后续权限、评测集覆盖和治理优先级提供基础，而不只是页面标签。

### 3. 文件上传成功、解析成功、索引就绪和发布成功有什么区别？

**回答：** 上传成功只表示原始文件安全落盘并创建业务记录；解析成功表示已提取出可处理结构；索引就绪表示切片、向量和成员关系经过校验；发布成功才表示它进入可被某个索引版本选用的知识集合。

这些状态不能合并，否则文件刚上传或部分处理失败时就可能被在线问答检索到。

### 4. 文件 SHA-256 去重与切片去重分别发生在哪个阶段？

**回答：** 文件哈希用于识别相同原始内容，避免同一文件重复创建无意义版本；切片去重用于同一文档版本内消除完全重复的检索片段，降低召回噪声。两者对象、作用范围和业务含义不同。

文件名相同不代表内容相同，跨文档文本相似也不代表可以合并，所以去重范围必须严格限定。

### 5. 批量上传中部分文件失败时，为什么成功文件仍然保留？

**回答：** 每个文件都是独立的业务对象和处理任务，一个坏文件不应该回滚已经完成的合法文件。批次提供的是操作视图，不是要求所有文件处于同一数据库事务。

我们会显示部分成功、保留成功项，并允许只重试失败项。这样既符合用户预期，也避免大文件批次反复重做造成成本浪费。

### 6. 同一文档发布新版本后，如何保证新问答不再检索旧版本？

**回答：** 发布新索引时，以逻辑文档为单位替换成员，保证一个索引快照只包含指定文档版本；随后新的 Agent Release明确绑定这个索引。查询只能在绑定的索引成员内搜索，而不是从全库中挑最新记录。

这样旧版本仍可供历史回放使用，但不会进入新 Run 的候选集合。

### 7. 为什么不能直接覆盖已经发布的索引数据？

**回答：** 原地覆盖会破坏历史回答的可解释性，也让回滚变得不可靠。昨天的回答和今天的回答即使使用同一个索引ID，实际内容可能已经不同，无法审计。

因此新知识通过新版本和新索引发布生效，旧数据保持不可变。切换失败时现有在线版本也不会被污染。

### 8. 为什么知识索引发布后，还需要创建或激活新的 Agent Release？

**回答：** 知识库的“当前发布索引”表示知识管理侧准备好了哪个版本，但在线 Agent 应使用哪一版必须由完整发布配置决定。否则知识管理员一次发布就会未经评测自动改变线上回答。

Agent Release是最后一道显式绑定，将知识变更与 Prompt、模型、RAG策略一起校验后再上线。

### 9. 历史回答为什么仍然可以引用旧文档版本？

**回答：** 每次运行保存了当时使用的 Release、索引、文档版本、父证据和引用原文。历史页面读取冻结事实，不根据当前索引重新检索。

这既是审计要求，也是正确的时间语义：我们要解释当时为什么这样答，而不是用今天的知识重写昨天的答案。

### 10. 索引回滚与 Agent Release 回滚有什么区别？

**回答：** 索引回滚改变知识管理侧当前指向的索引；Agent Release回滚改变在线问答使用的整套配置。前者不必然影响已经激活的 Agent，后者可能同时恢复旧 Prompt、模型、策略和知识绑定。

实际操作时要核对两者一致性，不能只回滚其中一个就假设在线行为已经恢复。

### 11. 如何保证一个索引快照中，同一逻辑文档只有一个版本？

**回答：** 在发布构建阶段按逻辑文档替换成员，并通过唯一性验证检查同一个文档ID是否对应多个版本。Agent收到索引成员后还会再次校验，不把异常数据交给相关度排序解决。

这是典型的双层防线：管理端防止错误发布，执行端防止错误快照被消费。

### 12. 如果同一索引出现同一文档的两个版本，系统为什么应该失败关闭？

**回答：** 两个版本同时出现意味着发布契约已经被破坏。按分数选择可能让新旧版本在不同问题上随机生效，造成最难发现的隐性错误。

因此系统应明确报告版本冲突并停止公司事实回答，让维护人员修复索引，而不是继续提供不确定结果。

## 五、文档解析与入库

### 1. 请说明文件从上传到可检索的完整处理链路。

**回答：** 文件先由 Java校验类型、大小和业务归属，保存到对象存储并创建文档版本和处理任务。Agent通过受控地址下载后核对大小与哈希，执行解析；扫描型PDF在文本不足时进入OCR；然后建立结构化父片段和检索子片段，调用Embedding并写入向量库。

最后系统校验父子关系、向量数量、维度和索引成员，只有通过后版本才能进入就绪状态。知识管理员发布索引，再由 Agent Release绑定后，在线问答才会检索它。

### 2. 为什么原始文件需要保存在对象存储中？

**回答：** 原始文件是内容来源和重新处理的依据。解析器、切片策略或Embedding模型升级时，我们需要从原文件重建，而不能依赖已经损失结构的信息。引用预览和审计也需要回到原始资料。

对象存储只负责文件内容，文档业务状态和发布关系仍由数据库管理，避免用文件存在与否推断业务状态。

### 3. TXT、Markdown、HTML、PDF 和 DOCX 分别如何解析？

**回答：** 纯文本和Markdown优先保持原始文本结构；HTML需要提取主体、去除导航和脚本噪声；普通PDF按页抽取并保留页码；DOCX等复杂办公文档通过结构化解析器恢复标题、段落、列表和表格。扫描PDF则需要OCR补充。

我不追求一个解析器包打天下，因为不同格式的错误模式不同，统一入口后仍要按格式保留最重要的结构信息。

### 4. 当前如何识别扫描型 PDF？

**回答：** 当前做法是先尝试普通文本提取，当提取内容低于最低有效长度时，将其视为可能的扫描件并进入OCR。这是一个实用但不完美的启发式规则。

它可能误判文字很少的正常PDF，也可能漏掉部分页面是扫描图的混合PDF。下一步应增加逐页文本密度、图片比例和OCR置信度判断。

### 5. 什么情况下进入 OCR？

**回答：** 仅对支持的PDF，在普通解析无法获得足够文本且OCR能力已配置时进入。OCR不是所有PDF的默认步骤，因为它成本更高、速度更慢，还可能引入识别错误。

OCR结果为空、置信度不足或服务失败时，应把文档任务标为明确失败，不能把空内容继续切片并宣称处理成功。

### 6. PDF 页码如何传递到切片和最终引用？

**回答：** 解析阶段按页保留文本起始位置，形成页码标记；父片段和子片段在原文中的位置据此映射到页码范围；证据和引用继续携带文档版本、父片段、页码及原文偏移。

这样页码不是生成阶段猜出来的，而是从解析原文一路传递，用户能够回到具体页面核查。

### 7. 为什么解析后不能只保留纯文本？

**回答：** 纯文本会丢失标题层级、条款边界、列表关系、表头和页码。一旦结构丢失，后续切片就可能把条件与结论分开，也无法生成准确引用。

RAG质量很大程度取决于入库结构，而不是只取决于Embedding模型。我们宁愿让结构无法可靠恢复的文档明确失败，也不静默制造错误知识。

### 8. 为什么要保留标题路径、列表、表格和原文位置？

**回答：** 标题路径帮助检索和重排理解语境，列表和表格决定内容之间的逻辑关系，原文位置用于引用闭包和完整性校验。它们共同保证召回的片段不仅相关，而且可独立解释。

例如只保存表格某个单元格的文本，很可能完全失去列名和适用对象，导致正确召回、错误回答。

### 9. 入库时为什么要校验文件大小和 SHA-256？

**回答：** 下载地址、网络和对象存储都可能导致内容不完整或拿错对象。大小和哈希与Java登记值一致，才能证明Agent处理的是预期文件。

这也是跨系统边界的完整性校验，避免文档元数据属于一个版本、实际解析内容却来自另一个版本。

### 10. 为什么要校验切片数量、Embedding 数量和向量维度？

**回答：** 每个检索子片段必须有且只有一个向量，数量不一致说明请求丢失、返回顺序或写入过程存在问题。维度错误则说明Embedding模型与向量列或索引配置不兼容。

如果不在发布前拦截，这类错误会表现为线上随机漏召回或查询失败，定位成本更高。

### 11. 入库阶段出现失败时，如何记录阶段和错误码？

**回答：** 任务按预检、解析、OCR、切片、向量化和验证阶段推进，记录当前阶段、进度、终态和稳定错误码。对外展示安全、可理解的信息，内部保留Trace用于定位，但不泄露存储地址、凭证和原始异常正文。

阶段事实还用于批量导入统计和失败项重试，不能只保存一个笼统的“处理失败”。

### 12. 当前失败重试是真正从失败节点恢复，还是重新执行入库流程？

**回答：** 从产品语义上，用户可以针对失败项发起新的处理尝试，并保留旧尝试记录；当前实现并不是所有阶段都具备精确检查点恢复，部分场景会重新执行前置步骤。面试时我会明确这一点，不把“可重试”夸大成“任意节点无损续跑”。

如果后续入库成本明显上升，我会为解析产物、切片结果和Embedding批次设计可验证检查点，但前提是保证版本、哈希和策略一致。

## 六、父子切片设计

### 1. 为什么项目由单层切片升级为父子切片？

**回答：** 单层切片很难同时满足精确召回和完整回答。切得小，检索容易命中，但条件、结论和例外可能被拆开；切得大，上下文完整，却会引入噪声并降低召回精度。因此我把检索单元和回答单元分离：子片段负责找到位置，父片段负责提供完整语义。

这次升级解决的不是“切片尺寸不好调”，而是两个目标天然冲突。父子结构让我们可以分别优化召回和证据完整性。

### 2. 父片段和子片段分别负责什么？

**回答：** 父片段是可以独立理解的原文条款或小节，保存完整语义、页码和结构；子片段从父片段内部切出，尺寸较小，用于向量和全文检索。子片段命中后，系统回到对应父片段参与证据组装。

父片段不直接追求召回数量，子片段也不直接承担最终回答，两者通过稳定的父子关系连接。

### 3. 为什么使用子片段检索，却使用父片段回答？

**回答：** 用户问题通常只对应条款中的几个关键词或一句语义，小片段更容易形成清晰向量并被检索命中。但最终回答需要看到适用范围、前提和例外，直接拿命中的一句话可能断章取义。

因此检索看“小窗口”，回答看“完整条款”，这是精度和完整性的平衡。

### 4. 如何定义一个“可以独立理解”的父片段？

**回答：** 一个父片段至少应该包含同一规则的适用对象、关键前提、主要结论、必要例外以及不可分割的表格行或说明。读者只看这个片段时，不需要依赖前后半句才能判断规则含义。

边界优先依据标题、编号条款、段落、列表和表格结构，而不是固定字符数。结构不可靠时宁可保留稍大的完整段落，也不猜测并拆断规则。

### 5. 为什么父片段不能简单等同于整章？

**回答：** 一章可能包含多个主题和大量背景，把整章作为父片段会快速耗尽上下文预算，还会把不相关内容送入模型。父片段应该围绕一个完整、相对独立的语义单元，而不是机械沿用最大标题范围。

只有章节很短、主题单一时，整章才适合作为一个父片段。

### 6. 如何避免拆散制度的前提、结论和例外？

**回答：** 解析时先识别标题、编号条款、列表和表格边界，再在完整结构内建立父片段。编号条款、列表、表格和代码默认按受保护内容处理，超过安全上限也不能随意从中间截断。

发布前还要检查父子关系和原文位置。无法在上限内保存完整规则时，应让文档处理失败或回答证据不足，而不是牺牲语义完整性。

### 7. 多个子片段命中同一个父片段时如何去重？

**回答：** Rerank仍保留各个子片段的命中和分数，方便调试；进入回答上下文时按父片段ID去重，同一父原文只放一次，同时记录它由哪些子片段支持。

这样既不会重复消耗Token，也不会丢失“为什么这个父片段被选中”的检索证据。

### 8. 表格拆分时如何保证每个片段都带表头？

**回答：** 表格按连续行组拆分，每个行组重复原始表头，并保留必要注释和页码。这样每一行即使脱离原表格，也能知道各列代表什么。

重复表头是有意的结构冗余，不应被普通文本去重误删；引用仍指向原始表格位置。

### 9. 单条制度或表格行超过父片段上限时如何处理？

**回答：** 如果它是不可分割的受保护内容，我不会直接截断。入库阶段应报告条款过长或质量门禁失败，或者在已发布的大上下文策略可以完整容纳时使用对应模型。

核心原则是不能为了成功入库而制造半条规则。半条规则往往比没有答案更危险。

### 10. 父片段、子片段、页码和原文偏移之间如何关联？

**回答：** 父片段属于一个确定的文档版本，子片段同时保存父ID、在父片段中的顺序以及起止偏移；父片段保存页码范围和原文哈希。引用再携带实际采用的父证据或原文跨度。

因此系统可以从回答引用反向定位到父原文、子命中、文档版本和原始页码，形成完整证据链。

### 11. 当前父片段、子片段和 Overlap 的默认参数是多少？

**回答：** 当前默认父片段上限约为2400个项目估算Token，子片段上限约为400，子片段重叠约为40。旧单层切片曾使用更大的子片段和更高重叠，但父子模式下职责已经不同。

这些是当前工程参数，不是行业标准答案。上线前应结合固定评测集、真实文档结构、召回率、完整条款保留率和延迟持续校准。

### 12. 当前 Token 计算与真实模型 Tokenizer 有什么差异？

**回答：** 当前切片阶段使用确定性规则估算中英文Token，便于本地处理和稳定测试，但它不等同于具体模型的Tokenizer。中英文混排、标点、特殊符号和代码可能出现偏差。

因此预算还需要安全余量，并受模型最大输入限制二次约束。长期方案是按实际模型Tokenizer做精确预算，同时保留与模型版本的绑定。

## 七、Embedding 与混合检索

### 1. 为什么项目同时使用向量检索和全文检索？

**回答：** 向量检索擅长理解口语、同义表达和语义相近问题，全文检索擅长精确命中编号、型号、专有名词和原文词组。企业知识同时包含自然语言和大量精确标识，只依赖一种检索方式会产生稳定盲区。

双路召回先提高候选覆盖，再通过融合和重排统一排序，是对不同失败模式的互补。

### 2. 向量检索更适合解决什么问题？

**回答：** 它适合用户表达和文档措辞不一致的场景，例如用户说“代码至少要测到什么程度”，文档写“核心模块行覆盖率”。Embedding能把相近语义映射到接近的向量空间。

但向量相似不代表事实相同，涉及数字、否定、版本和条件时仍要回到原文核验。

### 3. 全文检索更适合型号、编号和精确术语的原因是什么？

**回答：** 型号、错误码、制度编号和专有名词通常要求字符级精确匹配，它们在向量空间中可能没有稳定语义，甚至只差一个字符就代表完全不同对象。全文检索可以直接利用词项出现和位置。

因此精确词项是全文召回的重要补充，不能指望Embedding解决所有检索问题。

### 4. 当前向量维度是多少？维度由谁决定？

**回答：** 当前工程使用1024维向量。维度由选定的Embedding模型输出决定，并必须与向量数据库字段、索引和运行时校验一致。

维度不是越大越好，也不能只改数据库列。模型、入库、查询、索引和验证都要作为一个版本化整体治理。

### 5. 为什么文档入库和查询必须使用兼容的 Embedding 模型？

**回答：** 向量距离只有在同一或严格兼容的向量空间内才有意义。文档使用一个模型、查询使用另一个模型，即使维度相同，坐标含义也可能完全不同，检索分数没有可比性。

所以Embedding模型和版本应随索引保存，运行时只能用匹配策略查询。

### 6. 更换 Embedding 模型后为什么需要重新构建索引？

**回答：** 新模型会改变所有文档向量的空间分布，旧向量不能直接复用。正确做法是基于原始文档和切片构建新索引，使用同一评测集比较召回、排序、延迟和成本，再通过新Release切换。

旧索引保留用于回滚，不能原地覆盖后宣称历史运行仍可复现。

### 7. 当前 PostgreSQL 全文检索使用的是什么算法？

**回答：** 当前使用PostgreSQL原生全文检索，将内容转成词项向量，通过普通查询表达式匹配，再使用覆盖密度相关的排名函数排序。它满足轻量全文召回，但中文处理能力受当前文本配置限制。

我会准确描述实际能力，不把所有全文搜索都笼统称为Elasticsearch或BM25。

### 8. 当前实现能否严格称为 BM25？为什么？

**回答：** 不能。当前排名使用PostgreSQL全文检索的排名函数，并不是标准BM25公式。两者都属于词项检索，但文档长度归一化、词频饱和等评分机制不同。

面试中我会说“PostgreSQL全文召回”，不会为了显得高级而把它包装成并未使用的算法。

### 9. PostgreSQL simple 配置处理中文有什么局限？

**回答：** simple配置缺少真正的中文分词能力，连续中文可能被当作较长词项，用户问题和文档稍有不同就无法匹配。因此它对英文、数字和精确标识更稳定，对自然中文召回能力有限。

如果全文通道成为质量瓶颈，我会评估中文分词扩展或专门搜索引擎，并用真实评测证明收益后再引入。

### 10. 为什么真实接口中可能出现全文召回候选为零？

**回答：** 常见原因包括中文没有正确分词、查询改写与原文词项不一致、过滤条件排除了目标版本、索引内容为空或文本规范化不同。不能看到零候选就简单调大TopK。

我会先检查查询词项、文档词项和实际过滤范围，再判断是分词、数据还是发布问题。

### 11. 多个查询改写如何同时执行向量检索和全文检索？

**回答：** 意图阶段可以生成有限数量的独立检索查询。每个查询分别产生Embedding，并在同一冻结索引范围内并发执行向量和全文召回；所有候选随后进入统一去重和排名融合。

并发能降低总延迟，但查询数量、每路TopK和外部服务并发必须受发布策略限制。

### 12. 为什么向量相似度和全文检索分数不能直接相加？

**回答：** 两种分数的量纲和分布不同，向量相似度受Embedding模型影响，全文排名受词频和文本统计影响。直接相加会让某一路因数值范围较大而天然占优。

我们使用基于排名的融合，先避免分数量纲问题，再由Rerank统一评估候选与问题的相关性。

## 八、RRF、Rerank 与 TopK

### 1. RRF 在项目中解决什么问题？

**回答：** RRF负责把不同查询、向量召回和全文召回的排名合并成一份候选序列。它看候选在每个列表中的名次，不依赖原始分数可比，从而让多路结果可以稳定融合。

它的目标是候选覆盖和初步排序，不负责最终证明证据能够支持回答。

### 2. RRF 为什么基于排名融合，而不是直接融合原始分数？

**回答：** 不同召回通道的分数含义不同，而且更换模型或索引后分布会变化。排名虽然损失部分分数细节，却能提供跨通道更稳定的共同尺度。

这让融合参数更容易解释，也减少某一路分数未经标定就压制其他结果的风险。

### 3. RRF 后为什么还需要 Rerank？

**回答：** RRF只利用候选在各列表中的位置，没有深入比较问题与完整文本的语义关系。Rerank模型可以同时读取问题和候选内容，更准确识别条件、主题和上下文。

所以召回阶段追求不漏，Rerank阶段追求把真正相关的证据排在前面，两者职责不同。

### 4. Rerank 应该接收哪些文本和元数据？

**回答：** 至少应包含用户当前问题、候选子片段正文、文档标题和章节路径。标题和章节可以消除短片段的歧义，例如同一句“审批后执行”在不同流程章节中含义不同。

版本和租户范围不交给Rerank决定，它们必须在进入候选前由系统过滤。

### 5. vector_top_k 和 fts_top_k 分别控制什么？

**回答：** 它们分别控制每个检索查询从向量通道和全文通道拿回多少初始候选。两个值可以不同，因为通道的召回特性、速度和噪声不同。

它们决定的是第一阶段候选池，不代表最终送给回答模型的证据数量。

### 6. fusion_top_k 和 rerank_top_k 分别控制什么？

**回答：** fusion_top_k限制RRF融合后保留多少候选进入后续处理；rerank_top_k限制重排后保留多少高相关子片段。前者控制Rerank成本，后者控制父证据展开的范围。

如果融合候选太少，Rerank无法挽救被提前丢掉的正确资料；候选太多则增加延迟和成本。

### 7. final_evidence_top_k 为什么不能直接等同于 rerank_top_k？

**回答：** Rerank操作的是子片段，多个子片段可能指向同一个父片段；最终证据数操作的是去重后的独立父证据，还要经过等价、冲突和预算检查。两者统计对象不同。

独立配置可以避免一个父条款因多个子命中占满全部名额，也能控制最终上下文复杂度。

### 8. 为什么最终送入模型的是父证据，而不是 Rerank 返回的子片段？

**回答：** 子片段用于精确定位，但可能只有半句条件或一个表格行。父证据保留完整条款，才能让模型看到结论适用的前提和例外。

Rerank分数仍用于父证据排序，但不会把检索单元误当成完整事实单元。

### 9. TopK 越大是否一定越好？

**回答：** 不是。更大的TopK可能提高召回上限，也会引入更多近似但错误的资料、增加Rerank和冲突检查成本，并挤占回答上下文。超过一定范围后，收益通常递减。

TopK应该用固定评测集在召回、引用正确率、拒答准确率、延迟和成本之间寻找平衡。

### 10. TopK 过大会给延迟、Token 和冲突检测带来什么影响？

**回答：** 候选越多，Embedding以外的数据库传输、Rerank、父片段读取、等价判断和冲突对比都会增加；最终证据如果控制不好，还会占用大量Token并产生Lost in the Middle问题。

冲突候选对可能近似平方增长，所以除了TopK，还需要限制待比较的候选对数量。

### 11. Rerank 服务失败后，能否把 RRF 顺序冒充重排结果？

**回答：** 不能。RRF和Rerank的语义不同，静默使用RRF顺序会让调试记录与真实执行不一致，也可能突破已经评测过的质量边界。

除非发布策略明确声明并评测过降级路径，否则应返回可识别失败，并保留Rerank失败事实。

### 12. 如何用固定评测集确定合理的 TopK？

**回答：** 我会固定同一批问题、知识版本和模型，分别测试多组召回、融合、重排和最终证据参数。比较正确文档召回、父条款召回、回答模式、引用合规、误答、P50/P95延迟和成本。

选择能满足关键质量门槛且成本合理的最小配置，而不是只追求单一Recall最高值。

## 九、证据组装与上下文预算

### 1. 什么是项目中的 EvidencePack？

**回答：** EvidencePack是一次运行最终可用于充分性判断和回答的不可变证据快照。它包含文档和版本、父证据、命中子片段、原文哈希、采用形式、偏移、排序、预算和阻断原因。

它把“检索候选”转换成“获准用于回答的证据”，是检索与生成之间最重要的边界。

### 2. 为什么充分性判断、回答生成、引用和回放必须使用同一个证据快照？

**回答：** 如果每个阶段重新查询或重新选择证据，充分性可能基于一组资料，回答使用另一组，引用又指向第三组，最终无法证明结论来源。

冻结快照让所有下游消费者共享同一事实，并使历史回放不受当前索引变化影响。

### 3. 上下文预算需要计算哪些内容？

**回答：** 预算要包括系统和业务Prompt、用户问题、必要会话历史、证据文本、结构化输出开销、预留回答Token和安全余量。不同阶段模板大小不同，还要按更严格的阶段计算。

只看证据长度会在真正调用模型时溢出上下文，或迫使SDK做不可控截断。

### 4. 为什么不能只计算知识片段本身的 Token？

**回答：** 模型输入不仅有证据，还有指令、问题、历史和输出契约。证据刚好占满最大窗口时，实际请求必然超限。

因此证据预算只是总输入预算的一部分，且必须给输出和安全余量预留空间。

### 5. 父证据超过预算时，为什么不能从中间直接截断？

**回答：** 中间截断可能保留结论却删除前提，或者保留规则却删除例外，模型会把半条制度当成完整事实。截断后引用也难以表达内容缺失。

受保护条款必须整体进入或整体排除；无法完整容纳时应尝试已绑定的大上下文策略或返回证据不足。

### 6. FULL_ONLY 和 EXTRACTIVE_NARRATIVE 有什么区别？

**回答：** FULL_ONLY要求父证据全文进入模型，适合制度和流程等高风险内容。EXTRACTIVE_NARRATIVE只允许对明确标记的叙述性产品或技术资料，在全文放不下时选择原文中的完整句段。

节选不是模型摘要，所选文字必须逐字来自原文，并保留偏移和哈希。

### 7. 哪些类型的内容必须完整进入上下文？

**回答：** 公司制度、业务流程、编号规则、列表、表格、代码和无法可靠判断结构的内容默认完整保留。它们的顺序和上下文往往决定含义，不能仅凭模型选择几句话。

只有明确允许节选的叙述性段落，才可在严格校验下使用原文跨度。

### 8. 为什么模型只能选择原文句段，不能重新总结成“证据”？

**回答：** 摘要是模型生成的新文本，可能遗漏条件、改变程度或合并不同观点。一旦把摘要当成证据，后续引用就无法证明原文确实这样说。

模型可以帮助选择句段编号，系统负责按原文偏移取出并校验，实现“模型做语义选择，代码保证原文不变”。

### 9. 如何验证抽取片段确实来自原文？

**回答：** 每个跨度都携带父片段ID、起止偏移和文本哈希。系统按偏移重新读取父原文，要求逐字一致、顺序不变、范围合法，最终引用也使用同一跨度。

任一偏移或文本校验失败，就不能把该节选送入回答模型。

### 10. 什么情况下可以切换到大上下文模型？

**回答：** 只有受保护的完整条款超过主模型可用证据预算、Release已经绑定并验证过更大上下文策略，而且大模型确实能够完整容纳本次输入时，才允许切换。

这不是一般性的性能优化，也不能临时选择任意模型，因为模型变化会影响成本、行为和可复现性。

### 11. 为什么大上下文模型必须预先绑定到 Release？

**回答：** 模型策略包括Provider、模型名称、输入输出上限、超时和重试。运行时随意切换会让同一个Release实际行为漂移，也绕过发布评测和成本控制。

预先绑定后，选择条件、模型身份和预算都能进入运行快照并被审计。

### 12. 大模型仍然放不下完整条款时，系统为什么应该返回证据不足？

**回答：** 此时技术条件无法在不破坏原文的前提下提供可靠证据。继续截断或摘要会把系统限制伪装成确定答案。

证据不足是正确的业务结果，提示知识治理或模型容量需要改进，比输出可能错误的制度结论更安全。

## 十、重复证据与知识冲突

### 1. 完全相同文本去重和语义等价去重有什么区别？

**回答：** 完全相同去重通过原文和哈希确定，属于低风险确定性处理；语义等价去重处理措辞不同但事实相同的内容，需要比较数字、否定、对象、条件和时间。

后者必须更保守，并保留判断依据和被合并候选，不能只依赖向量相似度。

### 2. 为什么相似度高不能直接判定两段证据等价？

**回答：** “允许远程办公”和“不允许远程办公”在向量空间可能非常接近；金额、日期和比例只差一个数字也可能产生高相似度。相似度反映主题接近，不证明事实一致。

我们只用相似度筛选需要进一步比较的候选对，最终还要做语义和原文条件核验。

### 3. 两段内容数字、否定词或适用条件不同时应该如何处理？

**回答：** 默认视为不同事实并同时保留，随后判断是适用范围不同、版本关系还是潜在冲突。不能因为主体相似就把分数低的一段删除。

数字、否定、时间、对象和例外是等价判断中的硬重点，任一关键差异都可能改变业务结论。

### 4. 语义等价判断不确定时，为什么应该保留两份证据？

**回答：** 去重是有损操作，误删后后续阶段看不到被删除信息，也无法恢复。保留两份最多增加一些预算和噪声，错误合并却可能删除关键条件。

因此不确定时选择保守保留，并在调试事实中记录判断失败或不确定。

### 5. 同一文档的相邻父片段满足什么条件才能组合？

**回答：** 它们必须属于同一文档版本、顺序相邻、标题路径一致、都被本次检索命中，并且结构适合连续阅读，例如普通段落或同一表格的连续行组。组合数量也受限制。

组合只改变给模型的展示顺序，不制造新的合成引用，每个父片段仍独立定位。

### 6. 为什么不能跨标题、编号条款和文档版本拼接？

**回答：** 跨标题可能合并不同主题，跨编号条款可能混淆独立规则，跨版本更会把新旧内容拼成不存在的制度。模型看到连续文本后很难知道它们原本不属于同一语义单元。

所以相邻组装必须遵守结构和版本边界。

### 7. 两份正式文档内容冲突时，系统为什么不能按 Rerank 分数选择一份？

**回答：** Rerank分数只表示与当前问题的相关程度，不代表哪份制度法律或组织效力更高。分数高的可能只是措辞更像用户问题，并不一定是有效规则。

没有明确的适用对象、效力层级或版本关系时，系统应保留双方证据并阻断唯一结论，由知识治理人员解决冲突。

### 8. 发布时间和知识库优先级能否直接代表制度效力？

**回答：** 不能默认代表。发布时间只能说明时间，知识库优先级通常用于检索或展示，两者都不自动证明一份文件废止另一份文件。

只有业务明确建立了效力规则和替代关系，系统才可以据此裁决，否则应报告冲突。

### 9. 冲突检测为什么只能说明当前候选证据是否冲突？

**回答：** 系统只能比较本次召回并进入候选范围的证据。没有被召回的文档不会参与冲突判断，因此“当前未发现冲突”不等于整个知识库不存在冲突。

这也是为什么需要用召回评测覆盖冲突样本，避免关键对立资料长期在TopK之外。

### 10. 被去重、预算排除或冲突阻断的证据是否应该保留在调试记录中？

**回答：** 应该。它们解释了为什么某段资料没有进入最终回答，也是定位误答、漏答和预算问题的关键事实。在线用户不必看到全部内部过程，但管理员调试和历史回放需要可追溯。

保留事实不等于保存模型隐藏思维链，我们记录的是输入、结果、状态和确定性原因。

## 十一、引用与幻觉治理

### 1. 什么叫引用闭包？

**回答：** 引用闭包指最终答案中的每一条公司事实，都能追溯到本次获准使用的证据，并进一步定位到确定的文档、文档版本、索引、父片段、页码和原文位置。引用不能指向本次检索范围之外的资料，也不能只给一个无法核验的文档名称。

它解决的是“答案声称有依据”与“系统能证明依据确实存在”之间的差距。

### 2. 引用 ID 属于本次证据集合，是否足以证明引用正确？

**回答：** 不足。ID合法只能证明引用对象在本次证据集合里，不能证明这段原文支持答案中的具体结论。模型可能引用了同一文档中的相关段落，却没有覆盖数字、条件或例外。

因此还要校验引用文本和位置，并通过充分性评测或人工核验判断语义支持关系。

### 3. 如何验证引用原文、偏移、页码和哈希？

**回答：** 系统根据父片段和起止偏移重新读取冻结原文，要求引用文本逐字一致，并核对文档版本、索引成员、页码范围和内容哈希。完整引用必须等于父原文，节选引用的每个跨度都必须落在父原文合法范围内。

任何一项不一致都说明引用链断裂，不能把答案标为成功。

### 4. 完整父原文引用和节选引用有什么区别？

**回答：** 完整引用展示整个父条款，适用于制度、流程、表格和受保护结构；节选引用只展示明确允许压缩的叙述性父片段中的若干原文句段。两者都必须保留版本、页码和定位信息。

节选必须明确是原文节选，不能伪装成完整条款，也不能由模型改写。

### 5. 如何保证每条公司事实都有可追溯证据？

**回答：** 生成阶段只向模型提供冻结证据并要求公司段落声明引用，结构化输出会把事实段落与引用关联。系统随后检查引用范围、原文定位和回答模式，缺少合法引用的公司段落不能正常释放。

此外评测集会检查关键事实、来源、版本和引用合规，避免只验证格式。

### 6. 回答内容正确但引用来自错误版本，是否算成功？

**回答：** 不算。即使文字碰巧正确，错误版本意味着系统没有遵守当前发布配置，下一次就可能引用已经失效的规则。这属于版本准确性和引用闭包失败。

评测应把答案内容和版本命中分别检查，不能因为结果看起来对就掩盖链路错误。

### 7. 回答有引用但引用不支持结论，是否算成功？

**回答：** 不算。引用数量和格式只是最低要求，真正的标准是引用是否支持结论。尤其金额、日期、比例、适用范围和例外，必须能从引用原文中找到依据。

这种问题属于生成或引用选择错误，不应被“有引用”这一表面指标掩盖。

### 8. 检索为空时如何防止模型根据预训练知识补造公司制度？

**回答：** 公司问题只有在证据充分时才允许进入公司知识生成路径。检索为空或关键证据不足时，确定性路由直接选择证据不足，不让最终模型以公司身份自由回答。

同时结构化契约要求公司事实带合法引用，模型记忆无法制造本次证据集合中的引用。

### 9. 如何防止模型遗漏制度中的例外条件？

**回答：** 首先通过父片段保证前提、结论和例外一起进入上下文；其次在充分性和回答提示中明确检查适用对象、条件和例外；最后用包含例外条件的评测用例验证。

仅靠一句“不要遗漏”不够，数据结构和评测样本必须共同支持。

### 10. 为什么 Prompt 中写“不要编造”还不够？

**回答：** Prompt是行为引导，不是安全边界。模型可能误解、忽略或在复杂上下文中违反指令。真正可靠的治理还包括索引过滤、回答模式、结构化契约、证据快照、引用校验和失败关闭。

我的设计原则是Prompt提升正确概率，确定性机制限制错误影响。

### 11. 哪些校验应该由结构化契约和确定性代码负责？

**回答：** 回答模式枚举、必填字段、字段互斥关系、引用ID范围、文档版本、原文偏移、哈希、租户、索引成员和终态流转都应由代码校验。模型不能自己声明“我已校验通过”。

语义上是否真正支持结论可以借助模型判断，但其输入范围和结果使用方式仍由代码控制。

### 12. 通用建议为什么不应该携带公司知识引用？

**回答：** 通用建议并不代表公司规则，附上公司引用会让用户误以为建议得到了制度背书，也会混淆评测口径。纯通用回答应明确无公司依据、无公司引用。

混合回答中只有公司部分可以引用，通用部分必须单独标识。

## 十二、多轮对话与查询改写

### 1. 原始问题、规范化问题和检索查询有什么区别？

**回答：** 原始问题保留用户实际输入，用于审计和展示；规范化问题是在不改变意图的前提下补全指代、术语和必要上下文，供后续判断；检索查询则面向召回，可以拆成多个更聚焦的表达。

分别保存三者，才能判断查询改写是否改变了用户意图，也方便定位召回失败。

### 2. “那个方案还有什么要求”如何改写成可独立检索的问题？

**回答：** 系统先从有限会话历史中确认“那个方案”指向的明确对象，例如“研发内部AI工具接入方案”，再改写成包含对象和询问目标的独立问题。如果历史中存在多个候选或指代不清，就不猜测，而是返回澄清问题。

改写只能补回已有上下文，不能自行增加方案状态或公司结论。

### 3. 为什么项目把查询计划合并到意图识别阶段？

**回答：** 意图识别本来就需要理解问题、指代和是否涉及公司知识。在同一次结构化判断中同时给出有限检索查询，可以减少一次独立改写模型调用，降低延迟，并避免两个模型阶段对问题理解不一致。

这项优化保留了查询数量限制和旧路径兼容，没有把检索控制权完全交给模型。

### 4. 合并后减少了哪一次模型调用？

**回答：** 对公司知识和混合问题，意图阶段若已经返回合法检索查询，就不再单独调用查询改写模型。后续Embedding、双路召回、RRF、Rerank和证据判断保持不变。

它减少的是一个串行语义阶段，并没有跳过检索质量或证据校验。

### 5. 旧 Prompt 没有返回检索查询时如何兼容？

**回答：** 查询计划字段是可兼容扩展。旧Prompt或旧Release没有产生该字段时，系统继续走原来的独立查询改写路径，而不是生成空查询或直接跳过检索。

这样新能力通过新Release生效，历史版本仍能按原契约运行和回放。

### 6. 为什么查询数量必须受到 rewrite_query_limit 限制？

**回答：** 每增加一个查询，都会增加Embedding、向量检索、全文检索和融合候选数量。模型如果任意拆分问题，成本和延迟可能失控，还会引入更多噪声。

限制值随RAG策略发布，并通过评测判断多查询带来的召回收益是否值得。

### 7. 查询改写如何避免改变用户原始意图？

**回答：** 改写只允许做指代消解、术语标准化和问题拆分，要求保留原问题约束；同时保存原始问题和改写结果供调试。涉及金额、时间、对象、否定和范围时要特别核对。

评测中应加入“改写后含义改变”的负样本，不能只看召回是否增加。

### 8. 为什么不能在查询改写时补造公司事实？

**回答：** 改写发生在检索之前，它没有证据资格。如果在这一阶段假设某订单状态、某制度结论或某版本有效，检索就会围绕错误前提进行，后续很难纠正。

查询改写负责表达用户需求，不负责回答用户问题。

### 9. Java 传递给 Agent 的聊天历史为什么需要限制长度？

**回答：** 完整历史会持续消耗上下文，增加延迟，也可能把旧话题和旧回答带入当前问题。Java只传递满足窗口和条数限制的必要历史，业务事实仍以当前数据和知识证据为准。

限制历史也是隐私和成本控制的一部分。

### 10. 上一轮模型回答为什么不能自动成为下一轮的事实来源？

**回答：** 模型回答可能存在错误、过期或仅为通用建议。如果把它当成新事实，错误会在多轮中不断自我强化。历史回答只能帮助理解指代，不能替代当前知识和业务状态查询。

需要公司事实时仍然要在当前Release绑定的知识中重新获得证据。

### 11. 如何判断用户是在追问上一话题还是切换了新话题？

**回答：** 结合当前问题中的指代、实体、主题和最近有限历史做结构化判断。存在“这个、那个、继续”等依赖表达时尝试补全；出现新的明确对象或领域时应降低历史影响。

判断不确定且会显著改变检索范围时，优先澄清，而不是强行继承上一主题。

### 12. 多轮历史过长时，项目后续可以如何治理？

**回答：** 我会采用滑动窗口加结构化会话状态，而不是无限累积原文。可单独保存当前主题、已确认实体和用户明确提供的条件；摘要只能用于理解，关键业务事实仍需重新查询。

摘要生成也要版本化和可审计，避免摘要错误长期污染后续对话。

## 十三、结构化回答与 SSE

### 1. 为什么模型回答采用结构化 JSON，而不是直接输出 Markdown？

**回答：** 客服回答不仅有正文，还有回答模式、公司段落、通用段落、澄清问题、证据不足原因和引用。结构化输出让系统能够校验这些字段的关系，再安全渲染成用户界面。

直接输出Markdown虽然简单，但很难可靠判断公司事实和引用边界，也无法阻止模型混写不同模式。

### 2. 为什么不能把模型原始 Token 流直接展示给前端？

**回答：** 原始Token可能包含尚未闭合的JSON、后来会被判定非法的字段、未验证引用甚至敏感错误信息。一旦展示给用户就无法收回。

系统只释放已经形成完整语义单元并通过当前校验的回答块，前端接收的是公开业务事件，不是Provider原始流。

### 3. AnswerSectionStream 如何处理尚未闭合的 JSON？

**回答：** 它增量解析模型返回内容，维护对象、数组和字段的闭合状态。只有完整字段或完整回答段落出现后才尝试校验和释放；半个字符串、半个对象会继续等待后续内容。

同时要求新内容只能追加既有前缀，防止模型流改写已经接收的内容。

### 4. 为什么必须先验证 contract_version 和 answer_mode，再释放正文？

**回答：** 这两个字段决定后续结构如何解释以及哪些内容允许出现。如果先显示正文，后来才发现模式是非法的或契约版本不匹配，用户已经看到了未经授权的内容。

因此根契约有效是流式释放的前置门槛，系统不会自行补造缺失字段。

### 5. 公司知识段落在输出前如何校验引用？

**回答：** 每个公司段落必须带引用，引用ID必须属于冻结EvidencePack，引用类型、版本和原文位置也要合法。通过后才能把该段落转换成用户可见内容。

这种段落级释放比等整份答案结束更快，同时仍保持公司事实的证据边界。

### 6. 模型输出未知字段时为什么应该失败？

**回答：** 未知字段可能是模型偏离Prompt、契约版本不一致或试图表达系统没有定义的语义。静默忽略会掩盖问题，自动接受又可能让前后端对同一回答有不同理解。

严格契约使错误尽早暴露，通过显式升级处理兼容变化。

### 7. 流式输出中途失败后，前端应该如何展示？

**回答：** 前端可以保留已经确认并展示的内容，但必须显示本次Run失败及安全错误信息，不能伪装成完整成功回答。Java还要把Run和助手消息置为一致的失败终态。

回放中保留失败阶段和已释放事件，便于判断用户实际看到了什么。

### 8. SSE 为什么比 WebSocket 更适合当前单向回答流？

**回答：** 当前主要需求是服务端持续向浏览器推送进度、正文、引用和终态，客户端控制仍可通过普通HTTP完成。SSE协议简单、天然按事件组织，并支持浏览器重连语义。

如果未来需要高频双向语音或实时协作，才有必要重新评估WebSocket。

### 9. SSE 事件序号有什么作用？

**回答：** 序号用于保持事件顺序、去重和断线续读。Java投影时只接受符合期望顺序的新事件，重复事件不会重复写消息，迟到事件也不能覆盖终态。

它还是回放时间线的稳定标识，使前端看到的过程与后台保存的事实一致。

### 10. Last-Event-ID 如何支持断线续读？

**回答：** 浏览器重连时带上最后已确认的事件序号，服务端只返回此序号之后的公开事件。这样连接中断不会要求重新创建Run，也不会从头重复正文。

续读依赖服务端已经持久化事件和幂等投影，不能只依赖内存中的网络流。

### 11. 如何避免 SSE 重连时重复创建一次 Run？

**回答：** 创建Run和订阅事件是两个动作。提交消息通过clientRequestId幂等，只产生一个Run；重连只携带已有Run ID和最后事件序号读取事件，不再次提交问题。

前端也要区分“重新发送”与“继续接收”，避免网络错误触发新的业务提交。

### 12. 首个进展事件和首个实质正文为什么必须分别统计？

**回答：** 进展事件只能证明系统开始工作，不能代表用户已经得到有用答案。如果把几十毫秒出现的“正在检索”当作首字延迟，会掩盖模型生成和证据判断实际需要的数秒时间。

因此性能报告要分别记录首进展、首正文、首个非标题段落和完整终态耗时。

## 十四、Java 状态、事务与幂等

### 1. 一次提问如何关联会话、用户消息、助手消息、Java Run 和 Agent Run？

**回答：** 用户消息和待生成的助手消息都属于同一会话，Java Run关联这次消息对和选定Release。调用Agent成功后再记录Agent Run ID，后续所有事件通过Java Run和Agent Run映射投影到对应助手消息。

这样业务页面以Java会话为入口，执行排障又能追到Agent内部运行。

### 2. clientRequestId 如何防止重复提交？

**回答：** 客户端为一次用户提交生成稳定请求ID，Java在租户范围内把它与用户消息建立唯一关系。相同ID再次到达时返回已有提交结果，不创建新消息和新Run。

这个ID表达的是同一次业务意图，不能在真正的新消息之间复用。

### 3. 仅通过“先查再插入”能否完全防止并发重复？

**回答：** 不能。两个并发请求可能同时查不到记录，然后都插入。真正可靠的幂等还需要数据库唯一约束或原子写入，并正确处理唯一冲突后读取已有结果。

应用层预查可以优化正常路径，但数据库约束才是并发底线。

### 4. 为什么要先在本地事务中创建 PENDING 状态，再调用 Agent？

**回答：** 先提交本地记录，能够保证远程调用发生前已有可追踪的Run和消息，即使网络立即失败也能落到明确失败状态。它也避免把外部调用放进长事务。

远程结果通过独立事务投影，状态变化更清晰，也便于重试和补偿。

### 5. 为什么不能在 Java 数据库事务中执行远程模型调用？

**回答：** 模型和Agent调用耗时长且不可控，会长时间占用数据库连接和锁；远程超时也不等于调用未执行，数据库回滚无法回滚外部副作用。

因此本地事务只保存意图和状态，远程执行后再用新事务更新结果，配合幂等和终态治理。

### 6. Agent 事件如何投影到 Java 的 Run 和消息记录？

**回答：** Java按事件类型和序号更新Run进度、阶段时间线、助手正文、引用和终态。投影只保存前端和业务查询需要的公开事实，Agent侧仍保留更完整的执行快照。

同一事件重复到达不会重复追加内容，非法顺序则被拒绝或记录异常。

### 7. 如何利用事件序号处理重复事件和乱序事件？

**回答：** Run保存最后成功投影的序号，新事件必须大于它并满足预期推进条件。小于等于最后序号的事件视为重复；出现跳号或并发更新失败时，不盲目覆盖，而是补拉或等待缺失事件。

数据库条件更新可以防止两个投影线程同时推进同一Run。

### 8. 为什么迟到事件不能覆盖已经确定的终态？

**回答：** 完成、失败、取消和超时表示本次业务结果已经确定。网络延迟可能让早期进度事件之后才到达，如果允许覆盖，用户会看到已失败的Run重新变成运行中。

状态机必须单调，终态之后只允许读取和审计，不再接受改变结果的中间事件。

### 9. 取消操作为什么需要幂等？

**回答：** 用户可能重复点击，前端也可能因超时重试。第一次取消发出后，后续请求应返回当前状态，而不是创建新取消任务或报不可预测错误。

Agent侧取消和Java侧状态更新都要接受重复请求，并处理Run已经自然结束的竞态。

### 10. Agent 不可用时为什么要同时将 Run 和助手消息改为 FAILED？

**回答：** Run失败但助手消息仍为PENDING，会让会话界面一直显示生成中；消息失败而Run仍运行中，又会让回放和监控错误。两者是同一次用户操作的不同视图，终态必须一致。

即使Agent尚未返回Run ID，Java也要关闭本地待处理记录，不能留下永久悬挂状态。

### 11. 为什么重试耗尽后要保留原始异常类型？

**回答：** 如果重试框架统一抛出一个包装异常，调用方可能无法区分连接失败、服务端拒绝和业务校验错误，最终映射成错误HTTP状态。保留最后一次真实失败，才能正确治理和告警。

重试只是传输策略，不应破坏错误语义。

### 12. CS_AGENT_UNAVAILABLE 为什么应该返回 503，而不是伪装成普通回答？

**回答：** Agent不可用属于服务暂时无法完成请求，503能让前端展示可重试状态，也能被监控准确统计。若返回200和一段兜底话，系统会把基础设施失败混入正常回答和质量指标。

失败应真实、可识别，同时对用户隐藏内部地址和原始异常。

## 十五、Prompt 与 Release Bundle

### 1. Release Bundle 中冻结了哪些内容？

**回答：** 它冻结Agent和Graph版本、各阶段Prompt版本与校验和、模型策略、RAG策略、知识库与索引绑定、允许能力以及整包校验和。一次运行读取的是这份不可变快照，而不是各管理表当前最新值。

因此我们能回答“这次为什么这样答”，也能精确回滚整套行为。

### 2. 为什么只记录 Agent 版本号还不足以复现一次运行？

**回答：** 同一个Agent代码可以配不同Prompt、模型、TopK、知识索引和超时策略，答案会完全不同。只记录一个语义版本无法知道当时实际用了什么配置。

完整复现至少需要代码和Graph身份、Prompt、模型、RAG策略、知识快照和输入事实。

### 3. 共享 Prompt 与智能客服私有 Prompt 如何组合？

**回答：** 共享Prompt提供平台统一安全边界和输出要求，私有Prompt定义客服阶段的业务任务，例如意图、充分性和不同回答模式。发布时按固定顺序绑定具体版本，不在运行时搜索“最新Prompt”。

共享内容不能覆盖客服专属契约，私有内容也不能降低平台安全边界。

### 4. 为什么 Prompt 发布后不能自动修改已有 Agent Version？

**回答：** Prompt发布只说明这个版本可被选择，不代表所有Agent都已评测并同意升级。自动替换会让线上行为在没有新Release的情况下变化，破坏审计和回滚。

正确流程是基于现有Agent版本创建草稿，显式绑定新Prompt，校验、评测后发布新Release。

### 5. 模型策略和 RAG 策略为什么也需要版本化？

**回答：** 模型名称、温度、Token上限、超时和重试会影响生成；各阶段TopK、预算和证据策略会影响检索。它们与Prompt一样决定行为，不能作为可随时修改的环境变量隐藏在运行外部。

版本化后才能做批次对比、灰度、回滚和历史解释。

### 6. Prompt 中的变量契约解决什么问题？

**回答：** 变量契约声明变量名称、类型、来源、是否必填、最大长度、敏感性以及是否允许不可信内容。它防止模板引用未声明字段，也避免把用户或文档正文注入可信指令位置。

它还让发布前可以校验模板和运行输入是否兼容，而不是到模型调用时才发现问题。

### 7. 如何区分可信指令和不可信内容？

**回答：** 系统和开发者维护的规则属于可信指令；用户输入、知识正文、工具返回和外部文件都属于数据。装配Prompt时使用明确分隔和变量权限，让不可信内容只能进入允许的数据位置。

即使文档里写着“忽略系统规则”，它也只是待分析文本，不能改变Agent权限。

### 8. Release checksum 如何计算和校验？

**回答：** 对整份规范化Release内容按稳定字段顺序序列化后计算摘要，发布端和Agent分别计算并比较。任何绑定版本、参数或知识索引变化都会改变摘要。

校验和不是加密授权，但可以发现传输、存储或装配导致的内容漂移。

### 9. Java 与 Agent 的 Release 内容不一致时应该如何处理？

**回答：** 应拒绝激活或拒绝运行，报告发布契约冲突，不能挑一端继续。否则Java页面显示的配置和Agent实际行为不同，所有回放与审计都会失真。

修复方式是重新同步并校验完整快照，而不是只修改某个摘要字段。

### 10. 历史回放为什么不能读取当前 Prompt 和当前策略重新计算？

**回答：** 当前配置可能已经变化，重新计算会把今天的行为冒充成历史事实。回放应该展示当时冻结的输入、版本、候选、证据、回答和错误，不要求模型再次生成。

这也是回放与“重新执行一次相同问题”的根本区别。

### 11. 回滚 Prompt 时是否一定要同时回滚模型和知识索引？

**回答：** 不一定，要看问题来源和兼容关系。如果只是Prompt回归，可以创建绑定旧Prompt、保留其他经过验证配置的新Release；如果旧Prompt依赖旧输出契约或知识结构，就需要成套回滚。

我们回滚的是一个经过验证的兼容组合，不是机械地把所有组件都退回同一时间点。

### 12. 即使配置全部冻结，能否保证模型再次生成逐字相同的答案？

**回答：** 不能绝对保证。模型服务可能存在非确定性、底层版本变化和并发差异，即使温度较低也未必逐字一致。冻结配置保证的是输入和治理边界可解释，不是字节级重演。

因此历史回放保存原始结果；回归验证比较事实、模式、引用和结构，而不是要求逐字相同。

## 十六、安全与权限

### 1. 为什么知识库文档也属于不可信输入？

**回答：** 文档可能来自外部、包含错误内容、隐藏文本或恶意指令，即使由内部人员上传，也不能因此获得系统指令权限。Agent的任务是把文档当作事实候选读取，而不是执行文档中的命令。

所以知识正文只能进入允许的不可信变量位置，后续仍受检索范围、证据和引用规则约束。

### 2. 文档中出现“忽略系统指令”时系统应该怎么处理？

**回答：** 这句话应被视为普通文档内容，不改变系统Prompt、可用工具或回答模式。Prompt装配要明确区分指令和资料，任何权限判断都由后端执行。

如果这类内容与用户问题无关，检索和重排应尽量排除；即使命中，也不能被解释为授权。

### 3. 为什么知识内容不能获得工具权限？

**回答：** 工具权限来自当前用户、租户、Agent发布配置和后端授权，不来自自然语言。如果文档写一句“立即执行退款”就能触发工具，攻击者只需污染知识库即可获得业务权限。

知识可以提供判断依据，但是否调用、调用什么以及能否执行必须经过独立策略和参数校验。

### 4. 系统指令、用户输入和知识原文如何隔离？

**回答：** 在Prompt中使用不同角色、固定装配顺序、明确分隔和变量契约。系统规则位于可信指令层，用户问题和知识原文进入受限的数据槽，并声明其中内容不能修改上层规则。

隔离还要由代码配合：不可信变量不能进入可信模板位置，工具和权限也不读取自然语言授权。

### 5. 为什么权限和租户过滤不能只依靠 Prompt？

**回答：** Prompt只能要求模型不要越权，但数据如果已经被检索并发送给模型，泄露已经发生。租户、用户、角色和资源归属必须在检索和工具执行前由后端强制过滤。

模型只应看到当前请求有权访问的数据，而不是看到全部数据后再决定不回答。

### 6. 向量检索和全文检索如何强制附加租户与索引范围？

**回答：** 两路检索都由服务端接收当前租户和Release绑定的索引ID，查询条件同时限制租户、索引成员和文档版本。用户输入不能覆盖这些字段。

父片段读取和引用校验还会再次使用同一范围，防止候选阶段正确、展开阶段却跨库读取。

### 7. 当前固定开发身份由哪一层注入？

**回答：** 当前首期身份由Java服务端固定注入开发租户和用户，浏览器不能自行提交或覆盖。这样可以先验证业务闭环，但它只是开发阶段的身份方案。

面试中我会明确说明这不是生产登录、JWT或组织权限已经完成。

### 8. 当前实现能否称为已经具备生产级部门权限？

**回答：** 不能。数据模型和检索链路预留了租户、部门和可见范围概念，当前实际运行仍是固定身份和公司范围知识，没有完成真实组织、角色和人员级授权验收。

预留字段不等于能力落地，生产上线前还需要真实身份接入、权限决策和越权测试。

### 9. Prompt、完整文档正文和模型异常为什么不能直接写入普通日志？

**回答：** 它们可能包含公司敏感资料、个人信息、凭证或Provider内部信息。普通日志通常复制范围广、保留时间长，访问控制也不同于业务数据。

日志应记录版本、哈希、数量、阶段、耗时和安全错误码；需要查看原文时，通过受权限控制的调试与回放读取冻结事实。

### 10. 运行回放为什么不能展示模型隐藏思维链？

**回答：** 隐藏思维链不是稳定业务事实，可能包含敏感推断，也不适合作为可解释性的依据。我们需要的是模型输入摘要、结构化输出、证据、阶段结果、错误和耗时。

真正可审计的是系统做了什么、依据是什么，不是暴露模型内部自由推理文本。

### 11. 如果未来支持用户指定 URL 抓取文档，需要增加哪些 SSRF 防护？

**回答：** 如果下一阶段由我设计，我会只允许经过校验的协议和域名，解析并阻断本地、内网、云元数据和保留地址，限制重定向次数并对每次跳转重新校验。下载还要限制大小、类型、超时和响应数量。

抓取服务应运行在网络权限受限的环境，不能让URL读取变成访问内部基础设施的通道。

### 12. 如果未来开放业务工具，如何实现最小权限和高风险操作确认？

**回答：** 如果下一阶段接入工具，我会为每个工具声明Schema、资源范围、风险等级和调用主体。查询工具可在后端授权后执行，高风险写操作必须展示确定参数，由用户确认或人工审批，并使用幂等键。

模型只能提出调用建议，最终权限、确认真实性、参数校验和审计由工具运行时强制完成。

## 十七、调试、回放与可观测性

### 1. RAG 调试页需要展示哪些执行阶段？

**回答：** 我会展示原始问题、意图和查询计划、向量召回、全文召回、RRF融合、Rerank、子到父映射、版本排除、等价与冲突判断、预算装配、充分性、回答模式、最终答案和引用。

每个阶段还应展示输入范围、候选数量、排名变化、耗时和错误，使问题能被定位到具体环节。

### 2. 为什么调试运行不应该写入普通员工会话？

**回答：** 调试是管理员针对指定版本反复实验，问题可能是合成样本，结果也可能故意失败。如果写入员工会话，会污染用户历史、反馈统计和业务指标。

调试Run应独立保存，但仍复用真实检索、模型和证据链路，不能变成另一套简化实现。

### 3. 向量候选、全文候选、RRF 排名和 Rerank 排名为什么需要分别保存？

**回答：** 最终没命中正确证据，可能是某一路根本没召回、融合提前截断，或Rerank把它排低。只保存最终结果无法区分这些原因。

分别记录各阶段候选和名次，才能有针对性地调分词、Embedding、融合参数或Rerank模型。

### 4. 为什么要记录子片段到父片段的映射？

**回答：** 检索分数来自子片段，实际回答使用父片段。没有映射，管理员无法知道某条长证据为什么入选，也无法判断多个命中是否只是同一父条款重复。

映射还用于验证父子版本一致和引用位置正确。

### 5. 为什么要记录证据被排除的原因？

**回答：** 候选可能因旧版本、等价合并、预算不足、TopK限制、父片段缺失或冲突被排除。结果相同，修复方式完全不同。

明确原因能避免把所有漏答都归咎于模型，也为参数调优和质量复盘提供证据。

### 6. Run 回放与重新执行一次问题有什么区别？

**回答：** 回放读取当时冻结的事件、版本、证据和答案，目标是还原已经发生的事实；重新执行会使用一次新的模型调用和可能不同的运行环境，结果可能变化。

因此排查历史投诉应先看回放，验证当前版本才创建新Run。

### 7. 回放中的 Release Bundle 有什么作用？

**回答：** 它说明本次运行实际绑定的Graph、Prompt、模型、RAG策略和知识索引，使候选、答案和错误都有版本背景。没有它，看到一条历史回答也无法判断应在哪个配置上复现。

回放只展示必要版本和校验和，不暴露完整敏感Prompt。

### 8. 如何通过 Trace 判断问题发生在解析、召回、重排、充分性还是生成阶段？

**回答：** 先看正确文档和父条款是否存在于已发布索引；再看各路候选是否召回；若召回则检查融合和重排名次；进入EvidencePack后检查是否因预算或冲突排除；证据正确仍回答错误，才定位到充分性或生成。

这种从数据源到输出逐层收敛的方法，比直接调Prompt更可靠。

### 9. 如何定位“文档命中了，但回答仍然错误”？

**回答：** “文档命中”粒度太粗。我会继续检查命中的是否正确版本、正确父条款，条款是否完整进入EvidencePack，充分性是否误判，回答是否漏掉条件，以及引用是否支持结论。

正确文档标题出现，不代表正确事实已经进入模型。

### 10. 如何定位“回答正确，但引用错误”？

**回答：** 先核对答案中的关键事实对应哪个EvidencePack条目，再检查模型引用ID、父片段、偏移和渲染映射。如果事实来自模型常识而非证据，即使答案碰巧正确也应判失败。

修复重点可能是引用选择Prompt、段落与引用绑定或渲染投影，而不一定是检索。

### 11. 如何区分首进展耗时、首正文耗时和完整运行耗时？

**回答：** 首进展是用户第一次看到系统开始工作的时间；首正文是第一个有实质内容的回答块；完整耗时是Run到达终态的时间。三者分别反映交互反馈、用户获得价值和整体资源占用。

性能报告必须说明口径，不能用快速进度事件替代真实答案延迟。

### 12. 当前项目还存在哪些性能瓶颈？

**回答：** 当前主要延迟来自多个串行模型阶段、Rerank、证据充分性和最终生成，复杂问题首正文仍可能达到数秒到十几秒。合并意图和查询规划减少了一次调用，但不是所有问题都改善。

后续优化应依据阶段耗时做并行化、模型分层、缓存和Prompt压缩，同时守住引用与拒答质量，不能只追求首字速度。

## 十八、RAG 真实评测

### 1. 为什么项目必须建立固定评测集？

**回答：** RAG质量受文档、切片、Embedding、TopK、Rerank、Prompt和模型共同影响。没有固定问题和人工预期，每次修改后只能凭印象判断，无法确认提升还是回归。

评测集把关键事实、禁止事实、来源、版本、模式和引用要求固化，使不同Release能够在同一尺度上比较。

### 2. 为什么随机手工问几个问题不能证明系统质量？

**回答：** 随机问题容易选择熟悉或简单样本，也无法覆盖无答案、冲突、旧版本、例外条件和模糊表达。即使几题回答很好，也不能推断整体稳定性。

人工探索适合发现新问题，固定评测负责可重复回归，两者作用不同。

### 3. 为什么评测批次要冻结 Agent、RAG 策略和知识索引？

**回答：** 批次可能运行较长，如果中途读取“当前配置”，前后用例可能使用不同版本，汇总指标失去可比性。冻结后，每条用例都在同一配置和知识范围内执行。

对比两个批次时，也能明确差异来自哪组发布资产。

### 4. 为什么评测复用真实 RAG 调试链路？

**回答：** 评测要证明真实检索、Rerank、模型、证据和引用链可用。如果另写一套简化流程，指标再好也不能代表线上路径。

复用调试链路又避免污染员工会话，兼顾真实性和业务隔离。

### 5. 为什么不能使用 Mock 结果冒充真实评测？

**回答：** Mock只能验证代码分支和契约，不能证明数据库内容、向量索引、外部模型、网络和真实Prompt组合能够工作。RAG大量问题只会在真实数据和真实服务中出现。

测试桩是开发辅助，真实评测才是产品质量证据，两者必须分别报告。

### 6. 当前评测包含哪些指标？

**回答：** 当前包括执行成功率、回答模式准确率、期望事实召回、禁止事实命中率、预期来源召回、引用合规率、版本准确率、用例通过率以及P50/P95耗时。

这些指标覆盖可用性、内容、来源和性能，但仍不能替代对关键制度答案的人工语义复核。

### 7. 执行成功率和用例通过率有什么区别？

**回答：** 执行成功率表示真实链路完成并返回了可解析终态；用例通过率还要求模式、事实、来源、引用和版本满足人工预期。一个Run可以技术上成功，但答案质量失败。

把两者混在一起会用HTTP成功掩盖业务错误。

### 8. 回答模式准确率如何计算？

**回答：** 每条用例预先标注期望模式，实际模式与之相等记为命中，在适用用例中汇总比例。模式标签要由人工根据问题性质和知识情况确定，不能由待评模型自己生成。

模式正确也不代表事实正确，所以它只是一个独立维度。

### 9. 关键事实召回率如何计算？

**回答：** 用例将必须覆盖的事实拆成最小人工标注项，对回答规范化后检查覆盖数量，再除以期望事实总数。当前实现偏向确定性字符串包含，便于重复计算。

这种方法简单可靠但不理解同义表达，因此需要人工复核假阴性，并逐步引入更稳健的语义评估。

### 10. 禁止事实命中率解决什么问题？

**回答：** 只检查应该出现的事实，无法发现答案额外编造了错误制度或泄漏旧版本。禁止事实显式列出绝不能出现的结论，用于监控幻觉、旧知识和错误扩展。

目标通常是零，但禁用事实集合也需要人工维护和版本化。

### 11. 来源召回和真正的检索阶段 Recall@K 有什么区别？

**回答：** 当前来源指标主要看最终引用是否包含预期文档，反映答案最终采用了正确来源。检索Recall@K则看正确文档、子片段或父片段是否出现在某个召回阶段。

前者适合端到端验收，后者适合定位检索问题，不能用一个名称混为同一指标。

### 12. 引用合规率能否证明引用在语义上支持结论？

**回答：** 不能完全证明。它能检查引用数量、文档版本、索引范围和原文非空，属于结构与来源合规；语义支持还需要核对结论中的数字、条件和例外是否来自原文。

因此关键用例仍要人工复核，后续可以增加专门的引用蕴含评测。

### 13. 为什么没有配置的指标应该记为不适用？

**回答：** 例如通用问题本来不需要公司引用，没有配置预期来源时，不能把它强算为来源命中，也不能当作失败。不适用项应从分母中排除。

这能避免大量简单用例把某项指标稀释成虚假的高分。

### 14. 为什么字符串包含检查会产生假阴性？

**回答：** 同一事实可以有不同空格、标点、Markdown转义和自然语言表达。人工期望写“kind+id”，模型回答“kind 与 id 组成的结构”，事实相同但字面不包含。

字符串指标适合自动筛查，失败后要结合原文和回答人工复核，不能为迎合匹配而硬编码措辞。

### 15. 为什么验收结果要同时保留“18/18 执行成功”和“17/18 自动质量通过”？

**回答：** 18/18说明所有用例都完成了真实链路，没有基础设施或契约失败；17/18说明按当前确定性自动规则有一条未满足。后来人工复核发现那条属于表达差异造成的假阴性，但原始自动结果不能被改写。

同时报告两者，既保留测量事实，也给出专业解释，避免把技术成功和质量成功混为一谈。

### 16. 为什么不能为了达到 18/18 而修改预期短语或硬编码回答？

**回答：** 这样优化的是测试表面，不是系统能力，会让指标失去可信度。正确做法是保留原运行，说明评测规则的缺陷，再用独立样本验证改进后的评估或回答策略。

评测应发现问题，不应成为驱动模型背标准答案的脚本。

### 17. 如何对比两个评测批次并发现回归？

**回答：** 两个批次必须基于同一数据集和明确的冻结配置。先比较整体模式、事实、来源、引用、版本、通过率和延迟，再逐题查看由通过变失败、由失败变通过以及答案模式变化。

关键制度题的回归优先级高于平均分的小幅提升，不能只看一个总分。

### 18. 为什么三份文档和 18 条用例不能代表全部生产知识质量？

**回答：** 三份资料主要覆盖研发制度和技术内容，知识类型、文档格式、语言表达和权限场景有限。18题足以证明闭环和首轮质量，却不足以覆盖全部公司制度、业务流程、产品资料、冲突和安全样本。

所以我把它定义为真实首轮验收，长期发布门禁仍需要更大的Gold集和持续补充线上失败案例。

## 十九、项目真实场景深挖题

### 1. 员工询问“核心模块和整体代码覆盖率要求”，系统如何保证数字来自正确制度版本？

**回答：** 我先保证当前Agent Release绑定的索引只包含目标规范的有效版本；检索命中具体条款后，恢复包含两个覆盖率数字及适用对象的完整父证据；充分性通过后，答案中的80%和60%分别绑定到该原文引用。

验收不能只看数字答对，还要核对引用版本、原文哈希和SSE最终快照一致。

### 2. 新文档版本已发布，回答却仍引用旧版，你会依次检查哪些环节？

**回答：** 我先确认新文档版本处理和索引验证成功，再检查知识发布索引的成员是否替换旧版，然后确认在线Agent Release是否绑定新索引。之后核对本次Run实际使用的Release和检索过滤范围，最后检查是否只是历史回放仍展示旧引用。

这类问题不能直接归咎于向量库，因为最常见原因是发布链条只完成了一半。

### 3. 正确子片段已经命中，但最终回答缺失例外条件，你会如何排查？

**回答：** 我会检查子片段是否映射到包含例外的正确父片段，父片段是否被预算截掉或错误节选，EvidencePack是否完整，然后看充分性和回答是否忽略了已有例外。

如果父证据完整而回答漏掉，属于生成和评测问题；如果父证据本身不完整，根因在解析或切片。

### 4. 向量召回正常、全文召回始终为零，你会检查什么？

**回答：** 先检查查询词和文档内容经过全文配置后产生什么词项，再确认中文分词、标点和大小写规范化；然后核对租户、索引成员和版本过滤；最后检查索引内容是否真实写入。

只有确认数据和查询正确后，才评估更换中文分词方案，不能靠调大fts_top_k解决零匹配。

### 5. Rerank 将正确证据排到后面，如何判断是查询、候选还是重排模型的问题？

**回答：** 如果正确证据在初始候选中且RRF位置合理，但Rerank明显降级，我会检查传入的标题、章节和文本是否完整，并用固定样本比较Rerank输出。如果候选本身缺失，则问题在查询或召回，不应怪Rerank。

同时检查候选数量是否过多导致相关信息被噪声淹没，以及模型是否适合中文和该领域。

### 6. 两份制度发生冲突，其中一份分数更高，系统应该如何回答？

**回答：** 分数高只表示更相关，不能代表更有效。我会让系统保留两份原文，判断是否适用对象、时间或条件不同；若无法由原文解释，就返回证据不足并提示存在冲突。

知识管理员需要建立明确替代关系或修订资料后，新Release才能恢复唯一公司结论。

### 7. 用户问了公司制度没有规定的字段，为什么不能根据经验补齐？

**回答：** 用户问的是公司要求，不是通用最佳实践。根据经验补齐会把模型建议伪装成组织制度，可能直接影响评审、审计和责任划分。

系统可以明确说明现有资料只规定到什么程度；若用户还需要建议，可以单独提供标注为非公司制度的通用部分。

### 8. 回答事实正确但引用不支持结论，应该如何判定？

**回答：** 判定失败。事实可能来自模型记忆或偶然猜中，系统没有证明它是基于当前公司知识得出的。需要定位正确证据是否未被召回、未被采用，或模型选择了错误引用。

只有答案和证据同时正确，才能称为可信的公司知识回答。

### 9. 用户重复提交导致两次模型调用，你会检查哪几层？

**回答：** 我会检查前端是否复用了同一个clientRequestId，Java是否有租户范围唯一约束和原子冲突处理，Pending Run是否在同一事务创建，以及网络重试是否错误地再次提交而不是续读SSE。

还要核对Agent内部是否对同一运行请求具备幂等保护，避免Java重试穿透后重复执行。

### 10. 页面很快显示“正在检索”，但十几秒后才出现正文，如何定位耗时？

**回答：** 我不会把首进展当作首字性能。通过阶段时间线分别统计意图、Embedding、双路检索、Rerank、证据判断和回答生成，确认最长串行阶段和外部模型耗时。

优化后用同一批真实问题比较首正文和完整耗时，同时检查回答和引用质量是否退化。

### 11. 新知识发布后无法检索到，你会如何检查文档、索引和 Release？

**回答：** 先确认文件版本解析、父子切片、向量和索引验证成功；再检查发布索引是否包含正确文档版本；然后检查Agent Release绑定是否更新；最后用调试页查看过滤范围、两路召回和查询改写。

这套顺序能把入库、发布、绑定和检索问题快速分层。

### 12. 如何用这个项目说明“测试通过”和“真实接口验收通过”的区别？

**回答：** 单元和契约测试证明代码在受控输入下满足预期，构建成功证明工程可编译；它们都不能证明真实COS、数据库、pgvector、Embedding、模型、SSE和前端组合可用。

项目最终用真实文档上传、真实索引、真实问答、引用哈希、失败场景和评测批次验收，并把未验证范围和性能限制保留下来。这才是我认可的完成证据。

## 二十、扩展设计题

### 1. 如果接入订单查询，如何区分 RAG 与实时业务工具？

**回答：** 如果下一阶段由我负责，政策、流程和解释类问题继续走RAG；订单状态、物流节点、退款进度等实时个人数据必须调用受权限控制的业务工具。意图层可以决定路径，但用户身份、订单归属和结果权限由Java或工具网关校验。

混合问题可以先查询实时状态，再用知识解释规则，但两类来源必须分别标注。

### 2. 如果接入退款操作，如何设计用户确认、权限校验和幂等？

**回答：** 我会先由只读工具查询订单和退款资格，后端校验资源归属并计算确定参数；执行前向用户展示金额、原因和影响，确认记录必须来自产品交互，不能由模型伪造。写操作使用包含用户、订单、业务动作和确认版本的幂等键。

高金额或特殊争议进入人工审批，模型不拥有绕过权限和审批的能力。

### 3. 退款工具超时且结果不确定时，为什么不能直接重试？

**回答：** 超时只表示调用方没收到结果，不代表服务端没有执行。立即重试可能产生重复退款。系统应使用原幂等键查询业务结果或调用状态查询接口，在确定未执行前不能创建新动作。

若长期无法确认，应进入人工处理并保留审计事实，而不是向用户承诺成功或失败。

### 4. 如果支持人工转接，需要同步哪些会话、证据和失败信息？

**回答：** 我会同步用户原问题、已确认实体、关键历史摘要、当前回答模式、检索证据与引用、已执行工具及结果、失败阶段和转人工原因。人工客服不应重新询问用户已经明确提供的条件。

同时只传递坐席有权查看的信息，模型内部推理和不必要的敏感正文不进入转接包。

### 5. 如果增加部门级知识权限，需要修改哪些层次？

**回答：** 需要接入真实身份和组织关系，在Java知识管理中维护可见范围，在索引元数据中固化租户和部门授权，在向量、全文、父片段读取和引用预览前统一过滤。调试、回放和评测也必须使用操作者权限。

权限测试要覆盖直接查询、跨库引用、历史回放和管理员边界，不能只检查页面按钮。

### 6. 如果接入企业网盘和 Confluence，如何处理增量同步与删除？

**回答：** 我会为外部对象保存稳定来源ID、内容哈希、版本和同步游标。变更先创建新的内部文档版本，经过解析、验证和人工或策略审批后发布；源端删除先标记待下线，不直接删除历史证据。

同步任务要幂等，支持重试和对账，外部权限变化也要触发可见范围重新评估。

### 7. 如果支持外部客户，身份、隐私和限流需要如何升级？

**回答：** 需要真实认证、租户和用户隔离、会话数据生命周期、个人信息脱敏、数据主体删除机制以及更严格的模型输入治理。接口要按用户、设备、租户和成本多维限流，并防止批量枚举业务资源。

外部客户场景还需要内容安全、投诉与人工转接，不能直接复用内部固定身份方案上线。

### 8. 如果把评测作为发布门禁，应设置哪些阻断条件？

**回答：** 我会对关键制度用例设置零容忍条件，包括错误版本、引用不闭合、禁止事实命中和应拒答却作答；再为模式准确率、来源召回、通过率和P95延迟设最低阈值。候选批次必须与基线逐题比较。

自动门禁之外保留关键变更人工复核，不能让一个综合平均分掩盖高风险回归。

### 9. 如果引入 MCP，为什么仍然不能省略业务权限校验？

**回答：** MCP规范化了模型发现和调用工具的方式，但不证明当前用户有权执行工具，也不验证订单、文档或租户归属。协议能力和业务授权是两层不同问题。

每次MCP调用仍要经过身份透传、服务端权限、参数Schema、风险策略、超时、幂等和审计。

### 10. 如果需要高风险写工具，如何设计审批、幂等键和审计？

**回答：** 我会让模型只生成结构化操作建议，后端先计算确定影响并创建待确认任务。用户确认或人工审批要绑定操作参数摘要和有效期；执行使用稳定幂等键，结果包括成功、失败和不确定三种状态。

审计记录谁在什么身份下提出、确认、审批和执行了什么，使用了哪个Agent Release和工具版本，但不记录密钥和不必要的敏感正文。

## 项目负责人总结口径

如果面试官要求我概括这个项目，我会说：我没有把它当成一个“大模型聊天页面”，而是按企业知识系统建设。Java负责身份、业务、配置和发布真相，Python Agent负责受控智能执行；知识通过版本化索引和Release进入线上；检索使用父子切片、双路召回、融合、重排和证据预算；回答通过五种模式、引用闭包和失败关闭控制风险；最后用真实文档、真实数据库、真实模型和固定评测集验证。项目当前已经证明完整闭环可用，但生产级组织权限、更大规模Gold集、工具执行和人工客服仍属于下一阶段，我不会把未落地能力包装成现状。
