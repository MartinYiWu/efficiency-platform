## 1. 盘点口径与总体架构

本项目采用 Vue 前端、Spring Boot 业务后端和独立 Python Agent。AI 主链接入 DeepSeek 文本模型、阿里云百炼 Embedding/Rerank，以及本地 PaddleOCR。

本文区分以下状态：

- **业务链已接入**：源码中存在业务调用与运行装配，不等于本次已经验证真实服务可用。
- **适配器已实现**：存在实现，但没有在当前默认组合根发现装配，或需要单独开关、依赖和配置。
- **仅依赖或选型**：出现在依赖清单、版本管理或历史选型文档中，不能作为当前业务已使用的证据。
- **配置值与默认值**：本地配置反映盘点时文件中的设置；代码默认值可以被配置覆盖，均不代表当前运行进程的实际生效值。

前端版本来自 package.json；Python 精确解析版本来自 uv.lock；Java 版本来自 Maven POM。数据库驱动版本不代表数据库服务端版本。此次没有连接核验 MySQL、PostgreSQL、Redis 服务端版本，也没有发起真实付费请求。

主链分工如下：

```text
Vue 页面
  → Java REST API：身份权限、业务事实、版本和持久化提交
  → AiInvokeFacade / WebClient
  → Python FastAPI：Agent 执行、模型调用、解析、检索及上下文处理
  → LangGraph / 具体能力与 Provider

Python SSE → Java 流式转发 → 浏览器 Fetch Streams
```

Java 工程由 13 个 Maven 模块组成一个可执行 Jar；Python Agent 是独立执行端。前端经 Java 访问 Agent。

### 6.1 知识库文档流程

```text
下载文件 → 长度和 SHA-256 校验 → 文件预检
  → TXT/Markdown 直接解码
  → HTML 使用 Trafilatura
  → PDF 使用 pypdf
  → 其他受支持格式交给 Docling
  → 必要时 pypdfium2 渲染 + PaddleOCR
  → 父子分块 → text-embedding-v4/1024 → pgvector → 数量与维度校验
```

知识库 PDF 的 OCR 条件是：整份 PDF 提取文本去除首尾空白后少于 80 个字符。满足条件时渲染整个 PDF 进行 OCR。混合 PDF 如果已有文本超过阈值，扫描页可能没有被 OCR 覆盖；不能描述为按每页质量自动识别。

### 6.2 HR 简历流程

HR PDF 先使用 pypdf；只要存在无文字页，就对整个 PDF 走 OCR。图片简历直接走 OCR。OCR 需要本地模型目录、模型文件及相关依赖就绪，否则相应格式能力不可用。

主要依据：[知识库格式分流](../../efficiency-platform-agent/src/efficiency_platform_agent/agents/customer_service/parsing.py)、[知识摄取](../../efficiency-platform-agent/src/efficiency_platform_agent/agents/customer_service/ingest.py)、[HR 提取](../../efficiency-platform-agent/src/efficiency_platform_agent/agents/hr/extraction.py)、[HR OCR](../../efficiency-platform-agent/src/efficiency_platform_agent/agents/hr/ocr.py)、[分析文件适配器](../../efficiency-platform-agent/src/efficiency_platform_agent/capabilities/analytics/polars_reader.py)、[HR 字典读取](../../ai-efficiency-platform/aiep-biz-aihub/src/main/java/com/aiep/aihub/application/hr/HrDictionaryFileReader.java)。

## 7. 知识检索与记忆算法

| 具体技术或算法 | 作用到哪些逻辑 | 当前状态或说明 |
| --- | --- | --- |
| PostgreSQL、pgvector | 保存客服知识分块和 1024 维向量 | 当前知识向量存储实现 |
| HNSW、vector_cosine_ops | 知识向量近似检索索引 | 工程 SQL 有定义，本次未核验目标数据库的实际索引状态 |
| pgvector 余弦距离运算符 <=> | 客服知识向量相关性检索 | 已在查询 SQL 使用 |
| PostgreSQL 原生 FTS | 知识关键词召回 | 使用 to_tsvector('simple', …)、plainto_tsquery |
| ts_rank_cd、GIN 索引 | 全文候选排序与全文索引支持 | 排序已在代码使用，索引在工程 SQL 定义 |
| RRF 排名融合，常数 60 | 客服向量与全文候选融合；记忆向量与词项候选融合 | 已实现 |
| 父子块检索与证据装配 | 子块匹配、父块保留完整条款，形成可定位引用 | 已实现 |
| 自研充分性、冲突与等价校验 | 判断客服证据能否支持回答、是否存在版本冲突和内容矛盾 | 已实现 |
| 记忆向量精确余弦计算 | 在合法授权记忆集合内排序 | 向量以 JSON 文本存于 PostgreSQL，由代码计算 |
| 记忆词项集合交集评分 | 记忆关键词召回 | 与向量候选经 RRF 融合 |
| 自研完整请求计窗与分段摘要 | 控制请求长度，选择近期消息、合法摘要和偏好 | UTF-8 序列化保守 token 上界，不是供应商实际 token usage |

两条检索链应分开描述：

```text
客服知识库：查询处理 → text-embedding-v4/1024
  → pgvector + PostgreSQL FTS → RRF → qwen3-rerank
  → 证据装配、充分性和冲突处理 → 回答及引用

Agent 记忆：Java 授权集合 → 精确余弦 + 词项匹配
  → RRF → 返回引用 → Java 当前权限与来源复核后读取正文
```

记忆索引和召回属于受能力开关、发布策略及执行授权控制的实现。当前记忆链未接入模型重排或 ANN 索引。客服知识库和 Agent 记忆均未实现 BM25，不能将 PostgreSQL FTS、词项交集或 RRF 直接称为 BM25。

主要依据：[客服检索](../../efficiency-platform-agent/src/efficiency_platform_agent/agents/customer_service/retrieval.py)、[知识查询 SQL](../../efficiency-platform-agent/src/efficiency_platform_agent/agents/customer_service/vector_repository.py)、[父子分块](../../efficiency-platform-agent/src/efficiency_platform_agent/agents/customer_service/chunking.py)、[记忆索引](../../efficiency-platform-agent/src/efficiency_platform_agent/persistence/memory_index.py)、[记忆融合](../../efficiency-platform-agent/src/efficiency_platform_agent/memory/ranking.py)。
