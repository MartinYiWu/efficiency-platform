# AI 智能客服首个完整闭环详细设计

> 状态：详细设计完成
>
> 日期：2026-10-19
>
> 范围：公司内部 AI 智能客服；知识库问答、引用、反馈、RAG 调试与运行回放
>
> 涉及工程：Java、前端、Python Agent、MySQL、PostgreSQL + pgvector、Redis、文件存储

## 1. 产品目标

AI 智能客服是公司内部平台中的独立 Agent，面向公司内部全体人员提供公司制度、业务流程、产品文档和技术文档问答。用户不需要具备客服角色。

首个完整闭环必须实现：

1. 管理人员通过后台上传单个文件或批量导入文件；
2. 系统完成文件校验、解析、分块、Embedding 和索引构建；
3. 管理人员手工发布文档版本，系统原子切换知识索引版本；
4. 内部人员通过独立的 AI 智能客服会话入口提问；
5. 独立智能客服 Agent 完成意图识别、查询改写、混合检索、重排、知识充分性判断、回答生成和引用校验；
6. 涉及公司事实的回答必须引用已发布知识；
7. 允许在独立区域提供明确标注为“通用建议，非公司制度”的模型通用知识；
8. 用户可以对回答点赞或点踩；
9. 管理人员可以查看 RAG 调试详情和完整运行回放；
10. 每次运行能够还原使用的 Agent、Prompt、模型、RAG 策略和知识索引版本。

## 2. 已确定的产品边界

### 2.1 用户与知识范围

- 使用者为公司内部全体人员；
- 首期不实现登录、注册、JWT、组织权限和部门权限；
- Java 固定注入开发身份 `tenantId=dev`、`userId=1`，浏览器不得覆盖；
- 固定开发身份同时具有 `SYSTEM_ADMIN` 管理权限，员工入口和管理入口均由 Java 注入该身份；
- 首期所有已发布知识均为 `COMPANY_WIDE`，对公司内部人员开放；
- 知识类型固定为 `COMPANY_POLICY`、`BUSINESS_PROCESS`、`PRODUCT_DOCUMENT`、`TECHNICAL_DOCUMENT`；
- 数据模型保留所属部门和可见范围字段，但首期不执行部门或人员级过滤。

### 2.2 知识接入方式

首期只实现：

- 后台单文件上传；
- 后台多文件批量导入；
- 手工创建文档新版本；
- 手工发布和回滚；
- 失败任务重试。

首期不接入企业网盘、Git、Confluence、数据库、内部网站或其他自动同步源。

### 2.3 独立 Agent 边界

AI 智能客服使用独立业务 Agent：

- Agent Key 固定为 `customer-service`；
- Python 代码位于 `efficiency_platform_agent/agents/customer_service/`；
- 独立拥有 Graph、状态、节点、意图、Prompt 绑定、模型策略、RAG 策略、知识库绑定、版本、发布、会话、反馈和评测；
- 不引用 `agents/operation/` 中的业务类、场景、Prompt、状态或契约；
- 不读取或写入 `ai_operation_*` 表；
- 运行在现有 Python Agent 服务进程中，通过公共 Agent Runtime 注册和调度；
- 只共享没有业务语义的运行框架、Provider、Tool Runtime、预算、取消、事件、数据库连接和日志组件。

### 2.4 非目标

首个闭环不实现：

- 外部访客客服；
- 客服坐席、工单、排班和人工转接；
- 微信、企业微信、钉钉、网页插件等外部渠道接入；
- 外部知识源自动同步；
- 部门和人员级知识权限；
- Tool/MCP 管理后台；
- LangGraph 可视化编辑器；
- 语音、图片和视频问答；
- 模型自动修改 Prompt；
- 基于互联网搜索补充公司事实。

## 3. 总体架构

```text
Browser
  -> Java Customer Service API
       -> 会话、消息、Run、反馈和引用持久化
       -> Knowledge Control Plane
            -> 文件元数据与对象存储
            -> 文档版本、处理任务、索引发布
       -> AI Hub Control Plane
            -> Agent、Prompt、模型和 RAG 配置
            -> 不可变 Release Bundle 发布
       -> aiep-platform-ai
            -> Customer Service Agent Internal API
                 -> CustomerServiceGraph
                 -> Prompt Assembler
                 -> Embedding / Retrieval / Rerank
                 -> LLM Provider
                 -> Citation and Output Guard
                 -> Agent MySQL / Redis / pgvector
       <- Agent SSE and terminal result
  <- Java projected SSE, messages, citations and replay views
```

### 3.1 前端职责

前端只访问 Java：

- 员工问答和历史会话；
- 流式答案、引用和反馈；
- 知识库、目录、文档和版本管理；
- 上传、批量导入、任务状态、失败重试、发布和回滚；
- Agent、Prompt、模型和 RAG 配置查看与发布；
- RAG 调试和运行回放。

前端不直连 Agent、MySQL、PostgreSQL、Redis、COS 或模型接口，不拼接 Prompt，不决定回答模式。

### 3.2 Java 职责

Java 是管理配置和用户可见业务数据的唯一真相源：

- `aiep-biz-knowledge`：知识库、目录、文档、文档版本、处理任务和索引发布；
- `aiep-biz-aihub`：独立 Agent、Prompt、模型策略、RAG 策略、Release Bundle、会话、消息、Run、引用、反馈和回放投影；
- `aiep-platform-file`：文件元数据、对象存储写入和受控读取地址；
- `aiep-platform-ai`：Java 调用 Agent 的唯一边界；
- `aiep-biz-system`：操作审计记录。

Java 不执行文档解析、Embedding、向量检索、重排、Prompt 渲染或回答生成。

### 3.3 Agent 职责

Agent 是执行真相源：

- 校验并保存 Java 发布的不可变 Release Bundle；
- 解析文档、生成结构化分块和 Embedding；
- 构建和验证知识索引版本；
- 执行独立 CustomerServiceGraph；
- 完成意图、改写、检索、重排、充分性、回答模式和引用判断；
- 渲染共享 Prompt 与智能客服私有 Prompt；
- 记录运行事件、检索快照、Prompt 快照、模型用量和失败事实；
- 通过 SSE 返回有序事件和最终契约。

Agent 不拥有知识库名称、目录、文档业务状态、用户反馈和用户可见会话真相。

### 3.4 数据存储职责

- Java MySQL：管理配置、知识业务元数据、会话、消息、反馈和运行投影；
- Agent MySQL `ai_efficiency_platform_agent`：Release Bundle、Run、事件、检查点、Prompt 快照和检索快照；
- PostgreSQL 数据库 `vector`：文档分块、Embedding 和索引版本成员关系；
- Redis：取消标志、短期事件协调、限流和幂等缓存；
- 对象存储：原始文件和可预览文件，不保存业务状态。

## 4. Java 领域数据模型

所有业务表使用逻辑引用，不建立跨模块或跨数据库物理外键。主键使用 `CHAR(36)` UUID，时间使用 `DATETIME(6)`，可变结构使用 JSON 并由 Java 强类型对象校验。

### 4.1 文件表

#### `pf_file_object`

| 字段 | 含义 |
| --- | --- |
| `id` | 文件唯一标识 |
| `tenant_id` | 固定为 `dev` |
| `storage_provider` | `COS` |
| `object_key` | 对象存储键 |
| `original_name` | 原始文件名 |
| `content_type` | 校验后的 MIME |
| `size_bytes` | 文件大小 |
| `sha256` | 文件内容摘要 |
| `status` | `ACTIVE`、`DELETED` |
| `created_by`、`created_at` | 创建审计 |

原始文件只通过 `file_id` 被知识文档版本引用。删除采用逻辑删除；存在已发布文档版本引用时禁止删除对象。

### 4.2 知识库表

#### `kb_knowledge_base`

保存知识库基本信息：`id`、`tenant_id`、`code`、`name`、`description`、`knowledge_type`、`visibility_scope`、`owner_department_id`、`status`、`current_index_release_id`、审计字段。

约束：

- `code` 在租户内唯一；
- `knowledge_type` 为四种已确认类型之一；
- `visibility_scope` 首期固定为 `COMPANY_WIDE`；
- `status` 为 `DRAFT`、`ACTIVE`、`DISABLED`；
- 只有 `ACTIVE` 知识库可以被 Agent Release 绑定。

#### `kb_directory`

保存知识库内目录树：`id`、`knowledge_base_id`、`parent_id`、`name`、`path`、`sort_no`、`status`、审计字段。

同一父目录下名称唯一；目录停用后不可新增文档，但不影响已发布索引中的历史版本。

#### `kb_document`

保存逻辑文档：`id`、`knowledge_base_id`、`directory_id`、`title`、`document_code`、`source_type`、`status`、`current_published_version_id`、审计字段。

约束：

- `source_type` 首期固定为 `UPLOAD` 或 `BATCH_UPLOAD`；
- `document_code` 在知识库内唯一；
- `status` 为 `ACTIVE`、`ARCHIVED`；
- 归档只阻止创建新版本，不删除历史引用。

#### `kb_document_version`

保存不可变文档版本：`id`、`document_id`、`version_no`、`file_id`、`file_sha256`、`content_type`、`change_summary`、`effective_date`、`status`、`parse_metadata`、`created_by`、`created_at`、`published_at`。

状态为：

```text
DRAFT -> PROCESSING -> READY -> PUBLISHED -> RETIRED
                 \-> FAILED -> PROCESSING
```

约束：

- `(document_id, version_no)` 唯一；
- 版本进入 `PROCESSING` 后文件、版本号和摘要不可修改；
- `READY` 表示解析、分块和 Embedding 全部成功，但尚未进入现网索引；
- 同一文档只有一个 `PUBLISHED` 版本；
- 新版本发布后，旧版本转为 `RETIRED`，历史引用仍可读取；
- `FAILED` 必须保存固定错误码和安全错误摘要。

#### `kb_ingest_batch`

保存一次单文件或批量导入：`id`、`knowledge_base_id`、`import_mode`、`total_count`、`succeeded_count`、`failed_count`、`status`、`created_by`、`created_at`、`finished_at`。

状态为 `QUEUED`、`RUNNING`、`SUCCEEDED`、`PARTIAL_FAILED`、`FAILED`、`CANCELLED`。

#### `kb_ingest_item`

保存批次内每个文件：`id`、`batch_id`、`file_id`、`document_id`、`document_version_id`、`status`、`error_code`、`error_message`、`retry_of_item_id`、时间字段。

一个文件失败不阻断同一批次的其他文件；重试创建新 Item 并关联原 Item。

#### `kb_processing_task`

保存文档版本处理任务：`id`、`document_version_id`、`agent_task_id`、`stage`、`status`、`attempt_no`、`progress_percent`、`error_code`、`error_message`、`started_at`、`finished_at`。

阶段固定为 `PREFLIGHT`、`PARSE`、`OCR`、`CHUNK`、`EMBED`、`VERIFY`。成功阶段不可回退；失败重试从失败阶段重新开始。

#### `kb_index_release`

保存知识库索引版本：`id`、`knowledge_base_id`、`release_no`、`status`、`document_count`、`chunk_count`、`embedding_model`、`embedding_dimension`、`checksum`、`previous_release_id`、`created_by`、`created_at`、`published_at`。

状态为：

```text
BUILDING -> READY -> PUBLISHED -> RETIRED
        \-> FAILED
```

同一知识库只有一个 `PUBLISHED` 索引版本。发布通过单个 Java 事务切换 `current_index_release_id`；回滚直接切换到指定历史 `READY` 或 `RETIRED` 版本，不重新解析和 Embedding。

#### `kb_index_release_document`

保存索引版本包含的文档版本：`index_release_id`、`document_id`、`document_version_id`、`document_sha256`。

唯一约束为 `(index_release_id, document_id)`，确保一个索引版本中每个逻辑文档只有一个版本。

### 4.3 Agent 与配置表

#### `ai_agent_definition`

保存 Agent 稳定身份：`id`、`agent_key`、`name`、`description`、`agent_type`、`status`、审计字段。

智能客服固定记录：

- `agent_key=customer-service`；
- `agent_type=INTERNAL_CUSTOMER_SERVICE`；
- 与运营助手使用不同的 Definition。

#### `ai_agent_version`

保存不可变业务版本：`id`、`agent_definition_id`、`semantic_version`、`graph_key`、`graph_version`、`status`、`change_summary`、审计字段。

状态为 `DRAFT`、`VALIDATED`、`RELEASED`、`RETIRED`。进入 `RELEASED` 后不可修改。

#### `ai_prompt_definition`

字段包括：`id`、`prompt_key`、`scope`、`owner_agent_definition_id`、`name`、`description`、`stage_key`、`status`、审计字段。

- `scope=PLATFORM_SHARED` 时 `owner_agent_definition_id` 为空；
- `scope=AGENT_PRIVATE` 时必须绑定智能客服 Agent；
- 共享 Prompt 不得包含具体 Agent 身份、业务规则或业务输出格式；
- 私有 Prompt 不得被其他 Agent 版本绑定。

#### `ai_prompt_version`

字段包括：`id`、`prompt_definition_id`、`semantic_version`、`status`、`checksum`、`change_summary`、`created_by`、`created_at`、`published_at`。

状态为 `DRAFT`、`VALIDATED`、`PUBLISHED`、`RETIRED`。发布版本不可修改。

#### `ai_prompt_message_template`

保存有序消息：`id`、`prompt_version_id`、`ordinal`、`role`、`message_key`、`content_template`、`content_format`、`trusted_instruction`、`checksum`。

角色支持 `system`、`developer`、`user`、`assistant`。静态模板不保存 `tool` 消息。

#### `ai_prompt_variable`

保存变量契约：`id`、`prompt_message_template_id`、`variable_name`、`value_type`、`value_source`、`required`、`sensitive`、`max_length`、`allow_untrusted_content`。

`system` 和 `developer` 消息只允许 `system_context` 来源且禁止不可信内容。

#### `ai_agent_version_prompt_binding`

保存 Agent 版本的 Prompt 组合：`agent_version_id`、`stage_key`、`ordinal`、`prompt_definition_id`、`prompt_version_id`、`required`。

共享 Prompt 更新不会自动影响 Agent。Agent 版本必须显式绑定具体 Prompt 版本并重新发布。

#### `ai_model_policy`

保存 Agent 私有模型策略：`id`、`owner_agent_definition_id`、`policy_key`、`semantic_version`、`provider`、`model_name`、`temperature`、`top_p`、`max_input_tokens`、`max_output_tokens`、`connect_timeout_ms`、`read_timeout_ms`、`max_retries`、`status`、`checksum`。

`(owner_agent_definition_id, policy_key, semantic_version)` 唯一。Provider 凭据属于平台连接配置，不进入本表。智能客服只绑定 `owner_agent_definition_id` 为自身的策略，不继承运营助手模型策略。

#### `ai_rag_policy`

保存 Agent 私有版本化 RAG 策略：`id`、`owner_agent_definition_id`、`policy_key`、`semantic_version`、`rewrite_query_limit`、`vector_top_k`、`fts_top_k`、`fusion_top_k`、`rerank_top_k`、`context_token_limit`、`citation_limit`、`status`、`checksum`、审计字段。

`(owner_agent_definition_id, policy_key, semantic_version)` 唯一。智能客服只能绑定归属于自身 Agent Definition 的 RAG 策略。

首个发布版本固定值：

| 参数 | 值 |
| --- | --- |
| `rewrite_query_limit` | 3 |
| `vector_top_k` | 30 |
| `fts_top_k` | 30 |
| `fusion_top_k` | 20 |
| `rerank_top_k` | 8 |
| `context_token_limit` | 12000 |
| `citation_limit` | 5 |

#### `ai_agent_version_knowledge_binding`

保存 Agent 版本可用知识：`agent_version_id`、`knowledge_base_id`、`index_release_id`、`priority`、`required`。

发布时必须绑定确切索引版本，运行时禁止解析“当前最新索引”。

#### `ai_agent_release`

保存环境发布：`id`、`agent_definition_id`、`agent_version_id`、`environment`、`release_status`、`release_snapshot_id`、`released_by`、`released_at`、`rolled_back_from_release_id`。

同一环境同一 Agent 只有一个 `ACTIVE` Release。

#### `ai_agent_release_snapshot`

保存不可变 Release Bundle：`id`、`agent_release_id`、`snapshot_json`、`checksum`、`agent_ack_status`、`agent_ack_at`、`created_at`。

Bundle 必须包含：

- Agent Key、Agent Version、Graph Key 和 Graph Version；
- 全部 Prompt 绑定及具体版本、角色顺序和 checksum；
- 模型策略完整快照；
- RAG 策略完整快照；
- 知识库与索引版本绑定；
- Tool Allowlist；
- 输出契约版本；
- 安全规则版本。

Java 只有在 Agent 校验并确认 Bundle 后才能激活 Release。

### 4.4 智能客服业务表

#### `ai_customer_service_conversation`

字段：`id`、`tenant_id`、`user_id`、`title`、`status`、`last_agent_release_id`、`created_at`、`updated_at`。状态为 `ACTIVE`、`ARCHIVED`。

每次提交消息时，Java 读取当时激活的 Agent Release 并冻结到新 Run；会话只记录最近一次使用的 Release，不会将后续消息永久锁定在旧 Release。

#### `ai_customer_service_message`

字段：`id`、`conversation_id`、`tenant_id`、`role`、`content_markdown`、`answer_mode`、`run_id`、`client_request_id`、`created_at`。

`(tenant_id, client_request_id)` 唯一，保证提交幂等。内部 Prompt、检索详情和调试数据不得写入用户消息正文。

#### `ai_customer_service_run`

字段：`id`、`conversation_id`、`tenant_id`、`user_message_id`、`agent_run_id`、`agent_release_id`、`status`、`answer_mode`、`last_event_sequence`、`failure_code`、`failure_message`、`started_at`、`finished_at`。

状态为 `PENDING`、`RUNNING`、`SUCCEEDED`、`FAILED`、`TIMED_OUT`、`CANCELLED`。澄清和知识不足属于成功回答模式，不属于失败状态。

#### `ai_customer_service_run_step`

字段：`id`、`run_id`、`sequence_no`、`stage`、`status`、`public_summary`、`internal_payload`、`started_at`、`finished_at`。

保存 Java 投影后的运行步骤，支撑调试和回放。`internal_payload` 只对管理页面返回，不进入员工聊天接口。

#### `ai_customer_service_citation`

字段：`id`、`run_id`、`message_id`、`citation_no`、`knowledge_base_id`、`document_id`、`document_version_id`、`index_release_id`、`chunk_id`、`document_title`、`version_no`、`section_path`、`page_no`、`quoted_text`、`content_hash`。

引用在回答保存时冻结。文档发布新版本、归档或索引回滚均不得改变历史引用内容。

#### `ai_customer_service_feedback`

字段：`id`、`conversation_id`、`message_id`、`run_id`、`tenant_id`、`user_id`、`rating`、`reason_code`、`comment`、`created_at`。

- `rating` 为 `UP` 或 `DOWN`；
- 点踩原因固定为 `INCORRECT`、`OUTDATED`、`IRRELEVANT`、`MISSING_CITATION`、`UNCLEAR`、`OTHER`；
- 同一用户对同一消息只有一条当前反馈，再次提交覆盖评分和原因并保留更新时间审计。

### 4.5 操作审计表

#### `sys_audit_log`

记录知识、Agent、Prompt、模型、RAG 和 Release 的管理操作。字段为：`id`、`tenant_id`、`actor_id`、`action`、`resource_type`、`resource_id`、`before_digest`、`after_digest`、`result`、`trace_id`、`created_at`。

首期必须记录上传、批量导入、失败重试、文档发布、索引回滚、Agent Version 校验、Agent Release 发布与回滚、Prompt 发布、模型策略发布和 RAG 策略发布。审计记录不保存文件正文、Prompt 全文、密钥或连接串。

## 5. PostgreSQL + pgvector 数据模型

使用数据库 `vector` 和 Schema `customer_service`。

### 5.1 `customer_service.document_chunk`

字段包括：

- `chunk_id`：稳定 UUID；
- `tenant_id`；
- `knowledge_base_id`；
- `document_id`；
- `document_version_id`；
- `chunk_no`；
- `section_path`；
- `page_no`；
- `content`；
- `content_hash`；
- `token_count`；
- `embedding vector(1024)`；
- `embedding_model`，固定为 `text-embedding-v4`；
- `embedding_dimension`，固定为 `1024`；

唯一约束为 `(document_version_id, chunk_no)`。建立 HNSW cosine 索引、`content` 的 GIN FTS 索引及 `(tenant_id, knowledge_base_id, document_version_id)` 普通索引。

### 5.2 `customer_service.index_release_document`

字段为 `index_release_id`、`knowledge_base_id`、`document_id`、`document_version_id`、`document_sha256`、`created_at`。

检索必须先按 `index_release_id` 限定文档版本，再执行向量和全文查询。不同索引版本复用同一文档版本的 Chunk，不复制 Embedding。

## 6. 文件与文档处理流程

### 6.1 文件规则

首期支持：

- PDF：`application/pdf`；
- DOCX：Office Open XML；
- Markdown：`.md`；
- TXT：UTF-8 `.txt`；
- HTML：`.html`、`.htm`。

单文件最大 10 MiB；单次批量最多 50 个文件且总大小不超过 200 MiB。批量导入使用多文件上传，不接收 ZIP 压缩包。

Java 必须校验扩展名、MIME、文件头、大小、空文件和 SHA-256。文件名不能决定类型。相同知识库中已存在相同 SHA-256 时拒绝创建重复版本并返回 `KB_DUPLICATE_CONTENT`。

新建文档时，标题固定取去除扩展名后的原始文件名，`document_code` 由 Java 生成 `DOC-` 加 26 位 ULID，目录由请求中的 `directoryId` 指定。批量导入中的每个文件独立创建逻辑文档；同名文件不会合并，只有 SHA-256 相同才判定为重复内容。给既有文档上传新版本只能使用版本接口，必须提交 `changeSummary`，不得通过批量导入隐式覆盖。

### 6.2 上传主链路

1. 浏览器将文件提交给 Java；
2. Java 完成预检，将原始文件写入对象存储并创建 `pf_file_object`；
3. Java 创建文档、文档版本、导入 Item 和处理任务；
4. Java 生成有时效和大小限制的对象存储读取地址；
5. Java 调用 Agent 摄取接口，传递任务、业务标识、文件摘要和读取地址；
6. Agent 重新校验摘要后解析文件；
7. Agent 按标题、段落、列表、表格和页面边界生成结构化文档；
8. 图片和扫描型 PDF 在文本不足时进入 OCR；
9. Agent 生成分块和 Embedding，写入 pgvector；
10. Agent 校验 Chunk 数量、空内容、维度和摘要并完成任务；
11. Java 查询任务状态并将文档版本更新为 `READY`；
12. 只有管理人员执行发布后，版本才进入现网索引。

### 6.3 分块规则

- 优先按标题层级、段落、列表、表格和页码切分；
- 每个 Chunk 目标上限为 800 tokens；
- 相邻普通文本 Chunk 重叠 120 tokens；
- 标题路径复制到所有子 Chunk；
- 表格作为完整逻辑块保存，超过上限时按行组拆分并重复表头；
- 单个段落超过上限时按句子边界拆分；
- Chunk 必须保留文档版本、章节路径、页码和内容摘要；
- 空 Chunk、纯页眉页脚和重复导航内容不入库。

### 6.4 发布与回滚

发布文档版本时：

1. Java 读取当前索引版本的文档集合；
2. 用新文档版本替换同一逻辑文档的旧版本；
3. 创建 `BUILDING` 索引版本和完整成员快照；
4. Agent 验证所有成员对应 Chunk 和 Embedding 完整；
5. 验证通过后索引版本进入 `READY`；
6. Java 在同一事务中将新索引设为 `PUBLISHED`、旧索引设为 `RETIRED`，同时切换知识库当前索引指针；
7. 文档新版本进入 `PUBLISHED`，旧版本进入 `RETIRED`。

回滚直接激活指定历史索引版本，并同步恢复其中每个文档的已发布版本指针。历史会话继续使用运行时冻结的旧索引版本。

## 7. 独立 CustomerServiceGraph

### 7.1 Graph 状态

`CustomerServiceState` 固定包含：

- `run_id`、`conversation_id`、`tenant_id`、`user_id`；
- `agent_release_id` 和完整 Release Bundle 引用；
- 当前用户问题和有界会话历史；
- `intent_result`；
- `rewritten_queries`；
- `retrieval_candidates`；
- `reranked_evidence`；
- `sufficiency_decision`；
- `answer_mode`；
- `draft_answer`；
- `citations`；
- `validation_result`；
- `usage`、`error`、`cancelled`。

### 7.2 Graph 节点

```text
load_release
  -> classify_intent
       -> clarify
       -> general_answer
       -> rewrite_query
            -> retrieve
            -> fuse
            -> rerank
            -> judge_sufficiency
                 -> insufficient_answer
                 -> compose_company_answer
                 -> compose_mixed_answer
            -> validate_citations
                 -> repair_once
                 -> output_guard
  -> persist_terminal_state
```

节点职责：

1. `load_release`：读取运行请求指定的不可变 Bundle，校验 Agent Key 和 checksum；
2. `classify_intent`：判断公司知识需求、通用建议需求、混合需求或缺少关键信息；
3. `clarify`：一次只询问一个会改变答案的关键问题；
4. `general_answer`：生成明确标注的通用建议，不创建公司知识引用；
5. `rewrite_query`：生成最多 3 条语义互补且不改变用户意图的检索查询；
6. `retrieve`：对绑定索引执行向量和全文双路召回；
7. `fuse`：使用 Reciprocal Rank Fusion 合并并去重；
8. `rerank`：对融合结果进行语义重排；
9. `judge_sufficiency`：判断公司事实是否有完整、有效且无冲突的证据；
10. `insufficient_answer`：说明当前知识库无法确认并给出缺少的知识类型；
11. `compose_company_answer`：只使用证据生成公司知识回答；
12. `compose_mixed_answer`：分区生成公司知识和通用建议；
13. `validate_citations`：验证每个公司事实与引用的闭包；
14. `repair_once`：只根据明确校验错误修复一次；
15. `output_guard`：检查标签、引用、敏感信息和最终契约；
16. `persist_terminal_state`：保存终态、快照和用量并发送终态事件。

任何校验失败最多修复一次。修复仍失败时返回 `INSUFFICIENT_EVIDENCE`，不得把未闭合回答标记为成功的公司知识回答。

## 8. 回答模式与判断契约

### 8.1 五种回答模式

| 模式 | 使用条件 | 输出规则 |
| --- | --- | --- |
| `COMPANY_KNOWLEDGE` | 问题涉及公司事实且证据充分 | 只输出公司知识，每个事实有引用 |
| `MIXED` | 公司知识部分有充分证据，同时用户需要通用方法建议 | 公司知识与通用建议严格分区 |
| `GENERAL_ADVICE` | 问题不涉及公司事实 | 标注“通用建议，非公司制度” |
| `CLARIFY` | 缺少一个决定答案的关键条件 | 只问一个问题，不生成结论 |
| `INSUFFICIENT_EVIDENCE` | 涉及公司事实但证据不足、过期或冲突 | 明确无法确认，不使用模型记忆补全 |

### 8.2 判断机制

使用“LLM 语义判断 + 确定性程序门禁 + 输出后校验”：

1. LLM 输出结构化意图、事实类型和回答需求；
2. 程序校验枚举、必填字段和 Agent 能力边界；
3. LLM 基于重排证据输出充分性决策及支持关系；
4. 程序验证所有引用都属于本次冻结索引版本；
5. 程序验证公司知识段中的事实句均绑定至少一个 Citation；
6. 程序验证通用建议段不使用“公司规定”“公司要求”“必须按照公司流程”等公司权威措辞；
7. 程序验证通用建议没有伪造内部文档引用；
8. 证据冲突时固定使用 `INSUFFICIENT_EVIDENCE`，同时展示冲突文档标题和版本，不替用户选择其中一个结论。

混合问题中的公司知识部分证据不足时，回答模式固定为 `INSUFFICIENT_EVIDENCE`。只有用户同时明确要求通用方法时，结果才在知识不足说明之后附加独立的“通用建议，非公司制度”区域；该区域不能改变或补全未确认的公司事实。

### 8.3 用户可见格式

`COMPANY_KNOWLEDGE`：

```markdown
回答正文……[1]

参考资料
[1] 《文档标题》V3，第 2 章，P.6
```

`MIXED`：

```markdown
### 根据公司知识

有内部依据的回答……[1]

### 通用建议（非公司制度）

以下内容来自通用知识，仅供参考，不代表公司现行规定。
```

`GENERAL_ADVICE` 的首行固定显示：

```text
以下为通用建议，非公司制度或内部流程。
```

## 9. RAG 执行规则

### 9.1 检索范围

- 只检索 Agent Release Bundle 绑定的知识库和 `index_release_id`；
- 只使用对应索引版本成员表中的文档版本；
- 不读取草稿、处理中、失败、已归档且未被索引引用的版本；
- 不使用其他 Agent 的向量 Schema；
- 不访问互联网补全公司知识。

### 9.2 混合召回与重排

1. 每个改写查询分别执行向量召回 30 条和 PostgreSQL FTS 召回 30 条；
2. 使用 RRF 按 `document_version_id + chunk_id` 合并；
3. 去除内容摘要相同的重复 Chunk；
4. 保留融合排名前 20 条；
5. Rerank Provider 重排并保留前 8 条；
6. 按 12000 tokens 上下文上限装配证据；
7. 同一文档相邻 Chunk 可以合并，但引用仍保留原 Chunk ID；
8. 最终回答最多展示 5 个引用，内部支持关系保留全部使用证据。

### 9.3 充分性规则

满足以下全部条件才能进入 `COMPANY_KNOWLEDGE`：

- 至少存在一条与问题直接相关的已发布证据；
- 回答计划中的每个公司事实都有证据支持；
- 引用内容能够直接支持对应事实，而非只包含相同主题词；
- 证据没有来源于过期文档版本；
- 多份有效文档之间不存在无法解释的结论冲突；
- 证据正文在上下文预算内完整传给回答模型。

## 10. Prompt 体系

### 10.1 共享 Prompt

首期共享 Prompt Key：

- `shared.safety.boundary`：不可信内容、敏感信息和指令优先级；
- `shared.citation.rules`：引用真实性和禁止伪造规则；
- `shared.output.json_repair`：只修复结构错误，不改变事实；
- `shared.general_advice.label`：通用建议固定标识和措辞限制。

### 10.2 智能客服私有 Prompt

首期私有 Prompt Key：

- `customer_service.identity.system`；
- `customer_service.intent.classify`；
- `customer_service.query.rewrite`；
- `customer_service.evidence.sufficiency`；
- `customer_service.answer.company`；
- `customer_service.answer.mixed`；
- `customer_service.answer.general`；
- `customer_service.answer.insufficient`；
- `customer_service.citation.review`；
- `customer_service.answer.repair`；
- `customer_service.output.guard`。

### 10.3 装配顺序

每个阶段使用有序消息，不拼成单字符串：

```text
system: shared.safety.boundary
system: customer-service Agent 身份与事实边界
developer: 当前阶段私有 Prompt
developer: shared.citation.rules 或 shared.general_advice.label
user: 用户原始问题
user: 有界会话上下文
user: 结构化证据数据块
```

用户输入、文档正文、历史回答和工具结果都属于不可信数据，不得进入 `system` 或 `developer` 消息。

### 10.4 输出契约

意图契约固定包含：

- `intent_type`：`COMPANY_QUERY`、`GENERAL_QUERY`、`MIXED_QUERY`、`AMBIGUOUS_QUERY`；
- `requires_company_knowledge`：是否必须检索内部知识；
- `requires_general_advice`：用户是否明确需要通用方法；
- `missing_field`：只有 `AMBIGUOUS_QUERY` 非空，描述唯一缺失条件；
- `normalized_question`：不增加新事实的规范化用户问题。

充分性契约固定包含：

- `sufficient`：公司事实是否全部得到支持；
- `supported_claims`：每项固定包含 `claim_id`、`claim_text`、`supporting_chunk_ids`；
- `unsupported_claims`：每项固定包含 `claim_id`、`claim_text`、`reason`；
- `conflicts`：每项固定包含 `claim_id`、`left_chunk_id`、`right_chunk_id`、`conflict_summary`；
- `recommended_mode`：五种回答模式之一。

`supporting_chunk_ids` 只能引用本次重排结果中的 Chunk；`sufficient=true` 时 `unsupported_claims` 和 `conflicts` 必须为空。程序根据 `supporting_chunk_ids` 生成连续的引用编号，模型不得自行发明引用编号。

最终回答契约固定为：

```json
{
  "contract_version": "customer-service-answer/1",
  "answer_mode": "COMPANY_KNOWLEDGE | MIXED | GENERAL_ADVICE | CLARIFY | INSUFFICIENT_EVIDENCE",
  "company_sections": [
    {
      "heading": "string",
      "paragraphs": [
        {
          "text": "string",
          "citation_nos": [1]
        }
      ]
    }
  ],
  "general_advice_sections": [
    {
      "heading": "string",
      "paragraphs": ["string"]
    }
  ],
  "clarification_question": "string | null",
  "insufficiency_message": "string | null",
  "citations": [
    {
      "citation_no": 1,
      "chunk_id": "string",
      "document_version_id": "string",
      "supported_text": "string"
    }
  ]
}
```

字段语义和约束：

- `company_sections`：公司知识内容；每个段落只表达一个可独立核验的事实结论，`citation_nos` 至少包含一个有效引用；非公司知识模式必须为空数组；
- `general_advice_sections`：通用知识内容；不得携带引用编号；只有 `MIXED`、`GENERAL_ADVICE`，以及用户明确要求通用方法时的 `INSUFFICIENT_EVIDENCE` 可以非空；
- `clarification_question`：只有 `CLARIFY` 非空，必须是一个问题；
- `insufficiency_message`：只有 `INSUFFICIENT_EVIDENCE` 非空，说明无法确认的具体范围；
- `citations`：只引用本次冻结索引版本中的 Chunk，`citation_no` 从 1 连续递增；
- `supported_text`：对应 Chunk 中直接支持公司知识段落的原文摘录，不得由模型改写；
- Agent Renderer 根据结构化字段生成 Markdown，模型不直接控制最终标题层级、引用编号和固定声明。

Prompt 必须逐项说明字段含义、允许为空的条件、枚举和禁止行为。Pydantic 与 Java DTO 同时实现该契约并拒绝额外字段。

## 11. Release Bundle 与配置独立性

智能客服业务和配置完全独立。共享 Prompt 只作为不可变组件被显式绑定，不形成动态继承。

发布流程：

1. Java 校验 Agent Version 状态为 `VALIDATED`；
2. 校验所有私有 Prompt 属于智能客服；
3. 校验共享 Prompt 状态为 `PUBLISHED`；
4. 校验模型、RAG 和知识索引版本均为可发布状态；
5. 生成规范化 Snapshot JSON 和 SHA-256；
6. Java 调用 Agent Release 接口；
7. Agent 校验 Graph、Prompt、输出契约、模型、RAG 和知识索引绑定；
8. Agent 幂等保存 `agent_release_bundle`；
9. Agent 返回相同 checksum 的确认；
10. Java 激活 Release；
11. 新 Run 固定使用该 Release ID，运行中不跟随任何配置更新。

共享 Prompt 发布新版本后，只显示“存在可升级版本”。智能客服必须创建新 Agent Version、绑定新 Prompt 版本、验证并重新发布。运营助手不受影响。

### 12.1 `agent_release_bundle`

字段：`release_id`、`agent_key`、`agent_version`、`graph_version`、`environment`、`snapshot_json`、`checksum`、`status`、`created_at_epoch_ms`。

`release_id` 唯一；相同 ID 不同 checksum 必须拒绝为 `AGENT_RELEASE_CONFLICT`。

### 13.6 核心接口契约

创建会话请求：

```json
{
  "title": null
}
```

`title` 为空时，Java 在首条用户消息提交后使用前 30 个字符生成标题。

新建文档上传使用 `multipart/form-data`，固定字段为 `file`、`directoryId`；文档继承所属知识库的知识类型，Java 生成标题和 `documentCode`。批量导入固定字段为 `files[]`、`directoryId`，文件按上传顺序创建 Item。既有文档新版本固定字段为 `file`、`changeSummary`、`effectiveDate`，其中 `effectiveDate` 使用 `yyyy-MM-dd`，`changeSummary` 长度为 1 至 500 个字符。

提交员工问题请求：

```json
{
  "contractVersion": "customer-service-message/1",
  "message": "用户原始问题",
  "clientRequestId": "浏览器生成的UUID"
}
```

提交结果：

```json
{
  "conversationId": "UUID",
  "runId": "Java Run UUID",
  "status": "PENDING",
  "agentReleaseId": "UUID"
}
```

Java 向 Agent 提交请求：

```json
{
  "contract_version": "customer-service-run/1",
  "request_id": "Java Run UUID",
  "conversation_id": "UUID",
  "tenant_id": "dev",
  "user_id": "1",
  "agent_release_id": "UUID",
  "message": "用户原始问题",
  "history": [
    {
      "role": "user | assistant",
      "content": "有界历史消息"
    }
  ]
}
```

`history` 只包含当前会话最近 12 条已完成消息，总字符数上限 12000；不包含失败 Run 的草稿、调试载荷和其他会话内容。

Agent 接收后返回：

```json
{
  "contract_version": "customer-service-run-view/1",
  "run_id": "Agent Run UUID",
  "request_id": "Java Run UUID",
  "status": "PENDING | RUNNING | SUCCEEDED | FAILED | TIMED_OUT | CANCELLED"
}
```

引用公开视图固定包含：`citationId`、`citationNo`、`documentTitle`、`versionNo`、`sectionPath`、`pageNo`、`quotedText`。`chunkId`、内容摘要和索引版本只在管理回放中返回。

文档处理请求固定包含：`contract_version`、`task_id`、`tenant_id`、`knowledge_base_id`、`document_id`、`document_version_id`、`file_name`、`content_type`、`size_bytes`、`sha256`、`download_url`。Agent 下载后必须验证大小和 SHA-256。

RAG 调试请求固定包含：`agent_key`、`question`、`agent_version_id`、`rag_policy_version_id`、`knowledge_bindings`。`agent_version_id` 和 `rag_policy_version_id` 必须归属于 `agent_key`。调试接口不接受浏览器提供的 Prompt 正文、模型密钥、数据库连接或任意向量 Schema。

列表查询参数固定为：

- 会话列表：`keyword`、`page`、`pageSize`；
- 历史消息：`beforeMessageId`、`limit`，`limit` 默认为 30，最大 100；
- 知识库列表：`keyword`、`knowledgeType`、`status`、`page`、`pageSize`；
- 文档列表：`directoryId`、`keyword`、`status`、`page`、`pageSize`；
- 运行列表：`agentKey`、`startedFrom`、`startedTo`、`runId`、`conversationId`、`status`、`answerMode`、`feedback`、`page`、`pageSize`；
- 反馈列表：`agentKey`、`startedFrom`、`startedTo`、`rating`、`reasonCode`、`answerMode`、`keyword`、`page`、`pageSize`。

分页列表统一返回 `items`、`page`、`pageSize`、`total`。历史消息按 `createdAt DESC` 查询，Java 返回后由前端按时间正序展示。

## 14. SSE 与运行回放

### 14.1 Agent 事件

每个事件必须包含 `run_id`、`sequence`、`event_type`、`status`、`occurred_at` 和强类型 `payload`。事件序号单调递增。

Agent 不向浏览器透传模型原始 Token。回答模型完成结构化输出、引用校验和输出门禁后，Renderer 才将已验证 Markdown 按段落切分为有序 `answer.delta`；Java 再投影为 `message.delta`。这样保留打字机展示，同时禁止未验证草稿进入用户界面。

事件类型固定为：

- `run.started`；
- `intent.classified`；
- `query.rewritten`；
- `retrieval.completed`；
- `rerank.completed`；
- `sufficiency.decided`；
- `answer.delta`；
- `citation.ready`；
- `answer.completed`；
- `run.failed`；
- `run.cancelled`；
- `run.timed_out`。

### 14.2 Java 公开事件

员工聊天只接收：

- `run.started`；
- `run.progress`；
- `message.delta`；
- `citation.ready`；
- `run.completed`；
- `run.failed`；
- `run.cancelled`。

查询改写、候选内容、充分性详情、Prompt 和模型信息只写 `ai_customer_service_run_step`，供管理回放查看。

### 14.3 回放内容

一次完整回放必须展示：

- 用户问题和有界会话上下文；
- Agent Release、Graph、Prompt、模型、RAG 和知识索引版本；
- 意图分类结果；
- 查询改写；
- 向量与全文候选；
- 融合与重排结果；
- 充分性决策；
- 回答模式；
- 最终引用闭包；
- 模型调用次数、Token、耗时和错误；
- 最终状态和用户反馈。

回放不展示模型隐藏思维链、密钥、连接串或未脱敏异常正文。

## 18. 并发、幂等与一致性

- 消息提交使用 `tenantId + clientRequestId` 幂等；
- 文件使用 SHA-256 去重；
- Agent Release 发布使用 `releaseId + checksum` 幂等；
- 文档处理任务使用 `documentVersionId + attemptNo` 唯一；
- 事件使用 `runId + sequence` 去重；
- 发布和回滚必须带当前版本条件，影响行数为零返回冲突；
- 取消为幂等操作，终态 Run 返回当前终态；
- 迟到事件不得覆盖 Java 终态；
- Java 事务内不调用 Agent、对象存储或模型服务；
- 远程调用前先提交本地 `PENDING` 状态，远程结果通过独立事务投影。

## 19. 日志与监控

Java 和 Agent 使用同一 `traceId`、`conversationId`、Java `runId` 和 Agent `runId` 关联链路。

必须记录：

- Release 发布与 checksum；
- 文档任务阶段、耗时、状态和错误码；
- Run 节点开始、完成、耗时和错误码；
- Provider、逻辑模型、调用次数、Token 和耗时；
- 检索候选数量、重排数量和有效证据数量；
- 回答模式和引用数量；
- 用户反馈。

日志不得记录：

- 密钥和完整连接串；
- 完整 Prompt 正文；
- 完整文档正文；
- 模型隐藏思维链；
- 未脱敏 Provider 错误正文。

## 20. 真实验收标准

测试类、Mock、静态检查和编译只能作为开发辅助，不能替代真实接口验收。完成必须同时满足以下真实场景：

1. 通过后台真实上传 PDF、DOCX、Markdown、TXT 和 HTML；
2. 一次真实批量导入包含成功和失败文件，成功文件继续处理，失败文件可重试；
3. Java、对象存储、Agent、Embedding 和 pgvector 中均产生对应真实数据；
4. 发布一个文档新版本后，新问题使用新版本，历史回答仍显示旧版本引用；
5. 回滚索引后，新问题恢复使用旧版本；
6. 分别针对公司制度、业务流程、产品文档和技术文档完成真实问答；
7. `COMPANY_KNOWLEDGE` 回答的每条公司事实都有可打开的真实引用；
8. 证据不足时返回 `INSUFFICIENT_EVIDENCE`，不使用模型记忆补造公司事实；
9. 纯通用问题返回 `GENERAL_ADVICE` 并显示固定声明；
10. 混合问题严格分隔公司知识与通用建议；
11. 模糊问题返回一个澄清问题，不创建伪结论；
12. 冲突文档不会被模型静默选择为唯一事实；
13. 点赞和点踩真实写入 Java MySQL，反馈后台可查询；
14. RAG 调试展示真实改写、召回、融合、重排、充分性、回答模式和引用；
15. 运行回放准确显示一次 Run 使用的 Release Bundle 和所有版本；
16. SSE 断线续接不重复创建 Run；
17. 取消、超时、Provider 错误和 Embedding 错误返回真实失败状态；
18. 全程监听前端、Java、Agent、MySQL、PostgreSQL、Redis 和 Provider 日志；
19. 发现异常、错误日志、引用不闭合或结果不符合回答模式时必须修复并重新执行真实验收；
20. 验收记录必须保存真实请求、脱敏响应、数据库证明、关键日志和最终判断，禁止编造调用成功、返回数据或产品效果。

## 21. 完成定义

只有以下条件全部满足，首个完整闭环才算完成：

- 独立智能客服 Agent 已注册并使用独立 Graph 和 Release；
- 知识上传、批量导入、版本、发布和回滚闭环可用；
- PostgreSQL 正式 Schema 和向量索引可用；
- 五种回答模式均通过真实接口验证；
- 公司知识引用闭包可追溯到冻结文档版本和 Chunk；
- 用户反馈、RAG 调试和运行回放可用；
- 共享 Prompt 与私有 Prompt 按固定版本绑定，变更不会自动影响其他 Agent；
- Java 是管理和业务真相源，前端未直连 Agent；
- 真实数据库、真实模型、真实 Embedding 和真实接口验收通过；
- 日志中不存在未处理错误或伪造成功。
