# 智能客服父子切片与证据组装设计

> 状态：方案已确认，书面设计待复核
>
> 负责人：项目开发与验收
>
> 适用范围：公司内部独立智能客服的知识入库、检索、回答证据与 RAG 调试
>
> 最后更新：2026-10-22
>
> 关联设计：[AI 智能客服首个完整闭环详细设计](2026-10-19-AI智能客服首个完整闭环详细设计.md)

## 1. 目标与现状

目标是让较小的语义片段负责精确检索，让完整、可独立理解的原文条款负责回答，同时防止重复证据、旧版本、跨文档冲突和上下文截断造成错误的公司事实回答。

现有 Agent 将文档分为单层 `document_chunk`：按标题和段落优先切分，超长段落按 token 窗口切分；向量与全文检索经 RRF 融合后调用 Rerank，重排片段直接传给充分性判断和回答模型。入库只去除完全相同的文本片段；`context_token_limit` 存在于策略契约，但尚未用于实际证据装配。Java 的索引快照对同一逻辑文档只保留一个指定版本。原详细设计第 6.3、9.2、9.3 节提出的相邻合并、预算装配和冲突处理不能据此视为已经落地。

本设计只改进独立智能客服的证据链，不引入 LangChain、LlamaIndex 或第二套 Graph Runtime，不改变运营助手、不接入新知识源，也不改变 Java 为业务和索引发布真相源、Agent 为执行端的边界。

## 2. 方案选择

| 方案 | 效果与限制 | 结论 |
|---|---|---|
| 单层片段加前后邻居 | 改动较小，但邻居可能跨条款或跨标题，仍需复杂的边界判断 | 不采用 |
| 命中子片段后取整章 | 容易保留上下文，但长章节挤占预算，噪声大 | 不采用固定整章 |
| 结构化父片段 + 检索子片段 | 精确命中，按原文结构恢复完整条款，可在父片段级去重和预算选择 | 采用 |

父片段不是固定大小的整章，而是一个可独立理解的完整条款或小节。它包括适用对象、前提、规则、例外及与结论不可分离的表格行；章节较短且主题单一时可整体成为父片段。子片段从父片段内部切出，只用于向量和全文检索。两者始终归属于同一文档版本。

## 3. 入库与数据契约

1. 解析后的文档保留标题层级、段落、编号条款、列表、表格、页码和原文顺序。解析器无法可靠识别结构时，不把猜测的条款边界当成事实；允许保留较大的完整段落，超过安全上限则使该文档版本处理失败并在任务中说明原因，不静默裁掉文字。
2. 先形成父片段，再在每个父片段内形成子片段；子片段不得跨父片段或跨文档版本。长小节沿下级标题、编号条款或完整段落拆为多个父片段。表格沿行组拆分时每组重复表头，并保留使该行含义完整的注释；单行不可完整容纳时入库质量门禁失败。
3. 父片段保存 `parent_id`、租户、知识库、文档及版本 ID、父片段顺序、标题路径、页码范围、完整原文、内容摘要和计数。子片段保存现有检索字段，新增 `parent_id`、在父片段内的顺序和原文位置。`chunk_id` 继续指向子片段；引用在展示完整父片段时仍定位到其中具体的原文位置。
4. 现有完全相同文本的哈希去重只作用于同一文档版本内的重复子片段；不同条款即使措辞相近也不能因此合并。父片段保存原文，不用模型生成的摘要替代。
5. 新索引版本必须先完成全部父子关系、Embedding 数量和引用定位校验，才能进入 `READY`。已有发布索引及历史回放不可在原地改写；通过重新入库、构建新索引和切换绑定完成迁移，保留旧索引用于回退。

数据库变更由 Agent 自有 PostgreSQL `customer_service` Schema 承担父片段及子片段关联；Java MySQL 继续保存文档版本、索引成员、发布指针、会话和引用事实。共享 DDL 的实际执行另行按项目规则预检和授权，本设计不授权执行迁移。

## 4. 查询与证据组装

查询顺序固定为：

```text
意图识别与查询改写
→ 已绑定索引版本内的向量召回和全文召回
→ 按子片段 ID 融合去重、RRF 排序
→ 对子片段执行 Rerank，并截取 Rerank TopK
→ 批量读取父片段
→ 同一父片段去重、组装完整原文
→ 版本与冲突检查
→ 按上下文预算选择完整父片段
→ 证据充分性判断、回答、引用校验
```

检索 TopK 与最终进入模型的父片段数量是不同概念。多个命中子片段归于同一父片段时只传一份父原文，同时保留所有命中子片段与得分供调试。跨父片段的相似内容去重只消除原文完全重复的内容；语义相近但条件、时间或例外不同的条款保留。

证据选择使用版本化 RAG 策略的 `context_token_limit`，计算系统提示词、用户问题、必要会话上下文和证据的整体预算，并为模型输出预留额度。预算不够时按相关度移除低优先级父片段；不得从入选父片段中间截字，也不得将原文压缩为未校验的模型摘要。若关键条款无法完整放入预算，返回证据不足，而不是把半条款送入模型。现有各阶段 TopK 保持独立配置，具体数值通过固定评测集和真实接口结果调整，不以“越大越好”作为原则。

同一逻辑文档在一个索引快照内只接受快照指定版本，不依据 `version_no` 在查询时自行改选。跨文档说法冲突时，先核对双方是否属于当前绑定的发布索引以及原文是否谈论同一条件；仍无法解释的冲突进入 `INSUFFICIENT_EVIDENCE`，不让 Rerank 分数或模型自行决定哪份制度生效。没有明确来源元数据的制度优先级不得凭标题推断。

## 5. 生成、引用与调试

回答模型得到的是完整父片段、命中子片段及可引用的定位信息。每个公司事实必须对应已提供证据；引用校验除检查 ID 属于本次证据集合外，还必须检查引用文本是否确实包含被引用的原文位置。引用支持结论的语义核验由充分性判断和评测复核承担，不能把“引用 ID 合法”视为事实已被支持。通用建议继续独立标注为“通用建议，非公司制度”。

RAG 调试页和运行回放显示：各路候选及分数、子片段 Rerank 顺序、子到父映射、父片段合并与预算取舍原因、文档及索引版本、冲突/证据不足原因、最终回答及引用。普通员工回答只展示结果和必要引用，不暴露内部装配步骤。

## 6. 异常与发布边界

- 父片段缺失、子父版本不一致、原文位置无效或索引成员不匹配时，入库/索引验证失败；查询时不得退回到错误片段继续回答公司事实。
- Rerank 服务失败维持现有错误治理，不伪称已完成重排；不得以未经记录的降级结果覆盖原运行事实。
- 新索引先构建并验证，Java 再发布索引版本，最后把智能客服 Agent Release 绑定到新索引。失败时保留既有活动版本，不修改历史运行快照。
- Prompt 与 RAG 策略继续从版本化配置加载；本改造不把可变规则写死在代码中。

## 7. 验收

建立带人工标准依据的公司真实问题集，覆盖制度、流程、产品、技术、长条款、跨页表格、同文档多子命中、旧版本、跨文档冲突和无答案。每题固定应命中的文档版本、父片段、关键事实和允许的回答模式。

先在旧索引记录基线，再使用新索引经 Java → Agent 真实接口逐题运行；核对 RAG 调试记录、回放、最终引用和服务日志。分别统计子片段 Recall@K、正确父片段召回、完整条款保留、引用支持、冲突/无答案误答、延迟和错误。遇到错误或不符合产品要求的结果，定位到解析、检索、装配、充分性或生成阶段，修复后重跑相应真实样本。自动指标用于筛查，关键制度问题以人工核验为准；不能把单条成功或仅有引用当成总体达标。

本设计不声明新能力已经实现，也不把已有一次真实问答通过等同于新索引验收通过。
