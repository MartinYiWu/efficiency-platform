## 布局与交互

平台聊天路由使用统一可视高度分配导航、助手导航和聊天主体；中间容器允许收缩。客服页历史、消息分别独立滚动；标题和输入区不收缩，不使用覆盖全视口的 fixed 输入框。移动端考虑动态可视高度与矮窗口，多行输入有最大高度。

用户发送后跟随最新消息；用户向上阅读则暂停跟随，提供回到最新入口，不对每段执行平滑动画。既有管理页布局不变。通用回答保留明确的非公司制度标识，避免标签、警告框重复。

## 决策契约

现有五种回答模式不变。先按问题与历史识别意图，需公司知识时执行真实检索与核验。充分性判断输出 sufficient、supported_claims、unsupported_claims、conflicts、recommended_mode，并增加：

| 字段 | 类型与默认值 | 含义 |
|---|---|---|
| evidence_status | 可选枚举，默认空 | SUFFICIENT 全覆盖；PARTIAL 部分覆盖；NO_RELEVANT_EVIDENCE 无相关依据；CONFLICT 冲突 |
| general_advice_allowed | boolean，默认 false | 是否允许在不冒充公司规定的前提下补充一般方法 |
| general_advice_scope | string[]，默认空 | 允许补充的具体范围 |
| company_specific_unknowns | string[]，默认空 | 本题无法确认且不得猜测的公司专属事项 |

旧 Prompt 缺少新字段时保持原有边界，不自动扩大权限。无相关依据进入既有充分性调用，判断能否提供一般流程、材料准备或确认方向；不另加固定决策模型调用。检索失败不是无命中；资料冲突、预算与引用守卫不得绕过。

公司知识只能来自本次直接证据。部分有依据并允许补充时使用 MIXED；无公司依据且允许一般帮助时使用 GENERAL_ADVICE；证据充分时正常公司回答。人员、内部入口、金额与期限等未知值不能按一般惯例填充。历史通用建议不能升级为公司依据。

## 答案与流式

结构化答案增加可选 knowledge_gap，说明当前可用资料未能确认的部分，不断言公司没有制度。正常回答顺序为 knowledge_gap、company_sections、general_advice。数据库 Prompt 要求显式输出 knowledge_gap（无缺口为 null），以保证前缀可以增量验证。

通用标题固定“通用建议，非公司制度”；公司段落绑定有效 supporting_chunk_ids，通用内容不带公司引用。完整段落增量解析后释放，支持字符串转义、Unicode、重复数据块与分块边界，最终渲染必须与已发出块前缀一致。不存在结束后拆段冒充模型实时输出的验收。

公开事件沿用 run.progress/message.delta/citation.ready/run.completed/run.failed。仅展示实际执行阶段，不展示推理过程。失败保留已输出部分但不发成功结束。首进展与首答案分别计时。

## Prompt 与回放

意图、充分性、公司、通用、混合与修复 Prompt 均经现有数据库管理接口创建新版本并绑定 Release，保持其余配置绑定。角色与字段定义明确；不可信变量只进入 USER。保留证据范围系统消息与原文节选边界。

内部检索快照持久化决策与实际回答结果。生产流式结束前发送携带既有 retrieval_facts 的内部快照事件，使 Java 运行回放保存真实依据；员工事件不泄露内部结构。Java Sufficiency DTO 与前端严格 schema 同步新增字段，保持旧数据兼容；调试/回放展示补充范围与公司专属未知项。

本轮不接入公开搜索，不声称已查询公开资料，不新增依赖、服务、业务表或 DDL。真实验证使用现有模型、数据库、知识索引和接口；故障与组件测试证据分开记录。
