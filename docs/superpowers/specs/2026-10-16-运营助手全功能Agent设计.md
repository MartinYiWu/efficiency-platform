# 运营助手全功能 Agent 设计

> 状态：已确认，待实施计划
>
> 范围：运营助手八个场景；Java、前端、Agent、真实基础设施及真实验收
>
> 日期：2026-10-16

## 1. 目标与边界

运营助手是一个由 LLM 主导规划、检索决策、研究综合与内容创作的 Agent，不是关键词路由器或固定模板生成器。程序负责提供工具、保存状态、控制预算、验证事实边界、渲染制品和向前端投影运行状态。

本期完成以下八个场景：

1. 行业热点研究；
2. 多平台内容创作；
3. 品牌运营方案；
4. IP 运营方案；
5. 活动运营方案；
6. 内容日历；
7. 增长实验；
8. 运营数据复盘。

内容修改是既有研究、文章或方案上的 `revise` 动作，不是第九个独立场景。平台内容包含微信公众号、小红书和今日头条。系统只生成、预览、复制和下载内容，不自动发布到任何平台。

## 2. Agent 总体结构

```text
用户消息 + 会话状态 + 可引用制品
  -> Intent & Planning Agent
  -> Tool / Research Agent Loop
  -> Scenario Specialist Agent
  -> Deterministic Guardrails and Renderer
  -> Java artifact/message/run projection
  -> Frontend SSE and artifact view
```

每个 Run 的 LLM 主导步骤由 `Intent & Planning Agent` 先产出结构化计划。该 Agent 可选择复用上轮制品、请求一次澄清、执行研究工具、调用某一场景专家或执行已有制品修改。它不直接持久化最终业务状态，也不能绕过 Java 服务。

### 2.1 意图与计划契约

```json
{
  "primary_scenario": "industry_digest | content_creation | brand_plan | ip_plan | campaign_plan | content_calendar | growth_experiment | operation_review",
  "action_mode": "new | refresh | create | revise | analyze",
  "user_goal": "string",
  "topic": "string | null",
  "time_window": "string | null",
  "platform": "wechat_official_account | xiaohongshu | toutiao | null",
  "artifact_reference": {
    "kind": "latest_research | ranked_item | article | plan | review | none",
    "selector": "string | null"
  },
  "required_missing_fields": ["string"],
  "next_step": "execute | clarify",
  "clarification_question": "string | null"
}
```

模型负责自然语言理解、跨轮指代和计划选择。程序验证平台、时间窗、制品归属、条目序号、工具许可和字段枚举。`next_step=clarify` 时只能返回一个决定性问题，不能访问外部来源或启动专家。

## 3. 真实研究 Agent

研究场景由 LLM 依据用户目标决定主题、时间范围、需要的来源类别和后续动作。真实来源工具只访问批准的公开域名和适配器；每次抓取均生成来源记录、正文摘要、时间、来源健康及稳定来源 ID。

LLM Researcher 接收真实材料，决定保留、合并、排序和解释热点。它可输出 `continue_research` 并给出明确的信息缺口；每次运行最多一次补充检索，达到调用、时间或来源预算后必须综合已有证据或如实失败。模型不得自行虚构来源、热度、发布时间或事实。

研究结果内部保留 `EvidencePack`，其中每项包含 `hotspot_id`、已核验事实片段、来源 ID 和时间。用户默认只看到榜单结果；来源和内部运行数据仅在用户显式请求或内部审计时读取。

## 4. 内容编辑 Agent

内容 Agent 直接读取指定研究制品的真实材料，而不是由程序预写文章内容。LLM 负责选题主线、文章结构、热点组合、分析与表达；程序不以规则替代编辑判断。

LLM 必须返回 `ArticleDraft`，字段定义在 Prompt 和 JSON Schema 中同步声明：

```json
{
  "title": "读者可见标题",
  "editorial_thesis": "内部主线，不默认展示",
  "introduction": "导语",
  "sections": [
    {
      "hotspot_ids": ["研究结果中的真实 ID"],
      "heading": "章节标题",
      "facts": "仅改写允许事实",
      "analysis": "以事实为基础的判断",
      "operator_takeaway": "运营选题或观察建议",
      "supporting_source_ids": ["内部来源 ID"]
    }
  ],
  "closing": "收束",
  "hashtags": ["仅小红书或头条使用"]
}
```

Prompt 必须逐项定义字段语义、允许事实、禁止补造范围、平台读者、篇幅、格式和输出限制。公众号正文要求 3000 至 4000 个中文字符；模型先在内部规划标题、主线、段落分配和事实核对，再只输出 JSON。小红书和头条由同一真实材料独立创作，不能机械压缩公众号文章。

服务端根据 `ArticleDraft` 确定性渲染 Markdown 和微信安全富文本。用户不可见 `hotspot_id`、来源 ID、研究任务、引用闭包、版本、Prompt 或内部计划。校验失败时，仅允许一次把失败字段、实际计数及允许材料返回给模型定向修订；禁止重复全文重写。

## 5. 策略与复盘专家

八个场景共享意图、计划、预算、事实边界、SSE 和持久化机制，但各专家有独立工具及交付契约：

| 场景 | LLM 的主要职责 | 必需真实输入 | 交付物 |
| --- | --- | --- | --- |
| 品牌运营 | 定位、受众、内容支柱与阶段策略 | 品牌资料、目标、约束 | 品牌运营方案 |
| IP 运营 | IP 定位、受众洞察与孵化路径 | IP 资料、受众、周期 | IP 运营方案 |
| 活动运营 | 活动机制、节奏、渠道、风险与指标 | 活动目标、受众、时间窗 | 活动方案 |
| 内容日历 | 选题、渠道、频率和节奏安排 | 主题范围、时间窗、渠道约束 | 内容日历 |
| 增长实验 | 假设、漏斗、实验、指标和停止条件 | 增长目标、漏斗阶段、周期 | 实验 Backlog |
| 运营复盘 | 从指标识别变化、原因、证据缺口与下一步 | 真实运营数据及指标定义 | 复盘报告 |

缺少必要资料时，Agent 必须按计划契约澄清；运营复盘不得使用模型想象的业务指标。每个专家只能使用其获准的工具与输入制品。

## 6. Prompt 资产管理

Prompt 是 Agent 的运行时行为定义，不是一段单独的模板文本。所有可调整的 `system`、`developer`、`user`、`assistant` 和 `tool` 消息均从 Agent MySQL 读取；代码不得内置规划、研究、写作、修订、平台风格或数据隔离的自然语言指令。代码只提供消息角色类型、变量类型、工具执行、Schema 验证和安全校验。

### 6.1 数据模型

`agent_prompt_set` 定义一个可调用的 Prompt 能力，不存放具体消息：

| 字段 | 含义 |
| --- | --- |
| `id`、`prompt_key` | 主键及稳定业务键，例如 `content.wechat.draft` |
| `name`、`description` | 运营人员可理解的名称和用途 |
| `scenario`、`stage` | 所属八个场景及 Agent 阶段，例如 `intent.plan`、`research.reflect` |
| `input_schema_version`、`output_schema_version` | 输入上下文和结构化输出的兼容版本 |
| `active_version_id` | 当前已发布版本 |
| `created_at`、`updated_at` | 审计字段 |

`agent_prompt_version` 定义一次完整可回滚发布：

| 字段 | 含义 |
| --- | --- |
| `id`、`prompt_set_id`、`version` | 一组 Prompt 消息的唯一版本 |
| `status` | `draft`、`validated`、`active`、`retired` |
| `model_policy` | 模型、温度、最大输出 Token、超时和工具调用上限 |
| `output_schema` | 本版本要求的 JSON Schema；与代码验证的契约版本匹配 |
| `allowed_variables` | 允许渲染的变量名、类型、敏感级别和最大长度 |
| `checksum` | 对版本元数据及全部消息按顺序计算的校验和 |
| `change_summary`、`created_by`、`created_at`、`published_at`、`supersedes_version_id` | 变更、审计及回滚链路 |

`agent_prompt_message` 存放实际消息，按 `ordinal` 严格排序：

| 字段 | 含义 |
| --- | --- |
| `id`、`prompt_version_id`、`ordinal` | 归属版本和消息顺序 |
| `role` | `system`、`developer`、`user`、`assistant` 或 `tool` |
| `message_key` | 稳定名称，例如 `agent_role`、`writing_rules`、`research_context` |
| `template` | 该角色要发送给模型的模板正文 |
| `required_variables` | 本消息实际使用的变量及类型 |
| `is_trusted_instruction` | 仅允许 `system`/`developer` 消息为真；用于发布校验 |
| `checksum` | 单条消息内容校验和 |

`agent_prompt_test_case` 保存每个版本的输入样例、预期结构、禁止字段和人工评语；`agent_prompt_release_snapshot` 保存 Run 和阶段实际采用的 `prompt_set`、`version`、消息校验和、模型策略与渲染后的消息校验和。正文不写入普通日志；审计读取受限于 Agent 内部权限。

### 6.2 运行时渲染

以公众号写作为例，运行时会按数据库顺序读取一组消息：

1. `system`：编辑 Agent 身份、事实边界、不可捏造和最终结构要求；
2. `developer`：字段语义、平台规范、长度目标、定向修订规则和工具使用规则；
3. `user`：用户的实际目标、语气和显式约束；
4. `tool`：真实研究工具返回的来源、热点和事实材料；
5. `assistant`：仅在修订阶段保存上轮结构化草稿；
6. `user`：仅在修订阶段保存验证错误及允许修订范围。

不同场景使用不同 Prompt Set：`intent.plan`、`research.plan`、`research.synthesize`、`research.reflect`、`content.wechat.draft`、`content.xiaohongshu.draft`、`content.toutiao.draft`、`content.revise`、`brand.plan`、`ip.plan`、`campaign.plan`、`calendar.plan`、`growth.plan`、`review.analyze` 及对应 `repair` Set。

变量必须由代码按类型注入，不能由网页正文、用户消息或历史文章拼接成 `system`/`developer` 指令。真实网页和用户输入只能渲染进指定 `user`/`tool` 消息的值位置；未绑定变量、越长内容、未知变量、角色错位或渲染后仍有占位符均阻断调用。

### 6.3 发布、回滚与故障策略

发布新版本必须依次通过：所有消息角色与顺序校验、变量白名单渲染、输入/输出 Schema 兼容校验、工具权限校验、禁止占位符检查、目标场景离线回归，以及一条真实模型调用的人工审阅。`active_version_id` 的切换是一次数据库事务；失败不能覆盖既有 active 版本。

运行创建时，Agent 解析本 Run 需要的所有 active Prompt Version 并写入 `agent_prompt_release_snapshot`。运行中的阶段只能使用自身快照，即使之后发布新版本也不得改变该 Run。回滚只切换 `active_version_id` 到已验证的旧版本；新 Run 使用回滚后的版本，旧 Run 保持原快照。

数据库不可用且没有已冻结的 Run 快照时，新 Run 以 `PROMPT_CONFIGURATION_UNAVAILABLE` 失败，不调用模型，也不悄悄退回代码内旧 Prompt。每次模型调用记录 `prompt_key`、`version`、消息校验和和模型策略，但普通日志不记录完整 Prompt 或敏感变量值。

## 7. 状态、数据与三端边界

- Java 是会话、用户消息、运行、制品、最终状态与开发身份的唯一业务真相源；
- Agent MySQL 保存检查点、计划、工具调用、证据、模型预算及中间状态；
- pgvector 保存 Agent 可检索的文档和向量；
- Redis 仅保存取消、限流和短期 SSE 协调状态；
- 前端只调用 Java `/api/operations/**`，不直连 Agent；
- Java 固定注入开发身份，客户端不能覆盖；
- Agent 重启后必须通过已持久化的研究快照恢复跨轮创作；
- 取消、幂等、断线重连和迟到事件不得篡改终态。

## 8. 预算、失败与可观测性

每次 Run 至少记录计划、模型调用次数、工具调用、来源数量、耗时、失败阶段及关联 ID。默认预算为：一次意图与计划、一次研究综合、最多一次补充研究、一次专家生成、最多一次定向修订。达到预算时必须交付已有合格结果、返回 `PARTIAL`，或明确失败；不得无限反思或重写。

日志记录阶段、Run ID、工具类型、来源数、字符计数、校验摘要和安全错误码，不记录密钥、Cookie、完整 Prompt、完整网页正文或用户敏感数据。

## 9. 真实验收

所有功能从 Java 公共接口发起，经过真实 Agent、真实数据库、真实 Redis、真实公开来源和真实模型。测试、Mock、fixture、编译和静态检查仅作开发辅助。

验收分为：

1. 意图识别：八类场景、跨轮引用、修改、刷新、歧义澄清及越权引用拒绝；
2. 研究：真实来源、LLM 研究综合、来源不足、补充检索、预算终止与证据闭包；
3. 内容：公众号、小红书、头条、跨轮创作、指定条目、定向修订、事实与长度校验；
4. 策略：品牌、IP、活动、日历、增长、复盘的真实输入与结果语义检查；
5. 运行：幂等、取消、SSE 重连、Agent 重启恢复、历史与制品读取；
6. 浏览器：前端只经 Java、刷新恢复、预览、复制、下载、控制台和网络无未处理错误。

每次真实验收都保存 HTTP/SSE、数据库只读查询、Java/Agent 日志扫描、真实结果摘要和失败根因。任一接口、状态、数据、日志或语义不符合预期时，场景判定失败，不得伪造通过。

Prompt 验收另行验证：数据库 active Prompt 版本被真实 Run 使用；Run 保存的版本与实际模型调用一致；发布新版本只影响新 Run；旧 Run 可按快照重放；无 active Prompt 时稳定失败且不调用模型。
