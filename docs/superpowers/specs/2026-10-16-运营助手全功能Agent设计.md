## 1. 产品目标与已确认边界

运营助手是一个由 LLM 主导意图理解、任务规划、工具选择、资料研究、内容组织和专业产出的 Agent。程序不替代 LLM 做编辑判断，而是负责权限、状态、工具执行、预算、数据持久化、结构校验、事实闭包和确定性渲染。

本期必须完整交付八个业务场景：

1. 行业热点研究；
2. 多平台内容创作；
3. 品牌运营方案；
4. IP 运营方案；
5. 活动运营方案；
6. 内容日历；
7. 增长实验；
8. 运营数据复盘。

以下能力是控制动作，不作为新的业务场景：

- `revise`：修改已有研究、文章或方案；
- `refresh`：重新获取时效性数据并生成新版本；
- `clarify`：缺少决定性输入时只追问一个问题；
- `general_chat`：回答与运营任务无关的普通对话，不创建业务制品。

内容平台包含微信公众号、小红书和今日头条。系统只生成、预览、复制和下载内容，不调用任何平台的发布接口，不自动发送或定时发布。本期不实现登录、注册、JWT、平台账号授权和多租户计费；所有开发请求由 Java 服务端注入固定开发身份。

每份研究、文章和方案必须在内部记录来源研究任务、使用的热点或数据条目、引用闭包、Prompt 版本、模型策略和制品版本，但这些内部元数据不得出现在默认聊天回复中，用户只看到可直接使用的结果。

## 2. 设计原则

1. **先识别意图，再选择场景**：任何业务消息都先经过 Intent & Planning Agent，不使用关键词硬路由替代语义理解。
2. **按场景和阶段加载 Prompt**：不存在万能 Prompt。编排代码决定稳定的 `prompt_key`，数据库决定该 Prompt 当前发布的多角色消息内容。
3. **使用模型原生消息角色**：`system`、`developer`、`user`、`assistant`、`tool` 在内部保持独立，最终由 Provider Adapter 按目标模型能力映射。
4. **LLM 做认知工作**：主题拆解、研究缺口、证据综合、文章主线和策略判断交给模型；程序只做确定性约束和数据处理。
5. **真实数据先于生成**：需要时效事实、热点或业务指标的场景必须先取得真实数据，不能让模型用训练记忆补造。
6. **输出契约与 Prompt 分离**：字段结构由版本化 JSON Schema 约束，字段语义同时在对应 Prompt 中明确说明；模型参数也独立管理。
7. **有界 Agent 循环**：允许规划、工具调用、反思和一次定向修订，但必须受调用次数、时间、来源和 Token 预算限制。
8. **失败优于伪造成功**：来源不足、模型超时、Prompt 缺失、Schema 不合法或证据不闭合时返回明确失败或部分完成。
9. **真实验收是完成门槛**：Mock、测试类、静态检查和编译只能辅助开发，不能代替真实接口、真实数据库、真实模型、真实来源和日志验证。

## 4. 总体架构与职责

```text
Browser
  -> Java Operations API
       -> Java conversation/message/run/artifact transaction
       -> Agent API
            -> Intent & Planning Agent
            -> Scenario Orchestrator
                 -> Prompt Resolver + Prompt Assembler
                 -> Research / Data Tool Loop
                 -> Scenario Specialist Agent
                 -> Output Validator + one Repair pass
                 -> Renderer
            -> Agent MySQL checkpoint/audit
            -> PostgreSQL + pgvector retrieval
            -> Redis cancellation/stream coordination
       <- Agent SSE
  <- Java-projected SSE + persisted artifacts
```

### 4.1 前端

前端只调用 Java `/api/operations/**`，负责：

- 会话和历史消息展示；
- 用户输入和 `clientRequestId`；
- SSE 阶段进度、断线续接和取消；
- 澄清问题展示；
- 最终结果、Markdown、微信富文本预览、复制和下载；
- 失败、部分完成和重试入口。

前端不选择内部 Prompt、不拼接模型上下文、不直连 Agent、MySQL、Redis 或向量库，也不显示研究任务 ID、来源 ID、引用闭包、Prompt 版本和内部计划。

### 4.2 Java

Java 是用户可见业务数据的唯一真相源，负责：

- 固定开发身份注入和数据归属；
- 会话、消息、Run、Artifact 及版本持久化；
- 以 `developerUserId + conversationId + clientRequestId` 保证提交幂等；
- 调用 Agent、消费 Agent SSE、投影公开事件；
- 拒绝迟到事件覆盖终态；
- 返回历史、结果、预览、复制和下载内容。

Java 不负责写 Prompt、不生成运营内容、不自行研究和排序热点。

### 4.3 Agent

Agent 负责：

- 意图识别、计划、场景和动作选择；
- 对话引用解析与候选制品选择；
- Prompt 解析、版本冻结和多角色消息装配；
- 模型调用、工具调用和预算控制；
- 研究证据、业务数据和中间状态管理；
- 八场景专业产出；
- Schema、事实闭包、篇幅和结构校验；
- 一次定向修订和确定性渲染；
- 可恢复检查点、内部审计和运行日志。

### 4.4 基础设施

- Agent MySQL：使用真实数据库 `ai_efficiency_platform_agent`，保存 Prompt 资产、检查点、计划、工具调用、证据、模型用量和中间状态。
- PostgreSQL + pgvector：使用真实数据库 `vector`，保存可检索文档、Chunk、Embedding 和向量索引。
- Redis：保存取消标志、限流和短期 SSE 协调数据，不保存唯一业务事实。
- 外部模型和数据源：直接使用已经配置的真实接口。开发阶段允许凭据保存在配置文件中，但日志、接口响应和提交说明不得打印凭据。

## 5. Run 状态机与执行主链路

### 5.1 状态机

```text
PENDING
  -> INTENT_PLANNING
       -> CLARIFYING -> SUCCEEDED
       -> PREPARING
            -> RESEARCHING / DATA_LOADING
            -> GENERATING
            -> VALIDATING
                 -> REPAIRING -> VALIDATING
                 -> RENDERING
            -> SUCCEEDED / PARTIAL
  -> FAILED / TIMED_OUT / CANCELLED
```

Java 对外稳定状态为 `PENDING`、`RUNNING`、`PARTIAL`、`SUCCEEDED`、`FAILED`、`TIMED_OUT`、`CANCELLED`；Agent 阶段状态通过进度事件呈现，不扩大 Java 终态枚举。

### 5.2 主链路

1. Java 在同一事务中保存用户消息和 `PENDING` Run。
2. Java 将 Run、当前消息、允许读取的会话与制品引用传给 Agent。
3. Agent 加载并冻结 `intent.plan` Prompt 版本，组装多角色消息并调用模型。
4. Intent & Planning Agent 输出结构化意图；程序校验场景、动作、制品归属和缺失字段。
5. 需要澄清时只生成一个问题并结束本 Run，不执行研究和内容生成。
6. Scenario Orchestrator 根据已验证的场景、阶段和平台解析稳定 `prompt_key`。
7. 需要真实资料时进入工具循环；不需要时直接读取合法的历史制品或业务输入。
8. 场景专家加载对应 Prompt，接收真实材料并生成结构化结果。
9. 程序执行 Schema、引用、事实、结构和篇幅校验；失败时最多进行一次定向修订。
10. Renderer 生成用户可见 Markdown 或安全 HTML，Agent 通过 SSE 返回结果。
11. Java 校验最终契约并持久化消息、Artifact 和终态。

## 6. Intent & Planning Agent

### 6.1 输入

Intent Agent 只接收完成判断所需的上下文：

- 当前用户原文；
- 有界的可见对话历史；
- 当前会话可引用制品的类型、标题、顺序和稳定 ID；
- 当前日期和时区；
- 八个场景及控制动作的能力描述。

隐藏思维链、内部日志、其他用户制品和未授权原始网页不得进入上下文。

### 6.2 输出契约

```json
{
  "contract_version": "intent-plan/1",
  "route_kind": "operation | general_chat",
  "primary_scenario": "industry_digest | multi_platform_content | brand_plan | ip_plan | campaign_plan | content_calendar | growth_experiment | operation_review | null",
  "action_mode": "new | refresh | create | revise | analyze | chat",
  "user_goal": "string",
  "requirements": {
    "topic": "string | null",
    "time_window": "string | null",
    "platforms": ["wechat_official_account | xiaohongshu | toutiao"],
    "requested_count": "integer | null",
    "constraints": ["string"]
  },
  "artifact_reference": {
    "kind": "latest_research | ranked_item | article | plan | review | none",
    "selector": "string | null"
  },
  "required_missing_fields": ["string"],
  "next_step": "execute | clarify | answer",
  "clarification_question": "string | null",
  "planned_capabilities": ["research | retrieve_artifact | compose | revise | analyze"],
  "confidence": 0.0
}
```

字段语义：

- `route_kind`：区分普通对话和运营任务，普通对话不创建业务 Artifact。
- `primary_scenario`：八个场景之一；控制动作不能伪装成第九个场景。
- `action_mode`：决定创建、刷新、修改、分析或普通回答。
- `requirements`：从用户输入提取的场景参数，不允许模型补造未提供的业务数据。
- `artifact_reference`：模型只解释“刚才那篇”“第 3 条”等自然语言指代，程序负责解析并校验归属。
- `required_missing_fields`：只有缺失后会导致结果根本不同的字段才进入该数组。
- `planned_capabilities`：模型提出需要的能力，不直接指定具体函数、Prompt 版本或越权工具。
- `confidence`：用于低置信度门禁，不作为向用户展示的结论。

### 6.3 澄清规则

- 一次只问一个决定性问题；
- 可从历史或已选制品确定的字段不得重复询问；
- 澄清 Run 不调用外部模型以外的研究工具，不产生伪制品；
- 用户回答后创建新 Run，并重新执行意图规划。

## 7. 场景 Prompt 加载与多角色装配

### 7.1 核心原则

完整 Prompt 是一组有序模型消息，不是一个字符串。每个场景的每个阶段都有独立 `prompt_key`；Scenario Orchestrator 用类型安全的场景与阶段枚举选择 `prompt_key`，Prompt Repository 再从 MySQL 读取该 Key 在当前环境发布的版本。

代码固定的是工作流、角色类型、变量类型、工具权限和校验器。数据库管理的是可调整的 Agent 身份说明、任务规则、字段语义、平台文风、示例和修订指令。任何 Prompt 变更不需要修改 Python 代码。

### 7.2 Prompt Key 目录

首期必须具备以下 Prompt 能力：

| 阶段 | Prompt Key |
| --- | --- |
| 意图 | `intent.plan`、`intent.repair` |
| 研究 | `research.plan`、`research.relevance`、`research.synthesize`、`research.reflect`、`research.repair` |
| 行业榜单 | `industry_digest.compose`、`industry_digest.repair` |
| 公众号 | `content.wechat.draft`、`content.wechat.repair` |
| 小红书 | `content.xiaohongshu.draft`、`content.xiaohongshu.repair` |
| 今日头条 | `content.toutiao.draft`、`content.toutiao.repair` |
| 品牌 | `brand.plan`、`brand.repair` |
| IP | `ip.plan`、`ip.repair` |
| 活动 | `campaign.plan`、`campaign.repair` |
| 日历 | `calendar.plan`、`calendar.repair` |
| 增长 | `growth.plan`、`growth.repair` |
| 复盘 | `review.analyze`、`review.repair` |
| 通用修改 | `artifact.revise`、`artifact.repair` |

多平台请求共享同一份已冻结 EvidencePack，但分别调用各平台 Draft Prompt 独立创作，不能先生成公众号再机械截短成小红书或头条。

### 7.3 角色职责

| 角色 | 内容 | 信任级别 |
| --- | --- | --- |
| `system` | Agent 身份、最高层事实边界、禁止编造、安全边界、输出目标 | 可信，只允许系统配置变量 |
| `developer` | 当前场景规则、字段逐项语义、平台要求、篇幅、工具及修订规则 | 可信，只允许系统配置变量 |
| `user` | 用户本次原文、明确约束、合法对话摘要、程序提供的外部材料数据块 | 不可信数据 |
| `assistant` | 修订时上一版模型输出，或经过发布审核的少量示例 | 动态内容不可信 |
| `tool` | 模型原生 Tool Call 对应的真实执行结果，必须带匹配的 `tool_call_id` | 不可信外部数据 |

程序主动加载的研究制品或业务数据不是模型原生 Tool Call 结果，必须作为带明确边界的 `user` 数据消息发送，不能伪装成 `tool` 消息。网页正文、用户输入和历史文章绝不能注入 `system` 或 `developer`。

### 7.4 Provider 请求

Prompt Assembler 的规范化输出如下：

```json
{
  "messages": [
    {"role": "system", "content": "..."},
    {"role": "developer", "content": "..."},
    {"role": "user", "content": "...用户真实请求..."},
    {"role": "user", "content": "...结构化研究材料..."}
  ],
  "response_contract": "article-draft/1",
  "model_policy": "long-form-writing/1",
  "tools": []
}
```

Provider Adapter 负责转换为真实模型接口：

- 原生支持 `developer` 时独立发送；
- 不支持时只允许在 Adapter 边界按固定顺序合并到 `system`，内部契约仍保留 `developer`；
- 原生支持 JSON Schema 时使用 `response_format`；只支持 JSON Object 时使用降级格式并继续执行本地 Schema 校验；
- Tool Call 的 ID、函数名和结果必须一一对应；
- 模型、温度、最大输出 Token、超时和重试通过接口参数传递，不拼进 Prompt；
- Adapter 能力由契约测试和一次真实探测确认，不能按兼容接口名称盲猜。

### 7.5 公众号 Draft Prompt 最低内容

`content.wechat.draft` 至少包含：

- `system`：公众号运营编辑身份、只能使用输入材料、事实和分析必须区分；
- `developer`：目标读者、文章目的、标题、导语、正文、收束、3000 至 4000 中文字符、结构字段逐项定义、禁止输出内部 ID；
- `user`：用户原始要求与语气；
- `user`：已冻结 EvidencePack 的可用事实、时间和来源摘要；
- `response_format`：`ArticleDraftV1` JSON Schema。

模型应先在内部完成主题、段落和篇幅分配，但只返回契约结果，不要求或存储思维链。篇幅要求必须在首次生成 Prompt 中明确；程序仍需按最终渲染后的中文字符数验证，因为 Prompt 约束不能替代确定性验收。

## 8. Prompt 数据模型与发布

### 8.1 表结构职责

#### `agent_prompt_definition`

定义稳定能力，不存放正文：

| 字段 | 含义 |
| --- | --- |
| `id` | 主键 |
| `prompt_key` | 唯一稳定键，如 `content.wechat.draft` |
| `scenario`、`stage`、`platform` | 所属场景、阶段和可选平台 |
| `name`、`description` | 名称与用途 |
| `enabled` | 是否允许发布和新 Run 使用 |
| `created_at`、`updated_at` | 审计时间 |

#### `agent_prompt_version`

定义不可变版本及其依赖引用：

| 字段 | 含义 |
| --- | --- |
| `id`、`prompt_definition_id`、`semantic_version` | Prompt 版本唯一标识 |
| `status` | `draft`、`validated`、`released`、`retired` |
| `model_policy_id` | 引用独立模型策略 |
| `output_contract_id` | 引用独立输出契约 |
| `checksum` | 版本元数据和全部有序消息的摘要 |
| `change_summary`、`created_by`、`created_at` | 变更审计 |
| `supersedes_version_id` | 被替代版本 |

版本发布后消息和变量不可原地修改；修改必须创建新版本。

#### `agent_prompt_message_template`

每行是一条独立角色消息：

| 字段 | 含义 |
| --- | --- |
| `id`、`prompt_version_id` | 主键和版本归属 |
| `ordinal` | 严格递增顺序 |
| `role` | `system`、`developer`、`user` 或作为已审核少样本示例的 `assistant` |
| `message_key` | 版本内唯一稳定名称 |
| `content_template` | 消息模板正文 |
| `content_format` | `text` 或 `json` |
| `trusted_instruction` | 只允许静态 `system`/`developer` 为真 |
| `checksum` | 单条消息摘要 |

唯一约束：`(prompt_version_id, ordinal)` 和 `(prompt_version_id, message_key)`。

`tool` 消息不属于静态 Prompt 模板，不能预先写入该表。它只能由一次真实 Tool Call 的执行结果在运行时创建，并与模型返回的 `tool_call_id` 绑定。修订时的上一版 `assistant` 结果同样是运行时消息；只有发布版本中经过审核的少样本示例才作为 `assistant` 模板保存。

#### `agent_prompt_variable`

变量定义必须独立，不使用 `allowed_variables` JSON：

| 字段 | 含义 |
| --- | --- |
| `id`、`prompt_message_template_id` | 主键和消息归属 |
| `variable_name` | 模板变量名 |
| `value_type` | `string`、`integer`、`boolean`、`json`、`string_list` |
| `value_source` | `system_context`、`user_input`、`conversation`、`artifact`、`tool_result`、`validation_error` |
| `required` | 是否必填 |
| `sensitive` | 是否敏感 |
| `max_length` | 渲染上限 |
| `allow_untrusted_content` | 是否允许用户或外部内容 |

`system` 和 `developer` 消息的变量只能来自 `system_context`，且 `allow_untrusted_content=false`。

#### `agent_model_policy`

独立保存 Provider、模型、温度、Top-P、最大输入/输出 Token、连接与读取超时、重试次数、工具循环次数和预算。多个 Prompt 版本可以复用同一策略。

#### `agent_output_contract`

独立保存 `contract_key`、语义版本、JSON Schema、字段说明摘要和 checksum。代码中的强类型 DTO/Pydantic 模型必须声明支持的契约版本，发布时校验兼容性。

#### `agent_prompt_release`

保存 `environment + prompt_definition_id -> prompt_version_id` 的当前发布映射、发布时间和发布人。同一环境同一 Prompt Key 只有一个 active release，切换必须在单个事务中完成。

#### `agent_run_prompt_snapshot`

每个 Run 的每个阶段首次执行前记录实际版本、消息 checksum、模型策略、输出契约、变量值摘要及引用数据快照 ID。Run 内重试和恢复只能使用快照，不受之后发布影响。

#### `agent_prompt_test_case`

保存发布前输入样例、预期契约、禁止字段和人工评语，只用于 Prompt 发布门禁，不作为真实业务验收结果。

### 8.2 PromptAssembler

装配器按以下顺序工作：

1. 根据 `prompt_key + environment` 读取 release；
2. Run 已有快照时强制读取快照版本；
3. 读取版本、消息、变量、模型策略和输出契约；
4. 校验版本状态及代码支持的契约版本；
5. 按 `ordinal` 渲染消息，并对每个变量执行类型、来源、长度和信任校验；
6. 拒绝未知变量、缺失变量、残留占位符、角色错位和超长消息；
7. 生成规范化消息数组、工具 Schema、模型参数和响应 Schema；
8. 写入快照与 checksum 后才允许调用模型。

数据库不可用、没有 active release 或快照不完整时，新 Run 必须以 `PROMPT_CONFIGURATION_UNAVAILABLE` 失败，不能静默退回代码模板。

### 8.3 发布与回滚

发布必须通过：消息顺序和角色校验、变量来源校验、Schema 兼容性、Provider 能力、Prompt 样例回归及至少一次真实模型调用人工审阅。发布只改变新 Run；进行中的 Run 继续使用快照。回滚是将 release 切回已经验证的旧版本，不修改历史版本。

## 9. 研究与真实数据 Agent

### 9.1 研究循环

```text
Research Planner
  -> search/fetch/feed/vector tools
  -> source normalization and deduplication
  -> relevance and claim extraction
  -> Research Synthesizer
  -> Reflect: enough / one supplement / partial / fail
  -> EvidencePack
```

LLM 决定研究问题、关键词、来源类别、信息缺口、热点合并和运营意义。程序负责工具权限、URL 安全、抓取限制、去重键、时间窗、上下文裁剪和 ID 稳定性，不在代码中预写研究结论。

Tool Loop 使用模型原生 Tool Call：模型选择已授权工具，Orchestrator 校验参数和预算，执行工具后以匹配 `tool_call_id` 的 `tool` 消息返回真实结果。每轮模型必须选择继续调用工具或完成研究，不允许程序伪造 Tool Call。

### 9.2 工具目录

- `search_public_web`：公开网页发现；
- `search_news_feed`：已配置 RSS/Feed 数据；
- `fetch_public_page`：抓取指定公开页面；
- `retrieve_vector_documents`：从 `vector` 检索已入库资料；
- `load_artifact`：读取当前会话合法制品；
- `load_operation_dataset`：读取用户明确提供或已接入的真实运营数据。

每个场景使用工具白名单。抓取工具必须限制协议、域名、DNS 解析、重定向、响应大小、内容类型和超时。

### 9.3 EvidencePack

```json
{
  "research_run_id": "string",
  "topic": "string",
  "time_window": "string",
  "sources": [
    {
      "source_id": "string",
      "url": "string",
      "title": "string",
      "publisher": "string",
      "published_at": "datetime | null",
      "retrieved_at": "datetime",
      "content_hash": "string"
    }
  ],
  "claims": [
    {
      "claim_id": "string",
      "statement": "string",
      "source_ids": ["string"],
      "evidence_excerpt": "string",
      "confidence": "high | medium | low"
    }
  ],
  "hotspots": [
    {
      "hotspot_id": "string",
      "title": "string",
      "summary": "string",
      "claim_ids": ["string"],
      "occurred_at": "datetime | null",
      "importance_reason": "string"
    }
  ],
  "gaps": ["string"],
  "status": "complete | partial"
}
```

来源数量、热度、发布日期和事实只能来自工具结果；无法证明时必须留空或标注缺口。原始正文可以直接提供给模型完成理解，但先经过格式清洗、重复移除和上下文预算打包；裁剪不能改变含义，也不能由程序编写替代性观点。

### 9.4 停止条件

- 已覆盖用户目标且关键结论有证据：完成；
- 存在明确关键缺口且未使用补充轮次：最多补充一次；
- 有效来源不足但仍可交付部分结果：`PARTIAL`；
- 无可用来源、全部工具失败或关键事实无法验证：失败；
- 达到模型、工具、时间、下载量或 Token 预算：停止，不无限研究。

- `refresh` 创建新的研究 Run 和 EvidencePack，不篡改旧研究；
- 修改后的结果重新执行原场景全部校验。

## 11. 校验、修订与渲染

### 11.1 确定性校验

程序至少验证：

- JSON Schema 和字段类型；
- 枚举、必填项和数组数量；
- 引用的 Claim、Hotspot、Artifact 是否存在且属于当前 Run/会话；
- 事实字段是否具有允许的引用闭包；
- 最终渲染后的中文字符数和平台结构；
- 禁止泄露的内部字段；
- HTML 安全、危险 URL、脚本和事件属性。

程序不以关键词规则重写观点、决定标题或替代 LLM 扩写正文。

### 11.2 一次定向修订

首次输出不合格时加载对应 Repair Prompt，消息包含：

- 原始目标和相同证据快照；
- 上一版结构化输出，作为 `assistant` 动态消息；
- 失败字段、实际值、目标值和允许修改范围，作为 `user` 消息；
- 原输出契约和模型策略。

只允许一次修订。仍不合格则失败或返回满足事实边界的 `PARTIAL`，不能连续全文重写直到碰巧通过。

### 11.3 渲染

结构化结果验证通过后才渲染：

- 行业榜单、方案、日历、实验和复盘渲染为稳定 Markdown；
- 公众号同时生成 Markdown 和经过净化的微信富文本；
- 小红书和头条生成平台化纯文本/Markdown；
- 字符计数基于最终用户可见正文，不采用模型自报值；
- Renderer 不补写内容，只负责转义、排版和去除内部字段。

## 12. 数据归属与持久化

### 12.1 Java MySQL

保存会话、用户/助手消息、Run、终态、Artifact、Artifact 版本、最终 Markdown/HTML、错误摘要和重试关系。Java 在 Agent 最终契约与终态合法后才保存成功结果。

### 12.2 Agent MySQL `ai_efficiency_platform_agent`

保存：

- Prompt 定义、版本、消息、变量、模型策略、输出契约、发布和 Run 快照；
- Agent Run、阶段检查点、意图计划和预算；
- 工具调用、来源尝试、来源健康和抓取元数据；
- Source、Claim、Hotspot、EvidencePack 及引用关系；
- 模型调用元数据、Token、耗时和错误；
- 场景中间结果及修订记录。

所有迁移必须是 MySQL 方言，包含唯一约束、索引和可重复执行边界。不得把现有 PostgreSQL Repository 仅替换连接串后直接当作 MySQL Repository。

### 12.3 PostgreSQL + pgvector `vector`

保存 Document、Chunk、Embedding 模型与版本、向量和检索元数据。向量库只通过 Agent 的 Retrieval Port 访问；Java 和前端不直连。

### 12.4 Redis

使用 `aiep:agent:` 和 `aiep:java:` 前缀保存短期取消、限流、SSE 协调和幂等辅助键。Redis 丢失不能导致 Java 业务事实或 Agent 持久检查点丢失。

## 13. 接口与 SSE 契约

### 13.1 浏览器到 Java

- `POST /api/operations/conversations`
- `POST /api/operations/conversations/{id}/messages`
- `GET /api/operations/conversations/{id}`
- `GET /api/operations/conversations/{id}/messages`
- `GET /api/operations/conversations/{id}/artifacts`
- `GET /api/operations/runs/{runId}`
- `GET /api/operations/runs/{runId}/events`
- `POST /api/operations/runs/{runId}/cancel`
- `GET /api/operations/artifacts/{id}`
- `GET /api/operations/artifacts/{id}/copy`
- `GET /api/operations/artifacts/{id}/download`
- `GET /api/operations/artifacts/{id}/wechat-html`

消息提交必须携带客户端生成的 `clientRequestId`；Java 不接受客户端传入的用户或租户身份覆盖服务端身份。

### 13.2 Java 到 Agent

复用 Agent 的 `/v1/conversations/{conversation_id}/messages`、Run 查询、事件和取消接口。内部请求至少携带 Java Run ID、会话 ID、消息 ID、当前消息、有限历史、允许的 Artifact 引用、时间与预算、固定身份上下文。Java 创建调用只在幂等保护下重试一次。

### 13.3 SSE

公开事件稳定为：

- `run.started`
- `run.progress`
- `message.delta`
- `clarification.required`
- `artifact.ready`
- `run.partial`
- `run.completed`
- `run.failed`
- `run.cancelled`

每个事件带 Run ID 和单调递增序号。前端通过 `Last-Event-ID` 或 `afterSequence` 续接；无法续接时读取 Java 已持久化状态，不重新创建 Run。公开事件不得包含 Prompt、原始网页、内部计划、密钥或内部来源 ID。

## 14. 失败、恢复和幂等

- 单个来源失败：记录失败并继续其他来源；
- 来源不足：返回实际数量和 `PARTIAL`，不凑数；
- 全部来源失败：明确失败，不让模型补造；
- 模型连接/读取超时：记录 Provider、阶段、耗时、请求 checksum 和错误类型，可按幂等策略有限重试；
- 模型输出错误：一次定向修订后仍失败则结束；
- Prompt 缺失或不兼容：调用模型前失败；
- 取消：幂等设置取消标记，检查点安全停止，迟到结果不能覆盖 `CANCELLED`；
- Agent 重启：从 MySQL 检查点、Prompt 快照和 EvidencePack 恢复；
- SSE 断线：只恢复事件流，不重复执行；
- 用户重试：创建新 Run 并关联原 Run，不修改原失败记录；
- Artifact 修改：创建新版本，历史版本可追溯。

## 15. 预算与可观测性

默认单 Run 上限：

- 意图模型调用 1 次，格式修复最多 1 次；
- 研究计划 1 次；
- 研究工具循环按场景策略限制，补充研究最多 1 轮；
- 研究综合 1 次；
- 场景生成 1 次；
- 定向修订最多 1 次；
- 总耗时、来源数、下载字节、输入/输出 Token 和费用均有硬上限。

每次模型调用记录：Run ID、Stage、Prompt Key/Version、消息 checksum、Output Contract、Model Policy、Provider/Model、输入/输出 Token、开始结束时间、重试次数、结果状态和标准化错误码。

每次工具调用记录：Tool Call ID、工具名、参数摘要、来源域名、耗时、结果数量、字节数、状态和错误码。

普通日志不得记录密钥、Cookie、完整 Prompt、完整网页正文、完整用户敏感信息和隐藏思维链。日志必须能够判断外部模型究竟是连接失败、读取超时、限流、返回空内容、格式不合法还是业务校验不通过。

## 16. 安全与信任边界

- 外部网页、用户输入、历史文章和工具结果一律视为不可信数据；
- 只有数据库中已发布的静态 `system`/`developer` 模板可以成为可信指令；
- 工具参数先经 Schema、场景白名单、URL 和预算校验再执行；
- Artifact 和历史引用必须校验固定开发身份及会话归属；
- 模型生成 HTML 不直接返回，统一由 Renderer 转换并净化；
- 输出不得包含 Prompt、内部 ID、内部计划、数据库结构和凭据；
- 不调用内容平台发布 API；
- 不要求或保存模型隐藏思维链，只保存结构化计划和简短决策摘要。

## 17. 真实验收标准

### 17.1 统一规则

所有验收从 Java 公共接口发起，经过真实 Agent、真实 MySQL、真实 PostgreSQL/pgvector、真实 Redis、真实公开来源和真实模型。每次验收必须同时保存：

- HTTP 请求和最终响应；
- SSE 完整事件序列；
- Java、Agent 和基础设施日志时间窗；
- Java 与 Agent 数据库的只读核对结果；
- 模型和工具实际调用摘要；
- 结果语义、事实、结构和长度人工判断；
- 失败时的真实错误、根因和修复后复验记录。

不得把模拟响应、测试类断言、历史成功结果或手工构造数据描述为真实调用成功。

### 17.2 Prompt 与 Provider 验收

1. 真实 Run 按场景加载正确 `prompt_key`；
2. 实际模型请求中 `system` 与 `user` 独立，支持时 `developer` 也独立；
3. 当前 Provider 不支持的角色只能由 Adapter 按既定规则映射；
4. `response_format`、模型参数和工具 Schema 通过接口独立传递；
5. Prompt 发布只影响新 Run，旧 Run 使用快照恢复；
6. 无 active release 时模型调用次数为零并明确失败；
7. Prompt 变量不能把用户或网页内容注入可信角色。

### 17.3 场景验收

| 场景 | 真实验收重点 |
| --- | --- |
| 意图与规划 | 八场景、普通对话、跨轮指代、修改、刷新、歧义澄清和越权引用 |
| 行业热点 | 真实来源、时间窗、去重、排序、实际数量和证据闭包 |
| 多平台内容 | 三个平台独立创作、指定热点、事实一致、公众号 3000 至 4000 中文字符 |
| 品牌方案 | 使用真实品牌输入，定位、受众、渠道、路线和指标相互一致 |
| IP 方案 | 不补造人物经历，定位、栏目、风格和成长路径完整 |
| 活动方案 | 机制、时间线、渠道、物料、指标、风险与真实约束一致 |
| 内容日历 | 日期、频率、平台、主题、CTA 和依赖可执行 |
| 增长实验 | 假设、变体、指标、护栏、停止和判定规则完整且不承诺虚假增幅 |
| 运营复盘 | 指标来自真实数据，事实、因果证据、假设和行动明确分层 |
| 运行能力 | 幂等、取消、超时、SSE 重连、Agent 重启、历史和 Artifact 恢复 |
| 浏览器 | 连续对话、澄清、进度、预览、复制、下载、刷新恢复及控制台/网络错误 |

任一接口报错、日志异常、终态错误、数据未持久化、结果不满足语义或事实要求时，该项验收失败。必须分析和修复后重新执行真实调用，不能修改验收口径掩盖问题。

## 18. 实施边界与顺序

详细文件级步骤由后续实施计划定义，但依赖顺序固定为：

1. Provider 多角色契约、Prompt MySQL 模型、Resolver、Assembler、发布与快照；
2. Intent & Planning Agent 及跨轮引用；
3. Research Tool Loop、EvidencePack 和真实来源闭包；
4. 行业热点和三平台内容生成；
5. 品牌、IP、活动、内容日历、增长实验和运营复盘；
6. Java 状态、Artifact/SSE 投影和前端完整交互；
7. 八场景真实接口、日志、数据库和浏览器验收；
8. 所有验收通过后再统一提交和推送 Java、前端、Agent、迁移、脚本和文档。

任何阶段不得以旧的单 `system` 模板继续扩展。迁移完成后，文件模板 Registry 只允许作为迁移输入，不作为运行时静默回退路径。

## 19. 非目标

本期不做：

- 自动或定时发布到微信公众号、小红书、头条或其他平台；
- 登录、注册、JWT、平台 OAuth 和权限后台；
- 商业付费热点数据源采购；
- 多租户计费、套餐和额度销售；
- Prompt 可视化管理后台；数据库迁移和发布脚本足以完成本期治理；
- 无界自治、多 Agent 并发扩散和模型自我修改 Prompt；
- 高可用集群和跨地域容灾。

## 20. 关键设计结论

1. Intent & Planning Agent 是所有业务消息的第一入口。
2. 每个场景、阶段和平台加载自己的 Prompt，不存在万能 Prompt。
3. Prompt 版本由多条独立角色消息组成，模型接口接收的是有序消息数组。
4. 用户输入、历史内容和真实数据只能进入不可信消息，不能进入 `system`/`developer`。
5. Model Policy 和 Output Contract 是独立资产，通过模型接口参数使用，不是 Prompt 正文列。
6. LLM 负责理解、研究、组织与写作；程序负责工具、安全、状态、证据、校验和渲染。
7. 八个场景全部交付并通过真实接口、真实数据和日志验收后，整个运营助手才算完成。
