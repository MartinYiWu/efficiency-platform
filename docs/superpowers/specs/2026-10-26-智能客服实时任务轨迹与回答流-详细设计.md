## 1. 目标与现状

用户提交问题后，应在同一条助手消息中尽快看到**真实执行中的任务轨迹**；公司知识回答仍以引用校验后的段落独立输出。进展可折叠、可恢复、可回放，不能充当答案，也不能把连接建立时间称为首段答案时间。

当前 Agent `graph.py` 在运行中形成阶段摘要，却由 `service.py` 的 `_publish_result` 等 Graph 完成后集中发布。Java `CustomerServiceEventProjector` 已把 Agent 事件映射为公开 `run.progress`、把事件写入 `ai_customer_service_run_step`；前端 `useCustomerServiceChat` 只保存最后一个全局 `stage/summary`，页面将它放在消息列表下方。正文 `answer.delta` 已按完整、有效引用的块提前发出；本设计保留该质量边界。

本次只改智能客服对话链路。不展示或保存 LLM 的 `reasoning_content`，不修改 Prompt、模型思考模式、RAG 召回策略、知识索引、评测用例，也不新增数据库表或迁移。

## 2. 员工界面

每次提交后，立即在本地助手气泡内显示“请求提交中”；这仅表示客户端已发请求。Java 提交成功且收到 Agent `run.started` 后，改为可展开的“处理过程”，默认展开，下面出现真实步骤：

1. 理解问题；
2. 查找公司资料；
3. 核对资料依据；
4. 撰写回答。

仅公司知识或混合问题执行第 2、3 步；通用问题和澄清问题不展示未执行的步骤。当前步骤显示“正在……”，完成步骤显示“……完成”。不显示百分比、猜测的文档数或模型未验证的事实。最后一条正文 `message.delta` 到达后，答案就在该气泡的处理过程下方按实际收到的块展示；引用按钮仍由 `citation.ready` 提供。完成后处理过程默认收起，用户可展开；失败或取消时保留真实已发生的步骤及终态，不把部分正文标为已完成答案。旧会话没有阶段事件时只显示原有答案，不补造步骤。

进展区域和最终答案区域分开存储与渲染。进展不写入 `ai_customer_service_message.content`，不进入后续对话历史，不作为引用或反馈的评价正文。现有气泡外全局状态行移除，状态归属于对应 `runId` 的助手消息。

## 3. 运行事件与顺序

继续使用 `customer-service-run-event/1`。`RunEventPayload` 增加可选 `phase: STARTED | COMPLETED`；旧事件缺少该字段时保持兼容。阶段键固定为 `intent`、`retrieval`、`verification`、`answer`。新的实时阶段事件只由程序发出，公开文案为固定映射，不拼接问题文本、检索片段、模型输出或内部异常。

| 内部事件 | 阶段与时机 | Java 公开事件 | 员工展示 |
|---|---|---|---|
| `run.accepted` | Agent 已接收运行 | `run.progress`，`accepted` | 请求已接收 |
| `run.started` | `intent/STARTED`，意图模型调用之前 | `run.started` | 正在理解问题 |
| `stage.completed` | `intent/COMPLETED`，意图结果已校验 | `run.progress` | 已理解问题 |
| `stage.started` / `stage.completed` | `retrieval`，检索调用前 / 检索链全部返回后 | `run.progress` | 正在查找公司资料 / 资料查找完成 |
| `stage.started` / `stage.completed` | `verification`，证据包与充分性判断前 / 判断后 | `run.progress` | 正在核对资料依据 / 依据核对完成 |
| `stage.started` | `answer`，调用回答生成前 | `run.progress` | 正在撰写回答 |
| `answer.delta` | 一个经过段落结构与引用 ID 校验的完整正文块 | `message.delta` | 追加到答案 |
| `citation.ready` | 最终引用冻结后 | `citation.ready` | 显示引用按钮 |
| `answer.completed` / `run.failed` / `run.cancelled` | 真实终态 | 原有终态事件 | 完成 / 失败 / 已停止 |

`verification/COMPLETED` 只表示检查已执行，**不预告**“证据充分”；证据不足由最终回答模式表达。跳过检索的意图不发 `retrieval` 或 `verification` 事件。失败时不补发未实际完成的阶段。`answer` 完成由 `run.completed` 表示，不单独制造重复阶段事件。事件的 `sequence` 继续由 Agent 对单个 Run 单调递增；`answer.delta`、引用和终态的既有顺序与内容保持不变。

Graph 接受可选同步回调 `on_stage(stage, phase)`。`run.started` 已覆盖 `intent/STARTED`；Graph 在每个真实边界调用其余阶段回调。`GraphResult.stage_summaries` 继续供 RAG 调试读取；实时运行不再把这些摘要在 `_publish_result` 中重复发送。原有不支持阶段回调的测试替身仍可走既有结果摘要路径。

## 4. Java 转发、存储与公开快照

`CustomerServiceRunEvent.Payload` 增加可选 `phase`，只接受上述两个值；`CustomerServiceEventProjector` 只公开已知阶段和固定中文文案，其他内部字段继续仅写入运行步骤审计。实时进展映射为 `run.progress` 载荷：

```json
{"stage":"retrieval","phase":"STARTED","summary":"正在查找公司资料"}
```

`run.started` 也带相同的 `stage/phase/summary` 字段。现有 `message.delta`、`citation.ready`、终态公开格式不变。前端允许旧 `run.progress` 缺少 `phase`，但新阶段事件必须提供 `phase`。Java 投影继续使用 `(run_id, sequence_no)` 唯一键和 `last_event_sequence` 防重；重复订阅不得追加重复正文或进展。

新增员工只读接口 `GET /api/customer-service/runs/{id}/timeline`，由现有 `CustomerServiceController` 提供。它先按租户获取 Run，并校验对应会话属于当前员工，再在同一只读事务中读取 Run、助手消息、引用与已投影的阶段步骤，返回：

```json
{
  "runId": "<Java Run ID>",
  "status": "RUNNING",
  "lastEventSequence": 12,
  "assistant": {"message": {"...": "现有 MessagePO 字段"}, "citations": []},
  "steps": [
    {"sequence": 3, "stage": "intent", "phase": "COMPLETED", "summary": "已理解问题", "occurredAt": "<ISO 8601>"}
  ]
}
```

`steps` 只含公开的四类阶段事件，按 `sequence` 升序。接口不返回 `internal_payload`、候选片段、Prompt、模型推理或调试细节。已投影的事件可由现有 `ai_customer_service_run_step` 和助手消息重建，因此不新增表。管理端现有完整运行回放不变。

Java 当前在员工订阅 SSE 时才消费 Agent 事件并落库。本次仍沿用该执行链：断线期间 Agent 继续保留该 Run 的事件，重新订阅时由 `afterSequence` 补齐并投影。Java 的公开快照与 SSE 游标使用**同一数据库读事务**取得一致的 `lastEventSequence`；前端先用快照替换当前助手内容和步骤，再从该序号续订。快照后到 SSE 建立前产生的事件由 Agent 续传补齐。该设计保证正常断线重连与刷新；Agent 进程在运行中被重启导致内存 Run 消失，属于现有运行生命周期约束，不能把它报成成功回放。

## 5. 前端状态和交互

`useCustomerServiceChat` 以 `runId` 保存该 Run 的 `steps`、最新 `sequence`、正文和终态；不再用单个全局 `summary` 代表所有消息。新组件 `CustomerServiceProgress` 只渲染服务端公开步骤，不渲染模型文本。`CustomerServiceChatPage` 将进展置于对应助手气泡内、正文上方；已完成 Run 默认收起，可手动展开。

`sseClient` 继续处理 SSE 的 `id`、`Last-Event-ID` 与去重。刷新或选择未完成会话时，先读取 `timeline` 快照，替换该助手消息与步骤，再以 `lastEventSequence` 连接 SSE；SSE 断线重连沿用内存游标。答案块在前端按与 Java 投影相同的 `\n\n` 规则拼接，避免流式过程与最终持久化正文排版不一致。终态后以已存消息和引用校准显示。旧 Run 没有阶段步骤时不显示空壳。

## 6. 错误边界、日志与验收

- 模型、检索或 SSE 出错时只显示该 Run 实际已有步骤和已有正文，并显示原有 `run.failed` 安全错误；不补发成功步骤。取消后停止该 Run 的进展与正文追加。
- Java 只接受 Agent 契约内的阶段键和阶段状态；公开文案由代码白名单确定。日志只记录 Run ID、阶段、序号、耗时和错误码，不记录正文、资料原文或凭证。
- 保持公司知识回答的完整段落、引用闭包、版本和证据校验。进展快不代表答案已核实；`run.completed` 才表示最终完成。
- 验收必须使用真实 Java → Agent → 向量库/模型接口，并同时观察 Java、Agent 日志。分别记录提交到首个真实进展、首个正文块、终态的耗时；前一指标目标是在现有开发环境的六个开放问法中逐次不超过 1 秒，未达标需定位，不能用静态动画替代。首段正文按实际值报告，不因有进展而视为性能合格。
- 六个未入固定评测集、且未用于本次实现调参的开放问法核对实际正文、来源、引用、SSE 顺序与刷新/重连；若没有可追溯的历史员工原问，明确标记为基于真实文档编写的开放问法，不冒称生产用户原话。原 18 题固定集复验质量无回退。注入断线、重连、取消与失败场景，验证无重复正文、无伪造完成；任何接口失败与日志异常单独记录并修复。
