# 运营助手质量完善与真实验收实施计划

> **执行要求：** 按任务顺序实施。每项能力必须通过真实 Java HTTP/SSE 接口、真实 Agent、真实模型、真实公开来源和真实数据库完成验证；测试类、Mock、fixture、编译成功只能作为辅助，不能作为完成依据。每轮真实调用都要同步检查 Java 与 Agent 日志，发现异常后先定位、修复，再重放受影响场景。

**目标：** 在现有运营助手 MVP 上补齐真实模型研究、平台成稿质量、跨重启引用恢复、会话历史恢复、链路日志和异常状态验证，使“识别意图 → 采集真实数据 → 筛选排序 → 连续对话 → 生成标准排版成稿 → 预览/复制/下载”达到已批准设计的验收标准。

**范围边界：** 本期不实现登录、JWT、用户注册、公众号/小红书账号授权、自动发布、定时发布、付费数据源、图片/视频生成。开发身份继续由 Java 固定注入；数据库与 Redis 使用现有真实配置。任何回复只展示用户需要的结果，研究任务、引用闭包、版本和内部运行信息保存在后台。

**架构原则：** 浏览器只调用 Java `/api/operations/**`；Java MySQL 保存业务会话、消息、运行和制品；Agent MySQL `ai_efficiency_platform_agent` 保存运行态及可跨重启恢复的排名引用快照；PostgreSQL `vector` 继续负责文档与向量；Redis 负责短期事件和取消信号。平台成稿必须由真实模型基于已验证引用闭包生成，再由确定性格式化与安全清洗层收口，不能用确定性模板冒充模型成功。

## 一、当前基线与必须补齐的问题

当前已有 Java → Agent → SSE → MySQL → 制品的真实闭环，热点研究、公众号、小红书、幂等、取消和非法引用均执行过真实调用。但它还不能按最终验收标准判定完成：

1. `local_live_research_factory.py` 把 `deterministic_fallback=True` 固定传给研究决策，导致热点研究 `model_calls=0`，没有真实执行模型筛选、去重、排序和摘要。
2. `ReferencedContentModelRuntime` 对带排名引用的成稿直接返回确定性草稿，真实模型没有参与；公众号正文约 1000 字，未达到 3000～4000 个中文字符。
3. 排名引用只保存在 `LocalResearchRunStore` 内存中，Agent 重启后无法继续用上一轮热点生成文章。
4. Java 已持久化会话、消息、运行和制品，但没有会话详情/历史接口；前端仅在 `useRef` 中保存会话 ID，刷新后不能恢复。
5. Java → Agent 提交、SSE、投影和制品持久化缺少完整、安全的关联日志。
6. 当前验收脚本尚未强制验证真实研究模型调用、3000～4000 字公众号、Agent 重启恢复、浏览器刷新恢复和 SSE 断线续传。

## 二、开源实现基线

编码前先更新 `docs/research/2026-10-15-运营助手MVP开源借鉴.md`，固定仓库 HEAD、许可证、实际借鉴点和不采用项：

- [AI News Brief](https://github.com/frankzch/ai-news-brief)：借鉴多源摄取、模型筛选评分、SimHash/向量两阶段去重和 PostgreSQL 持久化机制。
- [GPT Researcher](https://github.com/assafelovic/gpt-researcher)：借鉴研究规划、来源追踪、证据聚合和引用完整性判定。
- [doocs/md](https://github.com/doocs/md)：借鉴 Markdown 到微信公众号排版预览的产品机制，不引入其完整编辑器。
- [TryPost](https://github.com/trypostit/trypost)：只借鉴分平台草稿与预览交互；其 AGPL 代码不得复制或链接。

新增真实来源只考虑无需登录的公开入口。首批候选为 OpenAI RSS、Hugging Face Blog Feed、GitHub Blog Feed；必须先用现有 `SafeHttpTransport` 做真实网络、重定向、内容类型、字段完整性、历史时间范围和使用条款核验。探测失败或许可边界不清的来源保持禁用，不通过抓取页面绕过限制。
