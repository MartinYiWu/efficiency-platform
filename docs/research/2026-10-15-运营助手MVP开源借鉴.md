## 2. 实际采用的机制

### 2.1 来源先准入，再采集

借鉴 `ai-news-brief` 的处理顺序：每个来源必须先配置来源族、URL、超时、数量上限和启用状态；采集失败保留真实失败，不用模型补造新闻。首批只启用已经过现有代码验证的 Google AI Blog RSS、LangGraph Releases 和 Hacker News API；新增来源必须先完成真实准入探测。

### 2.2 归一化、聚类、去重、排序分层

不同来源先映射为统一候选条目，再按标准 URL、标题指纹和语义相似度聚类；排序只处理去重后的事件，不把同一事件的多个转载重复计数。排序的来源新鲜度、来源质量和跨源佐证是显式输入，模型不直接凭空给出“最热”。

### 2.3 研究证据与用户成稿分层

借鉴 GPT Researcher 的研究/交付分层：来源、抓取内容、事实声明和引用闭包作为内部研究制品；用户默认只看到排序结果或文章。用户要求查看来源时才输出可读来源摘要，不暴露内部任务结构和版本字段。研究决策必须真实调用模型并记录真实调用次数，确定性算法只负责准入、去重、契约和引用校验。

### 2.4 制品而不是自动发布

参考 doocs/md 的 Markdown 到微信公众号图文预览机制，以及 TryPost 的分平台草稿交互：Markdown 预览、微信公众号 HTML 预览、复制和下载。MVP 明确不接入公众号、小红书等平台账号，不提供发送或定时发布能力。

## 3. 明确不采用

- 不复制第三方源码或 Prompt。
- 不引入 TryPost 的 AGPL 代码、MCP 或发布链路。
- 不因为开源项目功能完整就扩大依赖；现有 HTTPX、feedparser、Trafilatura 和 Markdown 渲染链可以满足时继续复用。
- 不接入需要登录、付费账号或用户 Cookie 的来源。
- 不用 GitHub star、社区热度或模型主观判断代替本项目的真实来源和证据闭包。

## 4. 后续变更门禁

新增来源或直接采用第三方库前，必须再次记录固定提交/版本、许可证、数据费用、运行依赖、失败策略和本项目落点；未通过门禁的来源保持禁用。
