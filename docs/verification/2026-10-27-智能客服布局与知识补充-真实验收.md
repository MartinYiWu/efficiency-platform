## 实际失败与修复

首次无命中真实调用已输出部分建议，但最终 `MODEL_RESPONSE_INVALID`，没有记作成功；再次定位调用同样失败。安全诊断确认根 `answer_mode` 缺失、`clarification_question` 与 `insufficiency_reason` 错放进 `general_advice`。失败结果保留在 `chat-first-failure.json`、`chat-diagnostic-ready.json` 和原始日志。

修复通过数据库通用 Prompt 1.2.1 说明根对象与嵌套对象层级，加入完整 JSON 示例；没有伪补模型字段或放宽最终答案校验。生产解析器增加根 `contract_version`、`answer_mode` 完整正确后才释放内容的门禁。新诊断只记录阶段、受控字段位置与错误类型，未知键脱敏，不记录正文或异常上下文。

重启未就绪期间另有真实提交返回 409 与 `Retries exhausted: 1/1`，保留在 `chat-diagnostic.json`。定位为连接重试耗尽包装了原异常，未命中既有不可用映射。修复保留重试后的根异常，并由客服异常处理器输出实际传输状态；连接失败应为 503、`CS_AGENT_UNAVAILABLE`，不伪装为无知识。新增回归先复现原失败后通过，主目录还需真实断开 Agent 验证。

Java 打包曾因运行中的工作树 JAR 被 Windows 占用而失败，停止该 Java 后重打包成功；原失败日志保留，不计为构建通过。
