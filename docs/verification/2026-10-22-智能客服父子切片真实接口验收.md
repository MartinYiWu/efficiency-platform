## 已观察到的问题与未验证项

- 初次创建知识库用了不支持的枚举 `TECHNICAL_DOC`，接口返回 `KB_TYPE_INVALID`；改为实际支持的 `TECHNICAL_DOCUMENTATION` 后成功。初次文件上传未附正确 MIME，返回 `FILE_TYPE_INVALID`；按 `text/markdown` 上传后成功。两次错误均未计为成功调用。
- 自然提问“这个平台 Java ……”的一次聊天运行 `5ad2abce-96fc-48bc-8f7b-aa673e45909d` 返回 `CLARIFY`，要求补充 `platform_name`；明确指出文档和平台名称的后续运行才得到知识回答。意图/指代识别仍有产品效果缺口。
- 最新中文问题的全文检索候选为 0；当前正确答案主要依赖向量召回。不能据此宣称中文 FTS 有效。
- 首次打开真实回放页时出现 `CLIENT_CONTRACT_MISMATCH`：Java 的 `answer.delta` 步骤 `publicSummary` 实际为 `null`，前端契约错误地限定为字符串。已用失败用例定位并修正为可空；同一运行 `7eef89be-36b4-4fec-8bc7-17564eca64e0` 的页面复测已展示检索证据、最终回答和引用，未再显示契约错误。
- 旧索引调试快照的 `vector_candidates` 实际可为 `null`；前端契约已把该类集合归一化为空数组，浏览器读取运行 `d644043e-e476-467e-88c9-9e168ba622ac` 时契约解析通过。
- 新增跨页长表格按数据行源偏移定位页码、充分性 Prompt 纳入上下文预算的回归用例，两项均先在修复前失败、修复后通过。但目前没有真实跨页 PDF 入库和引用闭环，因此不声称该场景已通过真实接口验收。
- 尚无可用于真实验收的两份相互冲突且均现行的公司文档；冲突处理只有代码测试证据，没有真实接口通过结论。PDF 真实文件页码范围也尚未通过真实入库验收。
