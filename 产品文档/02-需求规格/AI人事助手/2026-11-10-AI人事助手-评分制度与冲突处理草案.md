## 1 已确认方向与来源

用户明确：岗位规则在Java端数据库配置，LLM分析简历是否达到岗位要求，建立完整评分制度，并结合本项目产品与UI设计。技术原则是Java拥有业务事实和评分真相，Agent负责受控智能执行。

沿用当前产品：九个岗位族、八类硬条件及容差、五维评分、80/65/50默认分档、结果证据与快照、人工放行/重算、候选人保留与面试官隔离。旧项目仅参考其“受控语义档位→后端映射”“冻结事实和规则”“批量评估原子要求”等实现思路，不继承旧表名、硬编码阈值或未通过真实校准的评分行为。

以下凡标为“建议”的参数/公式是本次待评审内容，不代表已获批准或已经实现。

## 3 岗位规则制度

每个岗位拥有独立的草稿和已发布评分配置，包含：

1. 基础信息：岗位族、部门、职级、岗位名称、JD上下文引用。
2. 硬性条件：稳定规则ID、八类条件类型、期望值/单位、比较方式、容差、证据要求、可否人工放行、关键性。
3. 软性要求：稳定要求ID、所在维度、业务描述、相对重要度、判断方式（确定性/语义）、各档锚点、原文证据要求、是否关键项。
4. 五维权重：技能/经验/项目/学历/加分，非负且合计100%。岗位族值仅为初始参考，不能直接代替配置者确认。
5. 阈值：强烈推荐/推荐/建议复核三个下限，0至100且严格递减，初始80/65/50。
6. 证据门槛、语义档位映射版本、计分精度/舍入、特殊标记开关、词典版本。
7. 生命周期：草稿、待校验、已发布、停用/归档；已发布内容不可原地改，停用不删除历史。

不存在已发布规则时，返回“岗位尚未配置评分标准”，不能用通用Prompt或旧默认分数兜底。启用条件至少包括原产品四项约束和评分标准完整性；发布校验必须由Java执行，前端置灰只是提示。

## 4 简历事实与语义评估

### 4.1 输入边界

简历先生成带页/段/块定位的结构化事实，区分原文事实、归一值、确定性派生值、人工确认值和未知项。LLM只能读取岗位规则快照与必要事实/证据，不能读取其他候选人的结果或面试官不该看到的信息；简历内指令不具有系统权限。

日期并集、实习排除、阈值比较、同义词版本、金额和总分归Java计算。LLM用于业务语义：相关经验、项目角色/复杂度、真实使用技能的上下文与跨领域可迁移证据。关键词或“主导”二字本身不能替代能力达标判断。

### 4.2 每项输出

每项返回`requirementId`、受控档位、证据块ID/原文引用、可核对的简短理由、待核验原因；不得输出最终总分、权重、最终分档或录用判断。要求集合必须恰好覆盖本次输入，无遗漏、重复、增项。引用存在性只证明引用来自材料，不证明候选人陈述已被外部核实。

优先一次批量评估一位候选人的语义要求；超上下文时按稳定要求ID有界分块，不逐项反复调用。分块数、修复和网络重试共同计入同一任务上限，不额外调用模型判定“是否循环”。

### 4.3 建议档位与映射V1

| 档位 | 建议标准分 | 判定含义 |
| --- | ---: | --- |
| STRONG_MATCH | 100 | 符合该要求的强档锚点，有明确职责/成果证据 |
| MATCH | 80 | 达到岗位基准锚点，有明确可定位证据 |
| PARTIAL_MATCH | 50 | 有明确证据，仅覆盖部分要求 |
| EXPLICIT_NOT_MET | 0 | 已确认事实或有效原文证据明确低于阈值；不是单纯未提及 |
| UNKNOWN | null | 材料没有足够信息，进入缺口/补充核实 |
| NEEDS_REVIEW | null | 证据冲突、日期精度跨阈值、归一歧义或校验未通过 |
| NOT_APPLICABLE | null | 只有岗位规则允许且Java确认不适用时使用，LLM不能自行删除要求 |

这套标准分是待校准建议，不能描述为旧项目已真实证明有效。每项还必须有具体档位锚点，例如项目角色区分“负责整个架构决策并有结果”“负责指定模块”“仅参与”，避免仅靠形容词打分。

技能证据“强/中/弱”沿用产品的跨经历/单经历/技能栏来源规则，表示材料支撑强度，不直接等于语义档位。重复同一段、同一项目提及多次不增加独立经历数；只在技能栏出现可以证明自述，不能证明熟练度或实际项目使用。

模型自报置信度不直接当作真实概率；优先使用可解释的缺失、冲突和证据校验状态。产品70%/85%解析门槛仍需有定义和黄金集校准，不能用模型自报数字伪造可信度。

## 5 五维评分与计算规则建议

### 5.1 通用加权

设维度权重为`W_d`（合计100），子项相对权重为`w_i`（技能采用产品1至10重要度）。`K_d`为具有有效、明确评估结果的适用子项，`A_d`为全部适用子项。

```text
维度分 S_d = Σ(i∈K_d, w_i × s_i) / Σ(i∈K_d, w_i)
维度证据覆盖率 C_d = Σ(i∈K_d, w_i) / Σ(i∈A_d, w_i)
总匹配分 T = Σ(W_d × S_d) / 100
总覆盖率 C = Σ(W_d × C_d) / 100
```

明确不满足但有有效证据的0分项纳入已知分母与覆盖率；无证据项不纳入已知分母，但保留在覆盖率分母。这里的覆盖率表示“材料足以作出判断”的比例，不是“满足项比例”。UNKNOWN和NEEDS_REVIEW不作0分。

若任一非零权重维度没有可评子项，则`T=null`，显示“待核验”；不能把它暗中按0分计算，也不能自动缩放其他维度权重。已能计算的维度继续展示。零权重维度可显示参考分，不计总分/总覆盖率门禁。

建议使用十进制精确计算，中间不舍入，最终展示分数1位小数、覆盖率1位百分比。分档比较使用同一展示精度的分数，避免64.95显示65.0却分到低档；舍入方式HALF_UP，映射/舍入规则随评分策略版本冻结。

### 5.2 各维度规则

| 维度 | 保留产品规则 | 需补充的可配置标准 |
| --- | --- | --- |
| 技能 | 核心技能重要度1至10、标准名归一、原文强中弱 | 每项熟练度/使用深度锚点；未知与明确不足分开；证据不直接等价能力 |
| 经验 | 年限拟合、行业相关、职能相关 | 三子项相对权重由岗位填写并校验；语义项采用上表映射，不由LLM给总经验分 |
| 项目 | 关键词、规模、团队规模、角色 | 各子项权重与达标锚点；角色表述模糊待核实；不靠项目数自动叠分 |
| 学历 | 硬学历门槛独立；专业相关性“不要求/优先/必须”属于软分 | 层次与相关性子项权重/评分表；软性“必须相关”仍不能代替硬门槛；不使用院校声望隐式加分 |
| 加分 | 命中技能等权，维度内最高100；维度权重计入100% | D-05批准后，仅明确可评项计分；未知导致低覆盖；不叠加额外5分 |

经验年限按月份计算，非实习区间取并集；若原文只到年份，不能猜月份形成硬性失败。原产品年限公式换算为月份：

```text
若m < L：100 × m/L
若L ≤ m ≤ U：100
若m > U：max(60, 100 - 8 × (m-U)/12)
```

要求`L>0，U≥L`；“不要求年限”显式不适用，不能以L=0进入除法。容差只影响硬门槛，不能偷偷修改经验分；临界状态另存。D-08是否保留超上限扣分及复核例外须在批准时冻结。

### 5.3 覆盖门禁与分档

建议初始最低覆盖率80%、高档最低覆盖率90%，关键语义要求必须已知；这两个值是可配置候选默认值，需业务评审/黄金集校准。岗位族80/65/50是分数阈值，与100/80/50/0原子映射不是一回事。

按固定优先级执行：

1. 明确硬性失败且未按岗位策略放行：`FILTERED`，不计算正式五维总分，总分“—”，保留与打捞。
2. 硬条件未知/关键项冲突/整维未知/覆盖不足：`REVIEW_REQUIRED`，可展示已知维度或注明参考总分，不进入正式可比排名。
3. 全部门禁满足：按冻结阈值分为强烈推荐面试、推荐面试、建议复核、暂不推荐；达到高档分数但不足高档覆盖门槛时保守降为待核验。
4. “建议复核”既可能是50分以上的正常分档，也可能是高分但证据不足；接口和页面必须保留不同`reasonCode`，不能用同一标签丢失原因。

分档只表达材料与岗位规则的匹配及面试优先参考，不产生自动淘汰或录用动作。排序只在同岗位、同评分配置版本、同计分主版本及有效事实版本下进行；跨版本列表先选择目标版本，不混合排名。

### 5.4 可复算例子

技术研发维度权重40/25/25/5/5，五维分80/90/80/80/100：

```text
总分 = 0.4×80 + 0.25×90 + 0.25×80 + 0.05×80 + 0.05×100 = 83.5
```

覆盖100%、无门槛失败时按默认线进入强烈推荐面试。若技能维度有四个等权要求，其中三个明确满足各80、一个未知，技能分仍80，技能覆盖75%；总覆盖90%。若该未知是关键要求，则83.5也必须待核验；不能仅看总分。

若加分项为空但岗位仍配置5%权重，启用前拒绝，要求补规则或由配置者调整权重。不会把空加分维度默认填100或0。

## 6 复核、版本与节约调用

- 人工修正创建新事实版本；人工放行创建独立覆核记录，仅允许配置为可放行的条件，需理由/操作者/时间，可撤销。每次影响计算的新操作生成新结果快照，原结果不覆盖。
- 语义缓存键至少包括租户/数据范围、事实快照哈希、语义要求与锚点哈希、词典版本、Prompt版本和模型路由版本；不能跨候选人权限复用。
- 仅改权重/分档阈值，复用原子判断，由Java重算；改熟练度期望、证据标准、岗位要求、事实、词典、Prompt或模型则重新判断受影响项。
- JD只作解释上下文时更改不重算分数，但解释/面试产物使用新的上下文版本，不覆盖旧产物。使用JD生成并采用新要求后必须新配置版本。
- 预演冻结编辑中的配置，独立保存结果，不写正式匹配历史；HR独立标注后才能计算一致率，不能向LLM再询问“与HR一致吗”。
- 单任务费用硬上限100元、60次付费HTTP、10分钟、单逻辑操作最多3次实际HTTP，包含网络/契约修复；批量任务还需共享累计授权。刷新、列表、重连、进程重启均不能再发评估或续额。
- 常规目标调用形态为解析1次、语义批评1次、必要解释1次；它是规划目标不是固定保证。长材料分块须先核算上限；不增加独立多Agent反复评委打分链。

## 7 必须验收的评分用例

| 用例 | 期望 |
| --- | --- |
| 必备资格明确不满足/允许放行/不允许放行 | FILTERED；允许时理由必填；禁止时后端拒绝 |
| 必备技能未提及 | 待核验，不能自动断言不具备 |
| 一个未知与一个明确不满足 | 未知不作0分，明确不满足可计0；覆盖率语义正确 |
| 63.95/64.95/65.00及80边界 | 按统一HALF_UP到1位后比较，页面和分档一致 |
