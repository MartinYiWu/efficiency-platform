## 1. 权威来源与目录职责

| 位置 | 唯一职责 | 禁止内容 |
| --- | --- | --- |
| `产品文档/01-产品总览/` | 产品范围、模块地图与术语入口 | 模块详细需求或页面逐项描述 |
| `产品文档/02-需求规格/` | 角色、能力、业务规则、数据边界与明确不做项 | UI 像素级样式或工程代码 |
| `产品文档/03-交互与UI规格/` | 页面地图、交互状态、角色可见性、视觉验收规则 | 前端框架或组件库的强制选型 |
| `产品文档/04-验收与追踪/` | 需求、页面、设计稿和工程归属的可追溯映射 | 第二份需求或 UI 正文 |
| `05-设计稿/` | 已评审的 PNG 与模块级设计稿说明 | 功能规格、生成提示词原文或工程代码 |
| `产品文档/archive/` | 被替代、重复或迁移前的来源资料与迁移说明 | 当前有效文档 |

## 2. 文档命名与元数据

- 功能规格、UI 设计规范使用 `YYYY-MM-DD-模块名称-文档类型.md`；日期表示该受治理版本建立日期，不随日常编辑变更。
- 追踪矩阵使用 `模块名称-需求页面追踪矩阵.md`；目录 `README.md` 与模板可使用稳定名称。
- 文件名、标题和目录禁止使用“最终版”“最新版”“final”“new”“副本”等不可追溯词。
- 正式文档标题下必须有元数据表，包含：状态、负责人、创建日期、最后更新日期、适用范围、不适用范围、关联文档与替代关系。

## 3. 状态与替代关系

状态仅可使用“草案、评审中、已批准、已废弃”。没有明确批准人、日期和范围证据的资料不得标为“已批准”。需求或 UI 决策发生实质变化时，新建受治理版本并在新旧文档中建立双向替代链接；不得静默覆盖已批准结论。

## 4. 链接与设计稿规则

- 仓库内链接只使用相对路径，移动文件后必须更新索引、设计稿说明与追踪矩阵。
- 设计稿不复制、不改名为状态性名称；页面编号、目录分组和文件名以对应模块的设计稿说明为准。
- UI 规格描述产品视觉与交互，不绑定 shadcn、Tailwind、Ant Design 等具体实现库；工程实现受前端工程自身规范约束。

## 5. 变更流程

1. 更新功能规格或 UI 规格的关联内容。
2. 同步更新追踪矩阵、设计稿说明和本目录索引。
3. 对照“明确不做项”、角色边界和数据边界进行评审。
4. 检查文件名、元数据、相对链接、重复来源与设计稿覆盖情况。
5. 记录批准或废弃证据；无证据时保持“草案”或“评审中”。
