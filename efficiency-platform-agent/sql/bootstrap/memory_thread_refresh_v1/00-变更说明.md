## V2 等待优先停止的兼容边界

旧无 pending 列的 legacy 清理仍兼容；V2 REFRESH_PENDING 下旧代码仅 SET state=REVOKED 会被 ck_memory_thread_pending 拒绝，RF03 必须适配，不能宣称旧 SQL 原样覆盖新状态。持 PG execution 行锁，在同一事务先把该原 PENDING receipt 写 candidate_phase=ABORTED、result_code=SOURCE_REVOKED（或当前真实批准原因）、receipt_state=REVOKED、dispatch_allowed=false、authorization_binding=NULL、next_wait_event_id=NULL，保当前 revision/fp/count；此刻 execution 仍 REFRESH_PENDING，receipt guard 可核同候选。随后 execution 置 REVOKED/fence+1，并清 pending_resume_request_id/pending_candidate_digest/pending_packet_revision/pending_context_fingerprint 四列。没有循环等待：receipt guard 要旧 pending，execution 的撤销分支允许清 pending 进入终态，不要求先撤销。之后按原 STOP→ERASURE/THREADS→DELETED 收口；保 wait refs/旧 count。

WAITING_CONTEXT 的 BUILDING/READY 无候选时可直接 REVOKED（pending 四列原本 NULL），后续 DELETED；不得为停止重回 ACTIVE、重领 frame 或先等刷新成功。STOP/source/原截止优先由协调器先判，后续密文擦除仍是 MySQL 原完整 proof 事务。合成 schema 用例提供 pending 旧 SQL 失败、正确事务顺序及 BUILDING wait 直接撤销两个分支。

## 独立审查增量修补

B 后继任 WAITING_CONTEXT 强制原 wait_phase 与原不可变 receipt.wait_phase 一致，RESERVED/PREPARED 不能降 BEFORE_PREPARE；B 前回原 wait 强制 READY。PG 原 receipt 的 op/HMAC/attempt 不变，MySQL 继任 wait guard 的 operation/attempt/HMAC/stage 绑定仍执行，协调器不因为换 id 重准备/重领 reservation。
