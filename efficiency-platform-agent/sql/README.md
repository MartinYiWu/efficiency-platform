# Agent 侧 SQL 变更包规范

本目录只管理 `efficiency-platform-agent` 纯 Agent 侧数据库变更。它不定义、修改或代管 Java 侧表结构；Agent 数据必须使用独立命名空间，禁止与 Java 表混写。

详细规则见[数据库与 SQL 规范](../docs/standards/05-数据库与SQL规范.md)，评审材料使用[SQL 变更说明模板](../docs/templates/SQL变更说明模板.md)。本文件描述的是未来变更的落地协议，不代表当前存在待执行脚本，也不授权执行任何 DDL 或数据写入。

## 1. 变更包目录

每个变更必须使用独立目录，目录名必须为 `YYYYMMDD_NNN_中文主题`：日期使用计划提交日，`NNN` 是当日从 `001` 开始的三位序号，中文主题应稳定、简短并表达对象与目的。

完整目录范例：

```text
sql/changes/20260901_001_agent运行状态/
├─ 00-变更说明.md
├─ 01-precheck.sql
├─ 02-up.sql
├─ 03-verify.sql
└─ 04-rollback.sql
```

目录中的五个文件缺一不可，职责不得混用：

| 文件 | 唯一职责 | 强制边界 |
|---|---|---|
| `00-变更说明.md` | 记录目标、非目标、影响、风险、授权、执行和回滚证据 | 必须按 SQL 变更说明模板填写；不得虚构审批或执行结果 |
| `01-precheck.sql` | 只读确认版本、对象、数据规模、冲突、锁风险和前置条件 | 必须是经评审的只读查询；不得修改 Schema、数据、会话持久状态或权限 |
| `02-up.sql` | 承载唯一的目标变更 | 未取得用户明确授权不得执行；不得把预检、验证或无关回填混入其中 |
| `03-verify.sql` | 验证结构、约束、数据结果和关键查询计划/行为 | 必须有可判定的通过标准；不得用验证脚本补做变更 |
| `04-rollback.sql` | 在声明的安全边界内回退本变更 | 必须写明触发条件、数据损失风险和不可逆事项；不安全时不得承诺完全回滚 |

### 1.1 首次初始化固定路径

在 Agent 独立 Schema 和权威执行账本都不存在时，普通变更无法先占用账本。仅这一场景使用以下固定包：

```text
sql/bootstrap/agent_database_bootstrap_v1/
├─ 00-变更说明.md
├─ 01-precheck.sql
├─ 02-up.sql
├─ 03-verify.sql
└─ 04-rollback.sql
```

该包的固定 `change_id` 是 `agent_database_bootstrap_v1`，只负责创建并验证 Agent 独立 Schema、权威执行记录表、`change_id` 唯一约束、状态约束和 bootstrap 记录。它不得创建业务表、业务索引、向量索引或执行数据回填，也不得复制为第二个 bootstrap 包。

PostgreSQL 初始化必须在目标数据库的一个受控事务内使用固定事务级 advisory lock：

- 锁常量：`EFFICIENCY_AGENT_BOOTSTRAP_LOCK_V1 = 7887332933888385649`；
- 固定归属：`efficiency-platform-agent/database-bootstrap/v1`；
- 作用域：只覆盖连接到同一目标 PostgreSQL 数据库并使用同一锁命名空间的执行者，不是跨数据库或跨集群的通用锁；
- 替代机制：仅在受审 ADR 证明其对同一目标全部执行者提供强一致原子互斥、唯一所有者、fencing token、有限租约和 compare-and-set 时可用；进程锁、文件锁、线程锁和“先查后建”不等价。

初始化执行顺序严格固定：

1. 只读预检目标数据库身份、Schema/账本不存在或完整存在、冲突对象、DDL 权限、事务能力、锁键登记冲突和长事务，并分类为“完全不存在”“完整成功”“部分/不一致”。
2. 展示实际 bootstrap SQL、固定锁键/归属、目标数据库作用域、影响、超时、事务、回滚和外部审计方案，取得针对本目标数据库的明确授权。
3. 开启事务并设置有限锁等待/语句超时，取得 `pg_advisory_xact_lock(7887332933888385649)`，在锁内重新做目录级只读检查。
4. 若已完整成功且固定 `change_id`、脚本校验值、Schema/账本/约束完全一致，只做 no-op 验证并记录外部审计。
5. 若完全不存在，在同一事务内幂等创建 Schema 和账本，建立唯一/状态约束，登记固定 bootstrap 记录并按 `claimed` → `running` → `succeeded` 转换；提交前通过系统目录验证所有权、结构、约束、校验值和最小权限。
6. 若部分/不一致或任一步骤失败，回滚整个事务；事务级锁随提交、回滚或连接终止释放。不得自动删除或猜测修复部分对象。
7. 在数据库外的受控审计中保存预检、授权、目标数据库标识、锁取得/释放、脚本校验值、事务结果、异常和恢复决定；不得记录敏感连接信息。

失败重试必须从新预检和新授权开始。完整成功后的重复 bootstrap 必须幂等 no-op；部分状态必须形成独立恢复设计。bootstrap 成功后，所有普通变更都必须回到权威账本原子占用机制，禁止复用固定 bootstrap 锁键、路径、临时高权限或一次性例外。

## 2. 执行门禁与顺序

任何共享数据库变更必须严格遵守以下顺序，执行者不得跳步：

1. 评审 `00-变更说明.md` 与五个文件，确认变更标识、目标环境、对象所有权和回滚边界。
2. 使用只读身份执行 `01-precheck.sql`，保存实际输出；预检失败或环境不符时立即停止。
3. 向用户完整展示预检结论、将执行的 `02-up.sql`、影响对象、锁/性能/容量风险、执行窗口和 `04-rollback.sql` 边界。
4. 取得用户对该变更标识、目标环境和本次 SQL 的明确授权。会议推断、历史授权、模板占位、代码合并或“可以看看”都不构成授权。
5. 在第一次写操作前，由唯一写入执行者通过权威执行记录的唯一键原子占用 `change_id`，状态进入 `claimed`；唯一冲突、影响零行或权威记录不可用时立即停止。
6. 在授权有效范围和执行窗口内把状态受条件保护地转为 `running`，再执行 `02-up.sql`；SQL、环境或影响发生实质变化时授权失效，必须重新展示并授权。
7. 执行 `03-verify.sql`，按既定标准核对结构、数据和关键查询。验证通过后才可把状态转为 `succeeded`；执行或验证失败必须记录为 `failed` 并停止后续写入。
8. 必要时由获授权执行者运行 `04-rollback.sql`，随后重新执行适用于回滚结果的验证；回滚不删除原失败尝试。
9. 回填 `00-变更说明.md` 中的实际执行人、时间、环境、输出摘要、权威状态转换、异常、验证结果、回滚动作和最终结论。

只读预检不构成后续写入授权。共享 DDL 或数据写入必须针对本次执行获得明确授权；执行者必须保留可审计证据。

## 3. 事务、超时与幂等

- `02-up.sql` 必须声明事务边界。可事务化的小变更应原子执行；不支持事务或要求并发构建的操作必须分阶段执行并声明失败恢复点，不得伪装成全事务。
- 所有等待数据库锁和执行语句的步骤必须设置有限的锁超时与语句超时；超时值必须在变更说明中写明依据，禁止依赖无限默认值。
- 变更必须说明幂等策略。重复执行应安全退出或产生明确冲突，不得靠吞掉所有异常伪造幂等。
- 大表 Schema 变更必须评估锁级别、表重写、磁盘峰值、复制延迟和兼容窗口；可用时应采用经验证的在线或并发方式。
- 大规模回填必须分批、限速、可续跑并有进度水位；禁止把大回填与结构变更混在同一事务。
- 执行窗口必须包含观察与回滚时间。超出窗口、锁竞争异常、容量越界或关键查询退化时必须按预先定义的停止条件处置。

## 4. 验证与回滚边界

`03-verify.sql` 至少应覆盖：目标对象及定义存在、约束或索引状态有效、受影响数据数量符合预期、租户边界未破坏，以及关键查询使用预期计划且延迟没有越过批准阈值。仅凭命令退出码或“无报错”不得判定成功。

`04-rollback.sql` 必须区分可逆结构、可恢复数据与不可逆事项。删除数据、缩窄类型、不可逆转换、外部副作用、已被新代码写入的新语义数据，以及无法重建的向量内容，不得承诺无损回滚。存在不可逆事项时，变更说明必须给出备份/快照、前滚修复、停止写入或恢复窗口等策略，并在授权前明确告知。

## 5. Alembic 与原始 SQL 的单一执行权

Alembic 是迁移编排入口；本目录中的原始 SQL 是受审变更包。Alembic revision 与变更包必须引用同一 `change_id`、脚本校验值和唯一执行模式：

| 执行模式 | 唯一写入执行者 | Alembic 行为 |
|---|---|---|
| `alembic_embedded` | Alembic revision | 原子取得执行权后执行受审 SQL |
| `external_controlled` | 受控 SQL 执行器 | 不再执行 SQL，仅在权威状态 `succeeded` 后校验/同步 revision |
| `verify_only` | 无 | 只允许 Alembic 外部纯只读验证；不得执行 revision、推进版本或写任何数据库状态 |

执行模式一经评审和授权不得在运行期自动切换。Alembic 版本表只是迁移视图，不能充当互斥锁或代替权威执行记录。

`verify_only` 只允许使用只读身份在 Alembic 外部核对迁移文件、revision 映射、系统目录或业务只读结果。它不得执行 `alembic upgrade`、`alembic downgrade`、`alembic stamp` 或 `alembic current`，不得执行所谓“校验 revision”，不得推进 revision，也不得写入权威账本。允许示例：只读取 revision 文件并运行不会改变会话持久状态的只读 SQL；拒绝示例：运行 upgrade/current 来“确认 revision”，或插入账本记录来“证明已验证”。

任何会更新 Alembic 版本表、权威账本、Schema 或数据的动作都是数据库写入，必须改选 `alembic_embedded` 或 `external_controlled`，完成明确授权、原子执行权占用、受控状态转换、对账和失败恢复后才可执行。不得用 `verify_only` 规避该流程。

### 5.1 原子执行权占用

权威执行记录必须存放在目标数据库的 Agent 独立命名空间内，并至少包含：目标环境、数据库、Schema、`change_id`、Alembic revision、执行模式、`02-up.sql` 校验值、授权证据引用、执行主体、尝试次数、状态和时间戳。同一目标执行命名空间内的 `change_id` 必须有数据库唯一约束；也可使用覆盖目标标识与 `change_id` 的等价唯一键。

明确授权后、第一次写操作前，唯一写入执行者必须用单条原子插入或等价 compare-and-set 把不存在的记录占用为 `claimed`。只有实际插入记录的执行器可以继续；“先查询不存在、再执行 SQL、最后登记”不具备并发安全性，明确禁止。并发尝试遇到唯一冲突、compare-and-set 影响零行或记录不可用时必须失败关闭，不得接管或并行执行。

### 5.2 权威状态机与恢复

```text
不存在 ──原子占用──> claimed ──开始执行──> running ──验证通过──> succeeded
                                      └──执行或验证失败──> failed
```

- `claimed` 和 `running` 表示执行权已被占用；并发执行器必须停止。
- `succeeded` 是终态；再次请求只能只读验证 `change_id`、revision 和脚本校验值，不得重放。
- `running` 超出窗口或租约不得自动接管。恢复人员必须先只读确认实际数据库状态和最后提交点，再使用当前状态作为条件原子标记 `failed`。
- 从 `failed` 重试前必须完成部分影响评估、回滚/前滚方案、验证和新的明确授权。脚本校验值未变且恢复方案允许继续时，才可原子地将 `failed` 重新占用为 `claimed` 并递增尝试次数。
- SQL 实质变化必须使用新 `change_id`；任何状态转换都必须校验当前状态、执行主体和脚本校验值，并追加尝试证据。失败历史不得删除或覆盖。

`alembic_embedded` 应在数据库能力允许时把变更、`succeeded` 状态与 revision 推进放入一致事务；非事务 DDL 必须声明提交点。`external_controlled` 下，Alembic 只有在权威记录为 `succeeded` 且 `change_id`、revision、脚本校验值完全一致时才能确认版本。任何不一致都必须停止并人工核对，不得自动补执行。

## 6. 执行记录

每次尝试（包括失败和回滚）必须记录：`change_id`、Alembic revision、唯一执行模式、权威记录位置/唯一键、`claimed`/`running`/`succeeded`/`failed` 状态转换、目标环境、数据库与 Schema、实际执行人、审批人、授权证据引用、开始/结束时间、客户端和事务边界、脚本校验值、尝试次数、命令输出摘要、影响行数、验证证据、异常和恢复动作。记录必须脱敏，不能包含 Secret、连接串、真实隐私数据、完整生产样本或未经批准的查询结果正文。

## 7. 明确禁止

- 禁止直接运行来源不明、未评审、被临时修改或无法关联变更标识的脚本。
- 禁止在脚本、注释、文档、输出和测试样本中写入密钥、令牌、连接串或真实隐私数据。
- 禁止使用字符串拼接产生动态 SQL；运行期值必须参数化，对象名必须来自受控白名单。
- 禁止绕过 `01-precheck.sql`、明确授权、`03-verify.sql` 或回滚边界记录。
- 禁止把大回填与结构变更放入同一事务，或在无停止/续跑能力时执行大规模更新。
- 禁止让模型或普通业务账号执行写 SQL；LLM SQL 的只读边界由安全规范和数据库规范共同约束。
