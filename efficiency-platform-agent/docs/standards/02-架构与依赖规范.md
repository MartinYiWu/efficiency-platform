## 1. 架构不变量

系统 MUST 采用 Harnessed Hybrid Multi-Agent Architecture。每次请求 MUST 经过统一 Harness 治理，并由 Strategy Router 在 Direct、Workflow、ReAct、Plan-and-Execute、Multi-Agent 中选择执行模式。所有模式 MUST 共享 Context、Tool、Memory、Provider、Persistence、安全、观测和评测边界。

LangGraph MUST 是唯一 Graph Runtime。系统 MUST NOT 引入或并存 AutoGen、CrewAI、LlamaIndex Workflow、去中心化 Swarm 或其他第二编排内核。引用第三方库的算法或数据结构 MAY，但 MUST NOT 引入另一套运行状态、暂停恢复、Checkpoint 或 Agent 对话生命周期。

## 2. 权威依赖方向

```text
API → Harness → Routing / Orchestration → Strategies / Agents / Workflows
                                            ↓
                   Context / Memory / Tools / Capabilities
                                            ↓
                         Providers / Persistence
                                            ↓
                              Core / Contracts
```

箭头表示上层 MAY 通过稳定契约使用下层。下层 MUST NOT 反向依赖上层；同层协作 SHOULD 通过明确端口完成，并 MUST NOT 形成循环导入。运行期注册、依赖注入和事件回调 MUST NOT 被用来规避此方向。

AST 守卫使用下表作为完整允许矩阵。每行列出该导入方可以静态导入的全部一级层；未列出的方向一律拒绝，同层只允许导入自身。`package` 表示根 `efficiency_platform_agent/__init__.py`，只 MAY 暴露 `core` / `contracts` 稳定契约：

该矩阵明确拒绝 `capabilities -> strategies`、`tools -> orchestration` 以及 Provider/Persistence/基础层到 Harness、Routing、Orchestration、Strategies、Agents、Workflows、API 的反向依赖。API 只作为组合入口依赖 Harness 和稳定契约；`tasks` 只通过 Harness 触发受治理 Run。执行层的单向关系固定为 `harness -> routing/orchestration -> strategies -> agents/workflows`，`orchestration` MAY 直接组合 Agent/Workflow，但这些下层 MUST NOT 反向依赖 Harness、Routing 或 Orchestration。

`ImportFrom` 必须解析相对层级并展开根包 `from efficiency_platform_agent import <name>` 与等价相对重导出。根包星号导入、未知一级层和未分类导入方 MUST 失败关闭；`__init__.py` 重导出与相对导入 MUST 服从同一矩阵，MUST NOT 成为绕过路径。

`observability`、`security`、`evaluation` 和 `tasks` 是横切或运行支撑边界：

- 业务层 MAY 调用其稳定端口；具体实现 MUST 依赖 `core` / `contracts` 及必要的基础设施端口，MUST NOT 反向控制 API 或执行策略；
- `tasks` MAY 触发统一 Harness 中的 Run，MUST NOT 复制 Graph 内部编排或以队列结果替代权威 Run 状态；
- `observability` MUST NOT 通过埋点改变业务分支；`security` 的拒绝结果 MUST 通过稳定错误契约返回；
- `evaluation` MUST NOT 在生产链路中隐式更换模型、Prompt、策略或答案。

## 3. 各层职责与限制

### 3.1 API

API MUST 负责入站协议解析、认证上下文接入、Schema 校验、流式事件和统一错误映射，并把规范化请求交给 Harness。

API MUST NOT：

- 编排 Graph、选择 Specialist 或实现业务流程；
- 直接调用 Provider、数据库、缓存、对象存储或 Tool；
- 创建与 `run_id + checkpoint` 并行的恢复、审批、补充输入或取消链路；
- 把框架对象或厂商对象写入稳定契约。

### 3.2 Harness

Harness MUST 为每次 Run 建立并统一执行身份、租户、用户、权限、幂等、预算、超时、取消、Checkpoint、审计、Trace、Guardrail 和错误映射。所有 Strategy、Agent 和 Workflow MUST 在该治理边界内运行。

Harness MUST NOT 包含具体厂商调用、业务 Agent 逻辑或某个 Strategy 的内部步骤；MUST NOT 因 Direct 模式简单而跳过身份、预算、审计或错误治理。

### 3.3 Routing

Strategy Router MUST 依据意图、风险、复杂度、工具需求、延迟和成本选择执行模式及允许的模型策略。路由结果 MUST 结构化、可观测、可测试，并携带选择理由或规则版本。

Strategy Router MUST NOT 直接执行 Tool、编排 Specialist、合并专家答案或承担 Multi-Agent 内部重试。它 MUST 选择“采用哪种执行模式”，MUST NOT 选择“某个专家的下一条消息”。

### 3.4 Orchestration

Orchestration MUST 提供统一 LangGraph Runtime、Graph/Node/Edge、Run 状态机、Checkpoint、重试/降级、暂停/恢复、审批、补充输入、取消和事件流语义。恢复 MUST 使用原 `run_id + checkpoint`，MUST NOT 新建旁路 Run 冒充恢复。

Orchestration MUST NOT 依赖 API，MUST NOT 封装具体厂商 SDK，也 MUST NOT 将某个业务部门流程固化为公共 Runtime 生命周期。

### 3.5 Strategies、Agents 与 Workflows

- Strategy MUST 声明适用条件、最大步骤、Token/时间/费用预算、暂停点、终止条件、Checkpoint 和失败恢复。
- Workflow MUST 表达步骤固定、强审计的确定性流程；模型只 MAY 在指定节点内处理受约束任务。
- Agent Plugin MUST 声明能力、输入输出 Schema、允许工具、预算、证据和终止条件，并通过注册机制接入。
- Multi-Agent MUST 由中央 Supervisor Graph 调度 Specialist Subgraph；Supervisor MUST 分配结构化子任务和裁剪上下文，控制并发、预算、权限、终止、冲突、重试与结构化汇总。
- Specialist MUST 只接收 Supervisor 分配的任务，并返回结构化结果、证据、引用或错误。

Strategies、Agents 与 Workflows MUST NOT 绕过 Harness、Context Builder、Tool Runtime 或 Provider；MUST NOT 直接持久化私有 Run 真相；MUST NOT 直接实例化厂商 SDK。

### 3.6 Context、Memory、Tools 与 Capabilities

- `context` MUST 是唯一上下文装配和预算入口，负责租户、用户、会话、历史、证据和不可信来源标记。
- `memory` MUST 区分短期、长期和情景记忆；检索结果 SHOULD 保留来源、时间和引用，MUST 遵守租户隔离。
- `tools/runtime` MUST 统一 Schema、权限、幂等、超时、重试、审计、外部副作用和结果大小；MCP MUST NOT 绕过该 Runtime。
- `capabilities` MUST 只组合可复用技术能力，MAY 调用 Provider、Tool、Context 与 Persistence 的稳定端口，MUST NOT 隐藏特定业务流程判断。

任何 Agent、Strategy 或 Graph Node MUST NOT 自行拼装无限上下文、直接调用外部系统、把模型自由文本当控制指令或跳过 Tool 权限。

### 3.7 Providers 与 Persistence

Provider MUST 对上实现内部稳定端口，对下封装厂商 SDK 或 HTTP API，并归一化配置、请求、响应、错误、超时、重试、限流、用量和降级。上层 MUST NOT 感知厂商响应对象、异常类型或配置键。

Persistence MUST 提供 Run、Checkpoint、Memory、Artifact、Prompt Version 和 Evaluation 等权威状态的存取适配。PostgreSQL Checkpoint MUST 是生产态恢复边界；生产环境 MUST NOT 用内存 Checkpointer 替代。Taskiq/Redis Broker 与短期 Redis Run Event MUST NOT 被视为权威状态。

Provider 和 Persistence MUST NOT 依赖 `api`、`harness`、`routing`、`orchestration`、`strategies`、`agents` 或 `workflows`。它们 MAY 依赖 `core` / `contracts` 的端口与数据结构，以及自身所需的第三方基础设施库。

### 3.8 Core 与 Contracts

`core` MUST 仅依赖自身和 Python 标准库，保存框架中立的稳定领域类型、枚举、状态、端口和架构守卫。`core` MUST NOT 依赖 `contracts` 或任何上层包、框架、厂商 SDK、数据库驱动。

`contracts` MUST 保存稳定的外部请求、响应、事件、错误和 Schema；MAY 依赖 `core` 的稳定概念以及经批准的 Schema 基础库，但 MUST NOT 依赖 API、Harness、Routing、Orchestration、Strategies、Agents 或 Workflows。

Core 与 Contracts MUST NOT 包含执行策略、I/O 实现、环境变量读取或厂商映射。对稳定契约的破坏性变更 MUST 提供版本与迁移策略。

## 4. Strategy Router 与 Supervisor 分工

| 维度 | Strategy Router | Supervisor |
|---|---|---|
| 生效范围 | 每个 Run 选择执行模式 | 仅在 Multi-Agent 模式内生效 |
| 输入 | 意图、风险、复杂度、工具、延迟、成本和治理策略 | 已选择的 Multi-Agent 任务、可用专家、裁剪上下文和预算 |
| 输出 | Direct/Workflow/ReAct/Plan-and-Execute/Multi-Agent 路由结果 | 专家子任务、调度事件、结构化汇总、证据和错误 |
| MUST 做 | 可解释、可测试地选择模式 | 控制专家选择、并发、权限、预算、终止、重试和冲突 |
| MUST NOT 做 | 调度专家、合并专家输出 | 改写全局路由政策、绕过 Harness 或把专家暴露给用户 |

二者 MUST NOT 相互替代。路由器选中 Multi-Agent 后，只有 Supervisor MAY 调度 Specialist；路由器选中其他模式时，Supervisor MUST NOT 被隐式插入。

## 5. Specialist 协作限制

Specialist Agent MUST NOT 点对点自由调用其他 Specialist，也 MUST NOT 与用户直接对话。需要另一专业能力时，Specialist MUST 返回结构化的能力缺口、证据需求或候选子任务，由 Supervisor 决定是否继续调度。

Supervisor 向 Specialist 提供的上下文 MUST 按最小必要原则裁剪，并包含 `run_id`、任务 ID、允许能力、预算、权限、终止条件和证据要求。Specialist 输出 MUST 可审计，MUST NOT 仅返回未校验的自然语言结论。

## 6. Provider 与外部系统边界

- Agent、Strategy、Workflow、Graph Node 和 Capability 的上层逻辑 MUST 依赖内部端口，MUST NOT `import` 或实例化 OpenAI、DashScope、数据库、Redis、COS、OCR、搜索等厂商 SDK 客户端。
- Provider MUST 将厂商异常映射为项目定义的错误分类，MUST 记录安全可用的观测字段，并 MUST NOT 在日志或异常中泄露 Secret 与敏感正文。
- 外部 Tool 与 MCP 适配 MAY 使用 Provider 或协议客户端，但最终调用 MUST 经 Tool Runtime 的权限、超时、重试、审计与结果治理。
- 模型输出 MUST 先通过 Schema 校验再进入 Graph State；当前 MUST NOT 引入 Text2SQL、模型生成 SQL 或面向业务数据库的直接分析，Agent 自有查询只能通过受控 Repository 和参数化语句执行。

## 7. 循环依赖与组合根

包间 MUST NOT 形成静态或运行期循环依赖。可替换实现 MUST 通过 `core` / `contracts` 的 Protocol、注册表或构造参数注入，在 API/Worker 等组合根装配。

注册模块 MAY 导入具体实现完成装配，但注册副作用 MUST 显式、可测试且不改变底层依赖方向。`__init__.py` MUST NOT 通过重导出隐藏不合规依赖。

## 8. MUST 先有 ADR 的变更

以下任一变更 MUST 在实现前提交并批准 ADR，必要时同时更新总体架构设计：

- 新增、替换或并存 Graph Runtime、Agent 编排框架或 Run 生命周期；
- 改变权威依赖方向，新增顶层包、跨层直连或公共生命周期；
- 改变 Harness、Strategy Router、Supervisor、Context Builder 或 Tool Runtime 的唯一治理边界；
- 放开 Specialist 点对点调用限制、改变中央 Supervisor 拓扑或新增执行策略类别；
- 改变 Run 状态、Checkpoint、暂停/恢复/取消语义或权威持久化边界；
- 让上层感知厂商对象、改变 Provider/Persistence 反向依赖限制；
- 破坏 `core` / `contracts` 稳定契约，或改变 Python 标准库隔离要求；
- 引入跨租户访问、高风险外部写路径、共享数据库新 Schema 或不可逆数据变更；
- 推翻已批准技术选型、引入付费商业数据源或进入当前明确非目标。

内部实现重构在不改变公共契约、依赖方向和运行语义时 MAY 不写 ADR，但 MUST 有匹配测试并更新受影响文档。

## 9. 验证与失败处理

当前 AST 依赖守卫 MUST 使用以下命令执行：

```powershell
python -m unittest tests.architecture.test_dependency_rules -v
```

当前守卫逐一验证上表全部一级层的允许矩阵，并覆盖根包名称展开、相对导入、`__init__.py` 重导出、星号导入、未知层、`capabilities -> strategies` 和 `tools -> orchestration` 等负例。命令通过只证明源码中可由 AST 识别的静态 import 规则通过；它不证明字符串动态导入、运行期注册、Graph Runtime 唯一性、Supervisor 拓扑或全部职责合规。

新增依赖规则 MUST 同步增加能够先失败的 AST 或契约测试。发现违规时，交付者 MUST 停止完成声明，列出导入方、目标层、规则和修复方案；MUST NOT 通过字符串导入、局部导入、重导出或忽略规则来消除测试表象。
