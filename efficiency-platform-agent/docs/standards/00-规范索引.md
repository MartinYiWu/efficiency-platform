## 1. 使用方式

进入仓库工作的开发者、编码 Agent、评审者和运行维护者 MUST 先阅读根目录 `AGENTS.md`，再按本索引选择与变更相关的详细规范。架构或扩展变更还 MUST 阅读 `Agent.md`、相关架构设计、技术选型和 ADR，并按各文档元数据判断其状态；`评审中`文档只能作为候选基线，MUST NOT 被称为已批准。

本索引只提供权威入口、路由和治理流程，MUST NOT 复制各分领域规范全文。链接存在只表示目标治理结构；交付者 MUST 通过当前仓库验证确认目标文件是否已经落地，MUST NOT 把规划链接误报为已交付能力。

## 2. 规则等级

规范正文 MUST 使用以下规则词表达约束，MUST NOT 使用“最好”“尽量”等模糊措辞代替规则等级。

| 等级 | 含义 | 不满足时的处理 |
|---|---|---|
| MUST / 必须 | 不满足即不合规 | 合并或交付前 MUST 修复，或取得书面例外批准 |
| MUST NOT / 禁止 | 明确不可出现的行为 | MUST 立即停止相关操作、消除影响并补充验证 |
| SHOULD / 应当 | 默认执行，存在充分证据时可以偏离 | MUST 在评审材料中记录原因、风险和补偿措施 |
| MAY / 可以 | 按场景选择的实践 | 不作为质量门禁，但采用后 MUST 遵守相关安全与架构约束 |

示例、模板和解释性文字 MAY 帮助理解，但 MUST NOT 降低 `MUST` 或 `MUST NOT` 的约束强度。

## 3. 规则优先级

规则冲突时 MUST 按以下顺序处理：

```text
用户当前明确要求
  > 根目录 AGENTS.md
  > 已批准 ADR / 架构设计
  > 分领域规范
  > 模板与示例
```

同一优先级存在冲突时，执行者 MUST 暂停有争议的变更，提交设计澄清或 ADR；MUST NOT 自行选择更宽松的规则。安全红线、共享数据库授权边界和纯 Agent 侧范围 MUST NOT 通过低优先级文档放宽。

## 4. 适用角色

| 角色 | MUST 承担的责任 |
|---|---|
| 需求或任务提出者 | 明确范围、非目标、验收标准和外部写操作授权；对重大例外指定批准者 |
| 开发者或编码 Agent | 读取相关规范，保护既有变更，测试先行，执行匹配门禁并提供新鲜证据 |
| 架构负责人 | 审查跨层依赖、Graph Runtime、核心契约、Provider/Tool 边界和 ADR |
| 安全或数据负责人 | 审查租户隔离、Secret、Prompt Injection、SSRF、文件、SQL 和高风险 Tool |
| 评审者 | 按变更范围核对规范、测试证据、未验证项和例外记录，不以文档存在替代实现验证 |
| 运行维护者 | 维护配置注入、可观测字段、告警、回滚和运行证据；MUST NOT 绕过代码定义的治理边界 |

一人 MAY 承担多个角色，但涉及共享 DDL、高风险写 Tool 或安全例外时，授权职责 MUST 明确记录，MUST NOT 由执行者默认自批。

## 8. 规范修改流程

规范修改 MUST 遵循以下顺序：

1. 明确问题、适用范围、受影响角色和当前自动化；
2. 若改变已批准架构裁决，先创建新 ADR 或替代设计，并标明替代关系；
3. 更新分领域规范，必要时同步 `AGENTS.md`、`Agent.md`、本索引、模板和 `CONTRIBUTING.md`；
4. 更新或新增能够执行的契约、架构或文档测试；
5. 执行与变更匹配的当前门禁，记录命令、退出码、通过/失败数量和未验证项；
6. 评审通过后更新文档状态和更新时间。

规范修改 MUST NOT 静默覆盖已批准裁决，MUST NOT 通过示例绕过正文规则，也 MUST NOT 把尚未安装的工具描述为当前门禁。

## 9. 例外流程

对 `MUST` 或 `MUST NOT` 的例外 MUST 写入对应设计或 ADR，至少包含：

- 被豁免的规则及文档位置；
- 技术或业务原因与备选方案；
- 风险、影响范围和数据边界；
- 补偿措施及可执行验证；
- 责任人、批准者；
- 生效时间、到期时间或复审条件；
- 恢复合规的移除条件。

口头约定、聊天记录、Issue 标题和代码注释 MUST NOT 代替正式例外记录。例外到期或复审条件满足时，责任人 MUST 重新评估；无法继续满足安全、租户隔离或共享数据库授权红线的例外 MUST 立即终止。
