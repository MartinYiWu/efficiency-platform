# 运营 Agent 分阶段实施计划

> **执行要求：** 每个阶段必须先生成独立详细实施计划，再使用 `subagent-driven-development`（推荐）或 `executing-plans` 逐任务执行。每个任务均使用复选框跟踪，并在任务间执行文件级复核和新鲜测试。项目永久不使用 Git，不执行提交、分支或 Git 差异流程。

**目标：** 按可独立验证的阶段建设完整运营 Agent，使品牌、IP、内容、渠道、活动、用户增长、数据复盘等场景能够通过统一底座和受控多 Agent 架构快速接入。

**架构：** 统一 Agent Harness 和 LangGraph Runtime 之上建设 Agent 快速构建底座、运营领域内核和 Operation Supervisor。复杂任务由 Supervisor 按能力调度 Specialist，确定性步骤使用普通节点，业务场景通过 Scenario Pack 组合能力。

**技术栈：** Python 3.13、uv、LangGraph 1.x、FastAPI、Pydantic v2、DeepSeek/OpenAI-compatible Provider、PostgreSQL、pgvector、Redis/Taskiq、HTTPX、Jinja2、Docling、PaddleOCR、Polars、COS、pytest/unittest；具体依赖只能在对应已批准实施计划中引入。

## 全局约束

- 只修改 `D:\efficiency-platform\efficiency-platform-agent` 纯 Agent 工程，不涉及 Java 侧或部署架构。
- LangGraph 是唯一 Graph Runtime；不得引入 AutoGen、CrewAI、第二 Agent Runtime 或去中心化 Swarm。
- Multi-Agent 使用中央 Supervisor 调度 Specialist；Specialist 不直接调用其他 Specialist。
- 业务 Agent 不直接调用厂商 SDK；模型、搜索、Embedding、Rerank、OCR、存储均通过 Provider 端口。
- 所有 Tool 调用经过 Tool Runtime 的 Schema、权限、超时、重试、审计和结果治理。
- 所有外部内容和模型输出视为不可信数据，不得改变系统指令、权限或 Tool 范围。
- 不主动发布内容、不管理平台账号、不接入付费商业热点/新闻/舆情数据源、不做 Text2SQL。
- 不提前建设监控平台和性能平台；必须保留 Run、Step、Invocation、Usage 和质量事实。
- 新增行为必须测试先行；完成声明必须附新鲜验证证据。
- 项目自行编写的注释、Docstring、SQL 注释和配置说明使用中文。
- 项目永久不使用 Git；通过文件快照、文件级差异包、进度账本和测试证据评审。

## 1. 计划拆分原则

运营 Agent 设计包含多个可以被不同评审者独立接受或拒绝的子系统，不能在一个实施计划中同时落地。每个阶段必须满足：

1. 有稳定输入输出契约；
2. 能使用 Fake/Stub 独立测试；
3. 不依赖尚未批准阶段的具体实现；
4. 通过阶段门禁后才能成为下一阶段依赖；
5. 真实 Provider、数据库和网络验收与离线测试分开记录。

## 4. 跨阶段契约冻结顺序

1. S1 冻结 Agent、能力、注册、校验和装配契约。
2. S2 冻结运行入口、Graph State、Prompt、Tool、Provider 和结果契约。
3. S3 冻结运营任务、Profile、计划、证据、交付物和场景包契约。
4. S4 冻结父子任务、DAG、上下文切片、子预算和聚合契约。
5. S5 只实现 Specialist，不得反向修改 S1～S4 公共生命周期；确需修改时先形成架构差异和兼容分析。
6. S6 只组合能力，不拥有第二运行时或复制 Specialist 实现。
7. S7 只验证真实集成和质量，不用 Mock 结果替代真实证据。

## 5. 每阶段统一评审包

每个阶段完成时必须提供：

- 实际新增和修改文件清单；
- 实施前文件快照或可复核的文件级差异包；
- 需求到测试的追踪矩阵；
- 失败测试、最小实现和通过测试的证据；
- 依赖、配置和敏感信息检查；
- 架构方向与中文注释检查；
- 已完成、部分完成、未验证和明确排除项；
- 下一阶段可依赖的稳定接口清单。
