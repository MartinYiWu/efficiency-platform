# S4 受控多 Agent 协作实施计划

> **执行要求：** 实施时必须使用 `subagent-driven-development`（推荐）或 `executing-plans` 逐任务执行。步骤使用复选框跟踪。项目永久不使用 Git，每个任务以实施前文件快照、文件级差异包、测试输出和进度账本替代提交操作。

**目标：** 在 S1 显式 Agent 注册底座、S2 统一执行主链和 S3 运营领域契约之上，实现一个有界、可恢复、可取消、可审计的 Operation Supervisor，使复合任务能够通过能力需求形成 DAG、分配不可突破的子预算、受控并行调度合成 Specialist，并以明确的完整、部分、等待、取消或失败状态聚合结果。

**架构：** S4 将框架中立的 DAG、预算账本、调度状态、节点函数和条件函数放在 `core`、`agents/operation/supervisor` 与 `strategies/multi_agent`，唯一 LangGraph `StateGraph` builder 固定放在 `orchestration/builders/operation_supervisor.py`。Harness 入站只提供受信运行上下文和原始 `OperationRequest`，Supervisor 依次调用 S3 的 intent、planning、assembly 端口生成任务、计划和最终交付包，不接受调用方预填 `OperationTaskSpec`、`OperationPlan`、`TaskGraph` 或结果状态。Supervisor 是唯一允许查询 Registry、经 Factory 装配 Specialist 并创建 `SupervisorTask` 的组件；Specialist 只能返回结构化结果或后续能力需求，不能直接发现、实例化或调用其他 Specialist。

**技术栈：** Python 3.13、标准库冻结 `dataclass`/`Protocol`/`asyncio`、S1 `AgentRegistry`/`AgentFactory`/`AgentPlugin`、S2 已规划的 LangGraph 1.x、`GraphRegistry`、统一 `GraphRuntime`、Harness、Checkpoint、事件和可唤醒取消端口、S3 运营领域契约与 intent/planning/assembly 端口、`unittest`/`IsolatedAsyncioTestCase`。本阶段只使用合成 Fake Specialist 和测试态内存替身，不连接真实 Provider、网络、数据库、Redis、COS 或外部 Tool。

## 全局约束

- 只修改 `D:\efficiency-platform\efficiency-platform-agent` 的纯 Agent 侧文件，不设计或修改 Java、网关、数据库 DDL、部署拓扑和外部平台接口。
- LangGraph 是唯一 Graph Runtime；只有 `orchestration/**` 可以导入 LangGraph。`strategies/multi_agent/**` 只提供框架中立状态转换、节点函数、条件函数和 Strategy 适配；`asyncio` 只用于受控有界 fan-out、绝对截止时间和取消竞争，不形成第二状态机或第二运行时。
- 只有 Operation Supervisor 可以查询 `AgentRegistry`、调用 `AgentFactory.create()` 和调度 Specialist；Specialist 禁止点对点通信、禁止持有 Registry/Factory/Supervisor 引用。
- S4 生产代码不得出现具体业务 Specialist 的 Agent ID、类名分支或部门枚举；选择只依据 `CapabilityRequirement`、任务类型、Schema、权限、工具和版本化注册元数据。
- S4 不创建任何真实业务 Specialist、业务 Prompt、真实 Provider、真实 Tool、网络请求、数据库/Redis/COS 适配器或外部副作用。
- S4 不修改 S1 `AgentPlugin.run(task: SupervisorTask) -> RunResult`；通过新增 `TaskDispatch` 包装 `SupervisorTask`，保持 S1 接口兼容。
- S4 只消费 S2 已冻结的 `GraphBuilder/GraphRegistry`、统一 `GraphRuntime.execute(selection, initial_state)`、恢复、取消和事件加法端口；不得反向要求 S2 为 S4 再改公共生命周期，也不得修改 S2 文件。
- Harness 入站不得携带预计算的 `OperationTaskSpec`、`OperationPlan`、`TaskGraph`、任务状态或结果；计划必须在同一受治理 Run 内由 S3 intent/planning 端口生成。
- 父预算是硬上限。子任务预算、修订预算和聚合保留预算之和不得超过父预算；等待、恢复、重规划、重试或候选切换都不得重置已消耗额度。
- 父 Harness 创建一次绝对截止时间；每个子 Agent 都继承同一绝对截止时间并使用 `asyncio.timeout()` 约束剩余时间。取消等待必须与子任务竞争并能立即唤醒，不能只在下一轮轮询。
- 预算只消费 S2 `GraphExecutionResult.usage`、`UsageSnapshot` 和 runtime facts 等 Harness 可信事实。Specialist 在 `RunResult`、metadata 或结果 envelope 中自报的 usage 不具权威性，必须忽略；绕过子 GraphRuntime 的 Fake Specialist 按分配额度保守核销。
- 默认上限固定为：委派深度 `1`、DAG 依赖深度 `8`、子任务总数 `16`、并发数 `4`、计划修订 `2`、单任务内容修订 `2`。配置只能收紧，任何请求、Prompt、模型输出或 Specialist 结果均不得放大上限。
- 共享 Graph State 只保存 JSON/msgpack 兼容值；不得保存 Agent 实例、协程、Task、锁、Semaphore、SDK 对象、数据库 Session、异常对象或 Secret。
- 所有用户输入、模型输出、Tool 输出和 Specialist 输出均视为不可信数据；结构和权限校验通过后才可进入控制流。
- 新行为必须按 RED → 最小 GREEN → 回归顺序实施；没有新鲜测试证据不得声明完成。
- 项目自行编写的注释、Docstring、计划、报告和配置注释使用中文；标识符和标准技术术语可保留英文。
- 永久不使用 Git，不执行或声称提交、分支、推送、Git diff、Git checkpoint 或基于 Git 的审查。

## 1. 前置状态、依赖假设与硬门禁

### 1.1 已确认的 S1 接口

S1 已实现且离线验证的接口是本计划可直接依赖的现状：

```python
class AgentRegistry:

        raise NotImplementedError

class AgentPlugin(Protocol):
    descriptor: ExtensionDescriptor

```

`AgentSpec` 已提供 `agent_id`、`capability_ids`、`supported_task_types`、输入输出/State/Checkpoint Schema 版本、允许策略、工具白名单、权限、`ExecutionBudget` 和终止条件。`SupervisorTask` 已提供 `task_id`、`parent_run_id`、`target_agent`、`input_data`、`context_view`、`allowed_tools` 和 `budget`。S4 必须适配这些接口，不以破坏性修改换取编排便利。

### 1.2 S2 通用执行端口：S4 只消费和注册

[S2 统一执行主链实施计划](2026-09-03-S2-统一执行主链-实施计划.md)负责冻结通用扩展点；S4 不再把任何生命周期能力列成要求 S2 后补的前置缺口。实施时只核对实际签名，使用 S4 组合根显式注册 `MULTI_AGENT` builder，并消费以下端口：

```python
class StrategyPayloadAdapter(Protocol):
```

S2 通用恢复和取消入站契约固定为 `ResumeRunRequestV1(contract_version="run.resume/1", tenant_id, checkpoint_id, resume_value)` 与 `CancelRunRequestV1(contract_version="run.cancel/1", tenant_id, reason_code)`。S4 不新增平行 API 契约；其 `resume_value` 使用 S4 自有版本化结构表达 `input_request_id`、`plan_revision` 和补充值：

```python
class OperationResumeValueV1(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)

    contract_version: Literal["operation.resume-value/1"] = "operation.resume-value/1"
    input_request_id: str = Field(min_length=1, max_length=128)
    plan_revision: int = Field(ge=0, le=2)
    value: dict[str, JsonValue]
```

S2 内部 `CheckpointView.resume_binding: JsonObject` 是恢复校验的权威绑定，只保存 S4 `input_request_id/plan_revision` 等控制字段，不保存补充正文；对外 `CheckpointViewV1` 仍只暴露 thread/namespace/checkpoint ID。S4 registration 提供 `ResumeValueValidator`，必须在 `WAITING_INPUT → RUNNING` 前把 `OperationResumeValueV1` 与 resume binding 精确比较。

S2 的 `CreateRunRequestV1.strategy_payload_schema_version/strategy_payload` 是唯一通用策略入站信封，默认是 `strategy.none/1 + {}`。`StrategyPayloadAdapter.adapt(schema_version: str, payload: JsonObject) -> StrategyPayload` 在 Harness 内深拷贝、验证并归一化后才构造初始 State；同 Run/Checkpoint 冻结且 resume_value 不能替换。S4 定义 `OperationStrategyPayloadV1(contract_version="operation-strategy-payload/1", operation_request)` 及 adapter，MULTI_AGENT registration 固定同一 schema version 和 `allowed_strategy_payload_keys=frozenset({"operation_request"})`。该 Pydantic 契约 `extra="forbid"`，不能携带 OperationTaskSpec、OperationPlan、TaskGraph、状态或结果；还继承 S2 的 65536 bytes、深度 8、每对象 128 成员、键长 128 约束，不能改变 identity/selection/run/budget/deadline/permissions/tools/models/checkpoint/events。API/调用方永远不能直接提交 AgentGraphState。

S2 的 `GraphBuilder/GraphRegistration/GraphRegistry` 以 `StrategyMode` 显式注册；S2 自身只注册 Direct/Workflow，S4 组合根注册 `MULTI_AGENT`，Router 通过注入的 `available_modes` 决定可选策略。`GraphRuntime.execute` 全文只使用上面的 `selection: StrategySelection` 签名，禁止提供接受裸 `StrategyMode` 的 execute overload 或 S4 私有 Runtime。S4 的 Checkpoint namespace 为 `s2:multi_agent:1`，`GraphExecutionResult.next_status` 只返回注册声明允许的 `WAITING_INPUT/SUCCEEDED/FAILED/CANCELLED/TIMED_OUT`。

S2 事件只做加法扩展：`run_waiting_input/run_resumed/run_cancel_requested/run_cancelled/run_timed_out/budget_exhausted/strategy_event`；S4 结构化事件封装在 `strategy_event.payload`，不得新增 `supervisor_event` 平行通道。等待和终态顺序统一为“Graph Checkpoint 成功 → Harness CAS 权威状态 → Harness 追加对应 Run Event”。恢复固定为“同租户、`WAITING_INPUT`、checkpoint 匹配 → CAS 到 `RUNNING` → `run_resumed` → `GraphRuntime.resume`”；取消固定为“`CancellationSignal.request` 已接受 → `run_cancel_requested` → Graph 节点前后观察并 Checkpoint → CAS 到 `CANCELLED` → `run_cancelled`”。S4 不能修改此顺序，也不能直接操作 EventStore sequence、内存 Checkpointer 或 LangGraph 私有 Snapshot。

可信 Usage 只来自 S2 `ModelRuntime`/`ToolRuntime` 形成的 `UsageSnapshot`、`GraphExecutionResult.usage` 和 runtime facts。若 Specialist 通过 S2 子图执行，S4 消费子图 `GraphExecutionResult.usage`；测试态 Fake 若绕过子图，则按已分配额度保守全额核销，或只登记调度器可证明的 iteration/tool-call，绝不读取 `RunResult.metadata` 或 envelope 自报 usage 后返还预算。

### 1.3 S3 既定边界：本计划使用的类型适配假设

运营架构已经确定 S3 拥有 OperationTaskSpec、Profile、OperationPlan、Evidence、Deliverable 和 ScenarioPack，S4 只消费、不复制这些领域权威契约。[S3 运营领域内核实施计划](2026-09-03-S3-运营领域内核-实施计划.md)已把计划接口具体化为：

```python
class FailureBehavior(StrEnum):
    FAIL = "fail"
    REQUEST_INPUT = "request_input"
    RETRY_ONCE = "retry_once"
    SKIP_WITH_WARNING = "skip_with_warning"


@dataclass(frozen=True, slots=True)
class OperationPlanStep:
    step_id: str
    task_type: str
    depends_on_step_ids: tuple[str, ...]
    required_capabilities: CapabilityRequirement
    input_schema_version: str
    output_schema_version: str
    input_reference_ids: tuple[str, ...]
    context: OperationContext
    allowed_tools: frozenset[str]
    required_permissions: frozenset[str]
    budget: ExecutionBudget
    expected_deliverable_ids: tuple[str, ...]
    quality_check_ids: frozenset[str]
    required: bool
    failure_behavior: FailureBehavior

@dataclass(frozen=True, slots=True)
class OperationPlan:
    contract_version: str
    plan_id: str
    task_id: str
    strategy: StrategyMode
    source_template_id: str | None
    source_template_version: str | None
    success_conditions: tuple[str, ...]
    steps: tuple[OperationPlanStep, ...]
    total_budget: ExecutionBudget
    termination_conditions: frozenset[str]
```

S3 同时冻结 `EvidencePack`、`DeliverableBundle` 和 `OperationQualityReport`，但没有定义 Specialist 运行结果封装；S4 因此只新增版本化编排层 `SpecialistResultEnvelope`，直接兼容承载这三个 S3 权威类型，不能复制它们的字段或把 Evidence 降格为未版本化字符串。实施时由 `OperationPlanCompiler` 将运行中生成的 S3 `OperationPlan` 一次性编译为 S4 只读 `TaskGraph`，由 `SpecialistResultDecoder` 将 S1 `RunResult.output` 解码为 `SpecialistResultEnvelope`。

S3 每个 Step 已显式给出 `task_type`、输入/输出 Schema 版本、`required_permissions`、工具白名单、能力要求、`required` 与子预算，不使用 S4 自创 `budget_weight`。S4 把 Step 预算视为请求上限，再放入 70% 工作预算池中逐字段缩放；`required=False` 只允许搭配 `SKIP_WITH_WARNING`，`required=True` 禁止搭配该行为，S4 编译时再次失败关闭。`failure_behavior` 决定失败后的动作，`RETRY_ONCE` 只允许一次执行重试，不等于内容修订。Specialist 选择必须同时校验 task type membership、S1 `all_of/any_of` 能力、输入/输出 Schema 精确相等、权限子集和工具子集，任一不匹配都在 Factory 创建前拒绝。`source_template_id/source_template_version` 必须成对为空或非空并原样进入运行事实。

### 1.4 S4 启动门禁

正式实施 S4 前必须满足：

1. S1 实际接口与本节一致，现有离线回归通过；
2. S2 已完成并提供 `GraphRegistry`、统一 `GraphRuntime.execute/resume`、Checkpoint、事件、可唤醒取消和可信 Usage/runtime facts 契约；
3. S3 已冻结 `OperationPlan`、含 task type/Schema/permissions 的 `OperationPlanStep`、`EvidencePack`、`DeliverableBundle`、质量契约及 intent/planning/assembly 端口；
4. 形成一份 `docs/superpowers/sdd/operation-supervisor-s4/依赖对照表.md`，逐项记录“本计划假设 → 实际接口 → 适配位置 → 是否阻断”；
5. 若实际接口不一致，只在 S4 依赖对照表中记录并停止对应任务；不得反向修改 S1～S3 公共生命周期、Run 状态机或持久化语义。

### 3.2 DAG 校验与就绪规则

`compile_operation_plan(plan, limits) -> TaskGraph` 必须执行：

1. `plan_id` 和 `contract_version` 非空，初始 `plan_revision == 0`；
2. 任务数在 `1..16`；任务 ID 唯一且稳定排序可复现；
3. 所有依赖存在、不能自依赖、不能有环；
4. 最长依赖路径不超过 `8`；委派深度固定为 Supervisor → Specialist 一层；
5. 每个 S3 Step 预算逐字段不超过 `OperationPlan.total_budget`，且所有 Step 请求预算已通过 S3 总和校验；
6. S3 `required` 原样编译为必需/可选标记，且再次校验 `required=False` 只配 `SKIP_WITH_WARNING`、`required=True` 禁配该行为；`failure_behavior` 独立映射为执行动作，`RETRY_ONCE` 最多执行两次；
7. 上游失败时，依赖任务不得进入 READY；根据失败策略进入 `SKIPPED` 或使计划失败；
8. 同一波次 READY 任务按 `topological_order` 后再按 `task_id` 排序，最多取 `max_parallel_tasks` 个。

### 3.3 预算切分与不可突破规则

预算分配使用整数基点和最大余数法，不使用浮点数。父 `ExecutionBudget` 的每个维度按 `work = parent * 7000 // 10000`、`revision = parent * 1500 // 10000`、`aggregation = parent - work - revision` 切分，因此舍入余量固定进入聚合保留且三者严格等于父值。S2 `BudgetGuard.start()` 在首次运行时一次性生成受信 `BudgetState.deadline_epoch_ms`；S4 只把它复制为 `parent_deadline_epoch_ms` 写入同一 Checkpoint，绝不自行重算。等待、恢复、重试和候选切换都沿用该绝对值；任何子任务的局部 timeout 只能取 `min(child_budget.timeout_ms, parent_deadline_epoch_ms - now_epoch_ms)`，不能延长父截止时间。

```python
@dataclass(frozen=True, slots=True)
class BudgetUsage:
    iterations: int = 0

```

硬规则如下：

- 每个子任务的最终预算是“S3 Step 请求预算、70% 工作池按各 Step 请求值等比例缩放后的额度、AgentSpec 自身预算、父剩余额度、父剩余时间”的逐字段最小值。
- 某维度所有 Step 请求总和不超过工作池时保留各请求值；超过时计算 `floor(work_pool * step_request / request_total)`，剩余额度按 `(除法余数降序, task_id 升序)` 每次加一，直到工作池耗尽。
- `max_iterations` 和 `timeout_ms` 每个被调度任务至少为 `1`；父预算无法为所有必需任务提供最小额度时，在调度前返回 `BUDGET_UNALLOCATABLE`。
- Token、费用、Tool、迭代和耗时任一维度消耗超过子预算时立即产生 `BUDGET_EXHAUSTED`，不能从未来任务静默透支。
- 重分配只能使用“尚未分配额度 + 已释放的未启动任务额度 + 未消费修订保留”；已消费额度、聚合保留和父截止时间不得恢复。
- 一次内容修订最多领取“原任务预算与当前修订保留余额”的逐字段最小值；`max_iterations` 或 `timeout_ms` 不能达到 1 时拒绝修订。计划修订只消耗 Supervisor 迭代和耗时，也从同一修订保留扣减。
- 恢复时从 Checkpoint 的账本快照继续；用户补充输入、计划修订、候选切换和进程重启均不得创建新账本。
- 消费量只接受 Harness 可信 `UsageSnapshot`/runtime facts；Specialist 自报 usage 不参与 `consume()`。没有子 GraphRuntime 可信事实的 Fake 执行按已分配预算保守全额核销，不能因自报低用量返还额度。
- 聚合预算不足时保留已有结构化结果并失败关闭，不能调用模型绕过保留额度。

### 3.4 Specialist 选择

`SpecialistSelector.rank(node) -> Sequence[SelectedSpecialist]` 只允许以下流程：

1. 调用 `registry.match(node.capability_requirement, kind=AgentKind.SPECIALIST)`；
2. 依次过滤 `node.task_type not in AgentSpec.supported_task_types`、S1 `CapabilityRequirement.all_of/any_of` 不满足、`node.input_schema_version != AgentSpec.input_schema_version`、`node.output_schema_version != AgentSpec.output_schema_version`、`node.required_permissions` 不是 Agent 权限声明子集、`node.allowed_tools` 不是 `AgentSpec.allowed_tools` 子集，或 Agent 自身预算无法提供最小一次执行的注册项；Schema 比较必须使用完整版本字符串，禁止模糊前缀匹配；
3. 仅在上述 task type/Schema/permissions/tools/capability 硬条件全部满足后，使用以下升序 tuple 稳定排序：额外能力数、额外权限数、额外工具数、Agent 声明最大费用、`agent_id`；
4. 返回候选注册元数据，不创建实例；调度时才由 `AgentFactory.create(agent_id)` 装配；
5. 装配失败可尝试下一个已排序候选，但每次候选切换必须产生事件且不增加预算；候选耗尽返回 `SPECIALIST_UNAVAILABLE`。

不得用具体 Agent ID、业务域名称、if/elif 路由、导入具体 Specialist 类或 Prompt 输出顺序覆盖上述算法。

### 3.5 等待、恢复与取消

- Harness 入站只允许 `operation-strategy-payload/1` 中的版本化 `OperationRequest`；S2 adapter 校验后把冻结 StrategyPayload 放入 State。Graph 必须先解码 OperationRequest，再调用 `intent.normalize(request)` 得到 `OperationTaskSpec`，构建 `OperationContext` 并调用 `planning.build_plan(task, context)`，随后才允许编译 `TaskGraph`。任何 payload 夹带或调用方预填 task、plan、graph、task_statuses、outcomes 或 completion_status 都以 `PRECOMPUTED_STATE_FORBIDDEN` 拒绝。
- 缺少关键输入时，框架中立节点生成 `InputRequest(request_id, task_id, missing_fields, reason_code, plan_revision)`；LangGraph builder 把 `input_request_id/plan_revision` 写入 Checkpoint `resume_binding`（不含补充正文）后调用 `interrupt()`，由 S2 Harness 按统一顺序进入全局 `WAITING_INPUT`。
- 恢复必须使用原 `run_id`、原 checkpoint namespace `s2:multi_agent:1`、匹配的 `request_id` 和期望 `plan_revision`；不匹配返回 `STALE_RESUME_INPUT`。
- 恢复只重新计算受补充输入影响且尚未成功的节点；已成功结果保持不可变，除非计划版本明确使其失效并产生 `TASK_INVALIDATED` 事件。
- 调度前、每个 Specialist 返回后、进入等待前、聚合前都检查 S2 取消信号。每个正在运行的子任务使用两个 `asyncio.Task` 竞争 `plugin.run(dispatch.task)` 与 `cancellation.wait_requested(run_id)`，并被 `asyncio.timeout(remaining_seconds)` 包围；取消获胜时立即取消/等待执行 task 的协作退出、递增 fence_token 并形成 Checkpoint，不能等到下一轮轮询。
- 已运行任务使用当前 `fence_token`；取消或恢复会递增 fence_token。旧 fence_token 的迟到结果记录 `LATE_RESULT_IGNORED`，不得进入聚合或返还预算。
- 取消是协作式的，不使用线程强杀。Graph 保存已完成范围和账本后映射到全局 `CANCELLED`，不把部分结果包装为成功。

### 3.6 部分失败、有限修订和聚合

- Specialist 异常先归一化为 `SPECIALIST_EXECUTION_FAILED`；原始异常类型和正文不进入 Graph State、事件或外部结果。
- 可选任务 `SKIP_WITH_WARNING` 失败后允许继续；必需任务失败后根据 `FAIL/REQUEST_INPUT/RETRY_ONCE` 的精确语义终止、等待或执行一次重试，不能声明完整成功。
- Specialist 可以在 `SpecialistResultEnvelope` 中返回 `requested_capability`，但只能由 Supervisor 将其转换为同层新任务；新任务仍受总任务数、DAG 深度、计划修订和剩余预算限制。Specialist 不获得目标 Agent ID，也不直接调用其他 Specialist。
- 内容修订最多 `2` 轮，计划修订最多 `2` 轮；修订计数在 Checkpoint 中单调递增，恢复不清零。到达上限返回 `REVISION_LIMIT_REACHED` 或 `QUALITY_NOT_MET`。
- Aggregator 按 `topological_order` 消费不可变 `TaskOutcome`，不改写 Specialist 原始 payload；`EvidencePack` 的 records/supports 必须无损合并并保留来源关联，交付物或证据 ID 重复、同一字段冲突时保留所有候选并输出 `conflicts`，不凭业务偏好静默覆盖。聚合后调用 S3 `assembly.assemble(task, plan, evidence_pack)` 形成最终 `DeliverableBundle`，不得在 S4 复制 assembly 逻辑。
- `COMPLETE` 仅在所有必需任务成功且所有成功条件满足时产生。`PARTIAL` 必须同时给出 `completed_scope`、`missing_scope`、`warnings` 和失败任务。全局映射固定为：`COMPLETE → SUCCEEDED`；`PARTIAL →` 仅当所有必需交付物已完成且计划允许部分结果时映射 `SUCCEEDED`，并强制 `metadata.completion_status="partial"`，否则映射 `FAILED`；`WAITING_INPUT → WAITING_INPUT`；`FAILED → FAILED`；`CANCELLED → CANCELLED`。

## 8. 执行停止条件

出现以下任一情况必须停止当前任务，记录证据并请求架构评审，不得自行扩大范围：

1. S2 或 S3 尚未交付，或实际接口无法无损表达本计划依赖；
2. 需要修改既有 Run 状态机、S1 `AgentPlugin.run` 或 `SupervisorTask` 的已有字段语义；
3. 需要引入第二 Graph Runtime、真实 Provider/网络、数据库 DDL 或外部写 Tool；
4. 预算无法在父上限内为必需任务和聚合保留最小额度；
5. Specialist 必须直接调用另一个 Specialist 才能完成场景；
6. 为通过测试必须硬编码具体业务 Agent ID、平台或部门名称；
7. Checkpoint 无法保证同 Run 恢复、Checkpoint→状态→事件顺序、fence_token 隔离、父 deadline 和预算单调性；
8. 部分失败无法在现有 RunResult/S3 交付契约中被明确表达；
9. S2 GraphExecutionResult/runtime facts 无法提供可信 Usage，且只能依赖 Specialist 自报值；
10. `EvidencePack` 无法通过版本化 Specialist payload 无损进入聚合和 S3 assembly。

此时交付状态应为“阻断”或“部分完成”，不能通过降低测试、跳过门禁或修改术语宣称完成。
