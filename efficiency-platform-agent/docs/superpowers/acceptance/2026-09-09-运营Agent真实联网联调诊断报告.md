## 3. 当前未通过原因

真实请求“收集昨天的 AI 行业动态并编写微信公众号推文”时，DeepSeek 搜索会触发较长的服务端检索和来源整理。当前真实表现包括：

- 意图识别偶发连续两次 30 秒流式超时，最终记录 `INTENT_BUDGET_EXHAUSTED`；
- 意图识别成功后，研究请求可能超过当前 90 秒 Specialist 预算，或返回没有可复核来源，记录 `RESEARCH_INSUFFICIENT`；
- 完整链路因此以失败终态结束，未产生正文或引用，符合失败关闭约束。

这不是前端 SSE、打字机或事件协议问题；Agent 日志已经能够打印模型超时、自动切换候选、研究开始、研究证据不足和 Run 失败等关键事件。

## 4. 后续进入业务联调前的必要决策

1. 是否把联网研究的 Specialist 超时从 90 秒提高到 150～180 秒，并同步提高单 Run 总预算。
2. 是否为研究场景固定使用更强模型；当前强模型真实研究可返回来源，但单次耗时约 2 分钟以上。
3. 是否接受真实 DeepSeek 搜索的长耗时；若不接受，应重新评估免费公共搜索 Provider，而不是伪造来源或绕过 Evidence Gate。

在上述决策确认前，系统保持“真实研究失败即明确失败，不用普通 Chat 响应冒充已联网核验”的行为。

针对输入“帮我写一篇今天的AI行业动态的公众号推文”，已在重启后的真实
FastAPI + SSE 实例上完成复验，结果为 `degraded_succeeded`，不是失败终态：

- 产生 1 份公众号独立成品和 1 条引用，用户侧未看到 Prompt、工具参数或隐藏推理；

本次修复包含三类根因处理：DeepSeek Responses API 的 `open_page` 来源恢复、
服务端搜索工具链用量与内容生成预算隔离、以及“写一篇今天的行业动态公众号推文”
到“研究前置 + 公众号成品”的确定性意图路由。由于外部搜索耗时和来源数量受上游
实时响应影响，结果保留 `degraded=true` 和质量告警，不把有限来源包装成完整热点清单。
