> 本文定义运营 Agent 的业务架构和后续实施边界。本文处于评审中，不表示依赖已经安装、功能已经实现、真实 Provider 已经验证或具备生产运行能力，也不构成业务上线结论。

## 2. 背景

项目已批准采用 Harnessed Hybrid Multi-Agent Architecture：统一 Agent Harness 治理运行，由 Strategy Router 在 Direct、Workflow、ReAct、Plan-and-Execute 和 Multi-Agent 之间选择，所有 Graph 使用 LangGraph，Multi-Agent 使用中央 Supervisor 调度 Specialist Subgraph。

运营 Agent 是首个用于反推底座完整性的真实业务 Agent。最初示例包括 AI 行业动态周报和一次生成小红书、微信公众号、今日头条三个平台的独立文案，但这两个示例只覆盖内容运营。真实运营工作还包括品牌运营、IP 运营、活动策划、用户运营、社群运营、增长运营、产品运营、渠道运营、数据分析和运营复盘。

因此，运营 Agent 不能被实现为一个周报工作流、一个多平台写作 Prompt 或一个无边界的巨型 ReAct Agent。它必须以完整运营生命周期为边界，同时允许后续通过 Specialist Agent、可复用能力和场景包扩展，而不修改 Harness、Graph Runtime 和公共运行生命周期。

## 3. 目标

1. 建立覆盖“洞察—策略—规划—执行物料—指标—复盘”的完整运营领域能力边界。
2. 建立一个中央 Operation Supervisor，能够理解复杂运营请求、生成计划并按能力调度 Specialist。
3. 明确何时创建子 Agent、何时使用确定性节点，避免巨型 Agent和无意义的 Agent 碎片化。
4. 让行业周报、多平台内容、品牌方案、IP 方案、活动策划、增长方案和运营复盘成为可插拔场景包，而不是底层硬编码流程。
5. 支持用户文本、用户上传文件、Agent 知识库和公共互联网四类信息来源。
6. 支持一个请求生成一个或多个相互独立的平台成品，共享事实和策略但不机械改版。
7. 通过结构化契约、来源证据、确定性规则和独立质量审校，提供可解释、可追溯的质量控制。
8. 让未来新增运营 Specialist 或场景时只扩展插件层，不修改统一 Harness、LangGraph Runtime、Provider 和持久化边界。
9. 明确无外部副作用的交付边界：只生成、预览、修改和导出运营产物，不主动发布或发送。

## 4. 非目标

- 不设计或实现 Java 侧接口、权限、网关、领域模型和数据架构。
- 不设计部署拓扑、监控平台、告警平台或性能容量方案。
- 不主动登录、操作或发布到小红书、微信公众号、今日头条等外部平台。
- 不接入付费商业热点、舆情、新闻或搜索数据源。
- 不做 Text2SQL，不生成或执行 SQL，不直接连接业务数据库分析。
- 不替代 AI 客服、AI 人事或 AI 行政 Agent；运营 Agent 只能生成相关运营方案、话术或任务建议。
- 不在没有真实业务数据时虚构曝光、转化、留存、ROI 等运营结果。
- 不建设无中央治理的 Agent Swarm，不允许 Specialist 点对点自由对话。
- 不在本文中确定每个平台所有具体字数、标签和排版阈值；这些规则由版本化 ChannelProfile 和真实样本验证确定。
- 不在本文中授权实现、安装依赖、调用真实模型、访问数据库或执行 DDL。

## 5. 现状

### 5.1 已批准能力

- 总体架构已经明确 Harness、Strategy Router、LangGraph、中央 Supervisor、统一 Context、Tool Runtime、四层记忆、Provider、持久化和评测边界。
- P4 已批准使用 DeepSeek Responses API 服务端 `web_search` 和 JSON Schema 返回带来源的结构化公共研究结果；当前不建设自有搜索、爬虫或浏览器服务。
- P3 已批准文档解析、PaddleOCR、Document AST 和结构优先切片。
- P2 已批准 DeepSeek 默认 LLM、可演进模型池、自适应模型需求、Embedding、Rerank、PostgreSQL FTS、pgvector 和 COS 适配边界。
- P5 已批准确定性评测、JSONL/Parquet 数据集和可选 MCP Client 边界。

### 5.2 当前实现状态

- 当前代码主要是目录骨架和框架中立的核心契约。
- `ExtensionDescriptor`、`AgentPlugin`、`SupervisorTask`、`RunRequest`、`RunContext`、Tool 和 Provider 契约已经存在，但不足以表达完整运营 Agent 定义、能力发现、领域计划、产物和质量结果。
- `agents/`、`strategies/`、`capabilities/research/`、`prompts/` 等目录尚无真实运营功能实现。
- P0～P5 组件批准不等于依赖已安装或真实质量已经验证。

### 5.3 核心差距

1. 缺少通用 `AgentSpec`、Registry、Factory 和 Validator。
2. 缺少运营领域任务、上下文、计划、交付物和质量契约。
3. 缺少按能力调度 Specialist 的 Operation Supervisor。
4. 缺少可参数化的平台 Profile 和多平台并行生成模式。
5. 缺少研究证据与运营结论、内容事实之间的强关联。
6. 缺少能覆盖品牌、IP、活动、增长和复盘的场景包机制。

## 6. 约束与设计原则

| 约束/原则 | 来源 | 对设计的影响 | 验证方式 |
|---|---|---|---|
| 只处理纯 Agent 侧 | 项目治理规则 | 所有组件均位于 Agent 工程；不设计 Java 接口 | 架构依赖检查和文档评审 |
| LangGraph 是唯一 Graph Runtime | 总体架构 | 所有策略和 Specialist Subgraph 由统一运行时承载 | 依赖与 AST 架构测试 |
| 中央 Supervisor 调度 | 总体架构 | Specialist 不直接调用其他 Specialist | 契约测试和调用图测试 |
| Agent 按能力发现 | 快速扩展目标 | Supervisor 不写死部门名和具体实现类 | Registry/Factory 契约测试 |
| 组合优先于深继承 | 可维护性要求 | Agent 通过 Spec、策略模板、能力和 Profile 装配 | 新 Agent 文件变化验收 |
| 有独立目标才创建子 Agent | 复杂度治理 | 确定性转换和格式校验保持为普通节点 | 组件职责评审 |
| 外部内容全部不可信 | 安全规范 | 外部文本不能改变系统指令、权限或工具范围 | Prompt Injection 拒绝测试 |
| 模型由 Harness 自适应选择 | ADR-0001 | Agent 只声明 ModelDemand，不写死模型 ID | 路由契约测试 |
| 无主动平台发布 | 用户确认 | 不存在发布 Tool、账号凭据或平台写操作 | Tool 白名单检查 |
| 无付费商业数据源 | 用户确认和 P4 | 搜索不可用时失败关闭，不自动切换付费来源 | Provider 配置与失败测试 |
| 用户输入不完整时自适应处理 | 用户确认 | 关键字段缺失才暂停；非关键字段形成显式假设 | 完整性策略测试 |
| 一个请求支持多个平台独立成品 | 用户确认 | 平台任务并行，每个平台独立生成和校验 | 多平台验收场景 |
| 工程注释和配置说明使用中文 | 项目治理规则 | 后续新增代码注释、Docstring 和配置说明使用中文 | 源码与配置治理测试 |
| 项目永久不使用 Git | 项目治理规则 | 审查使用文件快照、差异包和项目内进度账本 | 交付清单检查 |

## 7. 候选方案与裁决

| 方案 | 概述 | 优点 | 代价/风险 | 裁决 |
|---|---|---|---|---|
| 单一巨型 ReAct Agent | 一个 Agent 通过大 Prompt 完成研究、策略、创作和审校 | 原型代码少 | 上下文污染、行为不稳定、难以测试、成本和循环不可控 | 不采用 |
| 每个场景一个独立 Agent | 周报、品牌方案、活动方案和各平台分别独立建设 | 单场景容易理解 | 重复建设研究、上下文、质量和模型逻辑；场景组合困难 | 不采用 |
| 固定大工作流 | 所有运营任务走同一组固定步骤 | 稳定、容易审计 | 简单任务浪费，复杂任务缺乏适应性，难覆盖未知运营组合 | 不采用 |
| Supervisor + Specialist + 场景包 | Supervisor 生成受控计划，按能力调用 Specialist；确定性步骤使用节点；场景包组合能力 | 覆盖完整、可组合、可测试、支持并行和渐进扩展 | 需要先建设契约、Registry、规划和聚合机制 | 采用 |

最终采用 **一个 Operation Supervisor + 可注册的 Specialist Agent + 参数化 Channel Agent + 确定性工作流节点 + 可插拔 Scenario Pack**。

## 10. Agent、节点与服务的划分

### 10.1 创建 Specialist Agent 的条件

满足下列多数条件时应创建 Specialist：

- 能独立接受一个有业务意义的子目标；
- 需要多步推理、自主规划或反复探索；
- 有独立专业 Prompt、知识和工具范围；
- 需要独立上下文切片和记忆策略；
- 可能独立失败、重试、降级或暂停；
- 能返回可验证的结构化结果；
- 能被多个场景包复用。

### 10.2 保持为工作流节点的条件

以下能力默认保持为普通节点或服务：

- Schema 校验和字段归一化；
- 必填条件和平台 Profile 校验；
- URL 协议、时间窗、长度和重复检查；
- Markdown 或结构化格式封装；
- Artifact 保存和引用生成；
- 预算扣减、状态转换和事件记录；
- 不包含自主业务判断的确定性计算。

## 11. 核心领域契约

### 11.1 Agent 与能力定义

`AgentSpec` 是所有 Agent 的通用可机器读取定义，至少包括：

- `agent_id`、语义版本、负责人和显示名称；
- Agent 类型、能力 ID 和支持的任务类型；
- 输入、输出、State 和 Checkpoint Schema 版本；
- 允许策略、Prompt Bundle、Tool 白名单和知识范围；
- Memory Policy、ModelDemand Policy、预算和终止条件；
- 质量要求、兼容范围和降级行为。

`AgentRegistry` 管理 Agent，`CapabilityRegistry` 建立能力到 Agent 的匹配关系，`AgentFactory` 负责装配，`AgentValidator` 在注册前拒绝缺失或冲突的定义。

### 11.2 OperationTaskSpec

Operation Supervisor 对用户输入归一化后形成：

| 字段组 | 内容 |
|---|---|
| 任务身份 | 任务 ID、租户、用户、会话、父任务 |
| 运营范围 | 品牌、IP、内容、渠道、活动、用户、增长、产品、数据或复合任务 |
| 运营动作 | 研究、分析、规划、策划、创作、改写、适配、复盘、优化 |
| 目标 | 曝光、认知、拉新、激活、参与、留存、转化、复购或用户自定义目标 |
| 对象 | 品牌、IP、产品、活动、账号、用户群、渠道或内容资产 |
| 约束 | 受众、时间窗、语言、调性、长度、平台、素材、禁止项和截止条件 |
| 来源范围 | 用户输入、上传文件、知识库和公共互联网 |
| 交付物 | 类型、数量、平台、格式、结构和质量要求 |
| 自主假设 | Agent 补全的非关键条件、依据和可修改标识 |
| 完整性 | 已满足字段、关键缺失字段、是否必须等待用户输入 |

关键字段是否缺失不能只按字段名判断，必须结合任务判断。例如“改写用户已提供的公众号文章”不需要重新询问市场和品牌定位；“制定新品牌年度运营战略”在品牌、产品和目标完全缺失时必须暂停补充输入。

### 11.3 OperationContext 与 Profile

| Profile | 主要内容 | 使用边界 |
|---|---|---|
| BrandProfile | 定位、价值、调性、标准用语、禁用表达 | 只保存经用户或受信知识确认的品牌事实 |
| IPProfile | 身份、人设、专业边界、表达风格、内容支柱 | 候选人设与确认人设必须区分 |
| ProductProfile | 产品事实、功能、卖点、受众和使用场景 | 未验证的优势不得转为事实性宣传 |
| AudienceProfile | 受众特征、需求、痛点、场景和内容偏好 | 不保存超出必要范围的个人敏感信息 |
| ChannelProfile | 平台结构、语气、篇幅、排版、标签和校验版本 | 规则随平台变化而版本化，不散落在 Prompt 中 |
| CampaignProfile | 目标、主题、周期、资源、机制、风险和依赖 | 计划和已执行事实必须区分 |
| MetricProfile | 指标定义、口径、目标、来源和周期 | 无真实数据时只能定义指标，不产生结果值 |

### 11.4 OperationPlan

复杂任务由 Supervisor 形成有向无环任务图，包含：

- 目标和成功条件；
- 子任务、能力需求和候选 Specialist；
- 输入依赖、串并行关系和交付物；
- 分配给子任务的上下文切片、工具和预算；
- 质量门禁、暂停点和终止条件；
- 失败时的重试、降级、跳过或请求用户输入策略。

### 11.5 EvidencePack

每条事实性证据至少包含：来源标题、发布者、URL、发布时间、检索时间、支持的结论 ID、来源类型、时间窗状态、重复状态和质量状态。Schema 合法不代表事实真实；当前没有直接打开 URL 的能力时，只能声明来源字段完整和结论可关联，不能声明已经完成网页原文核验。

### 11.6 OperationDeliverable

统一交付物封装支持：研究报告、品牌/IP/活动/增长方案、内容矩阵、内容日历、平台内容、运营 SOP、Brief、任务计划、指标体系、数据分析和复盘报告。每种交付物拥有独立 Payload Schema，共享：

- 交付物 ID、类型、版本和标题；
- 适用对象、渠道和时间范围；
- 正文或结构化 Payload；
- Evidence 引用、假设、告警和缺失范围；
- 生成过程、Prompt/Profile 版本和质量报告引用；
- Artifact 存储引用。

### 11.7 Scenario Pack

场景包只定义任务模板，不拥有独立运行时。其元数据包括：

- 场景 ID、版本、适用意图和触发条件；
- 必需信息、可默认信息和澄清策略；
- 所需能力、推荐策略和计划模板；
- Prompt、Profile、输出 Schema 和质量清单；
- 预算、终止条件和失败行为。

## 12. 组件职责

| 组件 | 所有者 | 输入 | 输出 | 依赖 | 禁止依赖 | 职责边界 |
|---|---|---|---|---|---|---|
| Operation Supervisor | `agents/operation/supervisor` | RunRequest、Context | OperationPlan、Deliverable Bundle | Registry、策略、Specialist 端口 | 厂商 SDK、具体平台发布接口 | 理解、规划、调度和汇总，不承担全部专业创作 |
| Intent/Completeness Node | 运营工作流 | 用户输入、Profile | OperationTaskSpec、补充输入请求 | Prompt、Schema | 外部副作用 | 归一化需求，不制定完整方案 |
| Agent/Capability Registry | 通用 Agent 底座 | AgentSpec、CapabilitySpec | 注册快照、能力匹配 | Core 契约 | 业务 Provider | 管理注册和匹配，不执行 Agent |
| ResearchInsightAgent | 运营 Specialist | ResearchTask、Context | EvidencePack、InsightReport | Public Research、RAG | 发布 Tool | 研究和洞察，不编造来源 |
| BrandOperationAgent | 运营 Specialist | BrandTask、Evidence、Profile | BrandStrategyDeliverable | Research、Prompt | 平台写操作 | 品牌策略，不声称实施效果 |
| IPOperationAgent | 运营 Specialist | IPTask、Evidence、Profile | IPStrategyDeliverable | Research、Memory | 平台写操作 | IP 定位和运营规划 |
| ContentAgent | 运营 Specialist | ContentTask、Brief、Evidence | ContentPlan、ContentDraft | Prompt、Model | 发布 Tool | 内容策略与创作，不负责外发 |
| ChannelContentAgent | 运营 Specialist | ContentBrief、ChannelProfile | PlatformContent | Prompt、Profile | 平台账号和发布 API | 按一个平台独立创作；可按平台并行实例化 |
| CampaignOperationAgent | 运营 Specialist | CampaignTask、Context | CampaignPlan | Research、Profile | 实际报名、通知、交易系统 | 设计活动而不执行活动 |
| UserGrowthAgent | 运营 Specialist | GrowthTask、Context、数据摘要 | GrowthPlan | Analytics、Research | 直接触达用户 | 用户和增长策略 |
| AnalyticsReviewAgent | 运营 Specialist | 受控表格数据、MetricProfile | Analysis/Review | Polars、结构化读取 | Text2SQL、业务库直连 | 分析用户提供的数据，不虚构数据 |
| QualityReviewAgent | 运营 Specialist | Plan、Deliverables、Evidence | OperationQualityReport | Model、确定性质量规则 | 修改权限、扩大 Tool 范围 | 独立审校并提出结构化修订要求 |
| Output Assembler | 确定性节点 | 已通过交付物 | Result、Artifact | Artifact、Citation | LLM 自主决策 | 格式封装，不改变业务结论 |

## 13. 策略路由

| 任务特征 | 默认策略 | 示例 | 约束 |
|---|---|---|---|
| 简单、无需工具、单一结果 | Direct | 标题改写、语句润色 | 仍需 Schema 和输出检查 |
| 步骤固定、输入充分 | Workflow | 已有原稿转为单个平台格式 | 模型节点不能改变步骤和权限 |
| 需要少量动态研究 | Bounded ReAct | 探索一个近期话题的关键信息 | 限制查询、步骤、时间和 Token |
| 长任务、需要阶段计划 | Plan-and-Execute | 三个月品牌运营方案 | Planner 与 Executor 分离，计划可恢复 |
| 跨能力或多个独立产物 | Multi-Agent | 品牌定位、活动方案和三个平台内容 | Supervisor 调度，Specialist 不互聊 |

一个复杂 Run 可以在顶层采用 Multi-Agent，并在 ResearchInsightAgent 内部使用有界 ReAct；这不代表存在第二运行时。所有策略仍由同一 LangGraph Runtime、预算和 Checkpoint 管理。

## 14. 执行流与数据流

| 步骤 | 执行组件 | 输入 | 动作/状态变化 | 输出/落点 | 失败处理 |
|---:|---|---|---|---|---|
| 1 | Harness | RunRequest | 建立 RunContext、身份、预算和事件 | Run 进入运行态 | 输入或身份非法则拒绝 |
| 2 | Intent Node | 用户输入和可用 Profile | 识别领域、动作、目标、对象和交付物 | OperationTaskSpec | 结构连续失败则返回输入错误 |
| 3 | Completeness Node | OperationTaskSpec | 判断关键缺失；补全非关键字段并记录假设 | 完整 TaskSpec 或补充输入请求 | 关键条件缺失则进入等待输入 |
| 4 | Strategy Router | TaskSpec、风险和复杂度 | 选择 Direct/Workflow/ReAct/Plan/Multi-Agent | StrategySelection | 无合法策略则失败关闭 |
| 5 | Supervisor Planner | TaskSpec、Registry | 生成任务 DAG、预算和上下文分配 | OperationPlan、Checkpoint | 计划无终止或超预算则拒绝 |
| 6 | Context Builder | Profile、Memory、文件、知识 | 形成最小必要上下文切片 | SpecialistContext | 来源或权限不明则排除数据 |
| 7 | Specialist Executor | 子任务和 Context | 串行或并行执行专业任务 | 结构化 SpecialistResult | 按计划重试、降级、跳过或部分失败 |
| 8 | Research/Evidence Gate | EvidencePack | 去重、时间窗、字段和结论关联检查 | 合格证据或质量状态 | 证据不足则禁止事实型完整成功 |
| 9 | Platform Fan-out | ContentBrief、平台列表 | 为每个平台启动参数化 ChannelContentAgent | 多个 PlatformContent | 单平台失败可形成部分结果 |
| 10 | Deterministic Quality | 所有交付物 | 校验 Schema、长度、必填、引用和重复 | RuleQualityResult | 不合格进入修订或失败 |
| 11 | QualityReviewAgent | 计划、证据和交付物 | 审查目标、策略、可执行性和一致性 | OperationQualityReport | 最多触发受限修订，不无限循环 |
| 12 | Supervisor Aggregator | 所有结果 | 解决冲突、合并结果和告警 | Deliverable Bundle | 保留完成范围和失败项 |
| 13 | Output Assembler | Bundle | 生成结构化响应和可下载 Artifact | RunResult、Artifact 引用 | 存储失败不得伪装产物已生成 |

### 14.1 典型复合任务

用户请求：“为一个新的知识类个人 IP 制定三个月运营方案，设计首场线上活动，并生成小红书、微信公众号和今日头条的首批内容。”

```text
第一阶段（并行）
├─ ResearchInsightAgent：行业、竞品和受众研究
└─ IPOperationAgent：根据已有资料形成候选人设

第二阶段
└─ IPOperationAgent：结合研究确认定位、内容支柱和运营阶段

第三阶段（并行）
├─ CampaignOperationAgent：首场活动方案
├─ ContentAgent：三个月内容矩阵和日历
└─ UserGrowthAgent：拉新、激活和留存路径

第四阶段（并行）
├─ ChannelContentAgent(profile=xiaohongshu)
├─ ChannelContentAgent(profile=wechat_official_account)
└─ ChannelContentAgent(profile=toutiao)

第五阶段
└─ QualityReviewAgent：整体一致性、可执行性、证据和平台适配

第六阶段
└─ Operation Supervisor：汇总运营交付包
```

## 15. 多 Agent 协作规则

1. Supervisor 只能根据 Registry 中的稳定能力和契约选择 Specialist，不得依赖具体实现类。
2. Specialist 只接受 `SupervisorTask` 及其运营扩展契约，不直接面对入站 API。
3. Specialist 不直接调用其他 Specialist；需要新能力时返回结构化 `CapabilityRequirement`。
4. Supervisor 对父子 Run、任务 DAG、上下文切片、Tool 白名单、预算、并发和终止条件负责。
5. 每个 SpecialistResult 必须声明完成范围、证据、假设、告警、错误和建议后续能力。
6. 无依赖子任务允许并行；共享可变状态不得由多个 Specialist 直接写入。
7. 冲突结果由 Supervisor 按来源质量、Profile 权威性和任务目标裁决；无法裁决时显式返回冲突。
8. 子任务部分失败时允许返回部分交付，但必须标记缺失范围，不能伪装完整成功。
9. Supervisor 和 Specialist 均不能突破 Harness 分配的总预算；子预算重分配必须形成事件。
10. 多 Agent 深度、子任务数、并发数和修订次数必须受类型化配置约束。

## 16. 场景包设计

首批场景包用于验证能力组合，不限制运营 Agent 的完整范围：

| 场景包 | 主要能力组合 | 主要交付物 |
|---|---|---|
| `industry_digest` | 研究、证据、内容、审校 | 行业动态报告、来源 |
| `multi_platform_content` | 内容、渠道、多 Agent 并行、审校 | 多个平台独立成品 |
| `brand_operation_plan` | 研究、品牌、内容、指标 | 阶段品牌运营方案 |
| `ip_operation_plan` | 研究、IP、内容、渠道 | IP 定位与孵化方案 |
| `campaign_plan` | 研究、活动、内容、用户增长 | 活动方案、排期、物料和指标 |
| `content_calendar` | 内容策略、渠道、运营管理 | 选题库和内容日历 |
| `growth_experiment` | 用户增长、数据、指标 | 漏斗分析和实验计划 |
| `operation_review` | 数据分析、复盘、质量 | 复盘报告和行动计划 |

未知的新场景优先由 Supervisor 动态组合已有能力；只有存在稳定、重复的流程和质量要求时才固化为新场景包。

## 17. 记忆与上下文

| 记忆层 | 运营内容 | 使用规则 |
|---|---|---|
| 工作记忆 | 当前 OperationPlan、子任务、证据、草稿和质量结果 | 作为当前 Graph State，随 Checkpoint 恢复 |
| 短期记忆 | 当前会话的补充条件、修改意见和已生成版本 | 用于多轮修改，不自动成为长期事实 |
| 情景记忆 | 历史运营任务、确认决策、结果、失败经验和复盘 | 只有经过筛选、脱敏和权限校验才可提升 |
| 语义记忆 | 已确认的品牌、IP、产品、受众、渠道规范和知识文档 | 保留来源、版本、权限和有效期 |

Profile 不是模型从一次对话中任意推断后永久保存的事实。候选值、用户确认值、知识库权威值和历史推断值必须区分来源与可信级别。Specialist 只能获得其任务需要的最小上下文。

## 18. 质量设计

### 18.1 质量维度

- 目标一致性：结果是否服务于用户运营目标；
- 策略完整性：是否覆盖洞察、动作、节奏、资源、风险和指标；
- 事实可靠性：事实是否有关联证据，是否符合指定时间窗；
- 品牌/IP 一致性：是否符合已确认 Profile；
- 用户匹配度：是否面向目标受众的需求和场景；
- 渠道适配度：是否符合 ChannelProfile，而非机械换格式；
- 可执行性：是否包含明确动作、负责人占位、时间和交付物；
- 可衡量性：是否定义指标、口径、周期和成功标准；
- 内容质量：是否具体、有信息量、连贯并避免空洞套话；
- 内部一致性：研究、策略、计划、内容和指标是否互相支持。

### 18.2 双层质量门禁

确定性规则负责：Schema、必填字段、长度、平台结构、时间窗、来源字段、结论关联、重复率、预算和终止条件。

QualityReviewAgent 负责：目标匹配、策略合理性、可执行性、表达质量、受众匹配、品牌一致性、平台风格和跨交付物矛盾。审校结果必须使用结构化 `OperationQualityReport`，不能只返回自然语言评价。

### 18.3 有限修订

- 只有可修复且预算允许的问题才进入修订；
- 修订任务必须指出问题、目标字段和保持不变的事实；
- 默认不超过两轮，精确上限由后续类型化配置确定；
- 达到上限仍不合格时返回 `QUALITY_NOT_MET` 或带告警的部分结果；
- QualityReviewAgent 不得扩大 Tool 权限或引入新事实。

### 18.4 高质量声明边界

当前 P4 不主动打开模型返回的 URL，因此可以验证来源字段、时间窗和结论关联，不能保证网页原文已经复核，也不能保证互联网事实绝对真实。真实 PoC 若证明仅依赖服务端搜索无法满足事实质量，必须另行评审免费的网页正文读取和交叉核验能力，并复用 SSRF、版权和站点条款边界；不得在本设计中静默引入。

## 19. 状态模型

本文不新增一套与全局 Run 冲突的权威状态机。运营阶段是 Graph State 中的领域阶段，全局状态继续使用既有 Run 状态。

| 全局状态 | 运营场景进入条件 | 允许转移 | 退出条件 | 持久化/恢复要求 |
|---|---|---|---|---|
| `CREATED/QUEUED` | 请求已归一化、等待执行 | `RUNNING/CANCELLED/FAILED` | Worker 或同步执行开始 | 保存请求和版本 |
| `RUNNING` | Supervisor 或 Specialist 正在执行 | 等待态或终态 | 任务完成、等待、失败、取消、超时 | 关键阶段和长步骤保存 Checkpoint |
| `WAITING_INPUT` | 缺少关键业务条件 | `RUNNING/FAILED/CANCELLED/TIMED_OUT` | 用户补充输入且校验通过 | 使用原 `run_id + checkpoint` 恢复 |
| `WAITING_TOOL` | 等待受治理只读 Tool | `RUNNING/FAILED/CANCELLED/TIMED_OUT` | Tool 返回或失败 | 保存调用 ID、预算和幂等状态 |
| `WAITING_APPROVAL` | 当前首版原则上不应出现外部写操作 | `RUNNING/FAILED/CANCELLED/TIMED_OUT` | 未来受审能力批准或拒绝 | 未经新设计不得用于平台发布 |
| `SUCCEEDED` | 所有必需交付物通过质量门禁 | 无 | 最终结果和产物已持久化 | 保存终态和版本 |
| `FAILED/CANCELLED/TIMED_OUT` | 不可恢复错误、取消或预算耗尽 | 无 | 终态已记录 | 保留已完成范围和错误证据 |

## 20. 错误模型

| 错误类别 | 触发条件 | 对外契约 | 重试/降级 | 审计与记录 |
|---|---|---|---|---|
| `OPERATION_INPUT_INCOMPLETE` | 关键目标或对象缺失 | 等待输入及缺失字段 | 不自动重试 | 记录缺失项，不记录敏感正文 |
| `OPERATION_INTENT_UNRESOLVED` | 无法形成稳定任务理解 | 安全错误和可选补充建议 | 可在预算内重新结构化一次 | Prompt 和 Schema 版本 |
| `SPECIALIST_UNAVAILABLE` | Registry 无匹配能力或 Agent 不健康 | 能力不可用 | 选择兼容 Specialist 或返回失败 | 能力 ID、候选和原因 |
| `SPECIALIST_PARTIAL_FAILURE` | 部分子任务失败 | 部分结果、缺失范围和错误 | 按计划重试、降级或跳过 | 父子 Run、预算和完成范围 |
| `RESEARCH_UNAVAILABLE` | web_search 或知识检索不可用 | 明确研究不可用 | 不以普通 Chat 伪装搜索，不转付费来源 | Provider、状态、错误类别 |
| `RESEARCH_INSUFFICIENT` | 来源过少、超出时间窗或无法支持结论 | 资料不足或部分结果 | 可调整查询但受总预算限制 | 查询、来源数和质量原因 |
| `EVIDENCE_INVALID` | 来源缺失、重复、非法或无法对应结论 | 不可发布的事实型结果 | 删除无证据结论或请求补充 | 证据 ID 和原因码 |
| `PLATFORM_PROFILE_MISSING` | 请求的平台无有效 Profile | 缺少平台适配能力 | 可返回平台中立内容但必须标记降级 | 平台和 Profile 版本 |
| `OUTPUT_SCHEMA_INVALID` | Specialist 连续返回非法结构 | 结构化执行失败 | 有限结构修复后失败 | Agent、Prompt 和 Schema 版本 |
| `QUALITY_NOT_MET` | 修订达到上限仍不达标 | 告警部分结果或失败 | 不再循环 | 质量维度、修订次数和预算 |
| `BUDGET_EXHAUSTED` | Token、费用、步骤、Tool 或时间达到上限 | 已完成范围和终止原因 | 可按 Harness 策略降级，不能重置预算 | 实际 Usage 和预算来源 |

## 21. 安全与数据治理

1. 用户输入、上传文件、OCR 文本、公共搜索结果和模型输出全部标记为不可信数据。
2. System Instruction、业务 Prompt、外部资料和 Tool 返回必须分区组装；外部文本不能注册 Agent、修改计划权限或扩大 Tool 白名单。
3. 所有数据访问带租户、用户、Agent、Run、来源和权限范围；Specialist 使用裁剪后的只读上下文。
4. 当前不存在内容平台发布、消息发送、账号管理和其他外部写 Tool；生成的“发布计划”只是交付物数据。
5. 用户文件继续使用 P3 的格式、安全、大小、隔离和解析质量边界。
6. 当前不主动请求模型返回 URL；未来增加网页读取必须经过统一 SSRF Policy，拒绝私网、回环、链路本地、云元数据和禁止地址。
7. Secret 只通过受控配置引用进入 Provider，不进入 Prompt、Graph State、事件、日志、Checkpoint 或产物。
8. 日志和事件不得记录完整 Prompt、完整模型原始响应、用户敏感正文或可还原 Secret。
9. Profile 写入长期记忆前必须区分候选与确认状态，并保留来源、版本、权限和保留期限。
10. 本文不建设内容审核能力，但事实证据、品牌约束、外部输入隔离和安全输出边界仍然有效。

## 22. 运行事实与调试

当前只建设执行所需的运行事实，不提前建设监控平台。

| 信号 | 最小字段 | 采集点 | 用途 |
|---|---|---|---|

| Plan 事件 | plan_version、子任务数、依赖、重规划原因 | Supervisor | 解释任务拆分 |

### 23.2 代表性验收场景

1. 生成带来源的行业动态周报。
2. 同一主题一次生成小红书、微信公众号和今日头条三个独立成品。
3. 为新品牌制定阶段运营方案和指标体系。
4. 为知识型个人 IP 形成定位、内容支柱和三个月孵化计划。

6. 基于用户提供的运营数据形成复盘和下一阶段行动计划。
7. 执行同时包含研究、品牌、活动、内容、渠道和增长的复合任务。
8. 搜索不可用、来源不足、一个 Specialist 失败或一个平台 Profile 缺失时返回真实部分状态。
9. 用户在等待输入后补充条件，使用原 Run 和 Checkpoint 恢复。
10. 新增一个测试 Specialist 和场景包时不修改 Harness、Graph Runtime 或 Provider 公共生命周期。

## 24. 迁移与兼容

- 本设计不改变当前已批准的 Harness、Graph Runtime、中央 Supervisor 原则、Provider 边界、数据库选择和 P0～P5 组件裁决。
- 现有 `ExtensionDescriptor`、`AgentPlugin` 和 `SupervisorTask` 作为基础输入，未来通过新增或版本化契约补齐 AgentSpec、能力、运营计划和交付物；不得直接破坏已经持久化的契约语义。
- 新增运营契约前必须明确 Schema 版本；删除字段、改变类型或改变持久化语义时按兼容规范升级主版本。
- 仅将先前“运营内容生产 Agent”的狭窄讨论口径替换为完整运营 Agent，不存在运行数据迁移。
- 若未来引入直接网页读取、平台发布、业务数据库分析或新的权威状态边界，必须单独形成 ADR 或替代设计。

## 26. 风险与缓解

| 风险 | 概率/影响 | 触发信号 | 缓解措施 | 残余风险 |
|---|---|---|---|---|
| 运营范围过大导致首轮失控 | 高/高 | 单阶段同时实现全部 Specialist | 完整架构、分批实施、代表场景纵向验证 | 深度能力仍需持续迭代 |
| 巨型 Supervisor 承担专业工作 | 中/高 | Supervisor Prompt 出现大量领域规则 | 领域逻辑下沉 Specialist 和 Profile | 能力边界需持续评审 |
| Agent 碎片化 | 中/中 | 简单转换也创建独立 Agent | 使用本设计的 Agent 判定标准 | 边界判断仍需架构评审 |
| 平台规则过期 | 高/中 | 输出与真实平台惯例偏离 | ChannelProfile 版本化和真实样本回归 | 平台变化无法完全提前预测 |
| 搜索结果存在虚构或失真 | 中/高 | URL 不可复核、结论无来源 | Evidence Gate、失败关闭、真实 PoC；必要时另评网页读取 | 当前不直接核验网页原文 |
| 多 Agent 成本和延迟过高 | 中/高 | 简单请求启动多个 Specialist | Strategy Router、最小任务 DAG、并行和预算 | 质量与成本仍需真实数据平衡 |
| Quality Reviewer 与生成 Agent 同偏差 | 中/中 | 审校重复接受错误 | 确定性规则优先、固定样本、人工校准 | 语义质量不能被完全证明 |
| Profile 被一次错误推断污染 | 中/高 | 后续任务持续引用错误事实 | 候选/确认分离、来源、版本和权限 | 需要用户纠错机制 |
| 无真实数据却给出效果结论 | 中/高 | 输出包含无来源指标结果 | MetricProfile 和输出规则区分目标、估算与事实 | 用户提供数据本身可能有误 |

## 28. 验收标准

1. 运营 Agent 能表达品牌、IP、内容、渠道、活动、用户、增长、产品、数据和运营管理任务，而不是仅表达周报或文案。
2. Operation Supervisor 能将复合运营请求转换为有终止、有预算、可恢复的 OperationPlan。
3. Supervisor 能通过能力 Registry 调度 Specialist，不写死具体实现类或部门名称。
4. Specialist 不直接调用其他 Specialist，所有协作、预算和上下文由 Supervisor 控制。
5. 新增 Specialist 或 Scenario Pack 不修改 Harness、LangGraph Runtime、Provider 和公共状态生命周期。
6. 用户关键条件缺失时进入等待输入；非关键条件由 Agent 自主补全并显式返回假设。
7. 一个请求可以并行生成多个平台的独立内容，平台版本共享证据和 Brief，但正文不是机械复制。
8. 运营交付物不限于文章，支持策略、方案、日历、SOP、任务、指标、分析和复盘等结构化类型。
9. 事实型结论可关联 Evidence；来源不足、搜索不可用和冲突无法解决时不伪装完整成功。
10. 确定性质量门禁与 QualityReviewAgent 分工明确，修订次数和预算有上限。
11. 不存在主动发布、账号操作、付费商业数据源、Text2SQL 或业务数据库直连能力。
12. Run、Plan、Specialist、模型、Tool、证据、交付物和质量过程具备结构化运行事实，但不要求提前建设监控平台。
13. 测试覆盖简单任务、复杂计划、多 Agent 并行、等待输入、部分失败、恢复、安全拒绝和代表性运营场景。
14. 所有实现状态、真实集成状态和质量证据必须如实区分，设计批准不得被表述为功能已经实现。
