## 1. 背景与目标

当前工程已经建立纯 Agent 侧架构骨架和技术组件选型，但还缺少能够约束人类开发者与编码 Agent 的工程规则。规范体系必须解决以下问题：

1. 根目录必须存在一份可被编码 Agent 自动发现的强制规则；
2. Agent 架构总纲和普通工程规则必须分开，避免架构裁决被编码细节淹没；
3. 设计文档、ADR、实施计划、SQL 变更等产物必须有稳定命名和模板；
4. Python 注释、Docstring、异常、类型、异步和日志规则必须可检查；
5. Graph、Agent、Prompt、Tool、Provider 等 Agent 特有扩展必须有统一契约；
6. 数据库变更必须具备预检、执行、验证、回滚和明确授权边界；
7. 规范需要区分强制要求、推荐要求和可选实践，并定义例外流程；
8. 后续可以逐步映射到测试、Lint、类型检查和架构守卫，而不是永久停留在文字层面。

## 2. 当前候选方案

当前候选基线采用“根规则入口 + 模块化规范 + 可复用模板”的组织方式；正式批准仍需可审计的评审人与批准证据。

- `AGENTS.md` 是强制规则入口，面向所有进入仓库工作的编码 Agent 和开发者；
- `Agent.md` 是纯 Agent 侧架构与扩展总纲，解释运行范式、核心边界和扩展方式；
- `docs/standards/` 保存分领域详细规范；
- `docs/templates/` 提供设计、决策、选型、计划和 SQL 变更模板；
- `CONTRIBUTING.md` 规定日常开发与评审流程；
- `SECURITY.md` 规定 Agent 特有安全基线和报告方式；
- `sql/README.md` 作为 SQL 变更包的就近入口。

不采用单一超大规范文件，因为它会造成重复、冲突和维护困难；暂不建设独立策略引擎，因为当前通过文档、测试和 AST 架构守卫即可形成第一阶段治理闭环。

## 4. 规则表达方式

每份规范统一使用以下等级：

| 等级 | 含义 | 处理方式 |
|---|---|---|
| MUST / 必须 | 不满足即视为不合规 | 合并或交付前必须修复，或取得书面例外批准 |
| MUST NOT / 禁止 | 明确不可出现的行为 | 发现后立即停止相关操作并修复 |
| SHOULD / 应当 | 默认执行，但允许有证据地偏离 | 评审说明原因、风险和补偿措施 |
| MAY / 可以 | 可按场景选择 | 不作为质量门禁 |

强制规则尽可能同时声明：适用范围、验证方式、失败处理和例外授权者。不同文档冲突时按以下优先级处理：

```text
用户当前明确要求
  > 根目录 AGENTS.md
  > 已批准 ADR / 架构设计
  > 分领域规范
  > 模板与示例
```

## 5. 根目录文档职责

### 5.1 AGENTS.md

`AGENTS.md` 保持短而强，包含：

- 纯 Agent 侧边界，禁止设计或修改 Java 侧；
- 先阅读架构、选型和规范索引；
- 保护已有文件和未提交改动；
- 禁止绕过 Provider、Tool Runtime、Context Builder 和 Graph Runtime；
- 新功能的测试、类型、Lint、架构守卫要求；
- 数据库变更的只读预检和明确授权要求；
- 密钥、敏感数据和日志红线；
- 文档命名、计划和 ADR 入口；
- 完成声明必须附带新鲜验证证据。

它只保存最高优先级规则并链接详细规范，不复制每份规范全文。

### 5.2 Agent.md

`Agent.md` 包含：

- Harnessed Hybrid Multi-Agent Architecture；
- 五种执行策略及其选择条件；
- Supervisor + Specialist Subgraph 多 Agent 拓扑；
- Run 状态机和暂停、恢复、取消语义；
- Context、Memory、Tool、Capability、Provider 的边界；
- 新增 Agent、Strategy、Workflow、Tool、Provider、Prompt 的准入条件；
- 当前不支持的 ASR、TTS、语音视频、内容审核和付费热点数据源；
- 与详细架构文档的关系。

### 5.3 CONTRIBUTING.md

规定从需求到交付的标准流程：

```text
确认范围
  → 阅读规范和现有实现
  → 形成设计或 ADR
  → 编写实施计划
  → 测试先行
  → 最小实现
  → Lint / 类型 / 测试 / 架构校验
  → 文档同步
  → 评审与交付
```

同时定义分支与提交建议、文件变更范围、评审清单、禁止提交内容以及无 Git 仓库时的交付方式。

### 5.4 SECURITY.md

规定密钥、租户隔离、Prompt Injection、Tool 权限、SSRF、文件、SQL、日志、模型输出和依赖安全要求。内容审核不在当前范围，但基础运行安全不能因此省略。

## 6. 分领域规范设计

### 6.1 工程与目录规范

明确 Python `src` 布局、测试布局、配置位置、命名方式和模块职责。新增目录必须对应已定义的架构边界；禁止建立 `common`、`utils`、`misc` 等无明确所有权的垃圾层。通用代码应按真实能力归入 `core`、`capabilities`、`providers` 或其他明确边界。

### 6.2 架构与依赖规范

固定依赖方向：

```text
API → Harness → Routing / Orchestration → Strategies / Agents / Workflows
                                            ↓
                   Context / Memory / Tools / Capabilities
                                            ↓
                         Providers / Persistence
                                            ↓
                              Core / Contracts
```

规定 `core` 不依赖上层、内部层不依赖 `api`、Provider 不依赖策略层、业务 Agent 不直接调用其他业务 Agent。新增跨层依赖必须先提交 ADR，并同步架构守卫测试。

### 6.3 Python 编码与注释规范

覆盖：

- 包、模块、类、函数、变量和常量命名；
- 类型标注、不可变数据、Protocol 和 dataclass 使用；
- async 边界、阻塞 I/O、超时、取消和资源释放；
- 异常分类、错误映射和禁止吞异常；
- import 方向和循环依赖；
- 日志字段与敏感信息；
- Docstring 和行内注释；
- 待办标记、废弃代码和魔法数字。

注释规则固定为：

1. 注释解释原因、约束、不变量、风险和非显而易见的取舍，不逐行翻译代码；
2. 公共 API、Protocol、Graph Node、Strategy、Agent Plugin、Tool、Provider 和安全关键函数必须有 Docstring；
3. Graph Node 的 Docstring 必须说明输入状态、输出更新、副作用、暂停点、幂等性和异常；
4. Tool 的 Docstring 必须说明参数、权限、外部副作用、超时、重试和返回结构；
5. Provider 的 Docstring 必须说明厂商能力映射、超时、错误归一化和降级行为；
6. 待办标记必须关联任务编号或负责人，并说明移除条件；
7. 被注释掉的代码不得长期保留，由版本历史承担追踪职责；
8. 标识符使用英文，注释允许中文并保留标准技术术语；同一模块保持语言风格一致。

### 6.4 测试与质量门禁

定义单元、契约、架构、Graph、RAG、Provider 集成、安全和验收测试的边界。新增行为先出现能正确失败的测试，再写最小实现。完成交付至少执行：

- 单元与契约测试；
- 源码编译；
- Ruff；
- mypy；
- 架构依赖守卫；
- 与变更相关的集成或质量回归。

尚未安装的工具必须在文档中标为“门禁目标”，不能虚构已执行结果。

### 6.5 数据库与 SQL 规范

SQL 变更采用独立变更包：

```text
sql/changes/20260901_001_agent运行状态/
├─ 00-变更说明.md
├─ 01-precheck.sql
├─ 02-up.sql
├─ 03-verify.sql
└─ 04-rollback.sql
```

命名规则：

- 目录：`YYYYMMDD_NNN_中文主题`；
- 表、字段、索引、约束：数据库对象使用小写 `snake_case`；
- 索引：`idx_<table>__<columns>`；
- 唯一约束：`uk_<table>__<columns>`；
- 外键：`fk_<from_table>__<to_table>`；
- 检查约束：`ck_<table>__<rule>`。

每个变更包必须包含影响对象、数据量估计、锁风险、兼容窗口、执行顺序、验证标准和回滚边界。共享数据库 DDL 必须先执行只读预检，展示 SQL 和影响，取得明确授权后才能运行。结构变更和大批量数据回填必须拆分；禁止把密钥、真实隐私数据和不可审计的动态 SQL 写入脚本。本规范只定义流程，本次不会创建或执行实际 DDL。

### 6.6 Agent、Prompt 与 Tool 开发规范

规定：

- Agent Plugin 必须声明能力、输入输出 Schema、允许工具、预算和终止条件；
- Strategy 必须声明适用条件、最大步骤、Checkpoint 和失败恢复；
- Prompt 必须有稳定 ID、语义版本、输入变量 Schema、输出 Schema、适用模型和回归用例；
- 大段 Prompt 禁止散落在 Python 业务代码中；
- Tool 必须经过 Tool Runtime，声明权限、幂等、超时、重试、审计和结果大小限制；
- MCP 只解决协议互操作，不绕过内部 Tool 治理；
- Provider 隔离厂商 SDK、响应、异常和配置键。

### 6.7 安全与数据治理规范

覆盖租户与用户上下文、最小权限、输入不可信、Prompt Injection、SSRF、文件校验、只读 SQL、Secret、日志脱敏、模型输出校验、Artifact 生命周期和数据保留。任何跨租户访问、外部写操作和高风险 Tool 必须有显式策略与审计记录。

### 6.8 可观测性与运行治理规范

统一 `run_id`、`trace_id`、`tenant_id`、`user_id`、`strategy`、`agent_name`、`tool_name`、`provider`、`model` 等字段。规定 Graph、Node、LLM、Tool、RAG、OCR 和外部 HTTP Span，指标命名，Token 与费用记录，错误分类，以及禁止记录完整 Prompt、密钥和原始敏感文档。

### 6.9 文档命名与变更治理规范

文档采用中文主题和稳定前缀：

| 文档类型 | 命名格式 | 示例 |
|---|---|---|
| 架构/模块设计 | `YYYY-MM-DD-主题-设计.md` | `2026-09-01-Agent运行时-设计.md` |
| 实施计划 | `YYYY-MM-DD-主题-实施计划.md` | `2026-09-01-Graph运行时-实施计划.md` |
| ADR | `ADR-NNNN-短标题.md` | `ADR-0001-采用LangGraph作为唯一运行时.md` |
| 技术选型 | `YYYY-MM-DD-主题-技术选型.md` | `2026-09-01-OCR能力-技术选型.md` |
| 评审报告 | `YYYY-MM-DD-主题-评审报告.md` | `2026-09-01-RAG边界-评审报告.md` |

禁止使用“最终版”“最新版”“新版本”“修改版”作为版本管理方式。文档头必须记录状态、负责人、适用范围、更新时间和关联决策。状态限定为：草案、评审中、已批准、已废弃。已批准的架构裁决变更必须通过新 ADR 或替代设计完成，禁止静默覆盖历史决策。

## 7. 模板设计

### 7.1 架构设计文档模板

固定包含背景、目标、非目标、约束、架构图、组件职责、数据/执行流、状态与错误、安全、可观测性、测试、迁移、风险、待裁决项和验收标准。正式批准前不得残留未归属的待裁决项。

### 7.2 ADR 模板

固定包含状态、背景、驱动因素、候选方案、最终裁决、正面后果、负面后果、风险、替代或废弃关系。

### 7.3 技术组件选型模板

固定包含需求、硬约束、候选组件、功能对比、成熟度、许可证、成本、运维、生态、PoC 结论、最终选型和退出策略。

### 7.4 实施计划模板

固定包含范围、前置条件、文件清单、分阶段任务、每步验证、数据变更、回滚、风险和完成定义。

### 7.5 SQL 变更说明模板

固定包含目标库、Schema、影响对象、现状预检、SQL 文件、锁与性能影响、兼容性、执行授权、验证、回滚和不可逆事项。

## 8. 自动化映射

第一阶段规则与自动化的映射如下：

| 规则 | 验证手段 |
|---|---|
| 包和目录完整性 | `test_scaffold_contract.py` |
| 依赖方向 | `test_dependency_rules.py` AST 校验 |
| 运行状态与策略枚举 | `test_core_contracts.py` |
| Python 格式与基础缺陷 | Ruff，组件引入阶段启用 |
| 类型契约 | mypy，组件引入阶段渐进启用 strict |
| 单元与异步测试 | pytest + pytest-asyncio，组件引入阶段启用 |
| Secret 与敏感内容 | 评审检查，后续增加 Secret Scanner |
| SQL 完整变更包 | 评审检查，后续增加目录结构测试 |
| 文档命名和元数据 | 评审检查，后续增加文档 Lint |

规范不能宣称尚未安装的工具已经形成门禁。工具引入后必须同步更新 `CONTRIBUTING.md` 和质量门禁文档中的实际命令。

## 9. 例外与变更流程

必须规则的例外需要在对应设计或 ADR 中记录：

1. 被豁免的规则；
2. 业务或技术原因；
3. 风险评估；
4. 补偿措施；
5. 责任人；
6. 到期或复审条件。

口头约定、代码注释和聊天记录不能替代正式例外记录。规范修改遵循“修改设计 → 评审 → 更新规则 → 更新自动化验证”的顺序。

## 10. 验收标准

规范体系落地后必须满足：

- 根目录存在 `AGENTS.md`、`Agent.md`、`CONTRIBUTING.md`、`SECURITY.md`；
- 九份分领域规范和五份模板全部存在且可从索引导航；
- `sql/README.md` 明确 SQL 变更包命名、预检、授权、验证和回滚规则；
- `README.md` 增加规范入口；
- 所有文档不存在无解释的占位内容和互相冲突的规则；
- 规范明确不包含 Java 侧和部署设计；
- 现有 10 个架构测试继续通过；
- 新增文档结构测试，确保必要文件和核心章节不会被误删；
- 项目仍不包含具体业务 Agent、ASR、TTS、内容审核和付费热点数据源实现。
