## 1. 目标、非目标与现状

目标不是训练一个只输出场景标签的分类器，而是形成“可解释、可修正、可执行”的意图视图：目标集合、主题实体、时间、来源限制、交付要求、与上一轮关系及字段来源。

不建设独立 NLU 服务、不训练自有基础模型、不安装 Dify/Coze/Rasa Runtime、不修改业务权限、不把自然语言当作新增工具或场景的授权。

现有链路为 `conversation/service.py → intent_fast_path / IntentInterpreter → ScenarioResolver → 场景提交`。解释器已有结构校验、修复及预算管理；注册表已有未知场景拒绝。保留这些能力，逐步移除业务关键词快路径对语义判断的截断。当前源码入口均见[总览现状](2026-09-16-Agent意图与研究闭环优化总览-设计.md)。

## 2. 技术参考与选择

| 需求 | 开源实现位置 | 本项目采用 | 不照搬部分 |
|---|---|---|---|
| 可配置分类和结构化提取 | 总览 O1 Graphon 分类/参数提取节点，O2 Dify 参数验证测试 | 能力描述 + Schema + 语义解释 + 类型/枚举/必填验证 | Graphon 分类未命中回落第一类，不适合本项目，改为显式 UNKNOWN |
| 对话上下文、Other 分支 | O3 Coze `intent_detector.go`、`prompt.go` | 任务相关历史和未匹配结果 | 不导入 Go/Eino，不用单分类覆盖多目标 |
| 槽位补全、切换任务 | O4 Rasa `FormAction`、Forms 测试 | 已有值复用、增量覆盖、缺失项询问、任务隔离 | 不引入 Rasa Tracker/Runtime，不采用未经核对的商业对话功能 |
| 多语言日期解析 | [dateparser](https://github.com/scrapinghub/dateparser) + Python `datetime/zoneinfo` | 库识别日期表达，项目统一日历边界、基准时刻和时间口径 | 日期库的启发式默认不是业务真相；模糊表达不静默猜测 |

方案比较：关键词分类维护成本低但语义边界差；直接训练监督分类器需要业务标注且对新目标适配慢；推荐“受控模型解释 + 类型化状态 + 确定性执行约束”。这些约束属于产品语义，不宣称开源代码已经覆盖本项目所有需求。

## 3. 组件职责和调用链

```text
ConversationService
  → 读取同租户会话与 active_task（版本化）
  → ContextBuilder（可信注册描述 + 用户/历史，分区装配）
  → IntentInterpreterV2（一次结构化语义解释）
  → IntentPatchValidator（结构、引用原文、权限边界）
  → IntentStateReducer（应用增量，不负责猜意图）
  → TemporalResolver（确定日历范围）
  → CapabilityBinder（注册能力匹配及参数验证）
  → IntentDecisionPolicy
       ├─ READY → Scenario/TaskPlan → 原 Strategy Router
       ├─ CLARIFY → 保存 pending → 等待用户提供参数
       ├─ UNSUPPORTED → 说明能力边界，不执行
       └─ FAILED → 保留调用错误，不伪装用户表达不清
```

| 组件 | 输入 | 输出 | 职责边界 |
|---|---|---|---|
| Interpreter | 当前消息、裁剪历史、能力描述、结构 Schema | IntentPatchV2 | 识别语义，不写库、不触发业务工具 |
| Reducer | 上一快照、验证后 Patch、基准 revision | 新 IntentFrameV2 | 确定性合并；不调用模型 |
| TemporalResolver | TemporalExpression、Anchor、Timezone | ResolvedTimeWindow 或歧义 | 不决定任务类型，不读取系统隐式时间 |
| CapabilityBinder | Frame、显式注册目录 | CapabilityPlanV2 | 检查存在、权限、参数和依赖；模型候选非执行授权 |
| DecisionPolicy | 校验结果、未决项、绑定结果 | READY/CLARIFY/UNSUPPORTED/FAILED | 最终准入；不依据模型自报 confidence 单独放行 |

所有模型调用复用 ModelRuntime 和 ADR-0001；模板进入现有 Prompt 管理，禁止在组件内部另拼一套不可审计系统提示。

## 4. 类型化意图视图

### 4.1 IntentFrameV2

拟在 `contracts/intent_v2.py` 定义 Pydantic v2 边界契约，`extra=forbid`；核心状态转换使用不可变类型。V1 不原地增加大量可选字段。

| 字段 | 类型及规则 |
|---|---|
| `schema_version` | 固定 `intent-frame/2` |
| `task_id, revision` | 服务端任务 ID 与单调正整数版本 |
| `message_id, anchor_time, timezone` | 服务端可信消息 ID、接收时刻、有效 IANA 时区 |
| `dialog_act` | `new_task / answer_clarification / refine / follow_up / cancel / resume / chat`，受控对话操作，不是业务场景枚举 |
| `goal_nodes` | 最多 8 个 GoalNode，描述目标、依赖、候选能力；超限应澄清/拒绝，不能静默截断 |
| `topic, entities, exclusions` | 类型化字段记录；实体含原文、标准名、角色，未知标准名可保留原文 |
| `temporal` | 原表达、语义类型、基准、时区、解析窗口、时间口径及歧义 |
| `source_constraints` | 来源角色、允许/排除来源、语言、事件地区；事件地区和发布者所在地区分开 |
| `output_requirements` | 输出形式、目标平台、数量规则、风格、语言；目标平台不是来源平台 |
| `ambiguities` | 字段、候选解释、执行影响、是否阻断 |
| `binding` | 已验证能力计划或不可执行原因 |
| `decision` | 结果、原因码、需要澄清的字段；不记录隐藏思维过程 |

`GoalNode`：`goal_id, description, candidate_capability_ids, depends_on, parameters`。`parameters` 由选中能力的版本化 Schema 校验，禁止无约束 `dict[str, Any]`。未绑定阶段只保存目标描述和通用槽位，不接受任意执行参数。

固定的是契约和注册能力，开放的是用户表达。新增业务能力通过显式注册及测试扩展，不是在 Prompt 中再补一串触发关键词。

### 4.2 字段来源和未知值

每个业务字段采用 `FieldValue[T]` 概念，必须记录：

- `value`：已提取或规范化的值；未知为 null，不是空字符串或模型猜测。
- `origin`：`explicit / inherited / default / derived`。
- `source_message_id`、`source_span`：显式字段的文本区间；按 Unicode 字符切片验证必须对应当前/可见历史消息。
- `inherited_revision`：继承字段来自哪一版；跨任务继承必须明确。
- `normalizer_version`、`default_policy_id`：派生或默认时记录相应版本。
- `validation`：`valid / ambiguous / invalid / unknown`，及稳定原因码。

不让模型为权限、租户和预算提供这些字段。未明确条数时，可采用透明默认的“最多 5 条”；不能把默认写成用户要求“必须 5 条”。

### 4.3 IntentPatchV2 与清空语义

`IntentPatchV2` 包括 `base_revision, dialog_act, goal_updates, field_operations, unresolved_references`。字段操作采用显式的 `set / clear / append / remove`，带白名单字段标识、类型化值和来源；禁止任意 JSONPath。

- 没出现的字段不变；`clear` 才清空；`null` 不能同时表示未提及与清空。
- 用户“不要公众号了”生成删除交付平台操作；“不要国内新闻”生成来源/事件地区排除，不是删除主题。
- 原文跨度不匹配或指向网页内容时，Patch 无效，进入受预算限制的修复。

## 5. 识别精度和执行准入

### 5.1 一次解释为主，按错误补充调用

1. 从能力注册表导出候选 ID、描述、正反例、参数 Schema、执行风险及支持的输出。
2. 当前仅少量场景时全部提供；注册目录过大时才评估检索候选，不为八个场景额外引入向量路由。
3. 模型返回 Patch、目标及结构化歧义，而不是自由文本计划。
4. Schema 校验失败最多修复一次，复用现有解释器记账和截止时间逻辑。
5. 类型有效但有关键语义冲突时，可申请一次强模型复核；它与格式修复共享总调用上限，首轮建议最多 3 次，且不得突破 Harness 总预算。
6. 复核仍不能决定时，仅询问会改变执行的关键问题；模型超时或宕机返回技术错误，不能循环询问用户。

### 5.2 置信度不能伪造

删除业务快路径固定 `0.98/0.90` 作为准入依据的做法。模型自报数值最多用于诊断，不解释为准确率。

READY 必须满足：Schema 有效、关键字段可溯源、时间/范围无阻断冲突、能力与权限匹配、依赖无环、必需参数齐备。

若后续确有数值阈值需求，必须用独立中文标注集校准选择性准确率与覆盖率，并固定校准版本；未校准前不靠数值阈值放行。V1 `confidence` 为兼容字段时只保留真实旧解析结果，不给 V2 任意填 1.0；新链路在内部依据 Decision 执行。

### 5.3 快路径边界

业务新闻、内容生成、相对时间和多轮条件修改全部进入语义解释。快路径仅保留明确协议操作，例如按钮发送的取消命令、健康查询及已验证的幂等重放；纯聊天也必须避免错误触发研究。

“你叫什么名字”无研究工具调用；“这篇文章介绍‘收集昨天新闻’按钮怎么实现”不能因引用文字直接发起新闻任务。

## 6. 时间解析设计

### 6.1 语义与计算分离

模型或日期库抽取原始表达和语义结构：`calendar_period / rolling_duration / explicit_range / before_after / unspecified`。日期库识别自然语言，标准库负责最终边界，不让模型随意生成 epoch 值。

优先级：用户明确时区 > 会话受信任配置 > 租户默认 > 产品默认 `Asia/Shanghai`。默认必须可见且可覆盖。外部网页不能设置该时区。

固定 `anchor_time` 为请求接收时刻。等待、重试、恢复都不让同一时间表达漂移；新消息明确修改时间时使用新消息 anchor，纯继承保持旧 anchor。

时间窗口统一 `[start, end)`，入库 UTC，展示按用户时区。来源的日期无时区且无法可靠确定时，记录不确定性，不假设北京时间。

### 6.2 固定时钟用例

测试时钟：`2026-09-16T09:41:00+08:00`。

| 表达 | 本地窗口 | 判定 |
|---|---|---|
| 昨天 | 09-15 00:00 至 09-16 00:00 | 日历日，不等于最近 24 小时 |
| 最近 24 小时 | 09-15 09:41 至 09-16 09:41 | 滚动时长 |
| 上周 | 09-07 00:00 至 09-14 00:00 | 默认周一为周起点，策略版本化 |
| 9 月 10 日到 12 日 | 09-10 00:00 至 09-13 00:00 | 自然语言日期终日包含，内部右开 |
| 最近几天 | 默认近 7 天或澄清，由任务策略决定 | 标注默认，不伪装用户明确范围 |
| 昨天发布、今天有更新 | 发布窗口与更新条件分别保存 | 不把更新时间替代首次发布时间 |

“昨天”的 UTC 窗口为 `2026-09-14T16:00:00Z` 至 `2026-09-15T16:00:00Z`。夏令时地区按日历边界计算，不固定减 86400 秒。

日期库无法解析、模型与日期库不一致、范围反转、未知年份会实质改变结果时，输出 `TIME_AMBIGUOUS / TIME_INVALID`。不支持的表达保留原文并澄清，不静默退到 7 天。

默认新闻时间口径为首次发布时间；事件发生时间可另选。历史热榜任务要求历史榜单来源，不能用当前榜单回填。

## 7. 多轮合并和任务生命周期

| 新消息 | 状态操作 | 保留 | 清除/重算 |
|---|---|---|---|
| “只看国内的” | refine 当前研究任务 | 主题、时间、输出形式 | 地区约束、来源计划、质量覆盖 |
| “改成上周” | 更新 temporal | 主题及输出 | 时间窗口、来源历史能力判断、证据资格 |
| “再写成公众号” | 增加依赖研究结果的生成目标 | 可用研究证据 | 输出计划；不默认重新采集 |
| “不是 AI，是新能源” | 替换主题，形成新 revision | 未冲突的时间、格式 | 主题实体、候选事件和主题相关判断 |
| “另一个问题，帮我写招聘文案” | new_task | 仅明确可复用的用户偏好 | 不继承新闻主题、地区、时间 |
| “不要了” | 识别取消目标，必要时澄清 | 已有审计和产物 | 通过既有取消入口终止后续工具 |
| “继续” | resume/follow_up，校验引用对象 | 相应暂停任务状态 | 多个候选任务时不能随意选最后一个 |

合并优先级：当前明确值 > 当前明确清空 > 同任务已确认值 > 明示默认。推断不能覆盖明确值；继承不能跨任务污染。

执行中的任务修改采用检查点安全边界：当前节点结果标记原 revision；停止旧 revision 后续派发；新 revision 重新规划。不可逆外部写不在本项目新闻流程范围内。

尚未启动的澄清只更新待处理会话任务；已存在 WAITING_INPUT Run 的补充输入必须恢复同一 Run。终态不可逆，已完成任务的追加请求创建关联的新 Run，不“复活”旧 Run。

并发消息通过 `conversation_id + task_id + revision` 乐观锁防止覆盖；请求幂等键复用当前已有机制。版本冲突重读再合并，不静默后写覆盖前写。

## 8. 能力注册、绑定和复合目标

每个显式注册能力增加语义描述视图：`capability_id, version, description, examples, counter_examples, parameter_schema_ref, prerequisites, output_kinds, permission_tags`。由组合根生成目录快照；描述中的示例是泛化辅助，不是关键词触发表。

绑定阶段严格检查：ID 已注册、版本存在、用户有权限、参数校验通过、依赖可以满足。未知 ID 返回 `CAPABILITY_UNKNOWN`，不动态创建插件。

复合任务示例：“收集昨天 AI 新闻，挑三条写成公众号和小红书”：

```text
research_public_information
           ↓
select_supported_events（数量 3，证据不足不能凑数）
           ↓
generate_platform_content（两个输出目标）
```

以上是能力语义，不要求立即创建三个新 Specialist；优先绑定已有研究、内容和质量能力。具体执行模式仍由 Strategy Router 选择，跨专家由现有 Supervisor 调度。

意图决定“用户要求什么”；研究质量报告决定“材料够不够”；模型路由决定“用哪个候选模型”。三者不得混写成 task_type 的一组分支。

## 9. 澄清与意图视图输出

只对阻断执行且无法安全默认的参数澄清。例如已有“AI 行业”不能再要求用户提供 topic；需要历史热度而无历史来源时应说明能力限制，不反复问主题。

澄清优先级：目标/对象冲突 → 时间口径 → 来源范围 → 必需输出条件。一次询问一个关键问题，问题携带当前已理解条件；超过 2 轮仍存在关键歧义时暂停，允许用户取消或重述，禁止无限追问。

对用户可见的意图视图是结构化结果，不包含推理过程：目标、主题、准确时间、来源约束、输出格式、默认项、待确认项、revision。现阶段仅在 Agent 内部和版本化响应契约定义，不实现前端视图。

例：用户“收集一下昨天的 AI 行业动态新闻”应形成：

```json
{
  "schema_version": "intent-view/2",
  "dialog_act": "new_task",
  "goals": ["收集并整理行业新闻"],
  "topic": "AI 行业",
  "timezone": "Asia/Shanghai",
  "time_window": {
    "start": "2026-09-15T00:00:00+08:00",
    "end_exclusive": "2026-09-16T00:00:00+08:00",
    "basis": "published_at"
  },
  "output": "中文新闻简报",
  "count_policy": {"mode": "best_effort", "target": 5, "minimum": 1},
  "defaults": ["时区", "最多 5 条", "按重要性排序"],
  "missing_fields": [],
  "decision": "READY"
}
```

该对象是测试时钟下的展示投影，不替代完整 IntentFrame，也不宣称实际找到了 5 条。

## 10. 研究需求桥接

`ResearchBriefBuilder.build(frame, trusted_context, policy_snapshot) -> ResearchBriefV2`：

1. 仅接收 READY Frame；身份、任务、预算从可信上下文注入。
2. 把解析后的 TimeWindow 逐层传到 ResearchBrief、采集请求和 Provider 参数，禁止中间层填 None。
3. `source_platforms` 和 `target_platforms` 分别映射；“从公众号找新闻”不是“写公众号”。
4. 用户指定数量采用 exact/at_most；未指定为 best_effort，输出阈值由研究设计解释。
5. 为每个研究目标生成稳定 requirement_id，供 CoverageMatrix 对应，不用一个万能 `goal` 掩盖多个缺口。
6. brief 一经生成不可变；补采只能生成 scope 不扩大的子任务。

## 12. 存储、错误、观测和安全

逻辑存储 `intent_snapshot`：租户、会话、任务、revision、Schema/Prompt/模型/能力目录版本、结构 JSON、创建时刻；唯一键包含 tenant_id。`intent_decision` 保存可解释原因和候选差异，不保存模型隐藏思维链。可复用既有会话存储时不创建重复会话表。DDL 独立审查。

稳定错误：`INTENT_SCHEMA_INVALID`、`INTENT_PROVIDER_UNAVAILABLE`、`INTENT_BUDGET_EXHAUSTED`、`INTENT_REFERENCE_AMBIGUOUS`、`INTENT_REVISION_CONFLICT`、`TIME_AMBIGUOUS`、`TIME_INVALID`、`CAPABILITY_UNKNOWN`、`CAPABILITY_UNAVAILABLE`、`REQUIRED_FIELD_MISSING`。

事件包含 request/run/task/revision、阶段、耗时、使用量、决策码、缺失字段名和版本。不记录完整用户消息/凭据，不把每个查询词作为监控标签。

安全测试覆盖：Prompt 注入要求忽略来源限制、伪造 tenant_id、动态 import 能力、跨租户 task 引用、伪造原文跨度、超长数组和循环依赖。模型输出必须先校验再进入 State。

## 13. 验收数据与指标

先构建人工标注集，不用模型给自己的输出打分。首轮建议 240 个用例：单轮 60、多轮 60、日期边界 40、复合目标 30、越界与攻击 30、故障 20。开发/回归/冻结验收按 120/60/60 划分，语义相近改写不能跨集合泄漏。

| 指标 | 建议发布门槛（非当前成绩） |
|---|---|
| Schema 合法率 | 最终可执行对象 100% 通过校验；非法对象 0 次触发业务工具 |
| 日期边界固定单测 | 100%，包括 DST、跨年和午夜恢复 |
| 关键字段精确匹配 | 冻结验收集至少 95%，报告各字段分母，不用均值掩盖时间错误 |
| READY 精确率 | 至少 98%；同时报告覆盖率，禁止全部澄清来刷准确率 |
| 明确完整请求的可执行覆盖率 | 至少 90%；不必要澄清率不高于 10% |
| 越权/未知能力执行 | 0；跨租户继承 0 |
| 多轮修正 | 固定关键案例 100%；模型语义集另报告准确率 |

小样本门槛不代表总体统计保证。每次模型/Prompt/目录变化回放冻结集；输出原始正确数/总数，并记录模型非确定性，多轮重跑不得只报告最好一次。

| 用例 | 必须断言 |
|---|---|
| “昨天 AI 新闻” | 时间日历日，topic 完整，不追问已有字段 |
| “不是昨天，前天” | 替换原时间，其他已确认条件保持 |
| “从小红书找 AI 热点，写公众号” | 来源平台与目标平台不混淆 |
| “最近 24 小时”与“昨天” | 两个不同窗口 |
| “只要 3 条，不要融资” | 数量和排除条件保留至采集门禁 |
| “先收集，再改写两个平台” | 有依赖多目标，不并发生成无证据内容 |
| 换题及删除平台 | 不继承不相关槽位，clear/remove 可区分 |
| 两个并发 refine | 乐观锁不丢更新 |
| 模型失败/修复失败 | 不走普通聊天伪装成功，不重复耗尽预算 |

拟新增测试目录：`tests/orchestration/intent_v2/`、`tests/contracts/test_intent_v2.py`、`tests/conversation/test_intent_v2_flow.py`、`tests/evaluation/test_intent_v2_dataset.py`。实施后运行这些测试，并回归现有 `tests/orchestration`、`tests/conversation`、`tests/architecture`；本轮不声称新测试已存在或通过。

## 14. 迁移、发布和回滚

配置建议 `intent_pipeline_version=v1|v2`，默认 v1；每个任务固定版本，变更只影响新任务。先离线回放，再显式启用有预算的影子解析，最后小范围切换。

V2 → 旧场景仅在单场景、字段可无损映射时投影场景输入参数；不为通过旧 Resolver 而伪造带 confidence 的 IntentEnvelopeV1。V2 Binder 直接执行同等注册、权限和必填校验，旧 IntentEnvelopeV1 只供旧链路使用。多目标和字段来源保留在 V2，不强行压缩成一个 task_type。无法映射时走 V2 专用调度适配或明确不支持，不丢字段后继续。

对于依赖旧意图展示字段的消费者，必须先通过契约回放验证；需要新增意图视图字段的消费者使用显式 V2 协商。未完成协商时保留原 V1 入口，不能随意删掉旧字段或填造置信度以维持表面兼容。

旧 Run/pending 消费旧解释器；新 Run 使用新版本。回滚仅改变新任务入口，进行中 V2 可继续、暂停或显式取消，不能用 V1 解析其检查点。

建议顺序：契约与时间 → Reducer/多轮 → 模型解释和目录绑定 → 研究桥接 → 持久化和兼容 → 冻结集验收。每批先建立失败用例再最小实现，不在本设计交付中执行。
