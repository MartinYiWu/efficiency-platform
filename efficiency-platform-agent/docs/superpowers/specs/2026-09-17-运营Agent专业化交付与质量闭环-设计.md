## 1. 背景与目标

现有运营链已经具备语义意图、多源研究、证据门禁、中央 Supervisor 和平台 Specialist，但最终仍压缩为 `DeliverableV1.body: string`。模型把研究范围、方法说明、逐条事件、链接、风险和格式说明写进同一正文，前端又把该正文作为普通段落展示，最终形成难以阅读、难以继续操作的长文本。

本设计不重建研究与意图系统，而是在现有能力之上增加稳定的“专业交付层”：

1. 一个前台助手，后台按职责调用现有 Specialist；
2. 根据意图选择交付类型，而不是所有任务共用一篇正文；
3. 把结论、正文、来源、运行范围和下一步动作分离；
4. 用确定性质量规则检查结构、事实边界、来源和可读性；
5. 数据不足时有限补采，仍不足则返回可用的部分结果和明确缺口；
6. 保持 `deliverable/1` 和 `deliverable-set/1` 可回滚，不在同一 Run 中混用版本。

## 2. 产品调研结论与采用边界

本次通过公开产品页面、公开会话和官方文档核对了以下模式：

| 参考 | 观察到的模式 | 本项目采用 | 本项目不采用 |
|---|---|---|---|
| 扣子“自媒体运营达人” | 平台数据样本、规律拆解、选题建议、继续生成脚本 | “证据 → 洞察 → 可执行内容 → 继续动作”的交付顺序 | 不把少量样本包装成全量事实，不依赖不可审计技能 |
| 万有无界 | 专业 Agent、技能、任务推进和资产沉淀 | 后台职责分离、产物可复用、单一入口持续推进 | 不在当前页面暴露多 Agent 群聊或新增第二运行时 |
| KOL Agent | 热点市场、分类、互动量、原文和改写入口 | 研究列表与创作动作分离，保留原始指标和来源 | 不以社交热度代替事实可信度，不自动发布 |
| 135 AI 排版 | 选题、写作、编辑、排版分阶段 | 生成后可编辑、复制、换平台和继续加工 | 不引入模板商城、富文本编辑器或新运行依赖 |
| 乐聊 AI | 选题、采集、多角色写作、审核、发布链路 | 采用明确阶段与用户可见进度 | 未验证能力不作为验收事实，不自动发布 |

开源实现仍以 ADR-0002 固定的 Graphon、Coze Studio、Rasa、TrendRadar、Daybreak、Open Deep Research 和 GDELT 适配思想为依据。本设计只增加本项目契约和适配，不复制第三方平台或引入第二 Graph Runtime。

## 3. 设计原则

### 3.1 单一身份，后台专业分工

用户始终与“AI 内容运营助手”交互。意图解释、研究、事实整理、平台写作、诊断和质量检查由 Supervisor 调度，不把内部 Specialist 名称、Prompt、模型原始响应或隐藏推理展示给用户。

### 3.2 意图决定交付类型

IntentFrameV2 和 ResearchBriefV2 继续作为需求事实，不新增关键词路由。交付层只读取已经校验的目标、平台、时间、受众、来源约束和内容类型，再映射为以下交付类型：

| `deliverable_kind` | 典型意图 | 主体结构 |
|---|---|---|
| `ranked_digest` | 热点收集、行业日报、周报 | 概览、排序条目、来源和覆盖说明 |
| `platform_content` | 小红书、公众号、头条等内容创作 | 标题、导语、正文、标签和发布前检查 |
| `action_plan` | 活动策划、账号规划、内容日历 | 目标、受众、行动阶段、指标和待确认项 |
| `diagnosis` | 账号诊断、内容诊断 | 现状、证据、问题、优先级和改进建议 |
| `retrospective` | 活动复盘、内容复盘 | 目标、结果、差距、原因、经验和下一轮动作 |

复合请求由同一个 Run 产生多个有依赖关系的交付物。例如“先收集热点，再把前三条改写为小红书选题”先生成 `ranked_digest`，再把用户选定或规则选定的条目作为 `platform_content` 输入，不能把两个阶段混写成一段正文。

### 3.3 研究事实与创作表达分离

研究交付展示经过质量门禁的事实与来源；平台创作可以改变语气和结构，但不能新增未在证据包中出现的可核验事实、数字或链接。推测、观点和创意表达必须与事实陈述区分。

### 3.4 渐进披露

主阅读面只包含结论、条目、洞察和可用内容。候选数量、去重数、来源覆盖、淘汰原因、降级和冲突进入结构化的 `provenance` 与 `warnings`，由前端折叠展示。不得把执行日志拼进正文。

## 4. 总体执行链

```text
用户请求
  → ContextBuilder
  → IntentFrameV2 / IntentPatchV2
  → 必要字段校验与一次精准澄清
  → Strategy Router / Supervisor
  → ResearchBriefV2（需要研究时）
  → 多源采集、去重、聚合、排序、质量门禁与有限补采
  → EvidencePack / QualityReportV2
  → Deliverable Composer（按交付类型生成）
  → Presentation Validator（结构、引用、可读性、后续动作）
  → DeliverableSetV2
  → SSE 交付
```

Prompt 负责语义理解、摘要、洞察与表达；运行时负责版本、权限、预算、Schema、引用闭包、补采上限、质量状态和终态。模型不得自行宣告来源已核验、扩大来源范围、增加预算或把普通限制写成系统告警。

## 5. Deliverable V2 契约

### 5.1 集合契约

```text
DeliverableSetV2
  contract_version = "deliverable-set/2"
  run_id
  intent_revision
  summary: DeliverySummaryV2
  deliverables: OperationDeliverableV2[]
  next_actions: NextActionV2[]
  provenance: DeliveryProvenanceV2 | null
  degraded: bool
  warnings: WarningV2[]
```

`DeliverySummaryV2` 只包含用户可读的完成说明：本次做了什么、得到多少有效结果、交付是否完整。禁止塞入工具名、模型名、Token、异常栈或内部预算。

### 5.2 交付物共享字段

```text
OperationDeliverableV2
  contract_version = "deliverable/2"
  deliverable_id
  deliverable_kind
  platform
  title
  lead
  content                 # 按 kind 判别的严格联合类型
  citations: CitationV2[]
  copy_text               # 可直接复制的纯文本派生结果
  warnings: WarningV2[]
```

`content` 使用 Pydantic 判别联合，不允许自由 JSON：

- `RankedDigestContentV2`：`items`、`selection_summary`；
- `PlatformContentV2`：`body_markdown`、`hashtags`、`format_notes`；
- `ActionPlanContentV2`：`goal`、`audience`、`phases`、`metrics`、`assumptions`；
- `DiagnosisContentV2`：`findings`、`priorities`、`recommendations`、`evidence_refs`；
- `RetrospectiveContentV2`：`objectives`、`outcomes`、`gaps`、`causes`、`next_steps`。

### 5.3 排序条目

```text
RankedItemV2
  item_id
  rank
  title
  occurred_at
  summary
  why_it_matters
  content_angles[]
  metrics[]
  source_refs[]
  confidence = "high" | "medium" | "low"
  verification_status
```

`rank` 必须由已治理的排序结果产生，模型只能解释排序理由。缺少真实热度数据时，结果必须说明采用的是重要性、相关性或新近性排序，不得伪称“按全网热度”。

### 5.4 引用与来源

`CitationV2` 在 V1 的 URL、标题和来源上增加：

- `citation_id`；
- `published_at`；
- `source_type`；
- `source_tier`；
- `verification_status`；
- `supports_item_ids`；
- `independent_source_group`。

任何条目的 `source_refs` 必须属于同一交付物的引用集合。平台内容中的事实引用必须形成闭包，不允许模型产生新 URL。URL、标题和来源文本仍视为不可信数据，前端只按文本和安全链接展示。

### 5.5 后续动作

`NextActionV2` 是经过允许清单校验的建议操作：

```text
action_id
action_type
label
target_deliverable_id
target_item_ids[]
intent_patch
requires_user_input
```

首批允许：`rewrite_for_platform`、`expand_item`、`generate_script`、`replace_candidates`、`show_sources`、`refine_constraints`。它只生成下一轮对话输入，不自动发布、不调用高风险写工具。

## 6. 生成与质量规则

### 6.1 热点与研究摘要

- 开头用一至两句说明时间窗、候选数、有效数和排序口径；
- 默认展示目标数量，不足时展示实际数量，不使用旧内容凑数；
- 每条包含标题、事实摘要、运营价值和来源；
- 主体不展示裸 URL，URL 进入引用区；
- 每条摘要保持短段落，避免把研究方法重复到每个条目；
- 只有达到门禁的来源进入正式榜单，低置信度线索进入“待核实线索”或被淘汰。

### 6.2 平台内容

- 小红书：标题、短段落、自然口吻、标签和事实边界；
- 公众号：导语、分节正文、小标题、结论和可选行动号召；
- 今日头条：信息价值优先、事实与观点分层；
- 平台之间不得直接复制同一正文；
- `body_markdown` 只允许安全 Markdown 子集，禁止 HTML、脚本、图片热链和模型生成的任意组件指令。

### 6.3 计划、诊断和复盘

- 计划必须有目标、受众、阶段、负责人语义、指标和假设；
- 诊断必须把证据、判断和建议分开，优先级可解释；
- 复盘必须区分观测结果和推断原因；缺少业务数据时不得伪造效果指标；
- 关键约束缺失时只追问一个最影响执行的问题，非关键缺失使用透明默认值。

### 6.4 Presentation Validator

新增确定性展示质量检查，不替代 Research Quality Gate：

1. 交付类型与意图一致；
2. 必填结构完整，数组和正文长度受限；
3. 排名连续且不重复；
4. 来源引用闭包成立；
5. 研究型交付存在时间窗和排序口径；
6. 不出现内部 Prompt、工具参数、异常栈和隐藏推理；
7. 不把 `warnings`、`format_notes` 或来源清单重复写入正文；
8. 后续动作属于允许清单且目标存在；
9. 可复制文本由结构化内容确定性渲染，不接受模型另写一份不同正文；
10. V2 失败不能降格解析为 V1 成功。

结构错误允许在剩余预算内进行一次模型修复；引用闭包、权限、版本和运行状态错误禁止模型修复，直接失败关闭或返回部分交付。

## 7. 数据不足、补采与降级

沿用 Research QualityReportV2 和有限补采算法：

| 条件 | 决策 |
|---|---|
| 有效数量不足，仍有未使用的已准入来源与预算 | 定向补采缺失时间、主题或来源类型 |
| 补采没有新增有效事件 | 立即停止，不重复相同查询 |
| 事件只有单一低质量来源 | 排除正式榜单或标为待核实线索 |
| 来源冲突且无法消解 | 保留冲突说明，不生成确定性判断 |
| 达到轮次、时间或预算上限 | 返回 `PARTIAL`，保留已合格结果和具体缺口 |
| 所有来源不可用 | 返回 `NO_MATCHES` 或 `FAILED`，不得用模型常识冒充实时研究 |

交付集合的 `degraded` 来自确定性运行事实；模型只能在正文说明合理的内容假设，不能设置系统降级状态。

## 8. SSE 与用户可见进度

继续使用既有流式协议，允许增加以下用户安全阶段：

- `understanding_request`：正在理解目标与约束；
- `collecting_sources`：正在收集公开来源；
- `checking_evidence`：正在去重、核验时间和整合事件；
- `creating_content`：正在生成对应交付物；
- `checking_delivery`：正在检查来源、结构和平台格式。

事件只包含阶段、完成数量、目标数量、是否降级和安全说明。内部 Specialist、模型候选、Prompt、原始网页正文和推理过程只进入受控日志或审计事实。

## 9. V1/V2 兼容与发布

1. V1 继续只按原 Schema 解析，语义不改变；
2. V2 由请求能力协商或服务端灰度开关启用，同一 Run 固定版本；
3. 可从 V2 确定性投影 V1，用于旧前端回退；V1 不反向推导 V2 的来源质量和结构；
4. 前端先实现双版本解析和 V1 回归，再开启 V2；
5. V2 失败时返回明确错误或部分 V2，不把错误响应伪装成 V1；
6. 回滚只关闭新 Run 的 V2 入口，保留已经生成的 V2 运行事实和证据。

## 10. 测试与真实验收

### 10.1 Agent 自动化测试

- V2 Pydantic Schema、判别联合、未知字段和大小限制；
- 五类意图到交付类型的映射；
- 时间窗、引用闭包、排序连续性和复制文本渲染；
- 平台正文独立生成与证据约束；
- 一次结构修复、无增益停止、部分结果保留和 V1 投影；
- Prompt 注入、恶意标题/URL、超长正文和内部信息泄露；
- SSE 阶段顺序、取消、超时和单一终态。

### 10.2 十轮真实浏览器验收

| 编号 | 输入 | 主要验收 |
|---|---|---|
| A01 | 你叫什么名字？ | 普通对话，不误研究 |
| A02 | 收集昨天的 9 条 AI 行业动态 | 时间窗、数量、排序口径、来源和易读列表 |
| A03 | 最近 7 天 AI 行业周报 | 周报结构、去重、来源和覆盖说明 |
| A04 | 把第 1 条改成小红书文案 | 继承条目与来源、平台适配、无新事实 |
| A05 | 再写一个公众号版本 | 多轮约束继承、正文独立 |
| A06 | 帮我策划一个 AI 工具推广活动 | 精准澄清或透明默认、行动计划 |
| A07 | 给一个缺少数据的账号做诊断 | 明确数据缺口，不伪造指标 |
| A08 | 对一次内容活动做复盘 | 事实、判断、建议分离 |
| A09 | 模拟来源不足、冲突或超时 | 有限补采、部分交付、可解释降级 |
| A10 | 换一批热点，只看产品发布 | IntentPatch、生效范围、排除旧候选 |

每轮保留输入、Run ID、SSE 序列、交付契约版本、来源数、有效条目数、质量状态、页面截图和人工判定。真实研究至少覆盖免费 API、RSS/Atom 和公开页面中已准入的两类来源；离线回放不能替代真实验收。

## 11. 文件级预计改造边界

实施计划需基于源码重新定位，但预计限制在：

- `contracts/deliverables.py`：V2 契约和 V1 投影；
- `agents/operation/contracts/`：交付类型和证据引用；
- `agents/operation/specialists/model_backed.py`：按交付类型生成；
- `capabilities/quality/`：Presentation Validator 与确定性渲染；
- `prompts/resources/operation/`：类型化生成模板；
- `conversation/`、`orchestration/`：版本协商、后续动作和 SSE；
- `tests/`：契约、质量、兼容、注入和端到端测试；
- 本设计、计划、进度账本和验收证据。

不得修改 Java 服务、共享数据库 DDL、部署拓扑、收费来源、自动发布或高风险写 Tool。真实来源启用继续服从 ADR-0002 的逐源准入。

## 12. 设计完成条件

- 与 IntentFrameV2、ResearchBriefV2、EvidencePack 和 QualityReportV2 无重复权威字段；
- Agent 和前端对 V2 字段、版本、降级和回滚语义一致；
- 五类交付物均有结构、质量规则和用户后续动作；
- 十轮真实验收覆盖普通对话、研究、创作、策划、诊断、复盘和失败边界；
- 未把公开产品声明当成本项目已实现能力；
- 未新增依赖、真实来源、数据库迁移或生产切换授权。
