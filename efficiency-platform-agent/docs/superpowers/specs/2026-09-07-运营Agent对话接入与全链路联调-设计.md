# 运营 Agent 对话接入与全链路联调设计

| 项目 | 内容 |

## 2. 目标与原则

目标是让用户通过 `/ai-assistants/operations/chat` 输入自然语言，由运营总 Agent 自主理解意图、补全需求、选择场景、编排多个 Specialist，必要时进行免费数据检索，最终通过 SSE 返回高质量、可直接使用的运营成品。

设计原则：

1. 前端只提交自然语言，不传递场景 ID、Specialist ID、模型名或 Prompt。
2. LLM 负责语义理解和内容生成，Agent 负责约束、编排、校验和交付。
3. 场景和能力必须来自受控注册表，LLM 不得动态发明工具或节点。
4. 从第一天支持多 Agent、并行执行、失败降级、取消、Checkpoint 和断线重连。
5. 本地联调使用 InMemory 适配器，不以 Redis、PostgreSQL、COS 或 Java 服务作为前置条件。
6. API Key 只存在 Agent 进程，禁止进入浏览器、SSE 事件、日志和测试证据。
7. 代码、配置、接口文档和测试注释全部使用中文。

## 3. 实施基线与本轮补齐能力

### 3.1 实施前已具备能力

- S2：Run 契约、GraphRuntime、预算、取消、Checkpoint、FastAPI 基础路由和有限 SSE 编码。
- S3：运营领域上下文、OperationRequest、策略路由和运行边界。
- S4：Supervisor、多 Agent 调度契约、并行 Specialist 和失败降级模型。
- S5：运营研究、内容、品牌、IP、活动、增长、社群、分析和质量能力定义。
- S6：行业动态、多平台内容、品牌运营、IP 运营、活动策划、内容日历、增长实验、运营复盘场景包。
- 前端：运营助手页面布局、输入框、本地消息展示和页面路由。

### 3.2 本轮补齐能力

| 原缺失能力 | 影响 | 已完成处理 |
|---|---|---|
| 对话会话适配层 | 前端不能以人机对话方式提交任务 | 新增 Conversation Facade，复用 Run 生命周期 |

| 交付物封装 | 多平台成品结构不稳定 | 新增 DeliverableAssembler 和质量门 |

## 4. 总体架构

```text
前端运营助手
    │ POST 会话消息
    ▼
Conversation API
    │ 创建 Run、校验租户、请求幂等
    ▼
Conversation Facade
    │
    ├─ IntentInterpreter：自然语言 → IntentEnvelope
    ├─ RequirementCompleter：识别缺失字段
    ├─ ClarificationManager：生成澄清问题
    └─ ScenarioResolver：受控场景选择
    ▼
GraphRuntime / Supervisor
    ├─ Scenario Pack
    ├─ 多 Specialist 并行
    ├─ 外部研究与免费数据检索
    ├─ Checkpoint / Cancel / Budget
    └─ ModelSelector / 自动降级
    ▼
Quality Gate
    ├─ 结构完整性
    ├─ 平台格式
    ├─ 引用和证据
    ├─ 多平台独立性
    └─ 部分成功与降级标识
    ▼
DeliverableAssembler
    ▼
Event Hub → SSE → 前端增量展示
```

## 5. 交互协议设计

### 5.1 会话消息接口

```http
POST /v1/conversations/{conversation_id}/messages
Content-Type: application/json
X-Tenant-ID: tenant-demo
```

```json
{
  "request_id": "ui-唯一请求号",
  "user_id": "user-demo",
  "message": "生成小红书、微信公众号和今日头条三套新品文案",
  "attachments": []
}
```

```json
{
  "conversation_id": "conversation-001",
  "turn_id": "turn-001",
  "run_id": "run-001",
  "status": "queued"
}
```

该接口是对现有 `POST /v1/runs` 的薄适配，不复制 Run 执行逻辑。现有 Run 查询、取消、恢复和事件接口继续保留。

### 5.2 SSE 接口

```http
GET /v1/runs/{run_id}/events
Accept: text/event-stream
X-Tenant-ID: tenant-demo
Last-Event-ID: 12
```

新增 `RunStreamEventV1`，不修改基础 `RunEventV1`：

| 事件 | 说明 |
|---|---|
| `run_started` | Run 开始执行 |
| `intent_detected` | 意图识别完成 |
| `clarification_required` | 需要用户补充信息 |
| `phase_started` | 场景或 Specialist 阶段开始 |
| `assistant_started` | 开始生成助手内容 |
| `assistant_delta` | 一段增量文本 |
| `deliverable` | 一个结构化交付物 |
| `usage_update` | 当前 Token 使用量 |
| `stream_error` | 稳定错误信息 |
| `stream_done` | 流式终止和最终状态 |

事件数据必须包含 `contract_version`、`run_id`、`sequence` 和脱敏后的 `payload`。不得包含密钥、连接串、原始 Prompt、隐藏思维链或完整堆栈。

### 5.3 状态语义

```text
queued → running → waiting_input → running → succeeded
            │                 │
            ├─ failed        ├─ failed
            ├─ cancelled     └─ cancelled
            └─ timed_out
```

`waiting_input` 不是失败。用户补充信息后创建新的 turn，并通过有界上下文继续原会话。`degraded_succeeded` 是前端展示态，映射自核心 `succeeded` 终态及结果中的 `degraded=true`，不污染 Run 核心状态机。

## 6. 意图理解与场景解析

`IntentInterpreter` 使用 DeepSeek 结构化 JSON 输出，返回领域和目标、任务类型、渠道和平台、目标受众、风格、时间范围、是否需要检索、是否需要多 Agent、缺失字段、置信度和模型等级建议。

`ScenarioResolver` 只允许从现有场景注册表中选择：

```text
industry_digest
multi_platform_content
brand_operation_plan
ip_operation_plan
campaign_plan
content_calendar
growth_experiment
operation_review
```

LLM 输出的场景候选必须经过注册表校验；无法映射时进入澄清或通用运营任务路径，不得直接执行未知节点。

平台字段采用白名单和别名规范化：首轮支持小红书、微信公众号、今日头条及其受控中英文别名。未知平台必须稳定返回 `UNSUPPORTED_PLATFORM`，不得静默扩展成全部平台。澄清续轮只补齐上轮实际缺失字段，不覆盖用户已经确认的主题、渠道和平台范围。

## 7. 多 Agent 执行设计

Supervisor 根据 `ScenarioSubmission` 生成受控执行计划，并决定是否并行调用 Specialist。一个任务可以产生多个互相独立的交付物，例如三个平台文案分别执行，最后统一汇总。

Specialist 只通过以下端口访问模型和能力：

```text
Specialist → PromptRuntime → ModelRuntime → Provider
Specialist → CapabilityPort → 检索、引用、文档等能力
```

Specialist 不得自行读取密钥、决定其他 Specialist、直接写数据库或直接向前端发送事件。

模型选择由 Agent 结合任务复杂度、输出要求、预算、可用性和失败原因自主决策；运行时负责验证模型是否可用并执行自动降级，前端不感知具体模型名。

## 8. 运营交付物设计

```json
{
  "deliverables": [
    {
      "platform": "xiaohongshu",
      "title": "标题",
      "body": "正文",
      "hashtags": ["标签1", "标签2"],
      "format_notes": ["适合移动端分段"],
      "citations": [],
      "warnings": []
    }
  ],
  "summary": "任务总结",
  "degraded": false
}
```

质量门检查：必填字段完整、平台格式符合场景要求、多平台内容不是简单复制、研究类内容具有来源和引用、部分失败明确标识、结果适合前端直接渲染和复制。

## 9. 本地运行组合根

新增本地真实组合根，负责读取已有 `.env`（不输出 Secret）、构造 DeepSeek Chat 和 Streaming Provider、注册运营 Agent/Supervisor/Specialist/场景包、使用 InMemory Run Repository/Event Hub/Checkpoint，并挂载 FastAPI、CORS、SSE、查询、取消和恢复路由。

本地联调不依赖 Redis、PostgreSQL、COS。后续替换持久化和事件适配器时，只更换组合根，不改变业务接口。

前端开发环境通过 `.env.development` 声明 `VITE_API_BASE_URL=http://127.0.0.1:8080`，该配置只包含本地服务地址，不包含模型密钥。另提供显式 `test_mode` 的确定性 Fake Agent 服务，用于浏览器到真实 FastAPI/SSE 的零外网验收。

## 10. 前端接入设计

前端新增 `operation-chat` Feature：`api.ts` 负责消息、Run、取消 API；`sseClient.ts` 使用 `fetch + ReadableStream` 并支持 `Last-Event-ID`；`messageReducer.ts` 处理 queued、增量、澄清、交付物、错误和完成状态；`useOperationChat.ts` 封装发送、订阅、取消和重连；`types.ts` 与 Agent 合同一一对应。

页面只负责展示和交互，不负责模型、Prompt、场景和 Specialist 选择。

Hook 为每轮请求创建独立 `AbortController`，并把同一 signal 传给会话 POST 和 SSE。组件卸载时中止尚未完成的提交或订阅，防止页面离开后继续重连；用户主动取消仍通过正式取消 API 与 Run 权威状态仲裁。

## 11. 异常、降级与安全

| 情况 | 处理 |
|---|---|
| 意图置信度不足 | 返回澄清问题，不启动 Specialist |
| DeepSeek 超时 | 按模型池可用性自动切换，记录降级事件 |
| 单 Specialist 失败 | 其他 Specialist 继续，结果标记部分成功 |
| 所有模型不可用 | Run 进入 failed，返回稳定错误码 |
| 用户取消 | 协作式停止，状态为 cancelled |
| SSE 断开 | 前端按 Last-Event-ID 重连并去重 |
| 租户不匹配 | 返回 404 或 403，不泄露 Run 信息 |
| 未知场景 ID | 拒绝执行并记录契约错误 |

日志只记录请求号、Run ID、阶段、耗时和脱敏错误；Token 统计写入运行结果，不建设监控平台。

取消受理与图执行终态提交必须通过同一状态锁进行线性化仲裁：取消先被受理时，晚到的成功结果不得覆盖 `cancelled`；成功先完成提交时，后续取消返回终态冲突。

SSE 增量呈现位于质量门之后：多 Agent 先产生并校验最终交付物，再把安全正文分块为 `assistant_delta`。DeepSeek Streaming Provider 作为底层可复用能力保留，但首版不把各 Specialist 的未经治理原始 Token 直接透传到页面。

## 12. 验收标准

必须同时满足：用户自然语言可以触发运营总 Agent；创建 Run 不等待模型完整响应；SSE 能实时输出并支持重连；默认真实调用 DeepSeek；支持多轮澄清、多 Agent 并行和部分失败；支持一次生成多个平台独立成品；支持取消、查询和恢复；API Key 不出 Agent 进程；Fake 与真实模式边界清晰；浏览器完成 `127.0.0.1:5190` 真实联调；形成测试报告、浏览器证据和真实调用证据。

## 13. 明确不纳入本轮

不实施 Java 改造、生产部署、Redis Streams 升级、监控平台、内容审核、语音视频、Text2SQL、付费商业数据源、视觉 LLM 和平台自动发布。
