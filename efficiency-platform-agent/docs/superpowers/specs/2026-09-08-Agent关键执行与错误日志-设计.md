## 1. 问题与根因

当前终端只输出 Run 事件名称、状态和终态摘要。该日志能证明 Run 进入了 `multi_agent` 并以 `RESEARCH_UNAVAILABLE` 结束，但无法区分以下原因：

1. `deepseek_web_search` Gate 未启用；
2. 研究 Provider 没有完成装配；
3. OpenAI 客户端没有 `responses.create` 能力；
4. 上游返回认证、限流、超时、404、5xx 或其他 HTTP 错误；
5. 上游响应没有来源，或来源结构不符合证据契约。

根因是错误在产生边界被归一化时丢失了诊断维度：`DeepSeekWebSearchProvider` 把所有调用异常折叠为 `RESEARCH_UNAVAILABLE`，`GraphRuntime` 和 Harness 也会把未处理异常归一化，却没有把安全的内部诊断事实交给日志器。现有 `LocalExecutionLogger` 只观察公开 Run 事件和公开终态视图，无法恢复已经丢失的信息。

前两次身份与能力问答显示 Token 为 0 是正确行为：它们使用本地确定性产品响应，不调用模型。

## 2. 目标

1. 本地终端能够从一组连续日志定位一次 Run 在哪个组件、哪个阶段失败；
2. Provider 失败必须显示稳定错误码、异常类型、HTTP 状态、可重试性、调用次数和耗时等真实可得事实；
3. 所有诊断事件自动关联当前 `run_id`、`request_id`、策略、Agent、Provider 和逻辑模型；
4. 启动时显示关键能力是启用、关闭还是未装配，但不显示任何配置值；
5. 不记录用户正文、对话历史、Prompt、模型完整输出、来源全文、密钥、认证头、连接串和原始响应体；
6. 不记录每个 Token 或 SSE delta，避免日志洪水；
7. 不引入新服务、监控平台或部署要求。

## 3. 方案裁决

采用“稳定诊断契约 + ContextVar 关联上下文 + 现有本地日志器”的方案。

```text
API / Harness 绑定 RunDiagnosticContext
  -> Router / Graph / ModelRuntime / Provider 产生 DiagnosticRecord
  -> DiagnosticRecorderPort
  -> LocalExecutionLogger
  -> 本地终端中文键值日志
```

不采用以下方案：

- 只增加终态错误文案：错误产生边界的信息已经丢失，无法定位根因；
- 直接打印原始异常或响应体：可能泄漏认证信息、请求正文和厂商返回内容；
- 当前引入 OpenTelemetry、Collector、Prometheus 或 Grafana：超出本轮本地排障目标。

## 4. 稳定诊断契约

在 `core/diagnostics.py` 定义框架中立、不可变的诊断契约：

```python
class DiagnosticLevel(StrEnum):
    DEBUG = "debug"
    INFO = "info"
    WARNING = "warning"
    ERROR = "error"

@dataclass(frozen=True, slots=True)
class RunDiagnosticContext:
    run_id: str | None = None
    request_id: str | None = None
    strategy: str | None = None
    agent_name: str | None = None

@dataclass(frozen=True, slots=True)
class DiagnosticRecord:
    event_name: str
    component: str
    level: DiagnosticLevel
    capability: str | None = None
    status: str | None = None
    stage: str | None = None
    provider: str | None = None
    model: str | None = None
    provider_call_id: str | None = None
    reason_code: str | None = None
    rule_version: str | None = None
    error_code: str | None = None
    error_type: str | None = None
    error_location: str | None = None
    http_status: int | None = None
    retryable: bool | None = None
    duration_ms: int | None = None
    attempt: int | None = None
    input_tokens: int | None = None
    output_tokens: int | None = None
    evidence_valid_count: int | None = None
    evidence_rejected_count: int | None = None
```

`DiagnosticRecorderPort.record(record)` 是同步、不可抛出到业务链的窄端口；`NoopDiagnosticRecorder` 是测试和未启用日志场景的默认实现。所有字段显式定义，禁止任意 `dict`、自由文本异常消息和请求/响应载荷。每次真实网络尝试生成一个本地 `provider_call_id`，只用于串联开始、重试和终态日志；不采集厂商响应 Header 中的请求标识。

`bind_diagnostic_context()` 使用 `contextvars.ContextVar` 为当前异步 Run 绑定关联标识，并在 `finally` 中恢复，避免并发 Run 串线。Provider 不需要感知 Harness，也不需要修改现有 `ProviderRequest` 协议。

## 5. 日志覆盖点

### 5.1 启动与能力装配

真实组合根输出一次能力状态：

```text
INFO [AgentCapability] 事件=capability_ready 能力=deepseek_chat 状态=enabled
INFO [AgentCapability] 事件=capability_disabled 能力=deepseek_web_search 状态=disabled 原因码=gate_disabled
```

只允许输出能力逻辑名、布尔状态和稳定原因码；不得输出 Base URL、Key、连接信息或配置原值。

### 5.2 Run 与策略

保留现有生命周期日志，并为 `strategy_selected` 增加白名单字段 `strategy`、`reason_code` 和 `rule_version`。终态继续记录状态、错误码、降级和真实 Token。

### 5.3 模型调用

`ModelRuntime` 在候选调用边界记录：

- `model_invocation_started`：Provider、逻辑模型、attempt；
- `model_invocation_succeeded`：耗时、输入/输出 Token；
- `model_invocation_failed`：稳定错误码、类别、可重试性、耗时；
- `model_fallback_selected`：从失败候选切换到下一候选，只记录逻辑标识。

DeepSeek 流式 Provider 在模型候选边界之下补充真实 HTTP 尝试日志：每次请求使用独立本地调用 ID，显式重试记录 `provider_request_retrying`，终态记录 `provider_request_succeeded`、`provider_request_failed` 或 `provider_request_cancelled`。调用前已取消时不产生虚假的网络开始日志。该日志不记录 SSE 增量、请求正文、响应正文、Header 或密钥。

不记录消息、Prompt、options 内容和生成正文。

### 5.4 公共研究

`DeepSeekWebSearchProvider` 必须区分以下内部诊断原因，但对上仍保持既有稳定研究错误契约：

| 诊断阶段 | 诊断错误码 | 对上错误码 |
|---|---|---|
| Gate 关闭 | `RESEARCH_GATE_DISABLED` | `RESEARCH_UNAVAILABLE` |
| Provider 未装配 | `RESEARCH_PROVIDER_NOT_CONFIGURED` | `RESEARCH_UNAVAILABLE` |
| 客户端不支持 Responses | `RESEARCH_RESPONSES_UNSUPPORTED` | `RESEARCH_UNAVAILABLE` |
| 认证失败 | `PROVIDER_AUTHENTICATION` | `RESEARCH_UNAVAILABLE` |
| 限流 | `PROVIDER_RATE_LIMITED` | `RESEARCH_UNAVAILABLE` |
| 超时 | `PROVIDER_TIMEOUT` | `RESEARCH_UNAVAILABLE` |
| 404/接口不存在 | `PROVIDER_NOT_FOUND` | `RESEARCH_UNAVAILABLE` |
| 5xx | `PROVIDER_UPSTREAM` | `RESEARCH_UNAVAILABLE` |
| 连接或未知调用异常 | `PROVIDER_UNAVAILABLE` | `RESEARCH_UNAVAILABLE` |
| 无来源 | `RESEARCH_INSUFFICIENT` | `RESEARCH_INSUFFICIENT` |
| 来源结构非法 | `EVIDENCE_INVALID` | `EVIDENCE_INVALID` |

HTTP 状态从异常的稳定属性读取；异常正文、HTTP 响应体和请求体一律不进入日志。

### 5.5 Graph 与 Harness 未处理异常

在真正吞掉异常并归一化的边界记录 `graph_execution_failed`、`pipeline_preparation_failed` 或 `background_execution_failed`。日志包含异常类型、稳定错误码和安全位置；不使用会自动附带原始异常文本的 `logger.exception()`。

安全位置只由最后一个项目内 traceback frame 生成 `模块文件:行号:函数名`，不包含源代码行、局部变量和异常消息。

## 6. 输出格式与级别

本轮继续使用现有 `logging` Handler，保持 Windows/VSCode 终端直接可见：

```text
INFO [AgentProvider] 事件=research_invocation_started run_id=run-example request_id=request-example provider=deepseek_web_search 模型=deepseek-balanced attempt=1
ERROR [AgentProvider] 事件=research_invocation_failed run_id=run-example request_id=request-example provider=deepseek_web_search 阶段=responses.create 错误码=PROVIDER_NOT_FOUND 异常类型=NotFoundError HTTP状态=404 可重试=false 耗时毫秒=312
```

级别规则：

- `INFO`：启动能力、关键生命周期、调用开始和成功；
- `WARNING`：已处理重试、降级、证据不足；
- `ERROR`：当前 Provider、Graph、Pipeline 或 Run 失败；
- `DEBUG`：本轮不新增高频诊断输出。

## 7. 脱敏与失败隔离

1. `DiagnosticRecord` 不提供 message、payload、headers、url、prompt、content、response 等自由文本字段；
2. 异常只提取类型、整数 HTTP 状态、本地 Provider 调用 ID 和安全代码位置；
3. 本地 `provider_call_id` 仅接受长度受限的字母、数字、点、下划线和连字符；不得从厂商 Header、响应体或异常正文提取请求标识；
4. 日志 Recorder 自身失败必须被隔离，不能改变 Run 状态；
5. 用户可见 SSE 和 API 错误继续只返回现有 `safe_message`，内部诊断字段不得进入响应；
6. 测试必须使用合成 Secret、Prompt、Authorization、连接串和响应正文证明它们不会出现在日志。

## 8. 验收标准

1. 能从终端判断 `RESEARCH_UNAVAILABLE` 属于 Gate 关闭、Provider 未装配、Responses 不支持或哪类 HTTP/网络异常；
2. 每个 Provider 失败日志包含当前 Run 关联标识、阶段、稳定错误码、异常类型、HTTP 状态（真实可得时）、可重试性、attempt 和耗时；
3. 正常身份/能力快答仍显示 Token 为 0，且不会错误打印模型调用；
4. 普通 DeepSeek 对话显示模型调用开始、成功、耗时和真实用量；
5. Graph/Harness 未处理异常有安全错误位置，且 Run 仍按原契约失败关闭；
6. 日志中不存在用户正文、Prompt、模型正文、密钥、认证头、连接串、原始异常正文或响应体；
7. 不产生逐 Token/SSE delta 日志；
8. 现有 API、SSE、策略、模型降级和公开错误契约不变；
9. 单元、集成、架构、Ruff、mypy 和源码编译门禁通过；
10. 使用一次真实研究请求验证终端能给出具体失败阶段，但不把联网研究失败误报为成功。

## 9. 非目标

- 不建设监控平台、Dashboard、告警或日志采集服务；
- 不引入 OpenTelemetry、Prometheus、Grafana、LangSmith 或新的日志依赖；
- 不修改 Java 或前端；
- 不记录或展示隐藏思维链；
- 不改变 `RESEARCH_UNAVAILABLE` 的用户可见安全文案；
- 不为了日志修改 Provider 的计费、重试或业务结果语义。
