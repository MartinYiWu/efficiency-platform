# 运营助手内联研究结果与成稿制品分流设计

## 1. 背景与问题

当前运营助手已经能把“收集、汇总、整理热点资料”识别为 `industry_digest`，但运行层仍把研究结果无条件包装成 `deliverable_set`，只把“已生成 1 份独立交付物”作为对话正文发送。Java 收到 `deliverable` 事件后又把研究摘要保存为可下载制品，前端最终展示“已生成内容”和“下载 Markdown”。

这混淆了两种不同结果：

- 研究回答：用户只是要查看资料，应直接在对话中流式展示。
- 内容成稿：用户明确要求写推文、公众号文章、平台文案或导出时，才应生成独立制品。

## 2. 目标与非目标

### 目标

1. “收集、搜索、汇总、整理、分析资料”返回完整的内联对话正文，并通过现有 `assistant_delta` 形成打字机效果。
2. 研究回答不显示“已生成内容”、复制成稿、预览或下载 Markdown 等制品 UI。
3. “写推文、写公众号文章、生成平台文案、生成成稿、导出文稿”等明确创作请求继续生成独立制品。
4. 研究结构化结果仍在服务端保留，供后续“把刚才的热点写成推文”复用，并保持研究任务、引用和版本关联。
5. 旧版协议和非研究场景保持兼容。

### 非目标

- 不修改研究采集、排序、引用闭包和事实核验算法。
- 不改变文章内容结构和平台排版 Prompt。
- 不新增登录、自动发布或新的数据库。
- 不把所有 Markdown 渲染都移除；对话正文仍可使用 Markdown 语法安全展示，但不作为可下载制品暴露。

## 3. 核心语义

新增运行结果展示模式 `presentation_mode`：

| 模式 | 适用任务 | 对话正文 | `deliverable` 事件 | 用户可见制品 |
| --- | --- | --- | --- | --- |
| `inline` | 研究、汇总、资料整理、分析回答 | 完整结果 | 保留结构化数据并标记 `inline` | 否 |
| `artifact` | 推文、公众号文章、平台文案、正式成稿 | 简短完成提示 | 标记 `artifact` | 是 |

展示模式由服务端根据已冻结的意图与输出要求决定，不允许 LLM 自行决定：

- `output_types` 为 `digest` 或研究场景 `industry_digest`：`inline`。
- `output_types` 为 `article`，或场景为明确内容创作：`artifact`。
- 旧调用未提供展示模式时按 `artifact` 处理，避免破坏既有创作流程。

## 4. 端到端数据流

### 4.1 研究汇总

1. Intent V2 识别研究任务，冻结 `output_types=("digest",)`。
2. 研究 Agent 完成采集、筛选、排序、引用闭包和摘要生成。
3. Operation Runtime 将结构化 `ranked_digest` 渲染成完整、安全、可读的对话正文，并设置 `presentation_mode=inline`。
4. Harness 通过 `assistant_delta` 流式发送完整正文；同时发送带 `presentation_mode=inline` 的结构化 `deliverable` 事件供后端留存。
5. Java 持久化研究记录和助手正文，但公开制品列表过滤内联研究记录。
6. 前端收到内联事件后不加入 `deliverableSets`，只展示打字机消息。

### 4.2 基于研究结果生成成稿

1. 用户明确要求“把这些热点写成公众号推文”等创作任务。
2. Agent 从对话上下文或隐藏研究记录获取已有 `ranked_digest`，避免无必要重复研究。
3. Operation Runtime 设置 `presentation_mode=artifact`。
4. Java 持久化正式成稿，前端显示成稿正文、复制、预览和下载操作。

## 5. 组件修改

### Agent

- Operation Runtime：根据场景和输出要求选择展示模式；内联研究使用完整研究正文作为 `content`。
- Harness：把 `presentation_mode` 放入 `deliverable` 事件负载，保留旧协议默认值。
- 对话上下文：仍从结构化研究结果维护最近一次研究引用，不依赖前端是否展示制品卡。
- 日志：记录 `run_id`、场景和展示模式，不记录完整正文或凭据。

### Java

- 事件投影：读取 `presentation_mode`；两种模式都可持久化结构化结果。
- 助手消息：`inline` 以完整研究正文为最终消息内容，不改写为“已生成交付物”。
- 公开制品列表：排除 `presentation_mode=inline` 的研究记录。
- 可用上下文：仍允许内部读取内联研究记录，供后续创作任务使用。

为避免数据库迁移，展示模式写入现有内部元数据 JSON；旧记录没有该字段时继续按现有制品处理。

### 前端

- SSE Reducer：`presentation_mode=inline` 的 `deliverable` 事件不加入用户可见 `deliverableSets`。
- 历史制品区域：只展示 Java 返回的公开制品，不展示隐藏研究记录。
- 流式消息继续复用现有 `StreamingAssistantContent`，不新建第二套渲染组件。

## 6. 正文渲染规则

研究结果的内联正文至少包含：

- 研究主题和实际时间窗口；
- 实际获得的条目数量；
- 按排名排列的标题、摘要、关注价值；
- 对应来源链接或来源编号；
- 不足目标数量、来源受限或降级时的真实说明。

正文来自已经通过质量门禁的结构化 `ranked_digest`，不再调用一次 LLM 重新改写，避免事实、时间窗口和条数漂移。

## 7. 错误与兼容处理

- 内联正文渲染失败：运行失败并记录明确错误，不回退成空制品卡。
- `presentation_mode` 缺失：按 `artifact` 处理，保持旧调用兼容。
- 研究结果不足：仍内联展示真实结果，并保留 `degraded` 和 warning 信息。
- SSE 中断：沿用现有完整正文回退机制，不重复发送半段内容。
- Java 已存在的历史 `ranked_digest` 制品不删除，只对新内联结果应用隐藏规则。

## 8. 验证标准

### 自动化回归

1. Agent：研究请求输出完整 `content`，展示模式为 `inline`。
2. Agent：创作请求仍为 `artifact`。
3. Harness：内联研究同时产生 `assistant_delta` 和带模式的结构化事件。
4. Java：内联研究可持久化但不进入公开制品列表；创作制品仍可见。
5. 前端：内联事件不产生“已生成内容”区域；创作事件继续显示制品操作。

### 真实接口验证

1. `帮我收集整理一下上周AI热点数据，整理出最热的前10条`
   - 对话区逐步展示完整资料；
   - 不出现“已生成内容”和“下载 Markdown”；
   - 时间窗口、实际条数和来源真实。
2. 在同一会话继续输入 `把这些热点写成一篇公众号推文`
   - 复用上一轮研究结果；
   - 生成独立成稿制品；
   - 显示复制、预览和下载操作。
3. 验证 Agent、Java 和前端日志，无未分析错误；任何外部服务失败按真实状态报告。

## 9. 回滚

- Agent 恢复原 `content` 和事件负载逻辑。
- Java 恢复公开制品列表查询和事件投影逻辑。
- 前端恢复所有 `deliverable` 事件进入 `deliverableSets` 的处理。
- 不删除已生成的运行、消息或研究记录。
