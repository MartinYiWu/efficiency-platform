## 1. 目标与范围

保留现有“AI 内容运营助手”的名称、头像、返回导航、页面壳层和消息输入方式，升级回答的阅读结构与继续操作体验。参考专业运营 Agent 的优点，但不复制其品牌、视觉或未经验证的能力。

本设计解决：

1. 长正文挤在单一卡片，标题、来源、警告和格式说明相互干扰；
2. `deliverable.body` 未按 Markdown 或结构化内容呈现；
3. 研究结果与平台成品使用同一视觉模板；
4. 用户看完结果后只能手工输入下一步；
5. 采集范围、来源和降级信息过度暴露在主阅读面；
6. 宽屏、中屏和移动端缺少针对长内容的结构变化。

本轮不建设富文本编辑器、拖拽画布、自动发布、多 Agent 群聊、资产管理后台或新的 UI 组件库。

## 2. 体验原则

- **先给结果，再给依据**：首屏显示完成摘要与核心内容，研究方法和来源细节折叠。
- **按任务呈现**：热点榜、平台文章、行动计划、诊断和复盘采用不同语义组件。
- **一个助手持续推进**：后台能力不改变前台身份；用户通过后续动作继续同一会话。
- **来源可核查但不喧宾夺主**：每个条目展示来源数量和状态，完整链接进入来源区。
- **降级可解释**：说明少了什么、为什么、仍交付了什么，不显示内部错误。
- **复制即用**：平台内容和单条热点均可复制；复制文本来自 Agent 的确定性派生字段。

## 3. 页面信息架构

```text
页面头部（保持现有品牌）
└─ 对话视口
   ├─ 普通用户消息
   ├─ 普通助手短回复
   ├─ 任务进度条/阶段说明
   ├─ 专业交付区
   │  ├─ 完成摘要
   │  ├─ 主交付内容
   │  ├─ 来源与范围（折叠）
   │  ├─ 降级或冲突提醒
   │  └─ 后续动作
   └─ 精准澄清卡
输入区（保持现有交互）
```

普通短回复继续使用聊天气泡；结构化交付物不再塞进气泡中的通用 `Card`，而是在助手头像对齐的独立文档区展示。这样既保留对话上下文，又避免“卡片套气泡”和正文宽度过窄。

## 4. 核心视觉结构

### 4.1 完成摘要

显示一至两句话，例如：

> 已完成过去 24 小时 AI 行业动态整理。共收集 43 条候选信息，合并重复事件后保留 9 条，以下按重要性与新近性排序。

右侧可显示非交互状态标签：`已核验`、`部分完成` 或 `需要确认`。不得展示模型名、Token、内部步骤数或技术错误。

### 4.2 热点榜

采用连续编号列表，不为每条热点单独套大卡片。每条包含：

- 序号和标题；
- 发生日期或时间；
- 二至四句事实摘要；
- “为什么值得关注”；
- 来源数量、可信度和“查看来源”；
- 可选的“生成内容”菜单。

列表之间用留白和细分隔线区分。来源、标签和指标使用 Ant Design `Tag`、`Tooltip`、`Button`、`Collapse` 等现有组件。

### 4.3 平台内容

平台内容采用文档样式：标题、导语、分节正文、标签和发布前提示。正文允许安全 Markdown 渲染，但必须通过现有 `react-markdown` 能力，不新增富文本依赖；禁用原始 HTML。

操作包括“复制全文”“继续优化”“改写到其他平台”。平台和标签信息放在标题区或正文末尾，不在每个段落重复。

### 4.4 行动计划、诊断和复盘

- 行动计划：目标摘要 + 分阶段步骤 + 指标 + 假设；
- 诊断：问题、证据、优先级、建议；
- 复盘：目标与结果、差距、原因、经验、下一步。

以上均由类型化 ViewModel 渲染，不从 Markdown 标题猜测内容类型。

### 4.5 来源与采集依据

默认折叠，标题显示“来源与采集依据（9 条）”。展开后展示：

- 时间窗和排序口径；
- 候选、合并、保留和淘汰数量；
- 来源名称、发布日期、核验状态和安全外链；
- 冲突、未知时间和覆盖缺口。

裸 URL 不进入正文。外链使用 `target="_blank"` 与 `rel="noreferrer"`，链接文本优先使用标题和来源名称。

### 4.6 后续动作

使用紧凑按钮或建议词条展示 Agent 返回的允许动作，例如：

- 把第 1 条写成小红书文案；
- 生成公众号版本；
- 只看产品发布；
- 换一批候选；
- 查看完整来源。

点击内容生成动作只把受控的 `intent_patch` 作为下一轮输入交给现有发送流程，不直接调用发布、外部写入或未知 Tool。“查看来源”只展开本地来源区，不新建任务。

## 5. 组件与 FSD 边界

预计采用以下结构，最终以实施计划和当前源码复核为准：

```text
src/
  pages/operations-assistant/chat/
    OperationsChatPage.tsx
    OperationsChatPage.module.css
  widgets/operation-delivery/
    OperationDelivery.tsx
    RankedDigestView.tsx
    PlatformContentView.tsx
    ActionPlanView.tsx
    DiagnosisView.tsx
    RetrospectiveView.tsx
    SourceEvidencePanel.tsx
  features/operation-chat/
    ...现有会话发送、流式和取消
  features/operation-next-action/
    OperationNextActions.tsx
  entities/operation-deliverable/
    schemas.ts
    types.ts
    mappers.ts
    index.ts
```

依赖保持 `pages → widgets → features → entities → shared`。页面只负责消息流编排；DTO 使用 Zod 双版本校验后映射为展示模型；组件不直接读取原始 SSE payload。

如果实际复用范围不足，可先把交付组件放在运营页面模块内，避免为了目录形式创建空抽象。跨层导入仍通过公开 `index.ts`。

## 6. V1/V2 前端兼容

- 保留 `DeliverableSetV1` Schema 和现有回归测试；
- 新增 `DeliverableSetV2` 严格 Schema，未知字段按契约策略处理；
- `parseDeliverableSet` 改为版本分派，不用 `body` 是否存在猜版本；
- V1 使用安全 Markdown 文档样式作为最低改进，但不伪造 V2 的条目、来源质量和后续动作；
- V2 映射为判别联合 ViewModel；解析失败显示统一用户错误，不渲染半结构化原始 JSON；
- 同一集合只允许一个版本，避免一半新布局、一半旧布局。

## 7. 加载、澄清、降级和错误

### 7.1 加载进度

用单个轻量状态区显示当前阶段和已处理数量。阶段变化来自 SSE，不使用前端计时器伪造进度。完成后状态区折叠成简短执行摘要。

### 7.2 澄清

一次只突出一个最关键问题；可选项存在时使用按钮或单选控件，同时保留文本输入。提交后进入正常消息流，不在前端自行合并意图。

### 7.3 降级

降级提醒放在交付摘要下方，采用 Ant Design `Alert`：

- 说明当前仍交付了什么；
- 说明缺失内容，如“目标 9 条，当前核验到 6 条”；
- 提供“继续采集”或“调整范围”等允许动作；
- 不显示错误码、堆栈、Provider 或工具名。

### 7.4 错误

无可用结果时显示简短错误和恢复动作；已有部分合格结果时不得被全局错误遮盖。取消状态必须停止进度动效并保留已完成消息。

## 8. 响应式与可访问性

| 视口           | 结构                                                         |
| -------------- | ------------------------------------------------------------ |
| `≥1280px`      | 文档区最大阅读宽度约 920px；来源区可在内容下方展开           |
| `768px–1279px` | 单列文档区；操作按钮允许换行；表格转横向滚动或描述列表       |
| `<768px`       | 消息和交付物接近全宽；热点条目纵向排列；来源和动作进入折叠区 |

验收宽度固定为 1440px、1024px 和 390px。标题使用连续层级；按钮有可访问名称；折叠区声明展开状态；可信度不能只靠颜色表达；键盘可完成发送、展开来源、复制和触发后续动作；动效尊重 `prefers-reduced-motion`。

## 9. 样式与依赖约束

- 只使用 Ant Design 6、现有图标、CSS Modules 和平台 Token；
- 不引入第二 UI 库、富文本编辑器、聊天组件或新的 Markdown 依赖；
- 运营页面不再复用人事助手的整个 CSS Module，应建立自己的具名样式并只抽取真正共享的聊天壳层行为；
- 主体避免大面积阴影和嵌套卡片；通过排版层级、留白和分隔线建立结构；
- 不用静态内联样式，不增加无作用域元素选择器。

## 10. 测试与浏览器验收

### 10.1 组件与单元测试

- V1/V2 解析、映射和失败关闭；
- 五类交付物按语义渲染；
- 热点序号、来源状态、降级说明和后续动作；
- Markdown 不执行 HTML；恶意标题、URL 和超长内容安全展示；
- 点击后续动作进入现有发送流程；
- 部分结果不被全局错误覆盖；
- 键盘和可访问名称。

新测试必须先观察到失败，再实现最小代码使其通过。

### 10.2 E2E 与视觉检查

复用 Agent 设计中的 A01～A10 十轮真实会话。每轮在内置浏览器检查：

- 内容是否符合交付类型；
- 首屏是否先看到核心结果；
- 长段落、裸 URL 和元数据是否侵入主内容；
- 来源能否定位到对应条目；
- 后续动作是否保持上下文；
- 1440px、1024px、390px 是否无溢出、遮挡和无意义空白。

E2E 通过不等于真实 Agent 验收通过；必须分别报告前端行为、接口契约、真实来源和人工内容质量。

## 12. 非目标与后续阶段

本设计不包含：

- 自动发布到公众号、小红书、头条或 X；
- 可视化多 Agent 群聊；
- 富文本协同编辑、素材库和排期日历；
- 企业资产库、版本对比和审批工作流；
- 模板市场、账号授权或第三方登录；
- Java 服务、权限和数据库改造。

这些能力只有出现独立需求、接口和授权时再设计。
