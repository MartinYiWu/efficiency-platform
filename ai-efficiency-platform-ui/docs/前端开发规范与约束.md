# 前端开发规范与约束

## 1. 目的、范围与权威顺序

本规范约束 AI 效能平台前端的代码、依赖、测试、页面和文档交付，适用于 `ai-efficiency-platform-ui` 根目录及其子目录。

规则冲突时按以下顺序处理：用户当前明确要求 → `AGENTS.md` → 本规范 → 架构设计 → 既有代码风格。若仍无法判断，停止实施并说明冲突，不以个人偏好补全规则。

本文中的“必须”不可省略；“应”表示默认做法，偏离时需在变更说明中写明原因；“可以”表示可选能力。

## 2. 运行时与工具链

| 类别     | 当前标准                                  | 约束                                                    |
| -------- | ----------------------------------------- | ------------------------------------------------------- |
| 运行时   | Node.js 20.18+ 或 22+                     | 不使用低于 20.18 的 Node.js 执行构建或测试              |
| 包管理器 | pnpm 10+                                  | 只使用 `pnpm`，提交时保留 `pnpm-lock.yaml` 一致性       |
| 语言     | TypeScript 严格模式                       | 业务源码只使用 `.ts` / `.tsx`，不允许 JavaScript 源文件 |
| 构建     | Vite 6 + SWC                              | 输出浏览器静态 SPA，不引入第二构建系统                  |
| UI       | Ant Design 6 + `@ant-design/icons`        | 是唯一通用组件和图标来源                                |
| 测试     | Vitest、React Testing Library、Playwright | 按单元/组件/E2E 分层，不以截图替代行为测试              |

`package.json` 中已安装的依赖是当前可直接使用的集合。架构设计中的 Zustand、dayjs、classnames 属于允许评审引入的白名单，不表示它们已安装或可以绕过依赖审批。

## 3. 目录、命名与模块边界

```text
src/
  app/       启动、Provider、路由、全局样式
  pages/     路由页面编排
  widgets/   跨页面可复用的业务区块
  features/  用户可触发的独立业务动作
  entities/  业务实体、DTO 映射、Query 与展示模型
  shared/    无业务归属的 API、UI、配置、工具和类型
```

### 3.1 依赖方向

只允许 `pages → widgets → features → entities → shared`。`app` 只能向下装配，不能成为业务逻辑容器。

- 同层跨模块必须经模块根目录 `index.ts` 导出访问。
- `shared`、`entities` 不得反向引用业务上层。
- 不得从页面直接导入 `axios`、`echarts/core`、QueryClient 或其他基础设施实现。
- 不要为预期功能建立空 `features`、Store、Hook 或“万能组件”。

### 3.2 命名

- React 组件、类型、接口使用 PascalCase，如 `DashboardHeader`、`DashboardMetric`。
- 变量、函数、Hook 使用 camelCase；Hook 必须以 `use` 开头。
- 文件名与主导出保持一致：组件使用 `PascalCase.tsx`，模型、工具、配置使用 camelCase 或明确的小写名称。
- 展示层使用面向业务的中文文案；代码标识、路径、环境变量、Query Key 保持英文。
- 布尔值以 `is`、`has`、`can`、`should` 开头；事件回调以 `handle` 或 `on` 开头。

## 4. React、路由与组件约束

### 4.1 React 组件

- 函数组件只接收明确的 Props 类型；公共 Props 使用 `interface`，内部简单参数可使用内联类型。
- 一个组件只负责一个视觉/交互职责。文件超过约 200 行前应评估拆分，而不是继续累积条件分支。
- 不在 render 中创建服务端请求、订阅或图表实例；副作用放在 `useEffect` 并返回清理函数。
- 不使用 `any`、类型断言逃避校验或未解释的 ESLint 禁用。确需禁用时只作用于最小行并写明原因。
- 只有当抽象新增平台行为、一致性或复用价值时才封装 Ant Design 原子组件；禁止无意义包装 `Button`、`Input`、`Select`。

### 4.2 路由与应用壳

- 路由集中于 `src/app/router`；页面入口只在 `src/pages`。
- 新页面先定义路由、404 行为、页面级错误边界需求与 E2E 最小验收，再实现业务内容。
- 应用壳管理顶栏、导航、抽屉和主内容区；页面不可绕过 Shell 自行定位全局导航。
- 影响布局的样式必须以 CSS Module 类作用于组件根节点。禁止全局 `main`、`header`、`aside`、`section` 等元素选择器承担页面布局职责。

### 4.3 可访问性

- 真实按钮使用 `button` 或 Ant Design `Button`，真实导航使用 `nav`；不以可点击 `div` 代替。
- 图标按钮必须有 `aria-label`；标题按 `h1 → h2` 层级，不跳级。
- 弹层、抽屉、确认操作优先使用 Ant Design 已有无障碍行为；焦点移动不得依赖鼠标。
- 图表必须有 `aria-label` 和可读的文字摘要；颜色不可作为唯一状态表达。

## 5. 样式、设计令牌与响应式

### 5.1 样式边界

- 页面和组件布局使用 `*.module.css`；全局样式仅放在 `src/app/styles`。
- 先使用 Ant Design Token；跨页面可复用的颜色、间距、层级变量才可写入 `tokens.css`。
- 禁止在 JSX 编写静态 `style={{ ... }}`、在 CSS 中散落未定义的 z-index、阴影或色值。
- 使用 4px 间距体系；同一页面只使用已声明的圆角、边框和阴影等级。
- 禁止默认使用渐变背景、玻璃拟态、浮动粒子或无限动画。动画只服务状态反馈，并尊重 `prefers-reduced-motion`。

### 5.2 响应式

每个页面必须定义连续的结构变化，不得只缩小字体。

| 视口           | 默认策略                                           |
| -------------- | -------------------------------------------------- |
| `≥1280px`      | 完整导航与多列内容栅格                             |
| `768px–1279px` | 图标导航或收缩导航，核心卡片两列，复杂面板纵向排列 |
| `<768px`       | 抽屉导航、单列内容、触控优先的操作密度             |

页面验收至少覆盖 1440px、1024px 和 390px。应检查：内容区是否占用可用宽度、卡片是否按预期换列、导航是否可访问、长文案是否溢出、首屏是否出现无意义留白。

## 6. 服务端状态、接口与运行时校验

### 6.1 HTTP

- 仅 `src/shared/api/http.ts` 创建 Axios 实例；业务模块不得创建第二实例或全局拦截器。
- 基础地址、超时和通用头在共享层统一配置；认证接入时通过单一机制注入，不在组件中拼接。
- 接口错误必须转换为可展示的统一错误模型，禁止直接向用户暴露后端栈、SQL 或敏感字段。

### 6.2 TanStack Query 与 Zod

- GET 请求用 Query Hook；写操作用 Mutation Hook；组件不得直接调用 Axios。
- Query Key 以实体名开头，例如 `['dashboardOverview', range]`。
- Mutation 成功后只失效相关 Query Key，不以刷新页面同步缓存。
- API DTO 必须先经 Zod 运行时校验，再映射为页面 ViewModel；演示 fixture 不得成为生产请求失败兜底。

### 6.3 客户端状态与 URL

- TanStack Query 管理远端数据；Ant Design Form 管理表单字段；URL 管理可分享的筛选与分页条件。
- 如果未来安装 Zustand，只能管理主题、导航折叠、会话派生偏好等本地状态，不镜像远端接口数据。
- Token、权限、个人信息和原始接口错误不得写入 URL、浏览器日志或用户提示。

## 7. 图表与性能

- ECharts 只能通过 `src/shared/ui/Chart` 访问，使用按需注册模块。
- 图表组件必须在卸载时 `dispose()`，监听 resize 时必须解绑；空数据、加载、失败状态不可省略。
- 页面或大图表按需加载；新增依赖或大模块后必须检查 `pnpm build` 输出。
- 构建体积提示需要记录来源和影响。不得仅通过提高 Vite 阈值隐藏超限提示。

## 8. 依赖、环境与安全

### 8.1 依赖审批

新增任何运行时依赖前，在变更说明中写清：

1. 当前依赖为何不能满足；
2. 包的压缩后体积或预期构建影响；
3. 许可证和维护状态；
4. 可替换方案与移除成本。

未经专项确认，禁止引入第二 UI/状态库、Tailwind、Moment、Lodash、jQuery、富文本、拖拽、Markdown 或聊天组件库。

### 8.2 环境变量

- 浏览器可见变量必须以 `VITE_` 开头。
- `.env.example` 只含非敏感示例；`.env.local`、密钥、令牌和个人数据不得提交。
- 环境变量通过 `src/shared/config` 校验；不在页面中读取 `import.meta.env`。

## 9. 测试与质量门禁

### 9.1 测试职责

| 类型     | 覆盖目标                                | 不应覆盖                     |
| -------- | --------------------------------------- | ---------------------------- |
| 单元测试 | 配置校验、HTTP 工厂、数据映射、工具函数 | 框架内部实现                 |
| 组件测试 | 可访问语义、条件状态、用户可见文案      | CSS 类名或第三方组件内部结构 |
| E2E      | 路由、关键操作、真实响应式结构、404     | 穷举所有业务分支             |

新行为必须遵循“失败测试 → 最小实现 → 通过测试”。测试必须先观察到预期失败；如果测试立即通过，说明它没有覆盖新行为，应修正测试而不是直接宣布完成。

### 9.2 交付命令

```powershell
pnpm format
pnpm lint
pnpm typecheck
pnpm test:coverage
pnpm build
pnpm test:e2e
```

构建成功仅证明静态资源可生成；接口联调、鉴权、真实数据和业务验收必须单独说明状态。浏览器验收中发现的布局缺陷应先写可复现的 E2E 或组件测试，再修复。

## 10. 文档、服务与协作

- 变更架构、目录边界、依赖、构建命令、环境变量、质量门禁时，同步更新本规范、`AGENTS.md` 和 README 中受影响内容。
- 新业务页面/跨模块功能应保留设计、实施计划、范围、非目标和验收方式。
- 启动本地服务前先检查端口；不得停止或复用属于其他项目的进程。需要长期保留的本项目服务必须报告地址与端口。
- `.superpowers/`、`coverage/`、`dist/`、测试报告是本地/构建产物，不纳入业务代码评审。
- 当前目录没有 Git 元数据。未经用户明确指示，不初始化仓库、不创建提交、不推送或重写历史；未来接入 Git 后，提交使用文件白名单并保护遗留改动。
